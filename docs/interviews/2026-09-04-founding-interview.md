# 立项访谈整理稿（2026-09-04）

> 本稿是去敏整理：删去了来源项目的名称、客户名、文件路径与环境标识，只保留问题、答案与理由。原始对话记录存于私有仓库 `lazypack-discipline-vault`。
> 访谈方式：grilling（设计树 + 前沿轮次）。每轮列出当时能问的全部问题，附推荐答案；答完重算前沿。

## 起点

维护者的原话：「我打算把优秀的项目纪律沉淀下来。」来源项目是一个微信小程序，已有一套在事故中长出来的纪律：产物登记册（防旧设计稿被当成现行基准）、多 agent 先认领再开工（防撞车）、ESLint `no-undef`（防丢 `require`）、数据层断言 + 页面层语法检查双轨、工具失败如实报告。

第一次尝试直接写了一份模板目录进来源项目，被维护者整体撤回。原因：没问完就写。此后改为先访谈、不落文件，直到共识确认。

维护者用自己的话说出目标：一套装好就自动生效的项目规矩——事实只有一个出处；文档跟着改动更新；产物放哪、何时清；客户改主意时旧目标退场；何时改 ADR、何时改 CONTEXT；提交格式、质量门禁；版本号、打包、分支；`AGENTS.md` 只做指针；只用 Matt Pocock 的 skills 避免打架；理解代码库只靠 `/understand-codebase` 省 token。

agent 对照本机安装的 skills 做了覆盖分析：Matt 的流水线（`grill-with-docs` → `to-spec` / `to-tickets` → `implement` + `tdd` + `code-review` → `retro`）能覆盖想法到实现到复盘；覆盖不了提交格式、版本、发版、打包、分支。`/understand-codebase` 不是 Matt 的。

## 第 4 轮：补什么、怎么补

**Q8「文档自动更新」指什么** → C：流程为主（边问边写 + 收尾 `retro`），机器只拦能判断的几条。
**Q9 提交格式** → A：Conventional Commits + issue 号。维护者补充：优先采用大厂成熟规范（举例 Google 错误码规范）。agent 查到并采纳：Conventional Commits 1.0.0、Angular type 清单、Google eng-practices CL 描述法、SemVer 2.0.0、semantic-release 默认映射、Keep a Changelog 1.1.0、`google.rpc.Code`。
**Q10 版本号与发版** → 泛化为「固定层 + 编译阶段」：版本号规则固定；打包上传按平台（微信开发者工具、DevEco）在编译阶段实例化。
**Q11 分支** → 维护者提出角色模型：一个主规划 AI 长驻 `main`，执行 AI 干活，可能还有书记员更新文档；少用 worktree（不利于跨设备）。agent 调研业界三种模式（Claude Code 协调模式、Planner/Generator/Evaluator、无 worktree 顺序执行），结论：少用 worktree 成立，前提是同一设备同一时刻只有一个执行者写代码，跨设备靠 issue 认领人。
**Q12 中间产物放哪、何时清** → 由 agent 定，要求细且全、不针对单一项目。agent 给出「一个东西一个家」表（见 DECISIONS §4）。
**Q13 客户改主意怎么管** → A：新决议先进 `grill-with-docs`，落 ADR 写明取代哪条；受影响产物在登记册改状态；两边互指。
**Q14 质量门禁放哪一关** → 两关都要。先尝试 git commit hook；`AGENTS.md` 强规定 lint/format（JS/TS 用 biome，Python 用 uv + ruff + ty）；靴对抗性审查让执行者和审查者都必须跑门禁。
