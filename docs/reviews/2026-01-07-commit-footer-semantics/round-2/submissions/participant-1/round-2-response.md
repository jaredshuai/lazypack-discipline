## 针对分歧点的立场

### 分歧点 1: 「禁用 Fixes」的表述方式

- **修订后立场**：**坚持正面枚举，但改为「穷尽式封闭白名单」表述**（采纳 P3 的提法、P5 的句式，接受 P4 关于必须有执行落点的要求）。
- **论证**
  - **对 Participant 3**：实质一致。他的「正向穷尽式定义」比我第一轮的「正面枚举」多一个封闭性承诺，我采纳并把它写进本轮条文草案（见下）。分歧只在他想同时保留检查器句，见分歧点 2。
  - **对 Participant 4**：我**同意**「禁用」在审查层不是零效力——§6.3「`CODING_STANDARDS.md` 由审查者在审查时执行」确实提供了一个审查者驳回的载体。但我认为由此推出「禁用句式合法」**不成立**，三点：
    1. **射程错位。** 审查者能据以驳回的判据只能是「脚注关键词 ∈ 允许集合」。他**不能**驳回正文的 "this fixes #123"——因为 §5.2 明文要求正文写「为什么、有哪些没做好的地方、关联 bug 号」。禁用句隐含的范围比可执行的范围大，而这正是我要移除它的理由：它给后来的 AI 制造「这条被违反过」的假象（我第一轮 B.2）。
    2. **覆盖有洞。** GitHub 9 词族 + GitLab 另有 `Implement*`，只禁 `Fixes` 留下 P5 指出的空档；封闭白名单一次覆盖全部，审查者对其余别名的驳回依据直接就是「不在允许集合」，无需逐词点名。
    3. **换写法零成本。** 正面枚举 + 一句审查落点，与「禁用」句式覆盖同样的实践意图，不损失任何约束力，却使每句都可核对。既然零代价，就不该选依赖读者隐性推理（「禁用 = 隐含枚举全集」）的那一版。
  - **结论**：P4 要的是「别造出看似机器闸门的句子」，这与我目标相同；差异只在句式。采纳他的**执行落点**要求，不采纳他的**负面句式**。
- **条文草案（分歧点 1 的落点）**：

  ```
  脚注票引只用两词：`Refs #n` 表关联，`Closes #n` 表关闭。其余平台关闭词
  （`Fixes`、`Resolves`、`Implements` 及其大小写与冒号变体）不作脚注票引。
  脚注出现非允许词时由审查者退回（§6.3、§6.6②）。词表不改变平台行为：
  正文中关闭词与票号紧邻仍会触发关闭，见边界说明。
  ```

### 分歧点 2: 「检查器不做语义判定」是否入条文

- **修订后立场**：**坚持不写入条文；并撤回我第一轮 M1 中的该句**（本轮自我修正）。裁决记录须登记，条文不写。
- **论证**
  - **先自我纠错。** 我第一轮 M1 末句写了「检查器把脚注当信息行，不做语义判定」，同时 C.4 又说该立场「必须写进裁决记录」。P2（C-1）与 P5（D.2.1）指出：该句**不是现行 §5.1 条文**，提案是在借澄清词表之名夹带第二项规范变更。我核了 `DECISIONS.md:79`，确认此点。我本轮撤回 M1 的这句——我第一轮的建议本身就在扩大那次夹带。
  - **认同 P3/P4 的部分**：「是否真的满足关闭条件」是语义判断、归当轮执行者与审查者——**这一点 §6.6② 已经永久规定了**（「需要理解含义、权衡或授权的，执行载体是当轮执行者与审查者」）。P3 引 §6.6② 是对的。也正因如此，把它再抄进 §5.1 不新增任何归属，只是登记一个**当前实现的偶然属性**。
  - **反对写入的部分（归属 vs 状态）**：
    1. **它说的不是归属，而是状态。** 条文若写「检查器不做语义判定」，唯一可新增的含义是「检查器不得被接成会做语义判定的东西」——而那是对未来实施票的约束。§6.6④ 原话是「接线是独立一步……须有实施票写明范围与授权；**固定层不预设接线倾向**」。把未接线／未判定状态写进固定层，正是固定层预设了接线倾向（这次预设成反向）。
    2. **它污染 §6.6① 的运行时读取场景。** §6.6① 要求确定性工具「运行时读取该正文」作为唯一口径。同一句条文里既写「票引只用两词」（正则可判定 → 工具层候选），又写「检查器不做判定」，未来接 Level 1 格式检查时，工具读到的是自我否定的口径。混合规则应「按可判定的那一句分流，不整条判给一层」（§6.6②）。
    3. **它有实际返工成本。** 写入后，接线须再开一轮 §9 只为删一句话——我第一轮 C.4 担心的正是反向问题（不写则 AI 援引 §6.6③ 自行补闸门）；两侧不对称在于：不写句 + **登记裁定**同样能防住我担心的问题，而写了句必然欠下一次删除程序。P5 的第二版措辞（「本条可判定部分归工具层；是否接成阻断闸门须另获授权（§6.6④）」）我第一轮曾提过等价建议，现**不采纳入条文**——它是载体总纲的复述，写进具体条文即违反 §1.4「每条纪律只活在一处」。
  - **落点分层（回答「把当前未接线状态写成条文」与「明确语义判定归属」的区别）**：
    | 内容 | 正确落点 |
    |---|---|
    | 词表语义与判定判据 | §5.1 条文（唯一口径家，§6.6①） |
    | 可判定句归工具、语义句归审查者 | §6.6②/③/④ 总纲（既有，不抄） |
    | 本轮裁定「不列为硬阻断、可判定部分暂不接线」 | **裁决记录 + 实施票**（§6.6④ 合法稳态，§4.1「工具门禁配置与接线」行要求如实报告） |
  - **对 P3 的一处事实纠正**：其 D.3 说「提案坚持……符合 §6.6② 的规定，未将不可机械判定的语义强行塞入 hook」——但**「未塞入 hook」不等于「须把该状态写成条文」**。前者是 §6.6④ 的默认稳态，后者是一项新的规范动作。

### 分歧点 3: 规则归属（§5.1 集中 vs 分层）
