## 针对分歧点的立场

### 分歧点 1: 「禁用 Fixes」的表述方式

- **修订后立场**：**修改为正面枚举封闭白名单**；同时坚持「执行性质须显式登记」，但承载位置从条文移到裁定记录。
  - 条文句式采纳 P5 版：「脚注票引只用 `Refs #n` 与 `Closes #n`；其余平台关闭词（`Fixes`、`Resolves`、`Implements` 等）不用作脚注。」
  - 裁定记录补一句：「脚注词表合规由审查者按 §6.3 模式执行，本轮不接机器门禁（§6.6④ 合法稳态）。」

- **论证**：
  - P1 与 P5 对「禁用」句式的批评，两点成立：①禁用句式对平台无效——我第一轮发现 3 已独立得出同结论（平台扫描整条 commit message，正文 `fixes #n` 照样关票）；②只点名 `Fixes` 枚举遗漏，白名单从构造上补上。P1 的第三点「给后来的 AI 制造这条被违反过的假象」部分成立：白名单句式是陈述应然状态，确实比禁用句式更少诱导误读。
  - 我第一轮的「禁用 = 审查者驳回依据」与正面枚举**可以兼容**，因为两者解决不同层的问题：白名单解决「违反如何认定」（判定基准），执行性质解决「认定后谁来驳回」（执行主体）。白名单非但不取代审查者，反而让审查者的驳回依据更硬——「条文说只用两词」比「条文说禁用某词」更少解释空间。
  - 因此我的改写是：条文白名单化 + 裁定记录登记执行性质。原立场中「执行性质未被说透」的关切由裁定记录承载后，不再构成对条文句式的否决理由。

### 分歧点 2: 「检查器不做语义判定」是否入条文

- **修订后立场**：**修订——该句不入条文**；但要求裁定记录显式登记接线状态，防止后续 AI 自行补闸门。

- **论证**：
  - 我同意 P1/P5「会堵死未来工具化路径」的担忧，且 P5 的 §6.6 张力论证说服了我。关键在于 §6.6② 的切分：「脚注是否使用允许关键词」是纯正则可判定，属确定性工具候选层；「关闭条件是否满足」才是语义层。我第一轮主张入条文的「检查器不做语义判定」是 blanket 表述，会把前者（本可工具化）也一并否决——这正是张力来源：条文里的 blanket 句与未来 Level 1 词表格式检查直接冲突，届时还得再走一轮 §9 删它。按 §6.6② 的正确归属，可判定部分应留给工具候选层，条文不应预先关门。
  - 但我第一轮的核心关切并未被「不写」完全覆盖：条文沉默时，后续 AI 可能援引 §6.6③「须阻断者不得只活在常驻提示词」自行把词表合规升级为硬门禁。P1 的 C.4/M7 恰好补上这个缺口——把 issue #29 的边界裁定显式写进裁决记录。
  - 综合改写方案（两步）：
    1. §5.1 条文不含任何检查器行为描述，只定词表语义与判据；
    2. 裁定记录登记两句：①「词表合规为正则可判定（§6.6② 工具候选层），本轮裁定为暂不接线，属 §6.6④ 合法稳态」；②「关闭条件是否满足属语义判断，归审查者与执行者，不由检查器判定」。
  - 这比把 blanket 句塞进条文更精确：**可判定性归属**与**接线决策**分离。未来接 Level 1 格式检查无需修条文，只需按 §6.6 既有流程接线——条文既没堵死工具化，也没放行静默补闸门。我第一轮「避免虚假门禁」的实质诉求由登记句②保留。

### 分歧点 3: 规则归属

- **修订后立场**：**坚持 §5.1 集中管理，反对方案 D 分层**；但采纳 P2 担忧中的合理内核——控制行数：条文只收判据、单行表述，论证与示例留在裁定记录及本讨论存档（归档材料，非第二活文档）。

- **论证**：
  - P2 的膨胀担忧（6 类边界场景 → 二三十行）部分成立，但分层解法的代价比膨胀更大。`docs/agents/commit-footer.md` 或 CODING_STANDARDS.md 一旦承载边界判据，就成为同一纪律的第二个家，直接违反 §1.4「每条纪律只活在一处」与 §6.6①「口径只有一个家」。判据外迁后，审查者与未来格式检查要同时核对两份活文档，同源漂移风险正是我第一轮发现 1（RELEASE.md 派生漂移）的同类病灶——我们不能用制造新的第二源来治旧的第二源。
  - 「20+ 行」的正确解法不是搬家，是**分流**：条文级歧义的判据用单行写进 §5.1（按分歧点 4 的清单实测约 5 行）；论证、示例、补救流程细节进裁定记录与本讨论存档——归档材料不是活文档，不构成第二源。条文总行数可控在十行出头，膨胀担忧由此消解。
  - 另有一个 P2 未回应的硬约束：§6.6① 要求未来工具运行时读取 §5.1 作唯一口径。判据外迁意味着工具口径不完整——要么工具去读第二份文档（第二源），要么外迁的判据实际失效（判据不被执行等于没有判据）。集中管理是 §6.6 的推论，不只是风格偏好。
  - 最终立场：§5.1 集中 + 单行判据 + 论证归档。若维护者认为行数仍不可接受，正确出路是压缩边界清单（按分歧点 4 的优先级砍），而不是迁移判据归属。

### 分歧点 4: 边界场景补充

- **修订后优先级排序**（本轮必补，按优先级降序）：
  1. **无对应工单的提交**——「脚注可选；无对应工单时不写脚注，不虚构关联」。直接回应 #8「不能为满足格式」的原话，且是条文级歧义：现行与拟议条文都未说脚注可选，AI 会为凑格式虚构关联票。最高优先级。
  2. **同一 issue 双关键词裁决**——「同一工单在一个提交内只用一个关键词；以 `Closes` 为准者不得同时写 `Refs`」。条文级歧义，不补则同一份 diff 可被两种解读各判合法。
  3. **正文旁路风险**——条文一句「正文叙述不受此限，但正文应避免『关闭词 + 票号』紧邻组合」+ RELEASE.md 模板同步提示。这是已知实测风险（issue #29 记录的 `Fixes #8` format-pass 实测即旁证），不补则条文「防提前关闭」的核心承诺存在一条公开的失效路径。P5 的 B.4（效果承诺应降格为「防止脚注层面的提前关闭」）与 P1 的 B.2（平台扫描整条 message）从独立路径证得同一点，我坚持第一轮立场并将其列第三。
  4. **跨仓引用**——「跨仓引用须带完整仓标识或改用文字描述，公开材料遵守 §10.3 脱敏」。§8.1 harvest 从下游向本公开仓提 issue 是真实链路，平台不解析异仓 `#n` 且有泄露来源项目的风险。
  5. **revert / 误关补救口径**——「脚注不承担重开语义；误关由人工 reopen，后续提交用 `Refs` 续联」。P1（撤销已关闭工作）与 P5（误关补救）从两端切入同一缺口，一句话可收，边际成本极低。

- **论证**：排序依据三条判据——①不补是否立即产生条文歧义（场景 1、2 满足）；②不补是否让条文核心承诺有已知失效路径（场景 3 满足，4 部分满足）；③一句话能否收纳（场景 5 满足）。
  - 对 P1/P2 强调的「无票提交」与「同 issue 双关键词」：**同意列为最高优先级**，判据①直接适用。
  - **P5 的「票号形态」与我的「正文旁路」相比，优先级更低**：票号形态不是歧义而是归属问题——§1.1 已把工单位置归项目层，条文加一行「票号形态依项目层 issue-tracker 声明」（P5 条文稿已含此行）即可兜底，细则属 issue-tracker.md 职责，不必占本轮条文场景名额；而正文旁路没有现成的条文级兜底，不补即承诺落空。故票号形态以条文一行处理、入本轮；细则后续票。
  - 可后续票：squash/fixup 压扁（P5 自认是项目层流程问题）、关闭后追加引用（罕见场景，一句话兜底即可或后续票）。

## 修订后的总体立场

基于第二轮辩论，我的最终立场是：**支持修订后的方案 A**。与第一轮相比有三处调整：

1. **「禁用 Fixes」→ 封闭白名单正面枚举**（采纳 P5）：条文不再使用禁用句式；我第一轮「执行性质未说透」的关切移交裁定记录承载（审查者按 §6.3 执行、本轮不接机器门禁）。
2. **「检查器不做语义判定」→ 不入条文**（采纳 P1/P5 的 §6.6 张力论证）：改为裁定记录登记「词表合规可判定但暂不接线（§6.6②④）+ 关闭条件判断归人」，可判定性与接线决策分离，不堵死未来 Level 1 工具化。
3. **书写形式立场微调**：仍坚持钉死唯一规范形式（反对 P1 的「两种均合法」与 P5 的「交由模板示例」），但采纳 P5 B.5 的证据，钉死带冒号形式（`Refs: #n`），与 CC 1.0.0 原生示例一致。

未改变的立场：方案 A 方向正确；§5.1 集中管理；**实施链路缺口（改源文件 → DECISIONS.md 升 minor 0.6.0 → setup 内置快照与来源内容标识同步 → 重编译 RELEASE.md → 机检 + 消费者清点）仍是本轮最重要的强制项**，P1/P5 独立得出同结论，三方一致，应无争议入裁定。

新增采纳：**P1 的 D.3「关闭条件写在工单里；工单未写明关闭条件时，只用 `Refs`」为条文级必补句**——它把 #8 诉求从词表升级为可核对前置条件，并与我修订后的执行观闭环：判定权在规划者（工单写明关闭条件），执行在审查者（§6.3 驳回），检查器只管可正则判定的词表合规（暂不接线）。
