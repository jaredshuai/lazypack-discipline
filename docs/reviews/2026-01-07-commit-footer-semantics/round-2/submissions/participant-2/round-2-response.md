## 二、对其他参与者的评审

### 对 Participant 3 的评审

#### 认同的观点

1. **「正向穷尽式受管词表」这个框架优于负面禁用**。participant-3 的关键发现 4（正向穷尽优于负向禁止）与我分歧点 1 的结论**目标一致**：把词表写成封闭集合，靠「集合外即不受管」收敛实践，而不是靠一条平台执行不了的禁令。这一点我完全接受，并按他的框架重写我第一轮的拟稿（见分歧点 1）。

2. **`Refs` 的双向交叉引用价值**。他在 B.1 与关键发现 2 说两大平台对 `Refs #n` 生成交叉引用事件。这一点**比我在第一轮 B-3 的表述准确**：我当时写「`Refs` 在两个平台都无机器效果」，过于绝对。准确表述是——`Refs` 有交叉引用效果，但**没有关闭效果，也没有 linked-PR 效果**（GitHub 文档明说提交消息里的关键词不会把 PR 列为 linked pull request）。我据此修正第一轮措辞，同时保留我的推论：`Refs` 不产生任何**可校验的成败**，所以「`Refs` 写得对不对」仍然只能由审查者判。

3. **§5.2 与 §5.1 的分工**（正文叙述背景 vs 脚注票引）。这解决了我第一轮只指出「两处职责需明确分工」但没给方案的问题。他的分工表述可直接采用。

4. **术语用「工单/票」而非 `issue`**。他 D.4 的理由是风格一致；我的理由更强（N5）：`CONTEXT.md` 不存在，引入 `issue` 需要先建词汇表并登记，而沿用「票」是零成本。

5. **PR / Squash Merge 边界**（见分歧点 4）。他指出 squash 流下 PR 的 title/body 就是最终 commit message，因此 PR 描述的脚注同受词表约束。这条我认同且给更高评级。

#### 反驳的观点

1. **他的 §5.1 拟稿对本议题最高频的真实故障完全沉默。** 他在 B.3 明确观察到「正文中随意出现的自然语言（如 "Fixes the issue where..."）会意外击中平台关闭正则」——这是正确的观察。但他把处置定为**倡导**（「倡导正文仅作上下文阐述」），结果拟稿里一个字都没写。于是这份条文对最常见的翻车方式不置一词：执行者读到「脚注用 `Refs`/`Closes`」，完全可以合规地在正文写一句 "this fixes #37"，然后票照样被关掉，而条文没说这算不算问题。

   这是**观察与拟稿脱节**，不是措辞问题。他的 B.3 证明了缺口存在，拟稿却没有承接它。

2. **「禁用缺乏强制载体 → 因此只需正向定义」这个推导跳了一步。** participant-3 A.2 的论证是：既然检查器不做语义判定，「禁用」就没有强制载体（违反 §6.6②），所以条文只需正面定义合法词表。这里把「**不需要强制**」推出了「**不需要说明后果**」。但这两者不是一回事：不需要机器强制，不等于可以不说清后果。正向词表回答「能用什么」，不回答「碰到集合外的平台词会发生什么」——而后者恰恰是本议题要解决的事（#8 裁定的痛点本来就是「不能为满足格式而提前关闭整张票」，提前关闭正是从正文路径发生的）。

3. **「检查器不做语义判定完全符合 §6.6②」是偷换论证对象。** §6.6② 说的是「需要理解含义、权衡或授权的，执行载体是当轮执行者与审查者」——这是**分派规则**。而「检查器把脚注当信息行」是**某个具体脚本的当前配置状态**。participant-3 用前者论证后者应当入条文，论证对象不一致。补充两点事实：

   - 该句的出处是伪造的。提案 365–366 行写「根据 §5.1：> 脚注关联票。检查器把脚注当信息行，不做语义判定。」，而 `docs/DECISIONS.md:79` 的 §5.1 全文是「……脚注 `Closes #n` 关联票。」，**没有后半句**，提案引文还把原文「脚注 `Closes #n` 关联票」改写成了「脚注关联票」。
   - participant-3 自己在拟稿里也写明了「Angular 8 个」的 type 词表是 `build ci docs feat fix perf refactor test`——他誊抄时把提案原文的 `fix` 保留在 Angular 8 个里，但同一份拟稿里 `Fixes` 被列为禁用词；这两处不矛盾（一个是 CC type，一个是脚注词），但值得指出：**同一份拟稿里 `fix` 与 `Fixes` 都出现，而条文没有任何一句解释为什么小写 `fix` 合法、大写 `Fixes` 非法**。执行者（尤其是 AI）读到会犹豫。我的拟稿处理了这一点：按**词形与位置**区分（type 位置 vs 脚注位置），而不是靠词的大小写印象。

4. **「`Refs #n` 关联工单（阶段性进展，不关闭）」的语义锚点会与 §5.3 打架。** 把 `Refs` 锚在「阶段性进展/未完成」上，遇到「功能写完了、但依赖未就绪、票定义的关闭条件是『功能可用』」这种情形就不成立：该提交既非「未完成」，也不满足关闭条件，但确实该用 `Refs`。锚点应是「**本提交不满足该票的关闭条件**」，而不是「未完成」。

## 三、针对分歧点的立场

### 分歧点 1：「禁用 Fixes」的表述方式

#### 修订后立场：**坚持目标，采纳 participant-3 的闭合词表框架，保留「平台词处置」这一句**

我第一轮的表述是「平台保留词不得用于承载语义，且一旦写出即按关闭动作对待」。本轮修订：把 participant-3 的**正面穷尽**与我的**后果声明**合并成两句，因为两者回答的是不同问题——闭合词表回答「能用什么」，后果声明回答「碰到集合外的词会发生什么」，缺任何一句都不完整。

#### 最终表述建议（已按 N4 的抽取约束校对）

```
5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。type 用 Angular 8 个
（`build ci docs feat fix perf refactor test`）加 `chore` `revert`。
脚注票引词表封闭为两个词：`Refs #n` 关联票（本提交不满足该票的关闭条件），
`Closes #n` 关闭票（本提交满足该票的关闭条件）。
本仓不承载语义的其他平台关闭别名（`Fixes` / `Resolves` / `Implement` 及大小写变体）
不用于表达关联；平台按提交全文扫描关闭词，故这类词一旦写出即按关闭动作对待，
不受其出现在脚注区还是正文的影响。
可不可以关票由审查者按工单写明的关闭条件核对（§6.6②）。
```

四点设计说明：

- **正面枚举在前，集合外处置在后。** 枚举满足 participant-3 的收敛诉求；处置句满足本议题的真实痛点。
- **按类别枚举别名，不点名 `Fixes`。** 采纳 participant-3、participant-5 的意见（关闭词家族十余个，只禁一个词留大洞）。
- **用「位置 + 形态」而非「词的大小写」做区分。** 回应我对 participant-3 拟稿的反驳 3：type 位置用小写 CC type（`fix`），脚注位置用首字母大写的 `Closes`/`Refs`，两者由**位置**区分，不靠大小写印象。
- **第三句是本轮相对第一轮的加强版。** 我第一轮只写「一旦写出即按关闭动作对待」，本轮补上「平台按提交全文扫描」这个**理由**。没有理由，这句话会被读成「所以你要小心」；有理由，它才是可执行规则——执行者知道该改的是正文，而不只是「下次别写」。

#### 对 participant-4 的直接回答

**是否同意把「禁用」定位为「审查者驳回依据」？——部分同意，但必须补落点。**

- 同意的部分：这个词表动作**确实**只能落在执行者/审查者层，工具无法强制。这一点从第一轮起我就是这样主张的（我反对的是把它写成平台层面的保护，不是反对它由审查者执行）。
- 不能直接同意的部分：如 N2 所示，§6.3 指向的 `CODING_STANDARDS.md` 在本仓不存在。所以「禁用 = 审查者驳回依据」目前是**无落点的口号**。要让它成立，必须先回答「驳回依据住哪」——这就是分歧点 3，不是一条措辞能补的。

**participant-3 的「正向穷尽式定义」与我的立场是否本质一致？——目标一致，覆盖面不一致。**

目标一致（都主张封闭词表、不点名禁用）。覆盖面差一句：participant-3 的拟稿对「平台全文扫描」这一事实及其后果**完全留白**，而他自己在 B.3 已经观察到该事实。观察与条文脱节，是我认为他拟稿最需要修的一处。

**基于第一轮实读的 GitLab 官方正则，我的最终表述建议**——就是上面那段。其中「平台按提交全文扫描」一句的事实基础是 GitLab 官方文档的关闭正则与其官方示例：官方示例 `Awesome commit message / Fix #20, Fixes #21 and Closes group/otherproject#22. / This commit is also related to #17 and fixes #18, #19` 中，句中小写的 `fixes #18` **照样关闭**，只有不匹配的 `#17` 不关。GitHub 侧文档把关键词定义在「the pull request's description **or in a commit message**」，无位置限制。

### 分歧点 2：「检查器不做语义判定」是否入条文

#### 修订后立场：**修订——接受折中，把那句话拆成两半，只留分派声明，删工具现状声明**

这是我在第一轮之后第一次实质修订立场。

先把事实钉死：提案 365–366 行称「根据 §5.1：> 脚注关联票。检查器把脚注当信息行，不做语义判定。」，而 `docs/DECISIONS.md:79` 的 §5.1 全文是「5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。type 用 Angular 8 个（`build ci docs feat fix perf refactor test`）加 `chore` `revert`。脚注 `Closes #n` 关联票。」——**没有「检查器把脚注当信息行」这句**，且提案把「脚注 `Closes #n` 关联票」改写成了「脚注关联票」。所以这不是「澄清既有条文」，是借澄清之名新增一条关于工具的规范。

#### participant-3、4 的「语义判断归审查者」与我的「不应把未接线状态写成条文」，是否真的矛盾？

**不矛盾，但也不是同一个命题——participant-3、4 把两件事合成了一句，然后为其中一件辩护。**

拆开看：

| 半句 | 性质 | 是否应入条文 |
|---|---|---|
| 「（决定是否可关票）属于语义判断，载体是执行者与审查者」 | **分派规则**——§6.6② 已经这么写了 | 可入可不入。入的话是**重复**总纲，但重复有益，因为它把总纲落到本条 |

我第一轮反对的是第二半句，而且我认为第一轮的理由仍然成立：

- §6.6③ 的方向是「凡裁定为须阻止提交的规则，可判定部分必须落进确定性工具」，并明文「不得以『工具化不了』为由把该类规则整条留在常驻文件」。把「不做语义判定」这个**当前未接线的状态**写成条文，方向是反的：将来要接词表闸门，得再开一次 §9 删这句。

但 participant-3、4 的关切是正当的，而且我第一轮没有正面回答它：**如果条文只说词表，执行者会不会以为「词表写对了就等于可以关票」？** 会。这是真实缺口。所以我接受折中。

#### 折中条文（建议写入 §5.1 末句）

```
可不可以关票由审查者按工单写明的关闭条件核对（§6.6②）。
```

三点性质：

- 它是**分派**（§6.6② 的应用），不是工具现状；
- 它不断言任何接线状态，不预设工具层倾向（§6.6④）；
- 它关上了「词表对了 = 可以关票」这个缺口。

并且我建议进一步采用 participant-1 在第一轮提出的那句（我第一轮未采纳，现认为它比我的版本更可执行）：

```
工单未写明关闭条件时，用 `Refs`，不用 `Closes`。
```

这一句的价值在于它把「可不可以关票」变成**可核对的前置条件**（去票上看有没有写关闭条件），而不是让审查者凭 diff 猜。这与 §3.1 的角色分工一致：规划者产出规格与票，执行者只提交，审查者按票核对。**这一句我认为应该进 §5.1**，因为它是口径的一部分（词表与关闭条件的关系），不是场景判据。若要控体积，也可下沉到判据层——这正是分歧点 3 要裁的。

你担心「虚假门禁」。我认同这个担心，但它的解法不在条文里加一句「检查器不做语义判定」，而在别处：如 N3，检查器当前把 `Fixes` 当合法脚注上报，而脚本第 28 行的正则是硬编码的词表；条文改成封闭词表后，这个脚本必须同步改。**条文里那句「不做语义判定」既不能阻止脚本继续上报 `Fixes`，也不能阻止它被误接成闸门——真正能解决的是改脚本 + 在判据层写清边界。**

**第二，§4.1 表已经为这类材料指定了家，而且指定得很准。** 「给 agent 的按需说明 | `docs/agents/<主题>.md` | 被闸门或工具替代后删」——「被闸门或工具替代后删」正是词表边界的生命周期：现在靠人读，将来有闸门就删。集中管理等于拒绝这个已登记的家。

**第三，§6.6② 已经完成了分流，条文只需要声明分流结果。** 「能用路径、哈希、正则、存在性或退出码判定对错的，执行载体是确定性工具；需要理解含义、权衡或授权的，执行载体是当轮执行者与审查者。**混合规则按可判定的那一句分流，不整条判给一层。**」词表正是一条混合规则：写法可判定，语义不可判定。方案 D 就是照这一句执行；集中管理则把不可判定的那部分也塞进条文，再在条文里声明它不可判定——这是自我抵消。

**第四，participant-3、4 隐含的「集中管理」在他们的拟稿里其实不成立。** participant-3 的拟稿把「检查器把脚注当信息行」写进 §5.1（工具状态进条文），却把边界场景全部留在提案文档里（无家）；participant-4 把审查执行落在 §6.3 的 `CODING_STANDARDS.md`（本仓不存在，N2），也没说边界场景住哪。**他们支持的是「口径集中 + 判据无处安放」**，不是「判据也住 §5.1」。这是本轮我与他们的实质分歧所在。

### 分歧点 4：边界场景补充的优先级

#### 判断依据（先把标准立起来）

我用的标准是：**这个歧义会不会让「两个都合规的写法」同时通过条文。**

- 会 → **条文级歧义**，必须本轮补进 §5.1（或至少进条文的一句限定词）；
- 不会，但审查者需要知道「该怎么办」 → **判据级**，随判据文件一起补，或转后续票；
- 需要牵动其他条文、角色职责或平台特性 → **后续票**，本议题不背这个包。

#### 本轮必补（5 项，均为条文级歧义）

1. **同一票 `Refs` + `Closes` 同现**（participant-1 + 我）。按现措辞，每个票独立一行、独立判定，会**允许** `Refs #50` 与 `Closes #50` 同现——语义自相矛盾。补法：禁止，以 `Closes` 为准。
2. **无对应工单的提交**（participant-1 + 我）。条文说「脚注用 `Refs #n` 关联票」，那不关联任何票的提交（文档修正、重构、纯本地改动）写不写脚注？两种读法都通。补法：脚注可选，不虚构关联。
3. **票引用形态**（我 + participant-5）。条文写 `#n`，但 GitLab 官方正则第二个分支接受 `[A-Z][A-Z0-9_]+-\d+`（即提案自己记录的 `Closes VAL-TEST-006` 是合法关闭模式），GitHub 另有 `OWNER/REPO#N`。§1.1 又允许项目层声明任意工单位置。补法：一句限定词「票引用形态以项目层声明的工单系统为准」。
4. **平台关闭词的旁路处置**（我 + participant-4）。补法**分两层**：§5.1 已有「一旦写出即按关闭动作对待」的口径；判据层补处置动作。**只补口径不补动作，等于把风险写在纸上不给办法**——这是我给 participant-4 该项加优先级时的唯一保留意见。
5. **书写形式：推荐形式 vs 合规范围**（participant-3 + participant-4 + 我，三方共识）。补法：推荐 `Refs #n`；`Refs: #n` **同样合规、不反向阻断**。这是对 participant-4 拟稿的精确化（见上文对其反驳 3）。

#### 本轮补一句限定词，细则转后续票（2 项）

6. **PR / Squash Merge 边界**（participant-3）。**我把它提到本轮**，理由：它和第 4 项是同一族问题的两面——票引载体不止 commit message。squash 流下 PR 的 title/body 就是最终 commit message，所以 PR 描述同受词表约束；而 §5.1 只说「提交头」，未说 PR 描述，存在口径缺口。**但只需一句限定词，不需要展开细则**。
   附带说明：participant-4 提的「squash 时脚注可能被丢弃或改写」我同意它**不阻塞**——它其实是第 6 项那句限定词的一个后果（既然 PR body 就是最终消息，保留与否就不是独立议题）。所以这两条不该拆成两项。
7. **跨仓票引用的完整形态**（participant-1 + 我）。补一句「跨仓引用须带完整仓标识」，细则（GitHub `OWNER/REPO#N`、GitLab `group/project#N`、URL 形态）转后续票。理由：漏了这句，默认会有人写裸 `#n`，而裸 `#n` 在跨仓时指向不明。

#### 后续票（3 项）

8. **revert 撤销已关闭票的补救路径与责任角色**（participant-1 + 我）。牵连 §3.1 角色职责（谁有权重开、书记员 §3.4 的扫描是否介入），属**工单生命周期**议题，不属词表议题。转后续票。
9. **平台 sub-issue / child items**（我）。平台特性，§1.1 允许项目层声明。转后续票或交项目层。
10. **已关闭票追加引用 / 多提交并行的 close-wins 规则**（participant-1）。转后续票。
