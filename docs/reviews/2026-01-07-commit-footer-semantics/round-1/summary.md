## 关键共识

所有参与者都同意的观点：

1. **方案 A 的核心方向正确**：`Refs #n` 表达关联/阶段性进展、`Closes #n` 表达关闭，二分词表直接且彻底地解决了 Issue #8 裁定的核心诉求（"阶段性进展与完成关闭必须区分"）。

2. **`Refs` 作为关联词的平台安全性**：`Refs` 不是 GitHub/GitLab 保留词，不触发自动关闭，同时能在 issue 时间线生成交叉引用（cross-reference），提供完整的双向可追溯性。

3. **平台兼容性研究基本准确**：提案对 GitHub/GitLab 关闭关键词机制的梳理（9 个词、大小写不敏感、仅默认分支生效等）得到所有参与者的验证确认。

4. **边界场景覆盖方向正确**：提案 §5 的 6 类边界场景（多 issue、部分完成、依赖阻塞、多次推进、revert/hotfix、文档测试）覆盖主路，方向合理。

5. **「零迁移成本」需限定范围**：对本仓成立（历史使用已是 `Refs`/`Closes` 二分），但对下游存量项目和实施步骤而言成本非零（需重编译受管块、升版本号、同步快照）。

## 主要分歧

### 分歧点 1：「禁用 `Fixes`」的表述与执行性

- **观点 A（不可执行论）**：「禁用 `Fixes`」在平台上不可执行，因为平台扫描整条 commit message，正文中的 `fixes #n` 仍会触发关闭；应改为「正面枚举允许词表」而非「负面禁用」。
  - 支持者：participant-1, participant-2, participant-5
  - 核心论据：participant-2 引用 GitLab 官方正则证明句中小写 `fixes #18` 照样关闭；participant-1 指出 §3.3「直接在 `main` 提交」放大了误关闭代价。

- **观点 B（审查层执行论）**：「禁用」在审查者层面可执行（§6.3 模式），条文应明说这是「审查者驳回依据」而非机器闸门。
  - 支持者：participant-4
  - 核心论据：§5.1 明确「检查器不做语义判定」，禁用靠人工审查执行，本身合法。

- **观点 C（白名单化论）**：条文应写成封闭白名单（「只用 `Refs`/`Closes`」），明确排除 `Resolves`/`Implements` 等其余平台关闭词，而不是只点名 `Fixes`。
  - 支持者：participant-3, participant-5
  - 核心论据：GitHub/GitLab 关闭词家族合计十余个，只禁 `Fixes` 留下大洞。

### 分歧点 2：「检查器把脚注当信息行，不做语义判定」是否应写进条文

- **观点 A（不应入条文）**：这句话不是现行 §5.1 条文（提案 §1.4/§6.1 的出处标注错误），且与 §6.6 载体三轴分离存在张力——「脚注是否使用允许关键词」本身是正则可判定的（归工具层），把「不做语义判定」写死会堵死未来工具化路径。
  - 支持者：participant-1, participant-2, participant-5
  - 核心论据：participant-2 明确指出这是提案夹带的第二项规范变更；participant-5 指出未来接 Level 1 格式检查需再走一轮 §9。

- **观点 B（应入条文）**：决定是否真的满足关闭条件是语义判断，属审查者权限（§6.6②），条文写明检查器立场恪守了载体纪律边界。
  - 支持者：participant-3, participant-4
  - 核心论据：participant-3 认为这符合 §6.6② 对可判定性的区分。

### 分歧点 3：规则归属——§5.1 条文 vs `docs/agents/` vs `CODING_STANDARDS.md`

- **观点 A（提议方案 D：口径与判据分层）**：§5.1 只留口径一行（`脚注用 Refs #n 关联票，用 Closes #n 关闭票`），边界判据、6 类场景、平台别名审查要点下沉到 `docs/agents/commit-footer.md` 或 `CODING_STANDARDS.md`。
  - 支持者：participant-2（明确提议方案 D）
  - 核心论据：§5.1 现在只有一行半，6 类边界场景会让它膨胀到二三十行；按 §4.1 表，「给 agent 的按需说明」的家是 `docs/agents/`，且注明「被闸门或工具替代后删」。

- **观点 B（维持 §5.1 集中管理）**：词表与边界判据同属提交格式规范，应集中在 §5.1 维护。
  - 支持者：participant-3, participant-4, participant-5（隐含立场，未明确反对集中管理）

### 分歧点 4：边界场景的补充需求

所有参与者都认为提案的 6 类场景不完整，但补充清单各有侧重：

- **高优先级共识缺失**（3+ 人提及）：

  - 同一 issue 同时出现 `Refs` 与 `Closes`（participant-1, participant-2）
  - 跨仓引用（participant-1, participant-2）
  - 正文描述性用词的旁路风险（participant-2, participant-4）

## 关键发现汇总

### A. 方案合理性

1. **方案空间不完整**：提案只列出 A/B/C 三方案，但存在第四选项未被讨论：
   - participant-1 提议「方案 D：脚注不承担关闭语义」（只许关闭词、关联留正文）
   - participant-2 提议「方案 D：口径与判据分层」（§5.1 瘦身、判据下沉）
   - participant-5 提议「方案 C′：只许关闭词入脚注」
   提案应补记并给出弃用理由。

2. **「严格三分」命名名实不符**：方案 A 实为「两词二义 + 一词禁用」（语义类别只有关联/关闭两类），participant-2、participant-5 明确指出命名错误。

3. **方案 A 的推荐理由 #5 不成立**：participant-2 指出「`Refs` 不是平台保留词，不会触发意外行为」被错误推导成「所以禁用 `Fixes` 是安全的」，两者之间没有推导关系。

4. **AI 协作场景的特殊价值**：participant-3 强调，在 AI Agent 密集参与的环境下，消除近义词能显著降低模型决策熵与提示词噪音，这是方案 A 优于 B 的深层理由。

### B. 平台兼容性

1. **「禁用 `Fixes`」在平台上不可执行**（本轮最重要的外部发现）：
   - participant-2 实读 GitLab 官方文档，引用完整正则证明：`fixes #18` 出现在句子中间照样被关闭，「描述性使用」与「关闭使用」在平台层**没有分界线**。
   - GitHub 文档定义关键词出现在「the pull request's description **or in a commit message**」，无位置限制。
   - participant-1、participant-4、participant-5 均确认此发现，并指出提案 §9「对 `Fixes` 的处理」一节自相矛盾（既承认平台会解析正文，又把「禁用」列为卖点）。

2. **GitLab 官方正则支持非 `#n` 票号**：participant-2 发现 GitLab 正则第二个分支接受 `[A-Z][A-Z0-9_]+-\d+`，意味着 `Closes VAL-TEST-006` 是合法关闭模式，而提案词表只覆盖 `#n` 形态。

3. **平台对照不完备**：participant-1 指出提案只对照 GitHub/GitLab，但 §1.1 允许工单不在代码托管平台（本地 markdown、Gitea/Forgejo 等），此时「合并到默认分支时自动关闭」是假陈述。

4. **本仓 §3.3「直接在 `main` 提交」放大风险**：participant-1、participant-4 指出，本仓没有 PR 合并这道缓冲，`Closes #n` 一旦推送立即关票，这使词表区分在本仓**比常规 PR 流仓更必要**。

### C. 实施可行性

1. **实施链路缺口**（全员共识的最重要发现）：
   - 提案「后续步骤」遗漏 **DECISIONS.md 版本号升位**（0.5.0 → 0.6.0，按文件头部要求必须升位）。
   - 遗漏 **lazypack-setup 内置快照同步**（`references/DECISIONS.md`）与 **来源内容标识重算**。
   - RELEASE.md 是受管编译块（`src=DECISIONS.md@0.5.0`），手改模板会造成同源机检漂移，违反 §6.6①。
   - 5 位参与者全部指出此缺口（participant-1 称为「配套硬动作缺失」、participant-2 称为「核心发现 3」、participant-4 称为「最重要的发现」、participant-5 称为「关键发现 3」）。

2. **条文书写形式未钉死**：participant-4、participant-5 指出，本仓存在 `Refs: #38`（带冒号）与 `Refs #37`（不带冒号）两种写法，条文若不明文规定唯一规范形式，未来格式检查会失去判定基准。

3. **边界场景缺 5-7 类**：participant-1 列出详细缺失表，包括无票提交、同 issue 双关键词、revert 撤销关闭、已关闭票追加引用、跨仓引用；participant-2 补充平台 sub-issue/child items；participant-3、participant-4 补充 PR/squash 边界与正文旁路风险。

4. **消费者清点缺失**：participant-4 指出，除 DECISIONS.md §5.1 与 RELEASE.md 外，`docs/agents/issue-tracker.md`、lazypack-setup skill 正文、本仓 AGENTS.md 等处若提及词表，都需同步，提案未做消费者清点。

### D. 与既有条文的关系

1. **本议题的靶心不是词表，是判定权**（participant-1 的核心论断）：只换关键词不解决 #8 的诉求；须补「关闭条件写在工单里；工单未写明关闭条件时用 `Refs` 不用 `Closes`」，把「是否可关闭」变成可核对的前置条件，否则执行者仍会替规划者判定验收。

2. **§5.1 与 §5.2 重叠未处理**：participant-1、participant-5 指出，§5.2 要求正文写「关联 bug 号」，§5.1 把关联职责赋予脚注 `Refs`，两处职责需明确分工（正文 = 叙述背景，脚注 = 票引）。

3. **type 轴与脚注轴正交性**：participant-1 指出提案 §6.2 Level 2（`docs`/`test` + `Closes` 告警）与提案 §5.6 自己的示例（`test` + `Closes #101` 合法）直接矛盾，应否决 Level 2。

4. **术语从「票」改成「issue」是夹带的地基变更**：participant-2 明确指出，§5.1 现文用「票」，固定层其他条文用「工单」/「票」，改用 `issue` 等于把固定层词汇绑到 GitHub 词汇上，且未在 `CONTEXT.md` 登记。

5. **平台行为不应写进固定层**：participant-1、participant-2、participant-5 均指出，§1.1 允许工单位置由项目层声明，「合并到默认分支时自动关闭」的平台行为不应写进固定层口径，应移到项目层平台段或模板括注。

### E. 迁移成本

1. **「零迁移成本」命题需限定主语**：
   - 对本仓：成立（不重写历史、既有实践已是二分、AI 无培训成本）。
   - 对下游：不成立（已生成的 RELEASE.md 受管块仍写「Closes 或 Fixes」，需重跑 `[UPGRADE]` 对齐；重编译前存在分歧期）。
   - 对实施步骤：非零（版本号升位、快照同步、消费者清点）。
   - 5 位参与者全部要求把「零迁移成本」改写为限定范围的准确表述。

2. **格式不统一的迁移噪音**：participant-4、participant-5 指出，需按既有手法处理冒号变体（「冒号只作示例，不作强制」），否则未来格式检查会把其中一种判违规。

## 修改建议汇总

### 高优先级修改（必须采纳才可进入裁定）

1. **实施步骤补全**（全员共识）：

   - 同步 lazypack-setup 内置快照（`references/DECISIONS.md`）
   - 重新编译 RELEASE.md 固定段（新指纹 + 新版本标注）
