# 第一轮独立意见 - 参与者 1

议题：固定层 §5.1 脚注词表语义（Issue #29）
依据材料：`docs/proposals/issue-29-commit-footer-semantics.md`、`docs/DECISIONS.md` §5.1 及全篇、`skills/lazypack-setup/templates/RELEASE.md`、Issue #29 正文。
材料外推断一律标注「待核验」，不作为结论支点。

---

## 总体立场

**倾向支持方案 A 的方向（`Refs` / `Closes` 二分），但方案 A 现有文本不予原样通过。**

理由的一句话版本：提案把本议题当作**词表选择题**，而 #8 裁定的原话是**权限与提前关闭问题**（"不能为满足格式而提前关闭整张票"）。词表只让「关联 vs 关闭」变得*可表达*，并不让它变得*可判定*——不补上「关闭条件归谁定义」，改完条文仍然挡不住误关闭。

具体保留意见 4 条，详见「关键发现」：

1. **「禁用 `Fixes`」是一条无法执行的约束**，提案 §9 自己承认平台仍会解析正文，却仍把它列为方案 A 的卖点。
2. **本仓 §3.3「执行者直接在 `main` 提交」放大了 `Closes` 的代价**，提案完全没讨论这个本仓特有事实。
3. **「零迁移成本」对本仓成立、对下游不成立**，且提案后续步骤漏了「按 SemVer 升本文件版本号」与 lazypack-setup 内置快照同步——后者会让下一次 `/lazypack-setup` 把旧行写回目标项目。
4. **边界场景缺 5 类**，其中「无票提交」和「同一 issue 同时出现 `Refs` 与 `Closes`」是条文级歧义，不补会立刻产生争议。

## 详细论证

### A. 方案合理性

**A.1 三个方案没有覆盖真实选择空间，且方案 C 是稻草人。**

方案 C 被表述为「统一使用平台关闭关键词、不区分关联与关闭」，并据此判它「每次提交都会触发关闭」。没有理性参与者会提这样一个选项；真正存在、且提案 §2.1 已经点到（"Manual linking"）的第 4 个选项是：

> **方案 D（提案未列出）：脚注不承担关闭语义。** 关联用平台时间线的 cross-reference 或 PR/工单侧手动关联，`Closes` 只在「满足工单写明的关闭条件」这一显式动作时使用，且允许为空。

这个选项的价值在于它把「是否关闭」从 commit message 的措辞层面，移到了工单/PR 的操作层面，从而**结构性消除**误关闭风险，而方案 A 只是**降低**风险。提案应当列出并驳掉它，而不是靠一个稻草人衬托方案 A。

**A.2 方案 A 的理由 #1 存在循环论证，且证据被过度解读。**

「与本仓实际使用完全一致」——本仓 commit history 主要由 AI 按条文生成、经维护者裁定，它不是外部涌现惯例，而是本议题的**结果**之一，用它反推词表优劣是自我印证。更实际的问题是：提案 §1.3 自己列出的样本里同时存在 `Refs: #38`（带冒号）与 `Refs #37`（不带冒号）。**格式已经不一致**，却仍被用来论证"使用模式清晰且一致"。语义二分值得采纳，但"零成本明文化"这个论证强度被高估了。

**A.3 方案 A 相对 B 的优势项，恰好包含一个无效条款。**

A 的 5 条理由里，「禁用 `Fixes`」实际不构成对平台的约束（见 B.2）。剩下 4 条（二分清晰、认知负担低、`Refs` 不触发自动关闭、易扩展）成立。所以我的立场是：**采纳 A 的词表，删掉 A 的"禁用"句式**。

---

### B. 平台兼容性

**B.1 提案 §2.3 表格「`Refs` ✗ 无特殊语义」表述过强。**

平台对 `Refs #n` 并非"无副作用"：只要 commit message 出现 `#n`，工单侧就会留下交叉引用痕迹（GitHub 时间线 "referenced this issue in commit"）。准确的说法是「不触发自动关闭」，而不是「无语义、无行为」。这两者在讨论中后果不同——前者是我们要的性质，后者会让人以为脚注是纯本地文本、从而在下文 D.4 的工单本地化场景里做出错误假设。

**B.2 「禁用 `Fixes`」管不住平台，只能管住脚注。**

平台的 closing keyword 扫描范围是**整条 commit message**（正文、脚注区均在内），不限于脚注行。因此：

- 条文宣布 `Fixes` 不作为脚注关键词，**不会**阻止正文里 "Fixes #8" 触发关闭；
- 提案 §9「对 `Fixes` 的处理」一节其实已经承认「平台会解析提交消息正文，自动关闭功能仍然有效」，却同时把「禁用」列为降低认知负担的手段——**这是提案内部的一处自相矛盾**。

结论性建议：条文改用**正面枚举**（脚注只允许哪两个词、各自表达什么），不使用**禁用句式**（禁用某词）。禁用句式对平台无效，对检查器也无必要（检查器只看脚注行），却会给后来的 AI 制造"这条被违反过"的假象。

**B.3 本仓工作方式放大了 `Closes` 的不可逆性——提案的重大盲区。**

§3.3 明文：「同一设备同一时刻只有一个执行者写代码，**直接在 `main` 提交**」。§5.7 附注与 RELEASE.md §1.3 又说明版本标签在发版时打。把两者合起来看：本仓没有 PR 合并这道闸口，`Closes #n` 一旦推送到默认分支即**立即关票**，错误关闭要人工重开。提案 §4/§8 按"PR 合并后关闭"的一般模型讨论，未按本仓的实际推送模型讨论。这直接改变风险权衡，也进一步支持 B.2 的结论：**必须把「关闭条件由谁写明」放进条文**，而不是指望词表本身兜住。

**B.4 平台对照不完备，且与 §1.1 存在张力（待核验）。**

- 提案 §2 只对照 GitHub 与 GitLab。本包经 `/lazypack-setup` 分发给下游项目，而 §1.1 规定「项目层用 `docs/agents/issue-tracker.md` 声明实际工单位置」——工单可能根本不在 GitHub/GitLab（本地 `docs/work/` markdown 票据、Gitea/Forgejo、其他 SaaS）。对不同工单载体，closing keyword 集合并不相同（**待核验**：Gitea/Forgejo 的关键字集与可配置性；GitLab Self-Managed 的自定义 closing pattern，提案 §2.2 自己已提到）。
- 更关键的是：若工单在本地文件，`Closes #n` **没有任何平台效果**，"关闭"就退化为纯约定；此时 RELEASE.md 拟议文案「合并到默认分支时自动关闭」对该项目是**假陈述**。

建议：条文只规定**人类与 AI 之间的语义约定**；平台副作用（哪个分支、什么时机、是否自动）不写进固定层，由项目层平台段/`issue-tracker.md` 声明。这也符合 §6.6①「口径只有一个家」与 §2.2 的固定层/项目层切分。

### C. 实施可行性

**C.1 条文草案本身可用，但缺一条配套动作。**

§5.1/RELEASE.md 的替换文本清晰、无歧义，可直接执行。但提案 §10「后续步骤」只有"模板同步"一句，缺两项硬动作：

1. **本文件版本号须按 SemVer 升位**（DECISIONS.md 第 4 行：「改动任何一条须走 §9 讨论章程，并按 SemVer 升本文件版本号」）。这是裁定的组成部分，不是收尾杂务。建议 **minor**（0.5.0 → 0.6.0）：新增语义约束，但不否定任何既有 commit 的有效性。
2. **lazypack-setup 内置快照须同步**。RELEASE.md:4 显示该模板从「lazypack-setup 内置快照」编译，来源内容标识 `5f0e31b4b4965f2affc198bf8c76ef1e33f14b5a`。若只改 DECISIONS.md 而不重算快照与来源标识/`src=DECISIONS.md@<SemVer>`，下一次 `/lazypack-setup` 会把**旧口径**写回目标项目的受管块，形成条文与派生副本不一致——按 §6.6① 这正是被明令禁止的第二源。我未阅读 `skills/lazypack-setup/references/DECISIONS.md`（不在必读材料），**请主持人核验快照的更新与机检同源路径是否已覆盖本轮**。

**C.2 现状病灶诊断不足：模板与条文的分歧不是"语义模糊"，是同源违规。**

提案 §1.2 把 RELEASE.md:12 的问题描述为「用『关联票据』描述，语义模糊」。更准确的诊断是：§5.1 只写 `Closes #n`，派生模板却自行多写了一个 `Fixes #n`——**受管块正文偏离了唯一事实源**，属 §1.4「每条纪律只活在一处」/ §6.6① 的违例。这个诊断影响修复方式：如果本轮只改词表、不处理派生机制，同类漂移还会再发生。建议裁定时附一条：**核对受管块派生是否有机检（fp / blob 一致性）覆盖本行，缺失则登记为待办**（按 §4.1「工具门禁配置与接线」行的要求，配置下线或未接线须如实报告，不得静默失效）。

**C.3 六类边界场景不完整。**

提案 §5 的 6 个场景（多 issue / 部分完成 / 依赖阻塞 / 多次推进 / revert-hotfix / 文档测试）覆盖了主路，缺以下 5 类，前两类是条文级歧义，必须补：

| 缺失场景 | 后果 | 建议条款 |
|---|---|---|
| **无对应工单的提交**（`chore`/`ci`/`build`、§5.7 版本标签提交、§3.1 书记员文档修补提交） | 现行 §5.1 与拟议文案都没说脚注是否可选。AI 会为凑格式虚构关联票——这正是 #8 反对的"为满足格式" | **脚注可选；无对应工单时不写脚注，不虚构关联** |
| **同一 issue 同时出现 `Refs #n` 与 `Closes #n`** | §5.1 只处理"每个 issue 一行"，未定义同 issue 双关键词的裁决 | 明文：同一 issue 在一个提交内**只允许一个**脚注关键词，以 `Closes` 为准者不得同时写 `Refs` |
| **revert 使已关闭工作重新失效** | 提案 §5.5 让 revert 用 `Refs`，但被 revert 的原票已处于关闭状态，词表层面**无法表达"撤销关闭"** | 补充：工作失效须由工单侧重开或另开票，脚注不承担重开语义 |
| **关闭后追加提交**（已关闭票再被 `Refs`/`Closes` 引用） | 提案 §6.2 提到"警告重复关闭"，边界章节未定义该写法是否合法 | 补充：追加引用合法，但不得借此改变已闭环工单状态 |
| **跨仓引用**（§8.1 harvest 从下游项目向本公开仓提 issue；§10.3 要求脱敏） | 下游 commit 写 `Refs #29` 指向的 issue 不在该 repo 命名空间，平台不解析，且可能泄露来源项目 | 补充：跨仓引用须带完整仓标识或改用文字描述，公开材料遵守 §10.3 |

**C.4 检查器立场需要显式登记，否则 §6.6③ 会被误读。**

Issue #29 边界写明「讨论完成前条文保持原样，不把脚注争议新增为机器硬阻断」。这条裁定**必须写进裁决记录**。原因：脚注关键词是否属于允许集合，是纯正则可判定（§6.6② 归工具），而 §6.6③ 要求「须阻断者不得只活在常驻提示词」。若不明确本条**裁定为不阻断**，后续 AI 会援引 §6.6③ 自行去补闸门。

对提案 §6.2 分级表：Level 1（格式检查）与 §6.6② 判定一致，但当前裁定下**不接线**，属合法稳态（§6.6④）；Level 2 的告警建议**否决**，见 D.2；Level 3 依赖 API 访问，与 §2.2/§8.3 的边界无必要耦合。

### D. 与既有条文的关系

**D.1 §5.1 与 §5.2 重叠，提案未处理。**

§5.2 要求提交正文写「关联 bug 号」；§5.1 管脚注。同一 issue 号是否允许同时出现在正文与脚注？两处语义是否必须一致？**正文中的 issue 号会触发平台关闭解析（B.2）**，这直接决定「`Refs` 表达关联」能不能被守住。条文至少需要一句：`type(scope)!: 描述` + 正文的关联说明不承担脚注关键词语义，脚注区是唯一的词表位置。

**D.2 提案 §6.2 的 Level 2 与提案 §5.6、与 §5.4 双双冲突。**

- §5.6 示例：`test(auth): add unit tests for JWT validation` + `Closes #101`，判为合法；
- §6.2 Level 2：「使用 `Closes` 但提交类型是 `docs` 或 `test`（可能误用）」列为警告。
- §5.4：`docs`/`test` 不触发版本升位。

三者放在一起说明：**type 轴（§5.4，管版本）与脚注轴（§5.1，管工单闭环）是两条正交轴，不得互相推断。** 「添加 XX 测试」类工单的完成提交恰好是 `test` + `Closes`。建议条文加一句负面约束：**提交 type 不用于推断脚注语义，脚注关键词不用于推断版本升位**，并据此否决 Level 2。

**D.3 §3.1 角色表是本议题真正的落点，提案未接入。**

「关闭条件是否满足」在角色表里属于谁的判断？执行者的输出是「提交」，输入是「一张票」；规划者的输出才是「规格、票」。若执行者单方面写 `Closes` 即关票，等于执行者在替规划者判定验收。#8 的原话「不能为满足格式而提前关闭整张票」正是这个越权风险。

**建议在 §5.1 补第二句（本轮最重要的具体修改）**：

> 关闭条件写在工单里；工单未写明关闭条件时，用 `Refs`，不用 `Closes`。

这一句把词表与 §3.1/§1.1（工单位置由项目层声明）连上，也把 #8 的诉求变成可执行的判据，而不只是换一个关键词。

**D.4 §1.1 / §2.2 要求条文平台中立。**

§1.1 明确工单位置由项目层声明，且使用非上游默认位置前须核查开票/取票/写回各环节消费者。固定层若在 RELEASE.md 里写死「合并到默认分支时自动关闭」，就是把平台行为抄进了口径，与 §6.6① 及 §2.2（平台段承载项目层差异）冲突。见 B.4。

**D.5 术语需要归一。**

现行 §5.1 用「票」，§4.1/§1.1/§4.4 用「工单」，RELEASE.md:12 用「票据」，提案与拟议文案用「issue」。固定层唯一事实源里同指一物却四种称谓，且 `issue` 一词自带 GitHub 联想，会诱导下游把「工单 = GitHub issue」。建议：条文统一为**「工单」**，或在 §4.1 附近声明票／工单／issue 同义。另需避免"issue"一词把讨论拖向平台语义（B.4）。

**D.6 §5.5 变更记录：应显式排除。**

CHANGELOG 由提交生成（§5.5）。建议在裁决中写一句：脚注关键词不进入 CHANGELOG 与版本判定。防止后续把「有 `Closes` 即视为已交付」接入 §5.7 的发版完成认定——§5.7 已明令「版本标签的存在不证明上传或交付已经完成」，脚注更不证明。

### E. 迁移成本

**E.1 「零迁移成本」命题需要限定主语。**

- **对本仓历史 commit：成立。** 不重写历史、不追溯，只是把既有二分明文化。提案 §10 第 5 步"存量检查（可选）"标为可选是正确的；但应补一句：**存量核对若执行，须由书记员按 §3.4 事件驱动触发，且不与本议题裁定绑定**，否则容易被理解为本议题的隐含交付。
- **对下游项目：不成立。** 见 E.2。
- **对未来 AI 会话：非零但很小。** 词表新增一条判据（D.3 的"工单未写关闭条件则用 `Refs`"），要求开票时写关闭条件，这是规划者侧的行为变化，成本落在 §3.1 而不是 §5.1。

**E.2 下游侧的真实迁移面。**

`/lazypack-setup` 写出的是受管块（`lazypack:start block=release-discipline`），块内内容在 `[UPGRADE]` 时由固定层编译派生覆盖。因此本条一改，所有下游项目下次 setup 时其 RELEASE.md 固定段随之改写；正在进行的执行者会话若刚按旧模板写了 `Fixes #n`，在新口径下即成为不符项（方案 A）或仍合法（方案 B）。这不是阻碍——受管块本来就是单一事实源的投影——但"零迁移成本"的说法应当限定为"本仓零成本，下游经派生同步"。

**E.3 格式不统一的迁移噪音（提案未提）。**

§1.3 样本已存在 `Refs: #38` 与 `Refs #37` 两种写法。建议按 §5.7 附注的既有手法处理，一句话即可：**冒号只作示例，不作强制；两种写法均合法。** 不写这句，未来 Level 1 格式检查会把其中一种判违规，或在评审里引发无谓争议。

**E.4 已推送标签与历史票状态：不在本议题范围。**

历史上以 `Closes` 关闭但实际未完成的工单，属状态事实修正，须另开票并遵守 §4.2「工单关闭仅改变其闭环状态，不等于删除授权」。本轮不宜顺带改动既有票状态。

## 关键发现

1. **本议题的靶心不是词表，是判定权。** 只换关键词不解决 #8 的诉求；须补「关闭条件写在工单里；工单未写明关闭条件时用 `Refs` 不用 `Closes`」这一句，把「是否可关闭」变成可核对的前置条件。
2. **「禁用 `Fixes`」无法执行，且提案内部自相矛盾。** 平台扫描整条 commit message，正文一句 "Fixes #8" 照样关票（Issue #29 正文记录的 `Fixes #8` format-pass 实测正是旁证）。改为正面枚举允许词，不用禁用句式。
3. **本仓「直接在 `main` 提交」（§3.3）取消了 PR 这道缓冲，`Closes` 误用即推即关票。** 提案按 PR 合并模型讨论风险，低估了这一点，这是支持第 1 条的核心理由。
4. **提案漏了两项配套硬动作：本文件 SemVer 升位（建议 0.6.0）与 lazypack-setup 内置快照同步（来源标识 `5f0e31b4…`）。** 后者不做，下一次 setup 会把旧口径写回下游受管块，直接违反 §6.6①。
