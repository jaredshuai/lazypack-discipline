# 第一轮独立意见 - 参与者 3

## 总体立场

**倾向支持方案 A（严格二元词表），但对具体表述与边界定性持有保留与优化意见。**

方案 A 确立的「`Refs #n` 表达阶段性关联 / 不关闭」与「`Closes #n` 表达满足关闭条件 / 触发自动关闭」的二元正交模型，直接且彻底地解决了 Issue #8 裁定中指出的核心痛点（*「阶段性进展与完成关闭必须区分，不能为满足格式而提前关闭整张票」*）。在以 AI 协作和工程自律为核心的 lazypack-discipline 体系下，建立 1:1 的确定性语义映射具有显著价值。

保留意见主要集中在三个方面：
1. **对 `Fixes` 的定性方式**：方案 A 称对 `Fixes #n` 采取「禁用」，但在检查器不做语义判定的前提下，负向惩罚式表述既缺乏执行载体，又易引发概念混淆。更合理的做法是「正向穷尽式定义受管词表（Closed Vocabulary）」，将 `Refs` 和 `Closes` 确立为标准词表，不再将 `Fixes` 列入规范，而非在条文中做不可执行的惩罚性宣称。
2. **语法分隔符的兼容性**：应明确标准化格式（`Refs #n` / `Closes #n`）与 Git Trailers 冒号格式（`Refs: #n` / `Closes: #n`）的等价容错关系。
3. **条文术语与既有条文风格的一致性**：DECISIONS.md 的文字应保持简练、自洽，并与 §4「工单」、§5「提交与版本」统一术语体系。

## 详细论证

### A. 方案合理性

1. **方案选择空间的覆盖度**：
   - 提案梳理的 3 个方案（方案 A 严格二元、方案 B 宽松多词、方案 C 平台对齐）完整覆盖了从「强规范」到「纯放任」的光谱。
   - **方案 C 必须排除**：它直接违背 Issue #8 的前置裁定，抹杀了阶段性进展与闭环交付的边界，必然导致多提交任务在合入默认分支时误关 Issue，不具备采纳价值。
   - **方案 A 优于方案 B 的深层理由**：在人类独立开发场景下，`Closes` 与 `Fixes` 往往按偏好混用；但在 **AI Agent 密集参与代码编写与提交** 的环境下，近义词的存在是提示词噪音与生成漂移的温床。方案 A 消除近义词（Synonyms），将「阶段性追踪」与「终态闭环」分别收敛到单一动词，能显著降低模型决策熵与下游自动化工具的解析复杂度。
2. **方案 A 定性表述的修正**：
   - 提案将方案 A 称为「严格三分」，但其内在逻辑实为「二元正交动词（Refs / Closes）+ 排除冗余别名（Fixes）」。
   - 提案主张「禁用 Fixes」，但如果如 §6.1 所述「检查器不做语义判定」，则「禁用」便缺乏确定性工具作为强制执行载体（违反 §6.6② 原则）。因此，条文只需正面定义合法词表：*脚注由 `Refs` 与 `Closes` 构成*。未列入者自然不属规范推荐范畴，无需在核心条文中引入负向惩罚词。

### B. 平台兼容性

1. **GitHub 与 GitLab 机制深度契合**：
   - 在两大主流代码托管平台中，`close/closes/closed`、`fix/fixes/fixed`、`resolve/resolves/resolved` 均会在合入默认分支后无差别触发自动关闭。
   - 极其关键但提案未充分突出的一点是：**`Refs` 虽非自动关闭保留词，但两大平台均会为其生成完整的 Issue 时间线交叉引用（Cross-reference Event / Mention）**。这意味着使用 `Refs #n` 既能实现工单与提交的完整双向可追溯性，又能绝对免疫过早关闭的问题。这是「方案 A 在平台侧无副作用」的最硬核技术保障。
2. **冒号语法与标准兼容**：
   - Conventional Commits 1.0.0 规范定义 Footer 格式为 `<token>: <value>` 或 `<token> #<value>`。
   - 提案 1.3 节的实测数据显示，本仓历史提交中同时存在 `Refs: #38`（带冒号）与 `Refs #37`（无冒号）。
   - GitHub/GitLab 平台对带冒号与不带冒号均可正常解析。为避免下游或模型因冒号产生不必要的校验纠纷，规范应明确推荐无冒号风格（`Refs #n`），同时在审查口径中明确带冒号形式（`Refs: #n`）完全合法且等价。
3. **提交正文穿透风险的规避**：
   - 平台的关闭词匹配器不仅扫描 Footer，还会扫描整个提交说明。明确将 `Closes #n` 下沉至 Footer，并倡导正文仅作上下文阐述（如说明复现步骤或思路），有助于防止正文中随意出现的自然语言（如 "Fixes the issue where..."）意外击中平台关闭正则。

### C. 实施可行性

1. **边界场景覆盖评估**：
   - 提案 5.1 至 5.6 节提供的 6 种场景分类详尽、规则清晰：
     - **5.1（多 issue 独立成行）**：符合标准 Git Trailers 解析规范；
     - **5.2（部分完成）与 5.4（多步推进）**：确立了「前 N-1 次提交用 `Refs`，最终闭环提交用 `Closes`」的标准范式，彻底解决了 Issue #8 中暴露的"阶段性提交无所适从"的问题；
     - **5.3（依赖阻塞）**：倡导拆分实现工单与集成/上线工单，属于优良工程实践；
     - **5.5（Revert/Hotfix）与 5.6（文档测试）**：符合真实工程场景的因果逻辑。
2. **必要补充场景：PR / Squash Merge 边界**：
   - 在使用 Squash and Merge 的协作流中，PR 的 Title 与 Body 将成为最终合入默认分支的唯一 Commit Message。
   - 实施细则应补充说明：**PR 描述的 Footer 同样受本规则约束**。如果 PR 仅是一个大特性的阶段性子分支，PR 脚注应使用 `Refs #n`；仅当该 PR 合并代表工单达到验收关闭条件时，方可在 PR 脚注使用 `Closes #n`。

### D. 与既有条文的关系

1. **与 §5（提交、版本、发版）的协调**：
   - §5.1 原文为 `脚注 Closes #n 关联票。` 修改后明确分流为 `Refs`（关联）与 `Closes`（关闭），填补了语义空缺。
   - §5.2 规定提交正文提及「关联 bug 号」。需明确：§5.2 指的是正文中的叙述性上下文解释，而 §5.1 的 Footer 是驱动平台状态机与 Changelog 生成的结构化指令，两者定位不同、层级分明。
   - §5.5 CHANGELOG 机制：主流变更日志自动化工具依赖 `Closes #n` 提取闭环 Issue 清单。通过引入 `Refs` 分流阶段性提交，能自然净化生成的 CHANGELOG，避免其混入大量未闭环的半成品工单。
2. **与 §4（产物与工单管理）的协调**：
   - §4.2 明确规定：`工单关闭仅改变其闭环状态，不等于删除授权。`
   - 方案 A 的落地直接守护了 §4.2 的严肃性——只有工作真正完成、具备闭环条件时才触发 `Closes`，维护了工单生命周期的确定性。
3. **与 §6.6（载体三轴分离）的高度契合**：
   - §6.6② 明确区分了确定性工具判据与语义审查判据：*「能用路径、哈希、正则、存在性或退出码判定对错的，执行载体是确定性工具；需要理解含义、权衡或授权的，执行载体是当轮执行者与审查者」*。
   - 一个 commit 是否真正达成了工单的全部闭环条件，是**纯粹的工程与业务语义判断**，无法通过单一正则断定。因此，提案坚持「检查器把脚注当信息行，不做语义判定」，完全符合 §6.6② 的规定，未将不可机械判定的语义强行塞入 hook。
4. **条文表述风格与术语对齐**：
   - 提案建议的 §5.1 修改案使用了「关联 issue」；但 DECISIONS.md 全文（如 §4.1、§4.2、§5.1 原文）统一采用中文术语「工单」或「票」。建议在最终条文中沿用「工单」或「票」，保持风格严谨一致。

### E. 迁移成本

1. **本仓迁移成本审视**：
   - 历史 Git 提交记录属于不可变历史（Immutable History），规则调整不溯及既往，不存在重写历史的成本。
   - 本仓当前提交习惯中 `Refs` 已经占据绝大多数（约 20+ 次），`Closes` 约 7 次，而 `Fixes` 作为脚注实际为 0 次。因此，对本仓当前及未来开发而言，迁移成本在事实层面为零。
2. **下游项目迁移成本**：
   - 提案宣称"零迁移成本"对下游略有夸大。对于通过 `/lazypack-setup` 初始化的下游项目，其模板中曾写有 `Closes #n 或 Fixes #n 关联票据`。
   - 外部人类开发者受传统开源习惯影响，可能偶有手写 `Fixes #n` 的惯性。在缺乏强制阻断 hook 的情况下，这不会引发构建失败，但会产生轻微的认知对齐成本。
   - 综上，迁移成本评价应修正为：**「本仓为零，下游项目近乎零（仅存在极低的文档同步与习惯对齐成本）」**。

## 关键发现

1. **语义正交消除 AI 协作漂移**：`Refs` 专职「关联/推进」，`Closes` 专职「闭环/关闭」，构成 1:1 的确定性映射。对于多 AI 结对与自主 Agent 场景，消除近义词能有效降低提示词复杂度与输出不确定性。
2. **平台机制提供底层安全网**：GitHub/GitLab 对 `Refs #n` 生成双向时间线引用（Cross-reference）而不触发 Issue 关闭，为阶段性提交提供了完美的非侵入式追踪载体。
3. **载体定位严格符合 §6.6②**：决定是否闭环工单是审查者与执行者的语义权衡，检查器保持「不做语义判定」恪守了固定层纪律边界，避免了过度工程化与虚假门禁。
4. **正向穷尽优于负向禁止**：规范应通过定义正向受管词表（`Refs`、`Closes`）来收敛实践，而非使用不可执行的「禁用 Fixes」口径。
5. **冒号语法必须具备向下容错**：规范以无冒号为标准书写形式，但必须在语义解析与人工审查层面认可 Git Trailers 冒号语法的等价有效性。

## 修改建议（如有）

### 1. DECISIONS.md §5.1 条文拟订方案（建议采纳）

保持 DECISIONS.md 极简紧凑的文字风格，术语对齐「工单」，正向表述规范：

```markdown
5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。
type 用 Angular 8 个（`build ci docs feat fix perf refactor test`）加 `chore` `revert`。
脚注用 `Refs #n` 关联工单（阶段性进展，不关闭），用 `Closes #n` 关闭工单（满足关闭条件）。
检查器把脚注当信息行，不做语义判定。
```

### 2. RELEASE.md 模板条文拟订方案

在项目层模板中提供更具操作性的指引：

```markdown
- 脚注使用 `Refs #n` 关联工单（阶段性进展，不触发自动关闭）；使用 `Closes #n` 关闭工单（满足关闭条件，合并后自动关闭）。
```

### 3. 补充说明与容错指引

建议在讨论总结与支撑文档中明确两项补充共识：
1. **格式容错**：推荐书写格式为 `Refs #n` 与 `Closes #n`，但标准 Git Trailers 格式 `Refs: #n` 与 `Closes: #n` 同样视为合法合规，不做反向阻断。
2. **PR / Squash 适用范围**：规则不仅适用于单 commit，亦适用于 GitHub/GitLab PR 描述中的脚注区块。
