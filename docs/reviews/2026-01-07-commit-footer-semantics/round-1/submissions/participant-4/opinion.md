# 第一轮独立意见 - 参与者 4

## 总体立场

倾向支持方案 A（严格二分：Refs 关联 / Closes 关闭 / 禁用 Fixes），理由是它与本仓既存实践同构、认知成本最低、且完整回应 #8 裁定「阶段性进展与完成关闭必须区分」的核心诉求。但提案在**实施链路、词表书写形式、平台旁路风险**三处存在具体缺口，需修订后方可进入裁定。保留意见详见下文 C、E 两节与「修改建议」。

## 详细论证

### A. 方案合理性

三方案覆盖了合理的选择空间主轴：A（二词表+禁用 Fixes）、B（二词表+ Fixes 等价保留）、C（平台对齐、放弃脚注层区分）。方案 C 被正确否决——它直接违背 #8 裁定，无需再议。

方案 A 的推荐理由总体充分，但有两点值得补强：

1. **「禁用 Fixes」的执行性质未被说透**。§5.1 明确检查器不做语义判定，因此「禁用」在工具层无强制力，实际执行落在审查者（§6.3 模式）。这本身合法，但提案应明说「禁用 = 审查者驳回依据」，否则读者会误以为存在机器闸门。
2. **方案空间有一处遗漏**：未讨论「推荐使用 Closes、允许但不鼓励其余平台关闭词」的软约束变体（即 SHOULD/MAY 分层）。该变体与 A 的差别仅在审查严格度上，论证负担低，不提也罢；但提案宣称三方案覆盖选择空间时，严格说覆盖的是「硬约束」子空间。这不构成否决理由，属于论证完备性瑕疵。

### B. 平台兼容性

平台语义研究准确，与我掌握的事实一致：

- GitHub 9 个关闭词语义等价、大小写不敏感、仅默认分支生效；
- GitLab 另有 Implements 词族，语义同样等价；
- `Refs` 在两大平台均无保留语义，自定义安全。

方案 A 的平台兼容性成立：`Refs` 不触发任何平台行为，`Closes` 是标准关闭词。但有一个**提案已触及却未给出对策的旁路风险**：GitHub/GitLab 扫描的是提交消息（含正文）任何位置的 `fixes #n` 模式，不止脚注。方案 A 禁用的是「脚注写 Fixes」，但正文里一句顺口的英文 "this fixes #123" 在合并进默认分支时**仍会触发自动关闭**，词表约束对此无效。提案第 9 节承认了这一现象（「平台会解析提交消息正文……本仓不鼓励这种用法」），但「不鼓励」没有落点——既不在条文里，也不在边界与例外里。这是 6 种边界场景之外真实存在的第 7 种场景。

另有一个轻度提醒（不构成阻塞）：下游项目若采用 squash merge 工作流，PR 内各 commit 的脚注可能被压缩进合成提交消息时丢弃或改写，关闭词需确认保留在最终落库消息中。可在模板或边界说明中加一句提示，无需展开。

### C. 实施可行性

条文与模板的改写文本本身清晰可执行，6 种边界场景覆盖度好。但有**一处实施链路缺口，是本意见最重要的发现**：

**提案的「后续步骤」遗漏了派生编译链。** RELEASE.md 第 1–4 行显示该文件是受管托管块：`src=DECISIONS.md@0.5.0`、带来源内容标识（5f0e31b4…）、并注明「依据 lazypack-setup 内置快照编译，离线事实源查阅 lazypack-setup/references/DECISIONS.md」。按 §6.6①（口径单源、派生副本机检同源），正确的实施步骤不是「改 DECISIONS.md + 改 templates/RELEASE.md」，而是：

1. 改 DECISIONS.md §5.1（口径源）并升位版本号；
2. 同步更新 lazypack-setup 内置快照（references/DECISIONS.md）；
3. 由编译链路重新派生 RELEASE.md 固定段（含新的来源内容标识与 `@新版本` 标注）；
4. 全仓清点其余词表提及点（见 D 节）。

提案第 10 节只写了第 1 步和第 3 步的一半（改模板文件），漏掉快照同步与版本升位。若按现案执行，下游项目托管块里的指纹将与口径源对不上，同源机检会报漂移——这正是 §6.6① 要防的「静默失效」形态。§9 规程的「强制实施项」也明确要求派生一致性同步，提案应据此补全。

另一处细节歧义：**书写形式未钉死**。提案自己的使用分析（§1.3）记录本仓存在 `Refs: #38`（带冒号）变体，而拟议条文与全部示例均写无冒号形式。条文若不明文规定唯一规范形式（建议：首字母大写、无冒号、空格接 `#n`），则：(a)「与既存使用完全一致」的论断在细节上有出入；(b) 未来 Level-1 格式检查失去判定基准。这属于一句话就能修掉的歧义，但必须在条文层修，不能留给模板。

### D. 与既有条文的关系

- **§5.2（Google CL 正文法）**：正文说「为什么」、脚注做机器可读关联，职责切分天然兼容，无冲突。
- **§5.4 / §5.5（版本映射、CHANGELOG 由提交生成）**：版本升位只看 type 与 `!`，不看脚注词；CHANGELOG 由提交编译，词表变化不破坏生成逻辑。建议在实施时顺手确认 CHANGELOG 生成器不解析脚注关键词做分组（预期不解析，属一次性核查项）。
- **§6.6①（口径单源）**：关系最紧密的一条，见 C 节——提案目前的后续步骤不满足该条要求，必须补。
- **§4.1（发版规则的家）**：词表属于 RELEASE.md 固定段，改动走固定层，归属正确。

**缺口**：提案未做消费者清点。除 DECISIONS.md §5.1 与 RELEASE.md:12 外，`docs/agents/issue-tracker.md`（工单闭环纪律）、lazypack-setup skill 正文、本仓 AGENTS.md 等处若提及 `Closes`/`Fixes` 词表，都需同步。建议后续步骤增加一条「全仓检索 `Closes|Fixes|Refs` 提及点并逐一核对」的强制项——成本是一次 grep，收益是口径单源的完整性。

### E. 迁移成本

「零迁移成本」需要拆成两层表述才精确：

1. **本仓：成立。** 提交历史不可变且规则向前适用；§1.3 的使用分析显示实践已是 Refs/Closes 二分，条文修订属现状明文化。唯一出入是带冒号的 `Refs:` 变体（见 C 节），属书写形式层面，通过钉死规范形式消解。
2. **下游项目：非零但无手工负担。** 已运行过 setup 的项目，其 RELEASE.md 固定段仍是 @0.5.0 编译的「Closes 或 Fixes」旧词表，要等下次 `[UPGRADE]` 才随指纹漂移被换血。这段时间差是机制设计内的合法漂移，不构成阻塞，但提案应如实写明「下游随下次 setup 升级自动传播，无需手工迁移」，而不是笼统宣称零成本——§7.5 如实报告的要求同样适用于提案文本自身。

对现有 commits 无语义影响（历史提交不按新词表追溯追责），此点提案表述正确。

## 关键发现

1. **实施链路缺口（最重要）**：RELEASE.md 是带指纹的受管编译块，提案后续步骤漏掉「更新 setup 内置快照 + 重新编译派生 + 版本升位」，不满足 §6.6① 与 §9 规程强制实施项，照现案执行会造成同源机检漂移。
2. **书写形式未钉死**：既存使用含 `Refs: #n` 带冒号变体，拟议条文须明文规定唯一规范形式（建议 `Refs #n` / `Closes #n`，首字母大写、无冒号），否则「零迁移」论断有细节出入，也给未来检查器扩展留下二义性。
3. **平台旁路风险无对策**：「禁用 Fixes」只约束脚注，正文中的 `fixes #n` 仍会触发平台自动关闭；需在边界与例外中补第 7 种场景（正文描述性 fix 不得紧跟 `#n`，或优先用中文表述规避）。
4. **消费者清点缺失**：提案未排查 issue-tracker.md、setup skill 正文等其他词表提及点，与口径单源原则存在一致性风险；一次全仓检索即可闭合。
5. **「零迁移成本」需精确化**：对本仓成立，对下游是「随版本升级自动传播、无手工迁移」，建议按此改写，避免过度宣称。

## 修改建议

**对 §5.1 拟议条文的修订稿**（在方案 A 基础上补书写形式与审查落点）：

```
5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。
type 用 Angular 8 个（`build ci docs feat fix perf refactor test`）加 `chore` `revert`。
脚注用 `Refs #n` 关联 issue（相关但未满足关闭条件），
用 `Closes #n` 关闭 issue（已满足关闭条件）；
脚注关键词规范形式为首字母大写、无冒号、空格接 `#n`，
不使用 `Fixes` 等其他平台关闭词（由审查者执行）。
检查器把脚注当信息行，不做语义判定。
```

**对 RELEASE.md 固定段**：随编译链同步更新即可，措辞镜像条文。

**对提案「边界与例外」**：新增第 7 条「正文描述性用词」——提交正文使用 fix/fixes 等描述性词汇时不得紧跟 `#n`（如避免 "this fixes #123"），以防平台在默认分支合并时旁路词表约束、意外关闭 issue；中文正文天然规避。

**对提案「后续步骤」**：替换为——

1. §9 讨论与裁定；
2. 更新 DECISIONS.md §5.1 并升位版本号（口径源）；
3. 同步 lazypack-setup 内置快照（references/DECISIONS.md），由编译链重新派生 RELEASE.md 固定段（新指纹 + 新版本标注）；
4. 全仓检索 `Closes|Fixes|Refs` 提及点（含 docs/agents/、skills/、AGENTS.md），逐一核对同步；
5. 一次性核查 CHANGELOG 生成器不依赖脚注关键词；
6. （可选）存量 commits 书写形式清点，仅作事实记录，不追溯追责。
