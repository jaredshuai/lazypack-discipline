# 第一轮独立意见 - 参与者 2

> 评审对象：`docs/proposals/issue-29-commit-footer-semantics.md`
> 核验材料：`docs/DECISIONS.md`、`skills/lazypack-setup/templates/RELEASE.md`（两项属提示词指定必读）
> 外部核验：GitHub / GitLab 官方文档（本轮实读，非转述提案第二节）
> 独立性声明：本轮未阅读任何其他参与者提交，未调用任何项目工具、检查器或门禁流程，未读 git log 与工作区改动。唯一越出「三份必读材料」的读取是：① 外部平台官方文档；② 用文件检索确认 `skills/lazypack-setup/references/DECISIONS.md` 与 `templates/RELEASE.md` 两个路径是否存在——因为 D 维度的结论取决于这两份派生产物是否真实存在，我不核实就无法下判断，此处显式声明。

## 总体立场

**倾向支持方案 A 的目标（`Refs` 关联 / `Closes` 关闭的二分词表），但不接受 A 的执行形式「禁用 `Fixes`」，也不接受提案给出的落地路径。**

拆开看，A 里其实混了三件可以分别表决的事：

1. **承认 `Refs` 为关联词、`Closes` 为关闭词**——我支持，这既是 #8 裁定的诉求，也确实是本仓既成用法，属于把现状明文化，无争议。
2. **把词表收敛为两个词**——我反对。不是因为语义不清，而是因为**「禁用」这个动作在平台上不可执行，只在审查层可执行**，而提案把它写成了平台层面的保护，落进派生模板后变成了对所有下游项目的虚假承诺（详见 B 维度核心发现 1）。
3. **把「检查器把脚注当信息行，不做语义判定」写进 §5.1**——我反对，这是提案夹带的第二项规范变更，且与现行 §6.6 的载体纪律相冲突（详见 C 维度核心发现 3）。

另外我提议一个提案没有列出的选项（**方案 D：口径与判据分层**），理由见 A 维度——我认为「二选一还是三选一」本身就是个被错误框定的问题。

**一句话结论：词表该收敛，但「收敛」应表述为「本仓声明用语收敛到 `Refs`/`Closes`」，而不是「`Fixes` 被禁用」；落地面应走编译管线并升位固定层版本，而不是手改两份模板。**

## 详细论证

### A. 方案合理性

**A-1 三方案覆盖度评估**

| 维度 | 覆盖情况 |
|---|---|
| 词表语义 | 覆盖（关联 vs 关闭的核心诉求被 A、B 满足） |
| 别名收敛力度 | 覆盖（A 严 / B 松），但**只处理了 9 + 16 个平台别名中的 1 个** |
| 落地路径（编译 vs 手改） | **未覆盖**——三方案都假设「手改 RELEASE.md 模板」 |
| 版本升位 | **未覆盖**——三方案都没提 DECISIONS.md 的 SemVer 升位 |
| 规则归属（§5.1 条文 vs 审查者标准文档） | **未覆盖**——三方案都假设口径必须住 §5.1 |
| 非 GitHub 形态工单的逃生口 | **未覆盖** |

后四项不是边角料，其中两项直接决定改动能不能合法落地（见 D、E 维度）。所以我的判断是：**词表这一层的选择空间覆盖合格，但"如何落地"这一层根本没有进入选择空间。**

**A-2 推荐 A 的理由不成立（最关键的一条）**

A 的理由 5 写「`Refs` 不是平台保留词，不会触发意外行为」。这句话在**平台层面**成立，但 A 的整个论证把它当成了「所以禁用 `Fixes` 是安全的」。这两件事之间没有推导关系。

真实情况相反：正因为 `Refs` 不是保留词（无害），而 `Fixes` **是**保留词（有害且无法在本仓消除），所以「禁用 `Fixes`」这件事的收益是**认知收益**（少记一个词），而代价是**一条本仓执行不了的禁令 + 一条破坏性的下游变更**。把认知收益和执行成本放在一张表的「平台兼容性 ✅」一栏里合并叙述，是这份提案论证结构上最不严谨的地方。

**A-3 我提议的方案 D：口径与判据分层**

提案 §5 的 6 类边界场景（部分完成 / 依赖阻塞 / 多次提交 / revert & hotfix / 文档测试 / 多票），每类都要 5–15 行才能说清。全部塞进 §5.1 会让「提交头格式」这一条膨胀到二三十行，而 §5.1 现在只有一行半。

按 §4.1 表，「给 agent 的按需说明」的家是 `docs/agents/<主题>.md`，其「何时清」栏写明「被闸门或工具替代后删」——这正好是词表边界的形态：现在靠人读，等将来有门禁就删掉。按 §6.6②，「需要理解含义、权衡或授权的，执行载体是当轮执行者与审查者」，而「用 `Closes` 的那一刻是否真满足关闭条件」恰恰是需要理解含义的判断。

**方案 D 的形态**：
- §5.1 只留口径，最短可到一行：`脚注用 Refs #n 关联票，用 Closes #n 关闭票。`
- 边界判据、6 类场景、`Fixes`/`Resolves` 等平台别名的审查要点，进 `docs/agents/commit-footer.md`（新登记）或 `CODING_STANDARDS.md`（审查者执行，§6.3）。

这样 §5.1 保持瘦，语义判据有明确执行人，边界材料可随门禁成熟而删除。我认为这比 A/B 都更贴合本仓既有条文结构。

**A-4 `Refs` 这个词本身缺乏论证**

提案选 `Refs` 的理由是「本仓已经在用」。这是**路径依赖论证**，不是**最优化论证**。两者在「本仓内部没有迁移成本」这件事上等价，但在「这个词是否是最佳标记」上不等价。

补充观察：`Closes`/`Fixes`/`Resolves` 都是**动词**，`Refs` 是**名词**（实为 `Ref` 的省略式复数）。词表内部形态不齐，本身带来一点认知摩擦。反向候选（生态里都存在）：`Part of #n`、`Follows #n`、`Related to #n`（GitLab 官方文档就用它做关联示例）。

我不主张换词——换词要付 20+ 处存量的迁移代价，收益是纯洁癖。但我要求提案把「保留 `Refs`」写成一句**明示选择**（理由：存量 20+ 处零迁移），而不是让它看起来像是被论证出来的唯一正确答案。

### B. 平台兼容性

**B-0 核验结论：提案第二节大体准确，但有三处偏差，且遗漏了一条对本议题至关重要的官方机制。**

我实读了两份官方文档（GitHub Docs「Link PR to issue」页面正文；GitLab `doc/user/project/issues/managing_issues.md` master 分支原文），核对结果：

✅ 准确的部分：GitHub 的 9 个关闭关键词、大小写不敏感、可加冒号；GitLab 的 4 组关键词含 `Implement*`；两者均无官方「关联不关闭」关键词；`Refs` 非保留词。

⚠️ **偏差 1——「仅在默认分支生效」的机制表述被简化了。**
GitHub 文档的原话区分了两件事：PR 描述里的关键词「only when the pull request targets the repository's *default* branch」；而提交消息里的关键词是「The issue will be closed when you *merge* the commit into the default branch」。提案把两者压成一句「仅在默认分支生效」，作为固定层条文问题不大，但如果据此写检查器会理解错。

⚠️ **偏差 2——GitHub 明确说明「提交消息里的关闭词不产生 PR 关联」。**
原文：「the pull request that contains the commit **will not be listed as a linked pull request**」。也就是说 `Closes` 写在 commit 里的可追溯性收益，比提案默认假设的低：票会被关掉，但 PR 不会出现在票的 Development 区。提案 §2.1 的「Manual linking 可以实现关联但不关闭」只讲了手动关联能做什么，没讲自动关闭在提交场景下**丢掉了什么**。

⚠️ **偏差 3——提案漏掉了 GitLab 的一条与本议题直接相关的官方机制。**
提案 §2.2 写「GitLab 文档示例中使用 `Related to #5` 表示关联但不关闭 / 这不是官方关键词，仅作为文本描述」。前半句对，后半句**低估了**：GitLab 文档把这句话放在「Closing issues automatically」的正例里，与关闭用法并列；`Related to` 之所以有效，正因为它**故意不匹配**官方正则。这是 GitLab 事实上推荐的关联写法。

**❗ 遗漏（本轮最重要的外部发现）——GitLab 公开了关闭模式的完整正则：**

```shell
\b((?:[Cc]los(?:e[sd]?|ing)|\b[Ff]ix(?:e[sd]|ing)?|\b[Rr]esolv(?:e[sd]?|ing)|\b[Ii]mplement(?:s|ed|ing)?)(:?) +(?:
  (?:issues? +)?%{issue_ref}(?:(?: *,? +and +| *,? *)?) | ([A-Z][A-Z0-9_]+-\d+)
)+)
```

这条正则有三个后果，提案一条都没讨论：

**(i) 正则不锚定「脚注区」，它扫描整条消息。** GitLab 官方文档自己的示例：

```
Awesome commit message

Fix #20, Fixes #21 and Closes group/otherproject#22.
This commit is also related to #17 and fixes #18, #19
and https://gitlab.example.com/group/otherproject/-/issues/23.
```

文档明说：这条消息关掉 `#18 #19 #20 #21 #22 #23`，而 `#17` 因为不匹配而不关。注意 `fixes #18` 出现在句中、小写、前面是 `and `——**仍然关闭**。

**(ii) 正则的第二个分支接受 JIRA 式 ID。** `([A-Z][A-Z0-9_]+-\d+)` 意味着 `Closes VAL-TEST-006` 是**合法的 GitLab 关闭模式**。提案 §1.3 把这条列为本仓既成用法，却只让新词表覆盖 `#n` 形态——对本仓之外的、票号不是 `#n` 的项目，这条规则直接失准。而 §1.1 明确允许项目层声明非上游位置的工单系统。

**(iii) 关键词可被项目级关掉。** GitLab 提供 `Settings → Repository → Branch defaults → Auto-close referenced issues on default branch`，取消后「Referenced issues are still displayed, but are not closed automatically」；Self-Managed 管理员还能改全局模式。

**B-1 核心发现 1：方案 A 的「禁用 `Fixes`」在平台上不可执行，提案对此的表述是错的**

提案 §9「对 `Fixes` 的处理」三条：

> - 禁用 `Fixes` 作为脚注关键词，降低认知负担
> - 如果用户在提交消息正文中使用 `Fixes` 作为描述性词汇（如 "This fixes the bug"），**不受影响**
> - GitHub/GitLab 的自动关闭功能仍然有效（因为平台会解析提交消息正文），但本仓不鼓励这种用法

第二条和第三条互相打架，而且**都不成立**：

- GitLab 侧已由官方文档与官方正则直接证伪：`fixes #18` 出现在句子中间会被关闭。「描述性使用」与「关闭使用」在平台层**没有分界线**，只有「后面有没有跟票引用」这一条线。
- 更现实的坑是**所有格写法**：`Fixes #37's command examples`。按 GitLab 正则，`#37` 匹配后其后可有零次分隔，`'s ...` 不影响匹配 → 照样关闭。这是一个 AI 和人都极容易写出来的自然句子。
- GitHub 侧：官方文档的定义是关键词出现在「the pull request's description **or in a commit message**」，**没有任何位置限制**，也就意味着不能靠「放在脚注区」来规避。GitHub 未公开正则，`Fixes #37's ...` 的精确行为我无法从文档判定，**这一条我标为推断，未验证**——但既然文档层面不存在位置限制，靠位置防关闭就是不可依赖的。

**所以正确的处理方式不是「禁用」，而是：把 `Fixes`（以及 `Resolves`/`Implement`/大小写变体）明确归类为「平台保留词」——本仓不在它们身上承载语义；一旦在提交里写出这类词，无论本意如何，平台都会尝试关闭，必须当作关闭动作对待。** 这个表述是可执行的、可审查的、且对下游诚实。提案的「禁用」表述则会让下游以为「写了 `Fixes` 没关系，只是我们不鼓励」——这恰恰是本议题想防的事故。

**B-2 核心发现 2：提案 §7.2 的模板措辞包含对下游的事实性误判**

方案 A 的 RELEASE.md 建议措辞：

> `使用 Closes #n 关闭 issue（满足关闭条件，合并到默认分支时自动关闭）`

括号里的平台断言对**一部分**项目成立，对三类项目为假：
1. 票不在 GitHub/GitLab Issues（§1.1 允许项目层声明别处）——自动关闭不存在，该行为完全落空；
2. GitLab 项目关掉了 `Auto-close referenced issues on default branch`；
3. GitLab Self-Managed 管理员改了全局 closing pattern。

这段话会被 `/lazypack-setup` 编译进**所有**下游项目的 `RELEASE.md` 固定段（模板第 4 行已声明它是「派生自 DECISIONS.md@0.5.0」的受管块）。在一个给所有项目看的模板里断言平台行为，必须加限定词，否则固定层就在对没核实过的事实立法。改法：`（票若位于支持自动关闭的平台票系统，合并入默认分支时自动关闭）`。

**B-3 对 `Refs` 收益的重新评估（提案乐观了一点）**

`Refs` 在两个平台都无机器效果：不会建关联、不会关闭。GitLab 官方有关联写法 `Related to`（能建 related issue 链接），GitHub 有手动 Development 关联。所以本仓选 `Refs` 的实际收益是「人类可读的约定」。

这不构成反对方案 A——本仓的工单追溯本来就主要靠票正文与 §4.1 的登记册，而非平台链接。但它有一个后果需要在条文里说清：**`Refs #n` 不产生任何机器可校验的效果，因此它只能由审查者判定（§6.6②），不能期待任何自动门禁能证明它写对了。** 提案 §6.2 Level 1「检查脚注是否使用允许的关键词」是对的形式检查，可以；§9 理由 5「易于检查器扩展」如果被读成「可检查 `Refs` 写得对不对」，则超出能力。

**B-4 与 Conventional Commits 的关系缺位**

§5.1 是 CC 1.0.0 条文，但提案全篇只在附录挂了一个 CC 链接，没有说明：`Refs`/`Closes` 都不是 CC 规范定义的词，CC 只规定脚注语法（token + `<space>#` + value，`BREAKING CHANGE` 为保留 token）。`Closes #n` 在语法上是合规脚注，但**其语义完全由本仓自定义**。这一点必须写明，否则下游会误以为 CC 规定了 `Closes`，而 CC 其实没规定。

### C. 实施可行性

**C-1 核心发现 2：提案 §7.1 悄悄增改了条文内容，且与 §6.6 冲突**

提案 §1.4 和 §6.1 都写「**根据 §5.1 说明**：检查器把脚注当作信息行，不做语义判定」。

我核了 `docs/DECISIONS.md:79`，§5.1 全文是：

> 5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。type 用 Angular 8 个（`build ci docs feat perf refactor test`）加 `chore` `revert`。脚注 `Closes #n` 关联票。

**没有「检查器把脚注当信息行」这句。** 提案 §7.1 自己也把「当前条文」贴对了（没有这句），却又在「修改建议」里把它加了进去。所以：① 提案 §1.4/§6.1 的出处标注是错的；② 提案是在借「澄清词表」的名义，**新增一项关于工具行为的规范条款**。

（这一点也说明：本次提示词的「当前状态」第三条同样沿用了这个错误出处。提示词由主持人按 §9.2 从提案生成，错误随之传播。记录在此，供维护者核对生成链路。）

为什么这不只是措辞问题：

- §6.6③ 的方向是「凡裁定为须阻止提交的规则，可判定部分必须落进确定性工具」，并明文「不得以『工具化不了』为由把该类规则整条留在常驻文件」。提案做的事是**反向**的：把「不做语义判定」这个**当前的、未接线、非授权状态**写成条文。一旦写死，将来要把词表接成阻断闸门，就得再开一次 §9 会议来删这句话。
- §6.6④ 的口径是：接线是独立一步，需实施票授权；未授权时保持手动运行是**合法稳态**，不是条文内容。
- §2.3 同样要求：能接 hook 就写出 hook，**否则标明未接线**，但「不得宣称门禁已生效」。

**结论**：词表条款里不该写检查器立场。要么完全不提（推荐），要么按 §6.6④ 的口径写成「本条可判定部分归工具层，接线须另获授权」。

**C-2 核心发现 3：§7.1 忽略了三份副本与同源校验，落地路径错误**

`skills/lazypack-setup/templates/RELEASE.md:1` 的受管块标记是：

```
<!-- lazypack:start block=release-discipline src=DECISIONS.md@0.5.0 gen=__GEN__ input=__INPUT__ fp=__FP__ -->
```

第 4 行进一步声明：「派生自 lazypack-discipline 固定层 DECISIONS.md@0.5.0（依据 lazypack-setup 内置快照编译，来源内容标识: 5f0e31b4…；离线事实源查阅 lazypack-setup/references/DECISIONS.md）」。

即本议题涉及**三份**文件，而不只是提案提到的两份：

| # | 路径 | 角色 | 提案是否提及 |
|---|---|---|---|
| 1 | `docs/DECISIONS.md` | 口径唯一事实源 | ✅ |
| 2 | `skills/lazypack-setup/references/DECISIONS.md` | 离线内置快照（**已确认存在**） | ❌ |
| 3 | `skills/lazypack-setup/templates/RELEASE.md` | 由 1/2 编译出的受管块 | ✅（但路径错） |

§6.6① 要求：派生副本「由 `/lazypack-setup` 从固定层编译派生并机检同源（`src=DECISIONS.md@<SemVer>`、来源内容标识、字节/blob/版本串一致性检查）」；§1.4 要求「每条纪律只活在一处」，并把「人手把口径抄进配置或脚本」判为第二源、明确违反。

**因此提案 §10「后续步骤」第 3 步「更新 lazypack-setup/templates/RELEASE.md」是错误路径。** 手改模板会让三份副本与 `src=` 版本串、来源内容标识失配，同源校验立刻不通过。正确顺序应为：

1. 裁定条文措辞（§5.1 + 派生模板措辞一并定稿）；
2. 改 `docs/DECISIONS.md`，**按 §5 文件头要求升 SemVer**（见 E-2）；
3. 走编译管线更新 `skills/lazypack-setup/references/DECISIONS.md` 快照；
4. 由管线重新编译 `templates/RELEASE.md`，校验 `src=DECISIONS.md@<新版本>` 与来源内容标识一致；
5. 跑同源机检。

**C-3 §5 的 6 类边界：方向对，但漏了 5 类，且两条规则自相矛盾**

写得好的部分：§5.3 的「拆分 issue」建议是这节最有价值的一条——它承认有些票天然不该被单个提交关闭，应该在**开票阶段**解决，而不是在提交阶段纠结用哪个词。这条应该从「最佳实践」提升为条文要求。

漏掉的场景（按重要性排）：

1. **跨仓引用**（提案完全未提）。GitHub 官方语法 `KEYWORD OWNER/REPOSITORY#ISSUE-NUMBER`；GitLab 支持 `group/project#123` 与 issue 完整 URL。关闭上游依赖仓的票是常见且正当的操作，词表必须说明是否允许、用哪个词。
2. **同一提交内 `Refs` 与 `Closes` 指向同一票**。§5.1「每个 issue 独立一行，语义独立判断」的规则会允许 `Refs #50` 和 `Closes #50` 同现，这在语义上自相矛盾。需明确禁止。
3. **票号形态**。提案 §1.3 自己记录了 `Closes VAL-TEST-006`，但新词表只写 `#n`。按 B-0 的 GitLab 正则，`[A-Z][A-Z0-9_]+-\d+` 是官方认可的引用形态；而 §1.1 允许项目层声明任意工单位置。这条不写，「零歧义」就是假的。
4. **Revert 时原提交已带 `Closes`**。§5.5 说 revert 用 `Refs`，但如果当初关票的提交还在默认分支上，票已经关了，revert 只是把代码退回去。关错的补救路径（谁有权重开、§3 的书记员/清道夫是否介入）提案一字未提——而 §3.4 的书记员职责恰恰是「每张票关闭后扫一遍」。
5. **平台 sub-issue / child items**。GitHub 有 sub-issues、GitLab 有 child items。§5.2 讲的「一张票包含多个子任务」是票内任务列表，与平台 sub-issue 是两回事。关父票而留子票，平台行为是什么？需明确或交项目层。

另有两条规则需要收紧：
- §5.1「每个 issue 独立一行」与两个平台惯用的逗号并列写法（`Closes #10, #11` / `Fix #20, Fixes #21`）相冲突。若将来上 Level 1 检查器，这条会误伤平台原生写法。建议改为「同一提交可写多行，也可用平台支持的并列写法；每个票的关键词独立判定」。
- §6.2 Level 2「`Closes` + `docs`/`test` 类型 → 警告」与提案 §5.6「文档票完成时可用 `Closes`」直接矛盾。提案 §6.3 说不建议强制是对的，但既然自相矛盾，就不该作为「未来扩展可能性」列出——会让将来的实施者拿到一条已经自相矛盾的规格。

**C-4 条文措辞的可执行性**

提案给的 `§5.1` 建议措辞本身可用，但有两个可改进点：

- 「表示相关但未完成」把 `Refs` 的语义锚在「未完成」上。更准确的锚点是「**本提交不满足该票的关闭条件**」——因为存在「完成了，但按 §5.3 依赖未就绪」这类情形，两种描述在 §5.3 里会打架（§5.3 说这种情况该用 `Refs`，同时又说「票定义的是『功能可用』时依赖未就绪用 `Refs`」，此时票并非「未完成」而是「未验收」）。
- 缺少**否定式兜底**：应显式写明「平台其他关闭别名（`Fixes`/`Resolves`/`Implement` 及其大小写变体）不得用于表达关联」，并且——按 B-1——把它们的效果如实写成「一旦写出，平台会当作关闭动作」。

### D. 与既有条文的关系

**D-1 核心发现 4：术语从「票」改成「issue」是一次夹带的地基变更**

§5.1 现文是「脚注 `Closes #n` **关联票**」。提案全部改成「关联 **issue**」。这不是措辞调整：

- 本仓固定层对工单的既有称谓是「票」（§3 角色表「一张票」「已关票」）/「工单」（§1.1、§4.1 表）。
- §1.1 明确「项目层用 `docs/agents/issue-tracker.md` 声明实际工单位置」，即固定层**有意保持与具体工单系统无关**。改用 `issue` 等于把固定层词汇绑到 GitHub 词汇上。
- §4.1 把「词汇表（术语、边界）」的家定在 `CONTEXT.md`（只放词，不放实现）。**术语变更按 §4.1 应先在 `CONTEXT.md` 落词**。本轮我按独立评审边界未读 `CONTEXT.md`，无法确认 `issue` 是否已登记——请维护者核验；若未登记，本次改动会造出一个未登记的新术语，与 §4.1「册上查不到的产物视为未登记」相抵触。

**建议**：条文保留「票」，词表示例里注明 `#n` 是 GitHub/GitLab 的票引用写法。若确实要引入 `issue` 作为术语，单独走一轮、在 `CONTEXT.md` 登记，并说明它与「票 / 工单」三词的关系。

**D-2 与 §5 其他条款：一致，无冲突**

§5.2（正文说关联 bug 号）、§5.4（提交类型 → 版本）、§5.5（CHANGELOG 由提交生成）均不受影响。特别确认一点：§5.5 说 CHANGELOG 由提交生成，而 §4.1 表把「临时现场」之类交给清道夫——如果将来任何工具要解析脚注（§6 提案里提到的 Level 3），它会消费 `Closes`/`Refs`，但那是**读**，不受本次词表变更影响。

**D-3 与 §7 的关系：提案漏了一条 §7.1 义务**

§7.1：「执行者提交时同步 diff 涉及的文档行；书记员关票后补全局视角。」本次改动会改动 `templates/RELEASE.md`，而受管块**不得手改**（模板第 29 行明确「不要改受管标记行或块内固定段」）。因此 RELEASE.md 的更新必须由编译完成，**不能作为一次普通提交里的手改行**。这需要在实施票里写明，否则执行者会踩 §7.1 与受管块边界的冲突。

**D-4 与 §4、§6.6 的关系：需要一次归属裁定**

§6.6⑤：「规则迁入载体前须满足：口径位置已确定（§6.6①）、目的地已有登记的家（§4.1 表）。」

本次议题正好卡在这条上——它要先决定口径住哪：
- 若住 §5.1（提案默认）→ 判据部分要么留在条文（膨胀），要么下沉到 `docs/agents/` 或 `CODING_STANDARDS.md`；
- 若住 `CODING_STANDARDS.md` → §6.3「工具能查的不写进去」要求先剔除可判定部分（词表白名单本身是可判定的 → 应留工具层）；
- 若住 `docs/agents/commit-footer.md` → 需按 §4.1 表登记到 `docs/ARTIFACTS.md`。

提案没有做这个裁定，直接跳到条文措辞。按 §9.1「只有改固定层条文才开会」，既然要改 §5.1，开会是对的；但**开会之前应该先把这道归属问题作为选项摆上桌**，这正是方案 D 的价值。

### E. 迁移成本

**E-1 核心发现 5：「零迁移成本」只在最窄的范围内成立**

提案 §9 理由 1：「零迁移成本：本仓已经在实际使用 `Refs` 和 `Closes` 的二分法，条文修改仅是将现状明文化。」

对**本仓自身**成立；对**下游**不成立：

| 迁移对象 | 成本 | 提案是否评估 |
|---|---|---|
| 本仓存量 commit | 近似零 | ✅ |
| 本仓存量 commit 的写法归一 | 低但非零：§1.3 显示 `Refs: #38` 与 `Refs #37` 两种写法并存，将来上检查器须先定一种 | ❌ |
| 已按 0.5.0 生成模板的下游项目 | **非零**：其 `RELEASE.md` 固定段明确推荐 `Fixes #n`，方案 A 把既有合法用法判为非法 | ❌ |
| 非 `#n` 票号的项目 | **非零**：词表只覆盖 `#n`（见 C-3(3)） | ❌ |
| 非 GitHub/GitLab 票系统的项目 | **非零**：词表语义与模板措辞均按平台自动关闭假设写（见 B-2） | ❌ |
| 固定层版本号 | 未评估（见 E-2） | ❌ |

方案 A 的对比表把「迁移成本 ✅ 零（已在使用）」列为 A 优于 B 的理由之一。按上表，B 才是真正的低成本项——B 不撤销任何既有许可，是**纯增量**。建议把这一行改为：

| 迁移成本 | A：非零（撤销 `Fixes` 许可 + 版本升位 + 下游重生成） | B：低（纯增量，下游现有文本继续有效） |

这会改变权衡结果。我认为这个改变是**对的**，也是我倾向 B 的实质理由。

**E-2 未被提及的必做动作：固定层 SemVer 升位**

`docs/DECISIONS.md:4` 明文：「改动任何一条须走 §9 讨论章程，并按 SemVer 升本文件版本号。」

本次改动需要升位（不是 patch）：
- 新增 `Refs` 为规范用语 = **新增规范要求**；
- 方案 A 禁 `Fixes` = **撤销模板既有许可**，对按 0.5.0 生成的下游是破坏性变更。

按 SemVer 对「供下游钉版消费的规范」而言，这至少是 **0.6.0**；是否够到 1.0.0（若判为破坏性）应由维护者裁定。提案 §10 的五步后续步骤里没有这一步。

并且要注意：版本串会出现在派生产物里（`src=DECISIONS.md@0.5.0`），下游可据此判断是否过期——**升位本身就是一次对下游的通告**，不能当作纯记账动作。

**E-3 对「修改现有 commits」这一说法的事实校正**

方案 C 理由 3：「需要大量修改现有 commits 的语义理解」。已推送的 commit 无法改写，所以若「修改」指改写内容，该理由不成立；若指「今后对照新词表重新理解历史」，应具体化为可执行动作（如在 §4.1 表 / HISTORY 里说明历史 `Refs`/`Closes` 用法按新词表解释）。这是个表述问题，但在这份要进留档的提案里，值得改准。

**E-4 建议补进 §10 的后续步骤**

1. 裁定条文措辞与**归属**（§5.1 只留口径 / 判据下沉，见方案 D）；
2. 裁定术语（保留「票」还是登记 `issue`，见 D-1）；

## 关键发现

1. **「禁用 `Fixes`」在平台上不可执行，提案对此的表述是错的。** GitLab 官方文档的默认关闭正则是全文扫描、不锚定脚注区，官方示例里句中的小写 `fixes #18` 照样关闭；`Fixes #37's …` 这类所有格写法按该正则同样匹配。GitHub 文档把关键词定义在「the pull request's description **or in a commit message**」，无位置限制。正确表述是「平台保留词不得用于承载语义，且一旦写出即按关闭动作对待」，而不是「描述性使用不受影响」。**这条决定了方案 A 该不该改写，也决定了它能不能被诚实地写进派生模板。**

2. **提案 §1.4/§6.1 的出处标注是错的，且借澄清之名夹带了一条工具立场。** `docs/DECISIONS.md:79` 的 §5.1 并没有「检查器把脚注当信息行，不做语义判定」这句；提案 §7.1 自己贴的「当前条文」也没有，却在修改建议里加了进去。把未接线的当前状态写成条文，与 §6.6③/④ 的载体纪律相反，会导致将来接闸门须再开一次会删句。

3. **落地路径错了，且提案漏了第三份副本。** `templates/RELEASE.md` 的受管块标记为 `src=DECISIONS.md@0.5.0`，第 4 行声明由内置快照编译、离线事实源在 `skills/lazypack-setup/references/DECISIONS.md`（该文件已确认存在）。手改模板违反 §6.6① 同源与 §1.4 单源，且会使 `src=` 版本串与来源内容标识失配。正确顺序是先改源文件 → 升版本 → 更新快照 → 走编译 → 机检。

4. **`#n` 不是唯一的票引用形态，提案的词表因此不是「零歧义」。** GitLab 官方正则的第二个分支接受 `[A-Z][A-Z0-9_]+-\d+`，故提案自己记录的 `Closes VAL-TEST-006` 是合法关闭模式；GitHub 官方另有 `KEYWORD OWNER/REPO#N` 跨仓语法。结合 §1.1 允许项目层声明非上游工单位置，词表必须覆盖非 `#n` 形态并说明跨仓是否允许。

5. **词表该收敛，但「规则住哪」这个更前置的问题没有进入选择空间。** §5.1 是提交头格式条文，容不下 6 类（实际需 11 类）边界场景；§4.1 有「给 agent 的按需说明」这个家且注明「被闸门或工具替代后删」，§6.6② 把「用 `Closes` 时是否真满足关闭条件」判给审查者。建议增设方案 D：§5.1 只留口径一行，判据下沉，按 §4.1 登记。

**（附）另需维护者核验的一处事实**：本次提示词「当前状态」第三条沿用了提案 §1.4 的错误出处。按 §9.2，提示词由主持人从提案生成，建议核对生成链路是否需要交叉核验条文原文。
