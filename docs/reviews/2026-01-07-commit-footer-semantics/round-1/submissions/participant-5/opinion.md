# 第一轮独立意见 - 参与者 5

**议题**：§5.1 脚注词表语义（Issue #29）

**评审依据与未验证声明**：本意见基于提案文档（`docs/proposals/issue-29-commit-footer-semantics.md`）、`DECISIONS.md@0.5.0`（重点 §5，并通读全文以核对与其他条文的一致性——评审维度 D 明确要求核对 §4/§5/§6/§7 关系）、`skills/lazypack-setup/templates/RELEASE.md`、Issue #29 正文（经 API 获取）。离线评审：未读其他参与者意见，未读 `docs/reviews/` 留档，未运行 git log 或项目工具。提案 §1.3 的本仓使用数据（`Closes` 7 次、`Refs` 20+ 次、`Fixes` 脚注 0 次、含 `Closes VAL-TEST-006`）按材料采信，**未独立验证**。

## 总体立场

**倾向支持方案 A，但有保留意见。**

方案 A 的核心判断正确：`Refs`/`Closes` 二分与本仓既有实践一致、满足 #8 裁定「区分阶段性进展与完成关闭」的诉求、与两大平台语义无冲突，且 `Refs` 是唯一能安全承载「关联不关闭」的脚注词。但提案要落地，有**五个必须先修订的问题**：

1. 「严格三分」命名名实不符，会污染裁定记录；
2. 拟议条文是「示例式」而非「封闭白名单式」，禁用范围只点名 `Fixes`，漏掉 `Resolves`/`Implements` 等其余平台关闭词；
3. 提案把检查器行为误引为 §5.1 现行条文，并把「不做语义判定」升格入条文，与 §6.6 载体三轴分离存在张力；
4. 实施清单漏了 DECISIONS.md 版本号升级与 lazypack-setup 快照/来源内容标识同步（编译链关键环节）；
5. 措辞绑定「合并默认分支自动关闭」的平台行为，与 §1.1 允许工单不在代码托管平台的现状冲突（本仓实践已有 `VAL-TEST-006` 这类非 `#n` 票号）。

五点都是措辞与实施层面的修订，不动摇 A 的方向，故不换方案，支持**修订后的 A**。

## 详细论证

### A. 方案合理性

1. **选择空间覆盖基本充分，但漏了一个合法变体 C′**。三个方案分别代表「区分 + 最小词表」（A）、「区分 + 保留平台同义词」（B）、「不区分、平台对齐」（C），覆盖了主要决策轴（是否区分 × 词表开放度）。但存在未列出的第四选项 **C′：只许关闭词入脚注、关联只用正文叙述**——脚注仅在真正关闭时出现（`Closes #n`），阶段性进展不写脚注，关联信息留在正文（§5.2 本就要求正文写「关联 bug 号」）。C′ 同样满足 #8 的「不提前关闭」，提案应补记并写明弃用理由。我的判断是 A 仍优于 C′：(a) 本仓 20+ 次 `Refs` 使用是既成实践，C′ 废弃现状而非明文化现状，违背提案自己的「零迁移」价值排序；(b) 票引集中在脚注，机器可解析位置唯一稳定，正文叙述形态发散；(c) 平台上正文任何 `#n` 提及虽也进 issue 时间线，但可读性与一致性差。

2. **A 的推荐理由链条完整**：与本仓实践一致（材料数据，未独立验证）、语义二分清晰无歧义、`Refs` 非平台保留词、`Closes` 是两大平台标准关闭词。

3. **命名缺陷**：「方案 A: 严格三分」实为**两词二义 + 一词禁用**（语义类别只有「关联/关闭」两类）；而「宽松二分」的 B 恰有三个可用词。按语义类别数，A、B 都是二分；按词数，A 是 2 可用 + 1 禁用，B 是 3 可用。无论哪种口径，「三分」都指不到 A 上。建议改为：**方案 A「两词二义（封闭词表）」**、方案 B「关联词 + 关闭同义词（开放词表）」。

4. **`Fixes` 禁用的论证充分**：平台层面 `Fixes` ≡ `Closes`，保留它只多一个等价词的认知负担；本仓脚注从未用过 `Fixes`（材料数据）。B 的「用户灵活性」收益在本仓场景（执行者主要是读条文行事的 AI）接近于零。

### B. 平台兼容性

1. **平台语义研究基本准确**，逐项核对：
   - GitHub 9 个 closing keywords（close/closes/closed、fix/fixes/fixed、resolve/resolves/resolved）语义等价、大小写不敏感、冒号可选、仅默认分支生效——**正确**；
   - GitHub 无官方「关联不关闭」关键词，靠 PR 侧栏 Development 手动关联——**正确**；
   - GitLab 关闭词含 implement 家族、默认分支生效、self-managed 可自定义 pattern——**正确**；
   - 一处可精确化：GitLab 描述区的 relate 表述（如 `Related to #5`）在新版 GitLab 并非纯文本，可解析生成「相关 issue」链接；但这只发生在 issue/MR **描述**，不发生在 commit message，故不影响本提案结论，只是提案 §2.2 的「仅作为文本描述」可再精确。

2. **A 与平台自动关闭完全兼容，且有一处提案未点破的加分项**：本仓 §3.3 规定「直接在 `main` 提交」，没有 PR 审查这道缓冲。默认分支直推模式下，`Closes #n` 一旦推送立即关票、无人工拦截机会——这使词表区分在本仓**比常规 PR 流仓更必要**，是支持 A 的强论据，建议写进裁定理由。

3. **`Refs` 的平台行为**：`Refs` 不是任何平台的保留词，不触发关闭；但其中 `#n` 引用仍会作为 commit 提及出现在 issue 时间线，保留可追溯性。这是 A 优于 C′ 的又一论据，提案可补录。

4. **一个必须写进边界说明的平台事实**：平台解析的是**整条 commit message**，不是只解析脚注。正文若出现「关闭词 + #票号」的紧邻组合（如 `fixes #123`），合入默认分支时同样自动关票。提案 §9 已自认此点，但据此应把 A 的效果承诺从「防止提前关闭」**降格为「防止脚注层面的提前关闭」**——词表管得住脚注，管不住全文。模板宜加一句「正文避免关闭词 + 票号组合」的提示。

5. **Conventional Commits 兼容性确认**（提案未论证，补上）：CC 1.0.0 允许 `: ` 与 ` #` 两种脚注分隔符，且规范自身的示例脚注就含 `Refs: #133`——`Refs` 是 CC 规范**原生示义词**，`Refs #42`/`Refs: #42`、`Closes #n` 均为合法 CC 脚注。A 与 §5.1 采用的 CC 1.0.0 无冲突。

### C. 实施可行性

1. **条文修改建议清晰，但有两处措辞问题**：
   - **示例式 vs 白名单式**：拟议条文「脚注用 `Refs #n` 关联 issue，用 `Closes #n` 关闭 issue」没有说「只能用」。若有人写 `Resolves #n`，条文沉默。GitHub/GitLab 关闭词家族合计十余个，只点名禁用 `Fixes` 留下大洞。应写成封闭白名单：「脚注票引只用 `Refs #n` 与 `Closes #n`；其余关闭词（`Fixes`、`Resolves`、`Implements` 等）不用作脚注」。
   - **大小写与冒号形态未定**：提案 §1.3 引用的实际使用里 `Refs: #38` 与 `Refs #37` 并存。条文定语义即可，形态（统一首字母大写、冒号可选）交由模板示例统一，不必为此增条。

2. **六个边界场景基本完整、质量较高**：5.4「多次提交逐步推进」与 5.2「部分完成」直接回应 #8 诉求。可补两个小场景：①误用 `Closes` 提前关票的补救口径（人工 reopen + 后续提交用 `Refs` 续联）；②squash/fixup 压扁多条阶段性 `Refs` 提交时，以最终 squash commit 的脚注为准（项目层流程问题，可不入固定层，RELEASE.md 模板提一句即可）。

3. **实施清单不完整**（详见「修改建议」）：漏 DECISIONS.md 版本号升级、lazypack-setup 内置快照与来源内容标识同步、全仓 `Fixes` 字样排查。

4. **一个隐性实施难点**：`fix` 是允许的提交 type（§5.1），`Fixes` 却被禁作脚注词，执行者可能因 `fix:` type 与 `Fixes` 脚注的直觉关联而误用。提案 5.5 的 hotfix 示例（`fix(api)` + `Closes #95`）已在示范正确组合，建议该示例在 RELEASE.md 模板中保留，作为「反直觉组合」的显性样例。

### D. 与既有条文的关系

1. **与 §5.2 的职责重叠未处理**。§5.2 要求正文写「关联 bug 号」；A 把关联职责正式赋予脚注 `Refs #n`，两处都说「关联」。依 §1.4「每条纪律只活在一处」的精神，须澄清分工：**正文写叙述性背景（为什么关联、关联到什么程度），脚注写机器可追溯的票引**。提案完全没碰 §5.2，是同步修订清单的遗漏。

2. **与 §6.6 载体三轴分离的张力未讨论**。方案 A 拟在 §5.1 新增「检查器把脚注当信息行，不做语义判定」，有两点问题：
   - 该句**不是现行条文**——现行 §5.1 止于「脚注 `Closes #n` 关联票」，提案 §1.1/§6.1 把检查器行为（issue #29 中「`Fixes #8` 仍是 format-pass，评审实测」的实证）误引为条文出处；
   - 把「不做语义判定」写死进固定层，等于预先否决未来工具化。按 §6.6②，「脚注是否使用允许关键词」是正则可判定的，属确定性工具候选层；「是否真的满足关闭条件」才是语义层。而按 §6.6①，未来工具恰恰要运行时读取 §5.1 正文作为唯一口径——条文里混入检查器行为散文，会污染这个消费场景。若未来接 Level 1 格式检查，这句条文还得再走一轮 §9。
   - **建议不写该句**：§5.1 只定词表语义；是否工具化、何时接线，交给 §6.6 的既有分派与 §6.6④ 的授权流程。提案 §6.2 自己也建议「从 Level 1 开始」，与把「不做语义判定」入条文的主张内部矛盾。

3. **与 §2.3/§5.7 编译链的一致性**。RELEASE.md 受管块头部标明由 lazypack-setup 内置快照（`references/DECISIONS.md`）编译，带来源内容标识与 `src=DECISIONS.md@0.5.0` 版本锚。§5.1 改动必然连锁：固定层版本号升级、快照同步、内容标识重算、模板重生成。提案 §10.3 只写「更新 templates/RELEASE.md」，**漏了快照与标识**，照单执行会造成上游固定层与编译快照不同源——正是 §6.6① 要防的第二源局面。

4. **对 §4、§7 无实质影响**：§4.1 表无涉及脚注的行；§7.1「执行者提交时同步 diff 涉及的文档行」恰好覆盖模板同步动作；§9.5 留档由主持人按章程处理。

### E. 迁移成本

「零迁移成本」**对本仓基本成立，但应加限定语，且实施成本不为零**：

1. 本仓侧确接近零：历史 commits 无需也不应改写（git 历史不可变，语义明文化不溯及既往）；现有使用模式与 A 完全吻合（材料数据，未独立验证）；执行者是读条文行事的 AI，换词表即换行为，无人类培训成本。

2. 但有四笔被提案忽略的成本：
   - (a) DECISIONS.md 按头部要求须升 SemVer 版本号（0.5.0 → 0.5.1，澄清性 minor）；
   - (b) lazypack-setup 快照 + 来源内容标识 + 模板重编译（机械但有量）；
   - (c) **下游存量项目**：已生成的 RELEASE.md 受管块仍写「Closes 或 Fixes」，与新固定层不同源，须各下游重跑 setup `[UPGRADE]` 才对齐——重编译前存在分歧期（RELEASE.md 头部「出现分歧以本文件为准」可兜底，但应如实告知，不能宣称零成本）；
   - (d) 下游若有真实使用 `Fixes` 脚注的项目（本仓无，下游未知），禁用是一次性行为迁移。

3. 建议把「零迁移成本」改写为：「**本仓零迁移成本；下游存量需一次 `[UPGRADE]` 重编译对齐，若有 `Fixes` 脚注习惯需一次性归一**」。

## 关键发现

1. **方案 A 方向正确，但条文必须白名单化**：现行拟议措辞未禁止 `Resolves`/`Implements` 等其余平台关闭词，只点名 `Fixes` 留洞；「只能用 `Refs`/`Closes`」必须显式写出，否则未来任何格式检查（§6.6① 运行时读条文作口径）都无据可依。
2. **「严格三分」命名名实不符，且提案误引条文**：A 实为两词二义；「检查器把脚注当信息行」是检查器行为而非现行 §5.1 条文，把它升格入条文会与 §6.6 载体分派冲突、堵死未来工具化路径——建议删除该句。
3. **实施清单漏了编译链关键环节**：DECISIONS.md 版本号升级、lazypack-setup 内置快照与来源内容标识同步均未列入，照单执行会造出固定层与快照不同源的第二源状态。
4. **词表措辞须与工单寄主解耦**：§1.1 允许项目层工单不在代码托管平台（本仓已有 `Closes VAL-TEST-006` 非 `#n` 实践），此时无平台自动关闭；「合并默认分支自动关闭」的平台行为说明不应写进固定层条文，只宜留在 RELEASE.md 模板的括注里。
5. **选择空间漏了第四选项 C′**（只许关闭词入脚注、关联留在正文）：它同样满足 #8 诉求，应补记并给出弃用理由（废弃既成 `Refs` 实践、机器可解析位置不唯一），否则裁定记录的选择空间不完整。

## 修改建议

### 1. §5.1 条文（方案 A 修订版）

```
5.1 提交头：Conventional Commits 1.0.0，`type(scope)!: 描述`。
type 用 Angular 8 个（`build ci docs feat fix perf refactor test`）加 `chore` `revert`。
脚注票引只用两词：`Refs #n` 表关联（相关工作或阶段性进展，未满足关闭条件）；`Closes #n` 表关闭（本次提交满足关闭条件）。
其余平台关闭词（`Fixes`、`Resolves` 等）不用作脚注；正文叙述不受此限。
词表语义不随工单寄主变化，票号形态依项目层 issue-tracker 声明。
```

相比提案版本：白名单化、补禁用词族、删「检查器不做语义判定」句、删平台行为绑定、明确票号形态归属。

### 2. RELEASE.md:12（模板修订版）

```
脚注用 `Refs #n` 关联 issue（阶段性进展或相关工作，不触发关闭），
用 `Closes #n` 关闭 issue（满足关闭条件；GitHub/GitLab 等平台合并到默认分支时自动关闭）。
不用 `Fixes` 等其他关闭词作脚注；正文避免「关闭词 + 票号」紧邻组合以免意外关票。
```

### 3. 同步修订 §5.2

将「关联 bug 号」的落点与 §5.1 脚注分工写明（正文 = 叙述背景，脚注 = 票引），例如改为「关联 bug 号的叙述背景（票引用脚注词表）」，避免两处口径漂移。

### 4. 实施清单增补（并入提案 §10）

- DECISIONS.md 头部版本号 0.5.0 → 0.5.1（SemVer 澄清性 minor）；
- lazypack-setup 内置快照（`references/DECISIONS.md`）同步 + 来源内容标识重算；
- 全仓排查其余提及脚注词表的文件（presets/recipes/references 等），提案未列此步；
- 下游对齐说明：存量受管块以 `[UPGRADE]` 重编译对齐，重编译前如实标注分歧期。

### 5. 提案文档自身修订

- 更名「方案 A: 严格三分」→「方案 A: 两词二义（封闭词表）」，B 对应更名；
