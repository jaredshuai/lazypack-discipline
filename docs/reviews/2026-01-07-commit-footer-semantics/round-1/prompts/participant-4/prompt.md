# §9 讨论第一轮提示词：Commit 脚注词表语义（Issue #29）

> 用法：本提示词由主持人按固定层 §9.2 生成。维护者把它**原样贴给每位参与者各一份**（互不可见）。参与者不得阅读其他参与者的提交，不得查看本议题的 `docs/reviews/` 留档目录。

## 议题

固定层 `docs/DECISIONS.md` §5.1 脚注词表语义澄清：明确 `Refs`/`Closes`/`Fixes` 在 commit 消息中的语义边界。

**当前状态**：
- §5.1 只写「脚注 `Closes #n` 关联票」
- RELEASE.md 模板写「`Closes #n` 或 `Fixes #n`」
- 检查器把脚注当信息行，不做语义判定

**讨论输入**（来自 #8 裁定第四节）：
- 阶段性进展与完成关闭必须区分
- 拟议口径：`Refs` 表达关联，`Closes` 表达满足关闭条件后的关闭关联
- `Fixes` 是否作为关闭用语一并统一

## 第一轮任务：独立意见提交

### 1. 评审维度

请从以下角度评审提案：

**A. 方案合理性**
- 提案的 3 个方案是否覆盖了合理的选择空间？
- 推荐的方案 A 是否有充分理由？
- 是否有遗漏的方案或视角？

**B. 平台兼容性**
- 平台语义研究是否准确？
- 方案是否与 GitHub/GitLab 的自动关闭功能兼容？
- 是否有潜在的平台行为冲突？

**C. 实施可行性**
- 条文修改建议是否清晰可执行？
- 边界与例外处理（6 种场景）是否完整？
- 是否有实施难点或歧义？

**D. 与既有条文的关系**
- 与 §5（提交与版本规则）的其他部分是否一致？
- 是否影响其他条文（§4、§7 等）？
- 是否需要同步修改其他文档或模板？

**E. 迁移成本**
- 提案声称"零迁移成本"是否成立？
- 对现有 commits 是否有影响？
- 对下游项目是否有影响？
