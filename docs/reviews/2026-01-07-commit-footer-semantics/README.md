# §9 讨论：Commit 脚注词表语义（Issue #29）

## 议题

明确 `Refs`/`Closes`/`Fixes` 在 commit 消息中的语义边界。

## 背景材料

- **Issue**: #29
- **提案文档**: [docs/proposals/issue-29-commit-footer-semantics.md](../../proposals/issue-29-commit-footer-semantics.md)
- **当前条文**: DECISIONS.md §5.1（第 79 行）
- **模板文件**: skills/lazypack-setup/templates/RELEASE.md（第 12 行）

## 核心问题

当前固定层条文与模板存在不一致：
- §5.1 仅提及 `Closes #n` 关联票
- RELEASE.md 模板提及 `Closes #n` 或 `Fixes #n`
- 检查器把脚注当信息行，不做语义判定
- 本仓实际使用中已区分 `Refs`（关联）和 `Closes`（关闭），但未在条文中明确

**来自 #8 裁定的输入**：
- 阶段性进展与完成关闭必须区分
- 拟议口径：`Refs` 表达关联，`Closes` 表达满足关闭条件后的关闭关联
- `Fixes` 是否作为关闭用语一并统一

## 执行流程

### 第一轮：独立意见

1. 维护者用 5 个提示词分别调用 AI
2. 各参与者在临时目录输出 `opinion.md`
3. 维护者说"好了"触发主持人汇总
4. 主持人从临时目录读取并生成 `ROUND-1-SUMMARY.md`

### 第二轮：互评与收敛（如需要）

1. 主持人生成定制化提示词（包含第一轮汇总）
2. 参与者阅读他人意见并输出互评后的立场
3. 主持人汇总并评估收敛度

### 第三轮：修订投票（如需要）

1. 主持人提供修订后的方案
2. 参与者投票并给出理由
3. 主持人汇总最终投票分布

### 维护者裁决

1. 维护者对技术论证各自自洽的价值观分歧进行裁决
2. 主持人角色切换，执行维护者决策
3. 主持人搬运所有参与者输出到存档目录
4. 更新固定层条文和相关文档

## 提案方案概览

**方案 A（严格三分，推荐）**：
- `Refs #n`: 关联 issue（未完成）
- `Closes #n`: 关闭 issue（满足关闭条件）
- 禁用 `Fixes`，降低认知负担

**方案 B（宽松二分）**：
- `Refs #n`: 关联 issue（未完成）
- `Closes #n` 或 `Fixes #n`: 关闭 issue（两者等价）

**方案 C（平台对齐，不推荐）**：
- 不区分关联与关闭，统一使用平台关闭关键词
- 不满足 #8 裁定的核心诉求

## 关键评审维度

1. **方案合理性**：提案的 3 个方案是否覆盖合理选择空间？

3. **实施可行性**：条文修改建议是否清晰可执行？
4. **与既有条文的关系**：是否与 §5 的其他部分一致？
5. **迁移成本**：是否有迁移成本？对现有 commits 和下游项目的影响？
