## 1. 认可与反驳（主评 B）

**认可 B-07（及 B-06 的标记块方向）。** B §3：「`drift`：用户手改了块内 lazypack 生成的行 → **不覆盖**」。触发：用户改过 `RELEASE.md` 平台段或 AGENTS 托管块后再跑 setup。理由：现行 4.3「册上查不到的产物…先问维护者，不按文件名或日期猜」（DECISIONS L72）与访谈 Q2「不该没问完就写」。这是对已确认「不猜新旧」的**实现选择**，不是改 6.1/§5。代价：要能区分块内/块外，见 D02。

**反驳 B-11 的因果与条文改法。** B-11：「纯文档仓 / 无 `package.json` 的仓库装不了 Husky，按现条文 setup 必然失败或说谎」（B L115）。事实：6.1 写的是「提交前 hook」（DECISIONS L86），不是 Husky。无 `package.json` 推不出无法安装 Git hook：`.git/hooks/pre-commit` 是 shell（C-Q2 亦写此路径）；Python `pre-commit`、lefthook 等也不依赖 npm。B 把 `setup-pre-commit` 的 Husky 手法（本机 L1–12，**未验证**是否 Matt）当成 2.3 的唯一实现。触发：文档仓/非 Node 仓。若按 B-11 原文改 2.3，等于把「装不了 Husky」写成法定例外，日后 Node 仓也会拿它逃 6.1。代价：门禁从双关变成「写进 RELEASE 就算装完」。**需要的是完成声明（A-09-r2），不是改 6.1，也不是 B-11 那句限定。**

**B-06 版本戳单独不够。** B：「块头版本戳 == 当前版本且块内未被手改 → no-op」（L102）。「未被手改」不能从版本戳推出：戳只记编译源版本，用户改块内而 DECISIONS 仍 0.1.0 时会被标 `up-to-date` 并静默跳过，与 B-07 的 drift 自我矛盾。未验证推测：B 未给出第二基线（哈希/副本）。

**B §3 恢复示例与探测表打架。** 探测：「已存在即停并报告，不自选 v2」（L51）；同时又承诺 `upgrade` 重写块内（L103）。触发：合法重跑。前者是**本讨论留档**规则，主持人已声明不自动等同 setup 更新。示例回滚 `git checkout -- <这五个路径> && git restore AGENTS.md`（L72）：新建未跟踪文件 `checkout --` 删不掉；若块外已有用户改动，checkout 会误伤。脏仓即停（L106）不在固定层，首版当实现选择会把「工作区有无关修改」误判为失败。C 的「内存一次性写盘」同属 prompt-driven skill **无法兑现**的原子保证（Matt L15 已自陈非确定性脚本）。

**B-14：** skill 内快照作**编译输入**可接受（见 D01）；把快照写进目标仓或当第二事实源则与 1.4/`:6` 冲突。B 自己也写了与 `:6` 的张力（L159）。

对 C（需求忠实度，非偏好）：**C-01 不采纳为本议题固定层修订。** 访谈 Q11 已确认「少用 worktree…同一设备同一时刻只有一个执行者…跨设备靠 issue 认领人」（访谈 L37；DECISIONS L38）。C 指出 assignee 不是文件锁，作为**风险描述**成立，但短分支/`pull --rebase` 也不能保证排他写；「冲突时阻断退回」「自动回滚」未定义回滚范围。该条不阻塞 setup。**C-04 不采纳。** Q6「一定用；…不需验证」（访谈 L29）；1.2 是已确认硬边界。MCP 缺失是后续调查者会话的环境问题，不是 setup 编译器问题；setup 本身不应依赖那三个 MCP。降级等于撤销 Q6，须另开 §9，且与「只补 Matt 没管的」无关。

## 2. D01—D08

**D01 固定层分发 — 采纳 A-15 方向，用 B-14 的安装形态修订。** 可编辑源：公开仓 `docs/DECISIONS.md`。Skill 内可带该文件快照，**只作本机编译输入**，不写入目标仓。目标仓只有 2.3 派生物（指针块与项目层文件），不是第二事实源。块头可记 `compiled-from=DECISIONS@x.y.z`（实现选择）。跨设备：各机安装同一 skill 版本即有同一快照；断网可读快照。落后于上游时报告「可能落后」，不自动联网改仓。拒绝：目标仓再放一份 DECISIONS；C-02「运行期脚本指针」（无 CLI/脚本，且会造第三入口）。渠道未定不等于不能写契约：首版=用户已安装的 `lazypack-setup` skill 目录。

**D02 重跑 — 采纳 B-07 三态，修订检测方法。** `up-to-date`：托管区内容指纹与上次写入记录一致，且项目探测到的门禁命令未变。`upgrade`：指纹变（固定层版本变或探测命令变）→ 只预览块内/命令接线，块外与 `custom` 区保留。`drift`：指纹与记录不符且无法当纯升级解释 → 不覆盖，问保留/采用新版。无旧基线：无标记的已有 `CODING_STANDARDS.md` 等视为未托管，不猜、不覆盖（4.3），预览「跳过该文件 / 包一层标记」。标记缺损：当 drift。块外手改：不碰（Matt L82 先例，本机已核）。**不采纳** C「默认刷新标记内部」（会吞块内手改）。版本戳可作注释，**不能单独**当手改检测。

**D03 门禁完成 — 修订 A-09，否决 B-11 原文。** 四态：命令缺失=未接线；不适用（无代码/无 .git）=不适用，记原因；运行失败≠安装失败，setup 不代跑满套测试来宣称成功；安装失败=尝试写 hook 失败，如实报（7.6）。无 `package.json` ≠ 不能装 Git hook。setup **过程完成**≠门禁 **生效**：五份文档（或常驻文件一块+四文件）已按确认写入，且 hook 已接线或报告未接线/不适用。缺命令时不得虚构工具链，也不得在完成语里写「纪律已生效」（反 C 示例 L117）。6.4 仍要求角色自己跑门禁，作软兜底，不替代 6.1。

**D04 写入与恢复 — 不把留档禁覆盖套到 setup。** 合法重跑走 D02，不是「目标已存在即停」。脏仓：不强制停；只改本次清单路径。失败：停并列出已写/未写（7.6）；新文件可删回；已有文件给 diff，不擅自 `checkout` 用户旧改动。多文件原子写：**不能**由 prompt-driven skill 兑现（Matt L15），禁止写进验收。讨论成果「已存在不得覆盖」仅约束本 reviews 留档。

**D05 修订范围 — 本议题不改 3.3、1.2、§4。** C-01/C-04 延后。阻塞 setup 的只有：无 git、Matt 前置缺失、用户拒绝确认。跨设备、MCP、rebase 属后续开发流程。A-12 保留：§4 另审。B-12 不必改 1.3：Matt 已跑则会选好常驻文件（本机 L76–78）；未跑则 A-05 已停。

**D06 提问与前置 — 采纳 A-05/B-09 硬停，修订判定；提问上限是优化不是硬顶。** Matt 已配置：存在 `docs/agents/issue-tracker.md`（code-review L13 先例，本机已核）。仅有空文件或仅有 domain.md 不够。不代跑、不允许 C「已经或同时执行」（与 2.3「之后」及防重问冲突）。双存在：按 Matt L76–77 优先 CLAUDE，并报告双文件（1.3 风险），不平行写入。双缺失且无 tracker：停，不代选。查得到的不问（访谈 L19）；查不到必须问，3+1 不是硬上限。

**D07 首版 — 修订 B 阶段4、C 阶段4。** 场景：已有 git + 已跑 Matt 的 JS/TS 或 Python 仓，或无代码仓（hook=不适用）。平台段：探测到则薄草稿（手点/npm 一句），**不**要求微信/鸿蒙真实仓实测才能收口（DECISIONS L131 是未定项，不是首版门槛）。六项=2.3 清单，不是「必须六个物理路径都新建」：hook 可以是 husky 追加或 `.git/hooks/pre-commit` 或未接线记录。延后且不造成虚假完成：harvest、书记员/清道夫 skill、7.2 对子、完整上传剧本——完成报告须列出未接线/未测平台。C「无交互即可默认落地」与写前确认冲突，以确认一次为准（访谈 Q2）。

**D08 派工 — 讨论 vs 实现分权。** 讨论成果：唯一新路径，已存在则停。实现票：允许改目标仓已有文件的托管区，禁止改 DECISIONS/他人 reviews。每票绝对路径+禁写清单+角色验收再交下一角色。引用 Matt 必须路径+短引文；未验证不得当事实投票。
