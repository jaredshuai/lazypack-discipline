## 修正后条文

**位置**：§6.5 补充条款

### § 6.5 质量双轨（原有条文保持）

质量双轨：可测层（领域逻辑、数据推导）行为改动必须配套断言；迭代层（页面、组件）以语法/类型检查为底线，推导逻辑下沉到可测层。

**补充：单迭代上限**

一张票构成合格范围，当且仅当其关闭前能指出：
- 哪些行为断言由本票 diff 覆盖（可测层），或
- 哪些类型断言由本票 diff 覆盖（迭代层）

无法指出任一者时范围溢出，退回规划。

**门禁要求**：
关票时本票至少通过下列两组门禁之一：
- 可测层：行为断言（测试通过）
- 迭代层：构建 + 类型检查

**范围判定**：
大小范围不进本条，下沉项目层。本条只要求能对应到门禁断言，不限定故事点或代码行数。

## 与现有条文的关系

**补充关系**：
- 补充 §6.5 质量双轨的验收闭环：不仅要求分层，还要求能指出断言
- 补充 §3.1 规划者输出的隐含约束：票的范围要能对应到门禁断言

**不冲突**：
- §6.5 原有"可测层必须配套断言"仍然成立
- 本条补充"关票前必须能指出哪些断言"

**衔接 §6.1/§6.4**：
- §6.1 要求提交前 hook 跑门禁
- 本条要求关票前能指出本票覆盖的断言
- §6.4 审查者检查两边都跑了门禁

---

## 验收标准

**可判定部分**（P1 提取的内核）：
- 票须指向具体断言（测试名称、类型检查覆盖的文件）
- 且由本票 diff 覆盖（`git diff` 涉及对应测试文件或类型定义）

**人工审查部分**（§6.4）：
- 审查者检查：执行者能否指出哪些断言由本票覆盖
- 审查者检查：门禁是否通过（至少通过可测层或迭代层之一）

**不可判定部分**（下沉项目层）：
- 大小范围：一个票多大算合理
- 拆分粒度：什么时候该拆票

## 示例

### 示例 1：可测层，能指出断言
```
# 工单 #130
需求：实现日期格式化函数

提交 abc123：
- 新增 `utils/formatDate.ts`
- 新增 `utils/formatDate.test.ts`

关票检查：
- 能指出断言：`formatDate.test.ts` 中 3 个测试用例
- diff 覆盖：`git diff abc123` 包含测试文件
- 门禁通过：测试通过
- 结论：合格范围
```

### 示例 2：迭代层，能指出断言
```
# 工单 #131
需求：新增用户头像组件

提交 def456：
- 新增 `components/Avatar.tsx`
- 类型定义：`AvatarProps` 接口

关票检查：
- 能指出断言：TypeScript 类型检查覆盖 `Avatar.tsx`
- diff 覆盖：`git diff def456` 包含类型定义
- 门禁通过：构建 + 类型检查通过
- 结论：合格范围
```

### 示例 3：范围溢出，退回规划
```
# 工单 #132
需求：重构认证模块

提交 ghi789：
- 修改 20 个文件
- 未新增测试
- 未更新类型定义

关票检查：
- 无法指出断言：既无行为断言，也无新增类型断言
- 结论：范围溢出，退回规划

处理：
- 规划者拆分为多张票，每张票对应具体断言
```

### 示例 4：两组门禁都跑了（更严格，但合法）
```
# 工单 #133
需求：新增订单列表页

提交 jkl012：
- 新增 `pages/Orders.tsx`（迭代层）
- 新增 `services/orderService.ts`（可测层）
- 新增 `services/orderService.test.ts`

关票检查：
- 能指出断言（可测层）：`orderService.test.ts` 中 5 个测试用例
- 能指出断言（迭代层）：TypeScript 类型检查覆盖 `Orders.tsx`
- 门禁通过：测试 + 构建 + 类型检查全部通过
- 结论：合格范围（超出最低要求，更好）
```

## 与 #41 反前置规划的关系

**本条承载的部分**：
- 禁止范围溢出：票的范围必须能对应到门禁断言
- 防止"需求打磨到完美再交 AI"：要求可验证闭环，而非极致前置规划

**本条不承载的部分**（P5 诊断）：
- 澄清行为的度：什么时候该问、什么时候该开工
- 属 skill/指引层，不进固定层

---

## 与版本 2 的差异

**版本 2 的优势**（P4 论据）：
- 对称禁令直指行为："不得推迟开工"、"不得跳过澄清"
- 是唯一直接约束规划者行为的表述

**版本 2 的问题**（维护者裁定依据）：
- "推迟开工"的判据：什么算推迟？如何在版控中验证？
- "跳过澄清"的判据：什么算跳过？如何在版控中验证？
- 与 §6.6 "可判定优先"原则不符

**版本 1 的选择**：
- 只约束可判定的部分：能否指出断言
- 不约束不可判定的部分：开工时机、澄清程度
- 后者下沉项目层或 skill/指引层
