# §9 讨论：迭代开发与架构复盘 - 第一轮通用提示词

**讨论主题**：#41 反重前置规划 + 需求文档生命周期 与 #40 每轮迭代后的人工架构复盘

**讨论目的**：评估两个提案是否应纳入固定层条文，如何表述，以及与现有条文的边界划分。

---

## 背景材料

### 来源

两个提案均来自 Uncle Bob 访谈（2026-09-22），关于 AI 辅助开发中的实践经验：

1. **极致前置规划的问题**："计划写得越完美，agent 越固执照走，一有漏洞就卡住。"改代码成本趋近于零时，重规划是在拿贵的时间换便宜的时间。
2. **架构自动化的局限**："一个月前我还在人工做架构，AI 给的架构答案经常漏洞百出；架构规划全自动化暂时没有取得理想效果。"

### 提案 #41：反重前置规划 + 需求文档生命周期

**核心主张**：
1. **反重前置规划**：禁止"需求打磨到完美再交 AI"的工作模式
   - 条文形式建议：单迭代范围上限（一个迭代只做一个小需求）
2. **需求文档生命周期**："可运行系统 + 可通过的检测才是真需求"
   - 过程性需求稿用完即丢、不进版控

**关键张力**：与现有"文档跟改"条文的边界
- **用完即丢**：过程稿（需求草稿、AI 写的规划文档、讨论记录）
- **必须跟改**：登记册类文档（ARTIFACTS.md、DECISIONS.md、接口契约、架构决策）

两类文档混管会导致：过程稿进版控 → 文档腐烂；登记册不跟改 → 事实源漂移。

**提案方向**：给现有文档条文补一个"文档类型二分"定义。

### 提案 #40：每轮迭代后的人工架构复盘

**核心主张**：每轮迭代后必须有人工架构复盘，不许省略。

**具体形式**：
- 小步迭代（干一个故事/一个小需求）结束后，人复盘一次架构：模块拆分是否还合理、依赖有没有跑偏
- 配套工具降低复盘成本：架构可视化（UML 依赖图逐层下钻）+ dependency-cruiser 之类的依赖合规检查器，机器报违规、人做判断
- 复盘结论要落到产物（调整方案/拆分决策），不允许"看了一眼没问题"式复盘

**与现有条文的关系**：和"文档跟改"衔接，复盘产生的架构决策应触发对应文档更新。

## 现有固定层相关条文（0.6.0）

### §2 产物归属（部分相关）
- §2.1 `ARTIFACTS.md` 是产物状态与归属的唯一正文
- §2.2 项目层有自己的 ARTIFACTS 副本（从固定层编译）
- §2.3 新增架构性变更 → ARTIFACTS 登记，书记员 `/update-artifacts` 承接

### §4 文档跟改（核心相关）
- §4.1 事实变化 → 权威文档更新，一个事实只有一个家
- §4.2 执行者不得留 TODO 或"待补文档"
- §4.3 审查者检查执行者遗漏的文档同步
- §4.4 不在工单外的改动走 `/supplement-change`
- §4.5 事实/产物/权威文档登记在本仓 ARTIFACTS §3

### §7 产物完整性与接力
- §7.2 工单不是任务描述，是进度与决策凭据
- §7.5 审查者检查漏写 map、架构走歪、无人能找到的产物

## 你的任务

作为参与者 X，请从以下维度评估两个提案：

### 1. 问题真实性
- 两个提案描述的问题（极致前置规划、架构自动化局限）是否真实存在？
- 是否有其他解决路径？

### 2. 条文必要性
- 这些约束是否需要写入固定层？
- 是否可以通过现有条文（§2、§4、§7）+ 实践指引解决？

### 3. 边界划分
- **文档二分**："过程稿" vs "登记册" 的边界如何界定？
- **架构复盘**：复盘产生的决策属于哪一类文档？
- 与 §4 文档跟改的关系：是补充、修正还是冲突？

### 4. 可操作性
- 如何判断"单迭代范围上限"？
- 如何判断"必须有人工架构复盘"已执行？
- 复盘结论"要落到产物"的验收标准？

### 5. 条文表述建议
如果你认为应该纳入固定层，建议：
- 放在哪一节？（新增独立章节 vs 补充到现有章节）
- 如何表述？（给出具体条文草案）
- 如何与现有条文衔接？
