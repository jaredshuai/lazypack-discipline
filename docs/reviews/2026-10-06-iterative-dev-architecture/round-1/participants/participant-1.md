## 0. 前置勘误（会污染后续所有条文草案，请先处理）

## 1. 问题真实性

**两个问题都真实，但提案给出的解决方向与症状不完全对应。**

极致前置规划在 AI 会话里的可观察症状是：规格越长，agent 越把规格当**合同**而不是当**线索**——规格覆盖到的地方照走，覆盖不到的地方要么停下来要指令，要么自行补一个错误假设而不申报（后者正是 §7.6「不拼凑、不跳步」要防的）。所以问题成立。

但**本仓已经有解药**：§7.1 明写「主路是流程：规划者边问边写 CONTEXT / ADR」，§3.5 把规划者映射为 `grill-with-docs → to-spec → to-tickets`。"边问边写、写到能开票就停"已经是固定层认可的工作形态。因此 #41 第 1 点不是新洞见，而是对 §7.1 的换词复述——再加一条会直接撞 §1.4「每条纪律只活在一处」。

架构自动化的局限同样真实。除上面的勘误证据，0.6.0 其实已多处承认"机器接不住语义"：§6.5 质量双轨把 UI 层底线降到语法/类型检查、把推导逻辑下沉到可测层；§6.6② 直接把规则按可判定性分派给"工具"或"当轮执行者与审查者"。也就是说 **0.6.0 的认识论已经站在 #40 这一边，只是没有专指架构这件事**。#40 的独有价值因此不在"要有复盘"，而在"复盘的频率、产物与归属"——这三点现有条文确实没写。

其他解决路径存在：范围问题可以不动固定层，走 §2.4（项目层默认值头脑风暴，不必开 §9）加 `to-tickets` 的粒度实践即可收敛。

## 2. 条文必要性

**#41 第 1 点（单迭代范围上限）：不必要。**
理由不是"不重要"，是**无法验收**。若裁定它是强制条文，按 §6.6③ 必须先回答"违反是否阻止提交"；答案显然是不阻止，那就按 §6.6② 归入"需要理解含义、权衡"的一类，而 §6.3 又规定 CODING_STANDARDS 只放工具查不了的东西、§4.1 规定按需说明住 `docs/agents/<主题>.md`。三条串起来，唯一不违反现有口径的归宿是**指引文档**，不是条文。

**#41 第 2 点（文档二分）：必要，但需要的是"判据"而不是"二分"。**
真正缺的不是一个新定义，是两句话：什么算过程稿的**家**，以及谁有权把在册文档**降级**。§4.1 表已经给了两个先例——`.scratch/<feature>/`（票关闭且验证交付后经四步关卡回收）与「交接文档 → 系统临时目录，用完即弃」。缺的只是把判据说清，属最小加性改动。

**#40：一半必要。**
必要的那半：**架构性变更不得由执行者单方落地，须留可核对的裁定痕迹**。不必要的那半：**"每轮必须有人工复盘"**——它无法被证明发生过（见维度 4）。

现有条文能否覆盖？§3.4 书记员扫文档、§7.2 对子、§7.4 ADR 三条、§6.4 对抗性双跑构成一张网，但网里**没有一个环节负责"模块拆分是否还合理、依赖有没有跑偏"这个判断本身**：§3.1 规划者的输出包含 ADR，但触发条件是"客户改主意"（§7.3）与难逆转决定（§7.4），不是"每轮迭代后"；§3.4 书记员只补全局文档视角，明确不碰代码。所以 §3.1 与 §3.4 之间确实有一个空位。这是 #40 必要性最强的论证，我认可。

## 3. 边界划分

**0.6.0 的 §4.1 表不是二分，是四分**，照搬"过程稿 / 登记册"会分错三类东西：

| 型 | 表中实例 | 「何时清」 |
|---|---|---|
| 跟改型（权威） | `CONTEXT.md`、`docs/adr/`、`HISTORY.md`、`CODING_STANDARDS.md`、`RELEASE.md`、`docs/agents/` | 词过时即改 / 不删只标「已取代」 |
| 冻结型 | 研究笔记 `docs/research/` | 结论进 ADR 或 CONTEXT 后**冻结** |
| 归档型 | 设计稿 `docs/reference/` | 废弃 → `git mv` 至 `docs/archive/`，登记行同步 |
| 用完即弃 / 留证型 | `.scratch/`、交接文档、`prototype/<名>` 分支 | 四步关卡回收 / 用完即弃 / 留证不合回 |

若强行二分：「冻结」与「归档」会被塞进"用完即丢"桶，直接撞 §3.4③「严禁仅凭文件名或目录名推定，严禁将 specs、issues、out-of-scope 记录视为临时缓存」和 §4.2「工单关闭仅改变其闭环状态，不等于删除授权」。

**一处硬冲突，必须裁定**：#41 把"讨论记录"列为过程稿、用完即丢；而 §9.5 要求「每人每轮原文 + 投票结果 + 裁决」全程留档进 `docs/reviews/<日期>-<议题>/`。§9.6 又规定章程本身属固定层。二者不能同真。建议把 #41 的表述**收窄**为"AI 会话内的一次性需求稿与规划稿"，把 §9 留档明确排除在外。

**可执行的判据（不看名字，看两问）**：
1. 它在 `ARTIFACTS.md` 有登记行吗？（§4.3：册上查不到即视为未登记）
2. 它与代码不一致时，会不会误导读者做错误决定？

| 边界案例 | ①在册 | ②会误导 | 归属 |
|---|---|---|---|
| 会议记录 / §9 讨论原文 | 是（§9.5） | 否 | 留证型，不跟改、不删 |
| 技术调研 | 是 | 是（未冻结前） | 冻结型 |
| ADR 草稿 | 否 | 是（若已进 `docs/adr/`） | 未满足 §7.4 三条前**不得**用 ADR 名义进 `docs/adr/`——§4.2 `current` 同类唯一，草稿与正本并列会造成双源 |
| AI 生成的规划稿 / 需求稿 | 否 | 否 | 过程稿，家 = `.scratch/`，经 §3.4 关卡回收 |
| 接口契约 / 架构决策 | 是 | 是 | 跟改型 |

**复盘产生的决策属于哪一类**：满足 §7.4 三条 → ADR（跟改型，被取代时改「已取代」并互指）；不满足 → 它不是文档，是**一张票或工单评论**，属"工作与进度"区域。这里我强烈建议固定层明文禁止"每次复盘产出一份复盘报告 md"——那是文档腐烂的最大来源，见维度 4。

**与 §4 的关系**：补判据（补充），不修正也不冲突；与 §9.5 是真冲突（须裁）。另注意 `DECISIONS.md` 未定项里已经挂着「§4 表与 6.2 工具组合待多 AI 讨论复审」，本轮若要动 §4.1 表与工具名单，建议与该未定项**同票处理**，避免同一张表两次改判。

## 4. 可操作性

**「单迭代范围上限」怎么量化——四个候选，全不可靠**：

| 口径 | 可机检性 | 钻空子路径 |
|---|---|---|
| diff 行数 ≤ N | 可（`git diff --stat`） | AI 生成的样板与测试把行数虚报；反向也错：改 15 行可能是最难的地基变动 |
| 时间盒 ≤ 1 天 | 不可（会话时长不由人控） | 无人能验证，退化为自报 |
| 验收标准 ≤ 3 条 | 半可（要数自然语言） | 把三条写得含糊即可 |
| 一张票 = 一个 feature 切片 | 不可 | **正是"伪小需求"的路** |

关于"把大需求拆成伪小需求"：**设置上限不但防不了规避，反而制造规避动机**。因为唯一能观察到的规避信号是 tracker 上的互锁结构（一个 epic 下多张票互相 `blocked-by`、共享同一句验收标准、且由同一会话批量产出），而这类信号只能"检测"、不该"阻断"，阈值必然属项目层（§2.2）。结论：这一条给不出诚实的验收标准。

**「人工架构复盘已执行」如何证明——诚实答案：证明不了。**
任何"存在一份复盘产物"的证据，都能被"生成一份复盘产物"满足，而后者恰好是 §4.1「能推出来的不手写」和 §5.5「CHANGELOG 不充当完整验收台账」想防的方向。强制长文档 = 每次迭代多一个文件，半年就是一堆没人再读的 md。

版控层面能真正验收的只有两件事：
1. **留痕存在性**：票关闭时，存在当轮架构判断的三态记录之一 —— ①「无发现」二值声明（提交 trailer 或工单评论）；②新增/取代一条 ADR；③派生出后续票。三者的**存在性**都可用路径、退出码或 tracker 状态判定（§6.6② 的确定性工具那一支）。
2. **变更授权**：diff 触及模块边界（新增/删除顶层目录、跨模块依赖方向变化）时，存在维护者裁定记录。可判定的那一句进工具，"是否算架构性变更"的语义那一句给审查者——按 §6.6② 分流，不整条判给一层。

所以条文应写 ①②，**而不是写"必须复盘"**。前者能查，后者只能信。

**「复盘结论落到产物」的验收标准**：三态之一即可，且必须写明"①无发现"是合法稳态、不是偷懒。否则条文会训练大家造文档来过关。

**工具支持的现实性**：`dependency-cruiser` 只覆盖 JS/TS；Python 要 `import-linter`，ArkTS/Java/Go 各不同；本仓 §10.1 声明公开内容是「条文、去敏访谈整理稿、skills、reviews」——主体是 markdown，根本没有依赖图可跑。固定层若点名工具，与 §6.2（默认工具之外由 `/lazypack-setup` 问）和 §2.2（工具属项目层）双重冲突。还有一个更隐蔽的坑：**把"哪些模块允许依赖哪些"写进 dependency-cruiser 配置，就是把口径抄进配置，违反 §6.6①**（§4.1 表「工具门禁配置与接线」行已明写「配置不另抄判定口径」）。所以口径必须住在项目层架构文档或 ADR，工具只做执行。

**没有工具时如何执行**：§6.6④ 已给出合法稳态——未接线时保持手动运行，且不得宣称门禁已生效（§2.3）。手动执行路径也已存在：§1.2 指定 `/understand-codebase` 是**唯一**代码理解入口，依赖 codegraph / codebase-memory / fast-context 三个 MCP。建议 #40 的"配套工具"直接绑这三个已授权的入口，而不是引入新的依赖面（§1.3 不平行复述、§1.1 不侵入）。

## 5. 条文表述建议

**位置建议：不新增独立章节**（§1.4 每条纪律只活在一处；§3/§4/§7 已覆盖主题）。以下为最小补丁草案，每条附验收方式，供维护者裁定：

**A. §4.1 表「临时现场与运行时缓存」行，只扩写"东西"列**（不新增行，避免与 `.scratch/` 形成双家）：
> 临时现场与运行时缓存、过程性需求稿与 AI 规划稿（仅服务本次生成，不含 §9 讨论留档）| `.scratch/<feature>/` | 票关闭且验证交付后，经四步清理关卡安全回收

验收：路径规则可判；"是否仅服务本次生成"由清道夫按 §3.4③④ 判，争议件原地保留请裁定。

**B. §4.2 末补一句降级约束**：
> 在册（§4.3）者须跟改；`current` / `reference` 状态不得由规划者或执行者自行改判为过程稿，降级或移出登记须有维护者裁定记录。

验收：状态词与登记行是机读的；"改判"表现为一次 ARTIFACTS 行变更，可与工单裁定记录做存在性配对（§7.2 类对子）。这条同时堵住"把权威文档自称草稿以逃避跟改"的口子。

**C. §3.1 角色表补架构判断归属**（规划者行「输出」加"每票关闭后的架构判断留痕"；书记员行「输入」加该留痕）：
> 规划者（由人执行）在每张票关闭后判定一次模块拆分与依赖方向，输出为「无发现声明 / ADR / 后续票」三态之一；书记员在既有扫描中核对该留痕是否存在。

验收：事件锚点复用 §3.4「书记员在每张票关闭后扫一遍」与"事件驱动，不用定时器"，不新增触发器；写入位置属 issue 评论或提交 trailer，与 §3.2 防撞车边界不冲突。

**D. 新增 §7.7**：
> 架构性变更（新增或删除顶层模块、跨模块依赖方向改变、拆分方案调整）不得由执行者单方落地，须存在维护者裁定记录。可判定部分接入确定性工具，语义部分由审查者判；未接线时保持手动运行并按 §2.3 如实报告，不得宣称门禁已生效。

验收：机检句 = diff 触及的路径集合；语义句 = 审查者。§6.6③ 要求：若裁定"违反须阻止合并"，则工具化是强制前提，须另开实施票（§6.6④）。

**E. 需要一并裁定的衔接点**：留痕若用提交 trailer（如 `Architecture-Review:`），它与 §5.1 的关系要写明——§5.1 只规范 `Refs` / `Closes` 的 issue 关联语义并封闭了平台保留词白名单，trailer 是**另一类字段**还是并入词表，须裁定，否则两条新文互指会留下口径裂缝。

**F. #41 第 1 点的归宿**：写 `docs/agents/iteration-scope.md` 指引（§4.1「给 agent 的按需说明」行，被闸门或工具替代后删），口径只留一句：
> 规格写到能开出一张可验收的票即停，不追求完备；完备性风险由 §6.4 对抗性审查与票关闭后的架构判断承担。

版本影响：A–D 与 F 均为加性，按 §5.4 建议走 minor；但若 D 的"违反须阻止合并"被采纳而工具未接线，会形成 §6.6③ 的已知违规面，宜另开实施票而非与条文同批。SemVer 最终升位请 P2 与维护者定。

## 总体建议

| 议题 | 我的建议 |
|---|---|
| #41-1 反重前置规划 / 单迭代范围上限 | **不纳入固定层**，降为 `docs/agents/` 指引（F）；它与 §7.1 重叠，且无可验收标准 |

| #40 每轮人工架构复盘 | **改造后纳入**（C、D）：条文写"留痕存在 + 变更授权"，不写"必须复盘"；工具名单留在项目层，口径不抄进配置 |

**纳入的两项前置条件**（不满足则上面所有机检句都会失效）：
1. 背景材料勘误——用 0.6.0 正文重新锚定条号。
2. **ARTIFACTS 登记粒度必须先裁**（逐文件一行 vs 目录级一行）。若采逐文件，`docs/reviews/**` 这类目录会把反向引用检查淹没在误报里；若采目录级，A/B 的机检才成立。这是 B 与 D 能否落地的关键分叉，建议第二轮优先收敛。

我在此不提供最终裁定，仅提交实用主义视角的评估供主持人与维护者参考。
