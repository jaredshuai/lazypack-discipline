# 第一轮独立意见：参与者 5（批判性思维者）— 迭代开发与架构复盘

> 参与者 5，2026-10-08

> 依据 `round-1/prompts/participant-5/prompt.md` 与 `common.md` 独立完成；未读取任何其他参与者输出（`round-1/participants/` 尚为空）。材料边界：Uncle Bob 2026-09-22 访谈整理稿不在公开仓（`docs/interviews/` 仅有一篇 2026-09-04  founding 访谈），其引语按 issue #40/#41 原文转述采信，标「转述」，不作论证支点。推理过程与引文见同目录 `evidence.md`。

## 0. 总体立场

**两个提案的问题都真实，但按现表述均不应整条纳入固定层。** #41 的文档二分判据值得吸收为 §4.1 补丁；"禁止重前置规划 / 单迭代上限"与 #40 的"每轮必复盘"两个核心强制项都不可判定，且互相矛盾。详细建议见末节。

---

## 1. 问题真实性：问题存在，但诊断可能错位

**"极致前置规划"的病根未必是"计划太细"。** 转述的病灶是"agent 固执照走，一有漏洞就卡住"——但详实且正确的规格不会造成卡顿，**错而权威的计划才会**。反例：算法实现、协议对接、bug 修复这类任务，越精确的规格越好，无人主张"需求别写清楚"。真正需要的行为是"agent 遇到规格漏洞时上报而非硬走"——这恰恰是既有 §7.6（工具调用未达预期如实报告、不拼凑不跳步）的管辖域。若病灶是"agent 不报告"，对症药是强化 §7.6 的执行，不是禁止把需求写细。

**"AI 架构答案漏洞百出"是能力陈述，不是流程陈述。** 它描述 2026-09 时点的模型能力上限，把它写成永久条文等于把暂时性能力边界固化成纪律。模型能力若改善，条文沦为被习惯性忽略的死条文——按本仓上一轮讨论的教训（issue #36，提示词里的规则会被降级为"海盗法典"），无执行力的条文会腐蚀整个纪律体系的信用。

**证据基数为 n=1。** 两条提案出自同一次访谈。本仓登记册与 VISION 记载的实测痛点是文档腐烂、报告诚实性、门禁有效性——没有一条是"过度规划"。§8 harvest 机制的存在就是为了跨项目攒够证据再立法；单次访谈直接升格固定层，绕过了这套机制的设计意图。

## 2. 条文必要性：可执行内核已被覆盖，净增量恰是最弱部分

**#41 的"单迭代范围上限"不可判定。** "一个小需求"没有度量单位：改一行文案和一次数据迁移都可以是一张票。按 §6.6②，无法机械判定的规则归当轮执行者与审查者——但审查者同样需要判定口径，"小"不是口径。一条双方都无从核查的禁止性条文不满足固定层的收录门槛。

**#40 的可执行内核早已存在。** 依赖跑偏 → dependency-cruiser 类工具判定，§7.2/§6.6 已给出载体路由；架构决策落文档 → §2.3 登记 + §4 跟改已覆盖。净增量只剩"每轮必做"这一仪式性强制——恰恰是整条里最弱的部分。

**文档二分有真实增量，且与 §4.1 正面冲突。** 现有表把"需求、工单与规格"的家定在版控内（`docs/work/`），#41 却主张过程性需求稿不进版控——这不是纯补充，是对既有行的修正，必须正面处理而非并排放置。

**两提案互相拧着。** #41 的底层逻辑是"机器和迭代更便宜的地方，不花贵的人工时间"；同一把尺量 #40 自己，结论应是"信号触发复盘"而非"每轮强制"。#40 自己的配套句"机器报违规、人做判断"已含解药——无违规时仍强制复盘，就是对 #41 原则的自我违反。一组以"减重"为名的提案，落地了一个不问信号的固定仪式。

## 3. 边界划分：给一个可用判据，并指出真冲突点

**过程稿 vs 登记册的判据建议**：一份文档若携带下游消费者依赖的事实或决策 → 登记册类，须跟改；仅表达某时点意图、无下游消费者 → 过程稿，不进版控、用完即弃。此判据与 §4.1"能推出来的不手写；有生命周期的写清何时死"同构，应作 §4.1 的判据补丁，不开新章。

**复盘结论的分类**：复盘改变架构 → 触发 ADR/登记册更新，走既有 §4/§2.3 路径；结论是"无需调整" → 凭据住工单（§7.2"工单是进度与决策凭据"），不产生新文档。若条文要求每次复盘都产出新文档，激励是歪的——为交差批量制造"发现"，产出的噪声 ADR 正是 #41 另一半要防的文档腐烂。

**必须裁决的真冲突**：§4.1"需求、工单与规格 → `docs/work/`"行 vs #41"需求稿不进版控"。推荐解法：二分判据把规格类留在版控（它有下游消费者：执行者、审查者），过程草稿（讨论记录、AI 规划稿）明确为不进版控。

## 4. 可操作性：强制项不可验证，验证手段是循环的

**"必须有人工复盘"无法验收。** 提案自己禁止"看了一眼没问题"式复盘，但唯一非循环的验证手段是下游产物（架构决策是否触发了文档更新）——而那已是 §2.3/§4 的要求，不需要新条文。在工单上勾"已复盘"恰好就是提案禁止的形式主义；想验证复盘质量只能重做一遍复盘。

**"落到产物"的验收标准诱导造假。** 若"无产物 = 未复盘"，理性执行者会次次写出点什么，产物的在场不再证明复盘的质量。

**"单迭代上限"无判定单位**，见第 2 节。

**可操作的形态是信号触发，不是日历强制。** 依赖违规数、公共接口变更面、模块间新增边、圈复杂度突增——这些可机械检测，属 §6.6② 工具层；人在信号出现后做判断。把"每轮"换成触发条件枚举，#40 才有落地形态；dependency-cruiser 接线按 §6.6④ 属项目层授权事项。

## 5. 条文表述建议：拆解吸收，而非整条纳入

**建议纳入**（#41 的文档二分部分），作 §4.1 判据补丁，草案：

> §4.1 表下新增一段："文档分两类：携带下游消费者依赖的事实或决策者属登记册类，须按本节跟改；仅表达某时点意图、无下游消费者的过程稿不进版控、用完即弃，不占本表的家。"

**建议不纳入**：单迭代范围上限（不可判定）；"每轮必复盘"（仪式化、无法验收、与 #41 自相矛盾）。

**替代路径**（非条文化）：反过度规划落规划者 skill 层——`grill-with-docs → to-spec → to-tickets` 的澄清上限是 skill 行为，按 §2.4 属项目层可调项，不必开 §9；架构复盘落 `docs/agents/architecture-review.md` 按需说明 + dependency-cruiser 项目层可选接线。

**若维护者坚持入固定层的必要条件**：把"每轮"改为触发条件枚举；明确复盘凭据的家是工单而非新文档类；给条文加能力前提复核触发（"AI 暂接不住"立论的条文应带日落/复审条件，否则能力进步后无人记得拆）。

## 总体建议：需要更多信息 + 大幅修订后再议

- **#41**：文档二分方向正确，值得吸收为 §4.1 补丁；"禁止重前置规划"部分证据不足（n=1 访谈）、诊断可能错位（§7.6 已对症）、不可判定——建议降级为项目层指引或 skill 行为调整。
- **#40**：问题真实存在——体系里确实没有角色定期看整体架构（审查者看 diff、书记员看文档，漂移是跨提交累积的）；但"每轮强制"形态不可验收且与 #41 矛盾。建议改为"信号触发复盘"的项目层默认 + 可选工具接线，暂不升格固定层。
- **需要更多信息**：①过度规划在本仓或目标项目造成实际损失的案例；②"小需求"是否存在任何可判代理指标；③复盘触发信号清单的实证基础。
