## P0 裁定结果（已由维护者确认）

### P0-1：§4.1"需求/规格"与"过程稿不进版控"冲突

**裁定**：按下游消费者判定 + 防断链约束
- 有下游消费者（执行者、审查者依赖验收）→ 登记册，进版控
- 无下游消费者（AI 会话内探索）→ 过程稿，用完即丢
- 丢弃前，生效决策必须沉淀至 ADR、工单或登记册

### P0-2：§9 讨论留档与"讨论记录用完即丢"冲突

**裁定**：§9 留档不属于过程性记录，#41 表述应明确排除
- §9 留档是固定层演化凭据，属"决策归档型"
- 修正表述："过程性需求稿、AI 会话内的规划稿（不含 §9 讨论留档、不含 §4.3 在册文档）用完即丢"

## 背景材料

### 来源

两个提案均来自 Uncle Bob 访谈（2026-09-22），关于 AI 辅助开发中的实践经验：

1. **极致前置规划的问题**："计划写得越完美，agent 越固执照走，一有漏洞就卡住。"
2. **架构自动化的局限**："AI 给的架构答案经常漏洞百出；架构规划全自动化暂时没有取得理想效果。"

### 提案 #41：反重前置规划 + 需求文档生命周期

**核心主张**：
1. **反重前置规划**：禁止"需求打磨到完美再交 AI"
2. **需求文档生命周期**："可运行系统 + 可通过的检测才是真需求"
   - 过程性需求稿用完即丢、不进版控（已按 P0-1/P0-2 裁定澄清边界）

**关键张力**：与现有 §4.1、§7 条文的边界

### 提案 #40：每轮迭代后的人工架构复盘

**核心主张**：每轮迭代后必须有人工架构复盘，不许省略。

**具体形式**：
- 小步迭代结束后，人复盘一次架构
- 配套工具降低成本：架构可视化 + 依赖合规检查
- 复盘结论要落到产物

## 现有固定层相关条文（0.6.0，已核对）

### §2 两层结构与编译（部分相关）
- §2.1 固定层：本文件全部条文
- §2.2 项目层：平台打包、工具、验证命令
- §2.3 编译器 `/lazypack-setup`：问项目层问题，写出 AGENTS.md 等六个文件
- §2.4 项目层默认值可由多 AI 头脑风暴扩展

### §3 角色（部分相关）
- §3.1 角色是固定层
- **角色表**：规划者、调查者、执行者、审查者、书记员、清道夫
- §3.2 "允许写"列是防撞车边界
- §3.4 书记员在每张票关闭后扫一遍；清道夫在发版前或按需扫一遍

### §4 什么放哪（核心相关）
- §4.1 原则：一个东西只有一个家；能推出来的不手写；有生命周期的写清何时死
- **§4.1 表重点行**：
  - 需求、工单与规格 → `docs/work/<feature>/`，按保留目的与有效引用判断
  - 临时现场与运行时缓存 → `.scratch/<feature>/`，票关闭且验证交付后回收
  - 难逆转的决定 → `docs/adr/NNN-*.md`
  - 交接文档 → 系统临时目录，用完即弃
- §4.2 产物登记册状态词：current / reference / exploration / superseded / pipeline / wip
- §4.3 册上查不到的产物视为未登记

### §6 质量门禁（部分相关）
- §6.1 提交前 hook 跑：格式 + lint + 类型 + 测试
- §6.3 `CODING_STANDARDS.md` 由审查者执行
- §6.4 执行者和审查者都必须跑门禁
- §6.5 质量双轨：可测层配套断言；迭代层语法/类型检查为底线
- §6.6 载体三轴分离：口径住条文，执行优先工具，接线另需授权

### §7 文档跟着改（核心相关）
- §7.1 主路是流程：规划者边问边写；执行者提交时同步；书记员关票后补
- §7.2 机器只拦能判断的几条（"改了 X 却没动 Y"），具体对子由项目层定义
- §7.3 客户改主意：新决议进 ADR 并写明取代哪条
- §7.4 ADR 只在三条全中时写：难逆转、没上下文会奇怪、真有取舍
- §7.5 交接只写本会话亲自验证过的事实
- §7.6 工具调用未达预期时如实报告

## 第二轮任务

### 背景：第一轮共识与分歧

**高度共识（4/5 或 5/5）**：

**核心分歧**：

- 复盘落点：§6 质量门禁 vs §7 文档跟改

### 你的任务

作为参与者 X，请评估**三个可合并草案**：

**条文草案**：

> **§4.1 表"临时现场与运行时缓存"行修订**：
> 
> 临时现场与运行时缓存、**过程性需求稿与 AI 规划稿（仅服务本次生成，不含 §9 讨论留档）** → `.scratch/<feature>/` → 票关闭且验证交付后，经四步清理关卡安全回收

> **§4.1 表下新增判据段落**：
> 
> 文档按是否承载下游依赖的事实/决策分型：承载者属登记册，须按 §7 跟改；过程稿（探索草稿、推导记录、临时交接）在结论沉淀后即弃（**沉淀前不得丢弃，防断链**），不占本表的家。在册（§4.3）文档降级或移出登记须有维护者裁定记录。

4. 是否有遗漏的边界情况？

#### 草案 B：§7 新增跨票据结构复盘（4/5 共识触发式）

**提案位置**：§7 新增 7.7

**条文草案**：

> **§7.7 跨票据结构复盘**
> 
> 一批票以 `Closes` 收束后（或发版前），规划者或书记员判定模块拆分与依赖方向是否偏移。三态之一：① 无偏移：合法结果，不产出文档，**不得补写"已复盘"记录**；② 有偏移：决定按 §4.1 回家（难逆转进 ADR，状态进登记册）；③ **禁止以书面记录充当复盘**。
> 
> 可判定形态：「本批改变模块边界或依赖方向，却无对应文档/ADR 变动」（§7.2 对子，由项目层定义）。未接线时保持手动运行（§6.6④），不得宣称门禁已生效。

**分歧保留**：落点是 §7（文档跟改）还是 §6（质量门禁）？

**你的评估**：
1. "一批票收束后"如何判定？是否清晰？
2. 三态是否可验收？如何防止形式主义？
3. 落点 §7 vs §6，哪个更合理？
4. "禁止以书面记录充当复盘"是否可判定？
