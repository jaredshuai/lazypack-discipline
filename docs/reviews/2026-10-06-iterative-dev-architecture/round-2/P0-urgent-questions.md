> 主持人整理，2026-10-08

## Q1：ARTIFACTS 登记粒度（阻塞草案 A/B 机检句）

### 问题来源
- P1（参与者 1）在草案 A 评估中警告
- P2（参与者 2）在草案 A/B 评估中独立发现

### 问题描述

**P1 原文**：
> 三案共同前提 **ARTIFACTS 登记粒度**未裁，P0 未覆盖；采逐文件会令 `docs/reviews/**` 淹没反向引用，三案机检句同时失效。

**P2 原文**：
> A 与 B 的机检句均依赖登记册的登记粒度（逐文件一行 vs 目录级一行）。该粒度未裁之前，两条草案里的可判定句都无法接线。

### 具体影响

#### 草案 A：§4.1 文档二分判据
- P1 修复建议："有没有 §4.3 在册项、工单验收标准或提交 trailer 指向了这个路径"
- 依赖：需要能判断"某个路径是否在 ARTIFACTS.md 登记"

#### 草案 B：§7.7 跨票据结构复盘
- ② 态要求："文档/ADR 有变动、处置票存在、新 ARTIFACTS 行现身，三者有一即过"
- 依赖：需要能判断"某次变更是否触及 ARTIFACTS 登记行"

### 为什么现在才发现

**现有 §4 条文未明确粒度**：
- §4.1 表给出了逻辑类别（词汇表、ADR、设计稿……）
- §4.2 定义了状态词（current/reference/exploration/superseded/pipeline/wip）
- §4.3 说"册上查不到的产物视为未登记"
- 但没有说一个目录算一条登记还是目录下每个文件各算一条

**P0 裁定时未覆盖**：
- P0 裁定了"文档分类冲突"（登记册 vs 过程稿的边界）
- 但没有裁定登记册内部的粒度（一行对应什么）

### 两个选项

#### 选项 A：逐文件一行
- **优点**：精确，机检句可以用 `git diff ARTIFACTS.md` 判断
- **缺点**：`docs/reviews/2026-10-06-**/` 这种讨论目录会产生大量登记行，淹没核心产物

#### 选项 B：目录级一行
- **优点**：登记册简洁，核心产物清晰
- **缺点**：机检句需要改为"路径前缀匹配"，复杂度上升

### 建议

**我的立场**：选项 B（目录级），理由：

1. **与 §4.2 状态词语义一致**：`current` 在同一类里唯一，指的是"当前的架构决策记录目录"而非"当前的某个 ADR 文件"
2. **符合 §4.4 的"非标路径登记"场景**：存量项目登记的是 `docs/specifications/` 而非其中每个 spec
3. **机检句可行性**：草案 A/B 的判据可以改为"git diff 涉及的路径是否在某个登记路径下"
4. **P1 警告的 `docs/reviews/**` 场景**：讨论目录作为 `exploration` 状态登记一行，不逐文件

**需要的配套修改**：
- 草案 A 判据："有没有 §4.3 在册项、工单验收标准或提交 trailer 指向了这个路径**或其父路径**"
- 草案 B 对子："文档/ADR 有变动（**含登记路径下的文件**）、处置票存在、新 ARTIFACTS 行现身，三者有一即过"

### 裁定请求

请维护者裁定：
- [ ] 选项 A：逐文件一行
- [ ] 选项 B：目录级一行
- [ ] 其他（请说明）

**优先级**：阻塞 0.7.0，必须在草案 A/B 修改前裁定

## Q2：§3.1 / §7 是否已要求票带非空验收标准（影响草案 C）

### 问题来源
- P1（参与者 1）在草案 C 评估中要求主持人核对

### 问题描述

**P1 原文**：
> 现有 §3.1 / §7 是否已要求票带非空验收标准；若已覆盖，①② 并入既有条文即可，不必新增（§1.4）。

### 现有条文检查

#### §3.1 规划者职责
> 输入：用户意图 + 调查者报告
> 输出：规格、票、ADR / CONTEXT 更新

- **未明确要求**票必须带验收标准

#### §7.2 文档跟改机检对子
> 机器只拦能判断的几条（「改了 X 却没动 Y」），具体对子由项目层定义。

- **未明确要求**票必须带验收标准

#### §7.5 交接诚实
> 交接只写本会话亲自验证过的事实；未验证标「未验证」。引用文件用路径，不复制正文。

- 要求诚实，但**未要求**票必须带验收标准

### 草案 C 的相关内容

**版本 1（①）**：
> 一张票构成合格范围，当且仅当其关闭前能指出：哪些行为断言由本票 diff 覆盖、哪些类型断言由本票 diff 覆盖。无法指出任一者时范围即溢出。

**版本 1（②）**：
> 关票时本票至少通过下列两组门禁之一：`§6.5 可测层`或`§6.5 迭代层`的构建+类型检查。大小范围不进本条，下沉项目层。

### 核查结果

**现有条文未覆盖草案 C 的约束**：
- 现有条文未要求票必须带验收标准
- 现有条文未要求验收标准必须能对应到门禁断言
- 草案 C 的约束是新增的

### 裁定请求

**确认**：草案 C（如果采纳）是新增约束，不与现有条文重复。

**无需裁定动作**，仅确认核查结果。
