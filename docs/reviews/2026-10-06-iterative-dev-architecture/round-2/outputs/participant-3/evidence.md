# 参与者 3 第二轮支撑论据：质量工程视角下的条文分析

> 参与者 3 - 质量工程师，第二轮论据清单，2026-10-08

## 1. 关于草案 A "防断链"检查点的证据链

### 1.1 缺陷模式分析：过早丢弃过程稿导致的"黑盒缺陷"
在敏捷与 AI 驱动开发中，开发人员或 Agent 经常在 scratch 目录或会话草稿中进行架构选型、边界条件试错和异常处理推导。若仅规定“过程稿用完即弃”，在缺乏前置把关时，常见以下质量缺陷：
- **场景 A**：Agent 发现了某个第三方库并发读写的边界竞态问题，并在草稿中推导了采用特定互斥锁的方案。但交付时仅提交了锁代码，草稿直接被清理，工单与 ADR 均无记录。三个月后，后续维护者因重构移除该锁，引发严重的偶发并发 Bug。
- **场景 B**：Agent 在推导业务规则时，针对异常输入做了静默降级处理，未形成测试用例，也未在工单中注明。QA 测试时无法判定此静默降级是“预期行为”还是“错误遮蔽”。

### 1.2 责任主体分析：为什么必须由审查者（§6.4）而非清道夫（§3.4）把关？
- **清道夫（Scavenger）定位**：清道夫的职能是“扫一遍垃圾、安全回收运行时缓存与临时现场”。清道夫执行的是基于文件系统路径与生命周期规则的机械操作，不具备深入代码 AST 与业务逻辑理解的能力，无法判断某个删除的 markdown 是否包含未沉淀的架构决策。
- **审查者（Reviewer）定位**：§3.1 和 §6.4 规定审查者必须运行门禁并核对实现是否符合规范。审查者处于提交前的关卡，能够对比工单需求、代码实现与探索现场。将“防断链”设为审查者的放行条件，才能在代码合入前阻断缺陷。

## 2. 关于草案 B 结构复盘与形式主义的论据

### 2.1 警报疲劳与 Rubber-stamping 的实证风险
在持续集成与质量工程中，过多的无差异检查点会导致审查者“注意力衰竭（Alert Fatigue）”。
- 若每一轮极小迭代（如仅修改一个样式常量或补全注释）都要求产出“架构复盘记录”，开发者与 Agent 会演化出固定的自动化填表话术（如：“已检查架构，无变更”）。
- **后果**：这种形式化的书面记录会产生“安全错觉”，而真正出现跨层违规依赖（如 UI 模块直接绕过 Domain 引入了底层 DB Client）时，审查者由于习惯性忽略该常规声明，反而导致架构腐蚀漏网。
- 草案 B 的“① 无偏移：合法结果，不产出文档，不得补写已复盘记录；③ 禁止以书面记录充当复盘”是典型的“负向门禁设计”，逼迫架构复盘只在真实存在结构异动时产生物理资产（ADR/登记册），极大提升了信噪比。

### 2.2 §7.2 机器对子与 §6.6 载体三轴分离的配合
- 草案 B 提出的可判定形态为「本批改变模块边界或依赖方向，却无对应文档/ADR 变动」。
- 这完全可以通过项目层的确定性工具（例如 `dependency-cruiser` 的 rule 规则、或者 ESLint 的 `no-restricted-imports`、或者 Git diff 中的目录级交叉引用）进行扫描。
- 符合 §6.6 载体三轴分离：“口径住条文（§7.7 规范逻辑），执行优先工具（项目层 linter 报违规），接线另需授权”。

## 3. 关于草案 C 两个版本的可判定性对比

| 评估维度 | 草案 C 版本 1（P2 抽象口径） | 草案 C 版本 2（P4 出口约束） |
|---|---|---|
| **核心抓手** | 可验证闭环（§6.5 自动化断言 / 语法检查） | 一次可验收增量（无明确技术锚点） |
| **机检可行性** | **高**。提交必须带断言绿灯或类型通过，可直接接入 §6.1 pre-commit hook | **极低**。无法通过自动化脚本检测“是否为一次增量” |
| **防推迟/防跳过** | 通过测试驱动与确定性断言自然牵引小步闭环 | 采用动机禁令（“禁止以...推迟/跳过”），无法客观裁定 |
| **固定层适配性** | 适合放 §2.4 作为基准口径，并由项目层定义具体默认切片大小 | 偏向工作流指导语，更适合作为方法论指引而非固定层纪律 |
| **质量风险** | 质量风险低，保证了单次交付的代码可测性与闭环 | 存在主观解释空间，易出现无自动化测试的“纸面验收” |
