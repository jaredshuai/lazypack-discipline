### 1.2 判据结构

#### 1.2.1 问：我的「单轴 + 独立报告义务」与 P1 的「三轴分离」差异在哪？能否融合？（问 A2-1）

**能融合。实质差异只有一处，而且是我要收回的一处。**

| P1 三轴 | 我的对应 | 关系 |
|---|---|---|
| ① 规则声明只有一个家 | 放在 §1.4 / §4.1，我只作引用 | **我反对把它写成新条的一轴**（见下） |
| ② 可判定性决定执行载体 | 我的单轴 | **完全一致** |
| ③ 门禁接线是独立一步，需另票授权 | 我称「独立报告义务」，认为授权是维护者/项目层决定 | **我接受 P1 把它写进条文**（见下） |

**我反对 ① 成为新条的一轴，理由是可核的**：① 就是 §1.4「每条纪律只活在一处」加 §4.1「一个东西只有一个家」（`:15`、`:53`）的原话。**把它写成新条的一轴，等于在新条里第三次重述 §1.4**——而我们正在讨论的整件事就是为了消灭重复表述。P1 在 result.md §5.1 把①写成了「口径住条文，执行优先工具，接线另需授权」的一句话总纲，这个总纲本身是好的；但它作为**独立的款**出现时，重复就产生了。

**融合方案：把①并入②的执行规则里，而不是并列为轴。** 具体写法见 §3 文本的 (b)：「判定口径留在条文正文，工具运行时读取正文，不在配置里另抄一份」。这样①以**约束**的形式存在（它是执行规则的一部分），不以**规则**的形式存在（不重述 §1.4）。**这是我本轮对 P1 唯一的实质修正要求。**

**我接受③写进条文，撤回我第一轮「授权是维护者决定、不必进条文」的立场。** 理由：【事实】`docs/agents/freshness-check.md:68` 现在写着「要把确定性检查接入门禁，须另有实施票写明范围和授权。本文件不授权接入 hook、CI、定时任务」。**授权边界已经存在，但只存在于一个流程文件里。** 这产生一个具体后果：**读固定层的 Agent 看不到这个边界**——它不在 `DECISIONS.md` 里。P1 主张把它升为固定层一句是对的：边界约束的是 Agent 的行为（Agent 不得自行接 hook），而 Agent 只读固定层与常驻入口。**所以我第三轮的条文会含「本条不授权 Agent 自行接线」这一款**（见 §3 的 (e)）。这是我第一轮立场的一次真实软化。

#### 1.2.2 问：如何回应 P4 的「两轴并用」？「强制后果」是判据的一部分还是独立决策？（问 A2-2）

**我给 P4 一半：强制后果必须留在条文里，但它的位置是「接线决定」，不是「归属判据」。**

**先认 P4 对的一半（这是本轮我明确被说服的推理）**：P4 result.md §1a 指出的失败模式是真的——**「须强制但机器不可可靠判定」的规则在草案里无处安放，执行者会拿「工具化不了」当借口把整条强制规则留在提示词里躺平，而躺平是草案最想治的病**（P4 原文：「这正是草案要治的病」）。这条批评对我的单轴同样成立，只是解法不同。

**驳 P4 的地方：把「违反后果」放在第一轴，会把一个不可验证的规范当成分类依据。**

- **可验证性差异**：判据条文在写纪律的当下就要被用来分类。**「能否被机器复核」是规则的属性，写完即可检查**（找一句判定口径，问它是否只用路径/哈希/正则/存在性/退出码）。**「违反是否产生强制后果」是项目层的事实，且会随时间变化**——今天没接线、下周接了，同一条规则的答案就变了。**用会变的事实当分类判据，分类结果就不稳定**：同一条纪律在不同项目、不同月份会落到不同层。**这是我对「两轴并用」最实的一条反驳。**
- **判据不封闭的机制不同**：P4 的两轴用「11.2 先分解出可判定的子规则」来补窟窿。这是**症状处理**——把无解的一类用工作流绕过去（分解步骤本身是语义判断，会在"怎么算分解干净"上再产生一次争议）。单轴把这一类**在判据阶段就有家**：它属于执行者/审查者，且条文同时要求把其中可判定的子句切出来（我的 (d) 款）。**P4 的 11.2 规定的正是我的 (d) 款**——所以两轴方案里"有用的那一半"可以被吸收进单轴方案，而单轴方案不需要那一半作为补丁。
- **强制的价值我承认，但它是投入信号**：一条被裁定为「违反须阻断」的规则，值得投入更多力气把它的检测假阳性压到可阻断的水平。**所以「强制后果」应保留为项目层决定「给这条纪律做检测器时的投入优先级」，而不是「这条纪律属于哪一层」的输入。** 这一句我写进条文 (e)。

**一句话回应 P4**：后果决定**花多少力气**，可判定性决定**放在哪儿**，接线授权决定**能不能上线**。三者都保留，但它们不是同一条轴上的并列项。

#### 1.2.3 问：P5 的「第四态」怎么看？本仓 `check_commit_msg.mjs` / `check_doc_pairs.mjs` 应如何定性？（问 A2-3）

**接受第四态，并且我要补一个更强的论证：它不是「额外加的一个态」，它是「可判定性单轴」的闭包条件——没有它，我的判据不封闭。**

**我第一轮的单轴有一个我自己没写出的漏洞，这里自己补上**：

- 判据问「能否被机器复核」。规则 `check_commit_msg.mjs` 的 §5.1 type 词表形状 → **能** → 按我的单轴，载体是确定性工具。
- 下一句问「那它在工具里以什么形态存在？」→ 提交前 hook？CI？**手动运行？**
- 如果条文只允许前两种，它就与本仓现状冲突；如果条文只说「工具」，它就**不封闭**——因为存在一种合法状态（可判定 + 有检查器 + 不接闸门）没有被条文覆盖，执行者遇到时会自己发明处理方式。

**所以第四态是判据的闭包要求，不是 P5 的额外提案。** 这个论证把 P5 的第四态从「第五席的偏好」提升为「采用任何以可判定性为第一轴的方案都必须支付的成本」。**P1、P4 若采用可判定性轴，同样必须写这一态，否则他们的条文也不封闭。**

**但我要改 P5 的写法（一个具体修正）**：P5 在 §5 的 4.5 文本里写「机械可判但不设强制后果的规则，**可落成手动运行的检查工具**」——把它写成一种**目标形态**。我认为条文不该把「手动」固化为目标态，理由是本仓的第四态是**裁定的结果，不是设计的方向**：【事实】`scripts/check_doc_pairs.mjs` 自身运行时打印 `checker exists and is runnable; not wired to hook/CI; not a gate.`——它把自己的状态写在输出里，登记册也记着「手动运行。未接 hook/CI。不宣称门禁已生效」。这是**如实记录的状态**，不是被条文认可的终态。

**因此正确的写法是：条文不指定状态，只强制记录状态。** 未接线是合法状态，但必须**显式**记为未接线或不适用及原因；条文既不要求接线，也不认可沉默。落进条文的形式见 §3 的 (e) 与 (f)。

**本仓两条检查器的定性（本轮给出明确答案）**：

| 对象 | 归属 | 状态 | 本条下的应有待遇 |
|---|---|---|---|
| `check_commit_msg.mjs`（§5.1 提交头格式） | **工具层**（§5.1 的 type 词表与形状可用正则与集合判定） | 已实现、可手动运行、**未接 hook/CI**（第四态） | 登记为**待接线项**，接线另需实施票授权；本条不改变其归属，也不得因此宣称门禁已生效 |

#### 1.2.4 问：「何时清」栏与 P1 的「接线授权」轴有何关系？（问 A2-4）

**关系：二者是同一条失效通道的两个断面，一个进条文，一个留 §4 表。**

- **接线授权（新条 (e)）管的是「Agent 能不能做」。** 判定对象是 Agent 的行为，约束对象是每一轮的执行者。它必须在固定层，因为 **Agent 只读固定层**。
- **「何时清」（§4 表新增行）管的是「东西什么时候死」。** 判定对象是一条纪律的强制力来源，约束对象是产物生命周期。它留在 §4，因为 §4.1 已经规定了「有生命周期的写清何时死」（`:53`），这是它的既有职责。

**我第一轮把这个列为 S 项（待 §9 讨论），本轮改判**：它与 (e) 是同一条款的两面，且 §4.1 已强制要求填这一栏，**因此不需要独立裁决，只需要写对措辞**。这是我对第一轮 S2 的一次降级处理。

### 1.3 「迁入」含义

#### 1.3.1 问：是否同意「口径正文不迁移」？为什么？（问 A3-1）

**同意。这一条我第一轮没写清楚（汇总报告把我归入「未明确区分」的三席），本轮明确站到 P1/P4 一边，并给出我的理由。**

- **理由一（本仓既有设计）**：【事实】`check_commit_msg.mjs` 运行时从 `docs/DECISIONS.md` §5.1 抽取 type 词表（`check_doc_pairs` P1 实测两文件同源 `sha256=619048d9…`；`docs/agents/commit-msg-check.md` 记录该流程）。**条文正文就是规则源**，脚本是执行器。按字面「迁入对应工具配置」把 8 个 type 抄进 lint 配置，会造出第二源，且改条文时不会同步——**这就是 §1.4 禁止的「同一句话出现在两处」，只不过两处都不是 `AGENTS.md`。**
- **理由二（可判定性轴的直接推论）**：如果口径要复制进配置，那么「口径在哪个文件」又变成一个可判定性问题，需要新的判据与新的同步纪律。**不迁移口径，这个递归就不存在了。**
- **理由三（对草案的实证反驳）**：P1 在 result.md §4a 举的反例（§5.1 type 词表若抄进 biome/ruff 配置会打断 `commit-msg-check.md` 的抽取流程）成立，我确认。

#### 1.3.2 问：这是否影响我第一轮提出的「setup 与 `tool-or-user` 冲突」问题？（问 A3-2）

**影响很大：这条冲突大部分消解，我把我的待裁决 P2 从「整条冲突」降级为「单点问题」。**

- **冲突原文**：【事实】`skills/lazypack-setup/SKILL.md:124`「配置所有权遵循 `tool-or-user` 原则，setup 实行**零工具私有配置写入**」。
- **第一轮的判断**：草案说「迁入对应工具配置」，若由 setup 执行，就要推翻 `tool-or-user` 与零写入两条，是硬冲突。

#### 1.3.3 问：草案原文「迁入对应工具配置」应如何改写？（问 A3-3）

**改写为（落进 §3 文本的 (b)(c) 两款）：**

#### 3.4 修订后的条文全文（落位中性，供第三轮投票）

> **〔新条〕纪律的执行载体**
>
> **(a)** 纪律的执行载体按「判定对象能否被机器复核」选择，不按「是否已产生强制后果」选择。
>
> **(b)** 可用路径、哈希、正则、存在性或退出码判定的部分，载体是该确定性工具的配置或脚本（格式化、lint、类型、测试、提交前 hook、CI）。**判定口径留在条文正文，工具运行时读取正文，不在配置里另抄一份**；本条的「迁入」指接入执行，不移出口径（§1.4）。
>
> **(c)** 需理解含义、需权衡，或取决于用户授权的部分，载体是当轮执行者与审查者：审查标准文档或按需说明文档，不进常驻提示词（§6.3、§7.2）。
>
> **(d)** 同一条纪律一部分可判定、一部分不可判定的，**按粒度切分**：工具只判机械部分，语义部分留给执行者与审查者。**工具通过不等于语义合格；常驻文件与审查标准文档也不得复述工具已判定的部分。**
>
> **(e)** 强制后果是**接线决定**，不是归属判据。把确定性检查接成阻止提交、阻止合并或阻止发布的闸门，须有实施票写明范围与授权；**本条不授权 Agent 自行接入 hook、CI 或定时任务**。**未接线是合法状态，须显式记为未接线或不适用及原因；不得因工具已存在、配置已写入或条文已写而宣称门禁已生效；未接线也不改变该纪律的载体归属。** 被裁定为违反须阻断的纪律，投入优先级高于仅告警的纪律，但不因此改判其归属。
>
> **(f)** 可判定但本轮不设强制后果的纪律，可落成手动运行或仅告警的确定性检查，结果按事实记录；本条不要求其必须接线。
>
> **(g)** 新增工具、文档或流程前，先判断它能否减少重复劳动与实际错误，以及引入的维护成本是否值得。**该判断本身不可工具化。**
>
> **(h)** 本条只裁剪常驻规则文件的内容，不改变 1.3 的单一常驻文件要求；**工具配置不是给 Agent 读的常驻规则文件，不构成平行复述。**
>
> **(i)** 常驻规则文件（`AGENTS.md` / `CLAUDE.md`）只保留每会话必踩、缺席即越界或谎报的内容：**入口指针与读取顺序**；角色与写权限边界；须明文可见的门禁要求（§6.4）；须停止并交回用户的条件与如实报告义务（未验证标「未验证」、工具失败如实报告、授权边界）。判定口径细则、状态词表与路径表只留指针，正文放唯一权威位置。**§9 属维护固定层的仓库的常驻项，不编译进目标项目。** 超出部分依 §4.1 往下挪。

#### 4.1 问：按紧急程度排序前 3 项（问 D）
