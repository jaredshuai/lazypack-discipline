## 0. 结论先行

**不同意草案原文，建议改写后采纳。** 三条主要理由：

1. **草案的实质内容已有条文承载**，新增独立章节会与 §6.1、§6.3、§4 表三处形成同义重复，违反 §1.4「每条纪律只活在一处」。
2. **判断标准选错了轴。** 草案用「违反是否产生强制后果」分类，但这是**接线状态**而不是**规则属性**。本仓就是反例：三条确定性检查器都已实现、全部未接 hook/CI，按草案口径会被误判为「提示词层」。
3. **二分法不够用。** 草案只有「工具层 / 提示词层」两档，而现实里大量纪律是**半可判定**的（文档同步、命名规范、注释质量——正是提示词点名要问的三例）。这三例的正确解法都是「按粒度切分」，不是二选一。

草案的方向与 `docs/VISION.md` 一致，我不反对方向；我反对的是它把一个**有条件的默认偏好**写成了**无条件的分类规则加强制迁移**，同时没有带上本仓自己的诚实报告义务和成本判断。

## 1. 对草案逐句表态

草案原句拆为四段。

### 1.1 「AI Agent 的行为约束优先通过确定性工具（lint、格式化、类型检查、测试、CI 闸门）实现。」

**表态：同意，但「优先」需要写成有条件的默认，并附成本判断。**

同意理由：这与 §6.1「能写成闸门的纪律先写闸门，再写散文」同向，也符合 `docs/VISION.md:39`「增加工具、文档或流程之前，先判断它能否减少重复劳动和实际错误，以及引入的维护成本是否值得」。

需要修改的地方：「优先」没有给出放弃工具化时的条件。按 VISION 的口径，条文应当要求**先做成本判断再决定载体**，而不是默认工具化、事后再解释。工具化本身有成本：配置本身要维护、工具可能下线、未接线时会静默失效。草案没有为这三项定价。

另：草案列举的四个工具类别就是 §6.1 已列的四项（格式 / lint / 类型 / 测试），「CI 闸门」是新增的载体提法。这一处是**实质增量**，值得保留。

### 1.2 「判断标准：若违反规则必须产生强制后果（阻止提交、阻止合并、阻止发布），则该规则属工具层；若违反规则仅作提示或由人工审查判断，则该规则属提示词层。」

**表态：修改。这是草案最需要重写的一句。**

三个问题：

**（1）混淆了两根轴。** 「能否被机器判定」是规则本身的属性；「是否已接线并会阻断」是项目层的接线事实。草案用后一根轴去分类，会得出错误结论。

事实反例（本仓自身，`:123` 开工实跑 6/6 PASS）：

| 纪律 | 确定性检查器 | 接线状态 | 草案会判为 |
|---|---|---|---|
| 提交说明标题格式（§5.1） | `scripts/check_commit_msg.mjs` 已实现 | 手动运行，未接 hook/CI（`docs/ARTIFACTS.md:50-51`） | 提示词层 |
| 固定层与快照同源、文档对子、登记册链接（§1.3/§7.2/§4） | `scripts/check_doc_pairs.mjs` 已实现，P1–P5+P8 全部 PASS | 手动运行，未接 hook/CI（`docs/ARTIFACTS.md:49`） | 提示词层 |
| 交接材料字节一致性（§7.5） | `scripts/handoff_manifest.js` 已实现 | 无 hook/CI 接线 | 提示词层 |

这三条都**有确定性工具**、都**能阻断**（检查器非零退出码即失败），但都未接线。按草案口径它们会被划进「仅作提示」的提示词层，等于让条文否认已存在的工具化成果。这与本仓反复书写的诚实口径（「不宣称门禁已生效」≠「不承认检查器存在」）直接冲突。

**（2）括号里的后果清单是「拦截时机」分类，不是「规则类型」分类，且漏掉了本仓真实存在的闸门类型。** 草案只列阻止提交 / 合并 / 发布。固定层里至少还有三类阻断语义：

- 阻止写盘：§2.3 与 setup 的「写前零写入拦截」（`skills/lazypack-setup/SKILL.md:159` 零写入门禁在写盘前判定拦截）
- 阻止迁移：Phase 2 受控物理迁移须取得基于计划指纹的单次整体确认
- 阻止删除/移动：§3.4 四步清理关卡第④步，存在争议原地保留并列清单请用户裁定

这三类都不是提交/合并/发布层面的阻断。按草案字面无处安放。

**（3）三类后果不同级，草案并列处理。** 阻止合并蕴含阻止提交；阻止发布蕴含前两者。把它们当同一档会让「只能做到 commit 层」的实现看起来已达标。

### 1.3 「AGENTS.md 或 CLAUDE.md 只保留无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议）和每会话必踩的操作提示」

**表态：修改。方向对，边界需要三处修正。**

先说事实：这一半**已有条文**。§4 表 `AGENTS.md` 行（`docs/DECISIONS.md:70`）写的是「只放指针 + 每会话必踩的几条 | 超过一屏往下挪」。草案与它同义，不是新规定。

需要修正的三点：

**（1）三类保留项不完整，漏掉本仓最吃重的一类。** 草案列的三类都是「结构性约定」，但本仓还有一类同等不可工具化、且明显更常被违反的：**报告诚实义务**。

- §6.4「两边都没跑的概率靠对抗性审查压低」
- §7.5「只写本会话亲自验证过的事实；未验证标『未验证』」
- §7.6「工具调用未达预期时如实报告」
- setup 核心原则 5「区分 setup 完成、命令接线、命令运行、Hook 激活与检查通过；缺命令不虚构，不谎称门禁已生效」（`skills/lazypack-setup/SKILL.md:23`）

这一类无法工具化，而且**方向是反的**：工具能证明「hook 文件存在」，不能证明「这份报告没有夸大」；一个全绿的门禁恰恰是最容易让 Agent 过度宣称的情形。草案把可判定性当作唯一分类轴，会系统性地把这类义务推向「可判定 → 迁走」的错误一侧。

同理应补入的还有**授权边界**：§2.3 写盘前单次整体确认、§3.4 第④步请用户裁定。它们的判定对象是「用户是否已授权」，不在仓库里，任何工具都查不到。

**（2）「多 AI 协作协议」（§9）不宜作为常驻入口的默认项。** §9 是**修改固定层时**的会议章程（§9.1「只有改固定层条文才开会」）。接入本产品的目标项目通常不维护固定层，也就永远不开这类会。当前 `resident-entry.md` 模板（13 行）里没有 §9 内容，这是对的。建议把 §9 限定为「维护本固定层的仓库」的常驻项，而不是编译进所有目标项目。

**（3）括号是穷举还是举例，必须写明。** 草案写「（角色边界、文档归属、多 AI 协作协议）」。若读作穷举，它就是错的（缺报告诚实、授权边界）；若读作举例，应写成「（……等）」并显式排除「可判定即迁入」的误读。条文不能靠读者猜。

**（4）「每会话必踩的操作提示」需要淘汰规则，否则会成为新的垃圾场。** 这一项本身是 §4 的既有措辞，但它没有准入条件。草案的整个动机就是清理堆砌，如果给保留项开一个无门槛的口子，清理会在下一轮反弹。建议加一句：只有「本会话不做就会出错」且「无法由工具兜住」的条目才留。

本仓可作为「必踩」样例的（均取自 `AGENTS.md:5-9` 与 `docs/agents/freshness-check.md`）：开工先读登记册并定位权威正文；只改权威位置、不平行复述；收尾按五态留下检查记录；改固定层须走 §9。

### 1.4 「其余规则迁入对应工具配置或 CI 流程。」

**表态：修改。这一句是草案里风险最高的一句。**

三个问题：

**（1）它指向一个 §4 没有登记的家。** §4 表「编码标准」行确实写着「工具能查的条目移进 lint 配置后删」（`docs/DECISIONS.md:65`），但 §4 表里**没有任何一行**以 lint/format 配置或 CI 门禁为「家」。而 §4.3 规定「册上查不到的产物视为未登记」（`:73`）。草案把迁移变成默认动作，会把大量纪律放进一个按现有条文属于「未登记」的位置。详见 §2.b。

**（2）它没有处理工具下线的生命周期。** §4.1 要求「有生命周期的写清何时死」（`:53`）。工具层纪律的失效路径是：配置被删 / 工具被换 / hook 被解绑，纪律随之静默失去强制力，而固定层条文不会自动察觉。§4 表现有各行都写了「何时清」，唯独新引入的工具层缺这一栏。

**（3）它与 setup 的现有原则硬冲突。** setup 明写「配置所有权遵循 `tool-or-user` 原则，setup 实行**零工具私有配置写入**」（`skills/lazypack-setup/SKILL.md:124`）。若条文要求把规则迁入工具配置、由 setup 生成，就是要求 setup 去写它此前被明令不写的文件。这是需要主持人与维护者裁决的冲突，不是我能在条文层消解的。详见 §2.d 与 §3.c。

## 2. 与既有条文的关系

### a) 与 §6（质量门禁）：**部分重复，且重复面很大**

事实对照：

| 草案语句 | 已有承载 |
|---|---|
| 「优先通过确定性工具实现」 | §6.1「能写成闸门的纪律先写闸门，再写散文」（`:89`） |
| 「工具能查的不写进散文」 | §6.3（`:91`）+ `templates/CODING_STANDARDS.md:8`（`:8`「工具能查的，不写进散文」） |

| 「AI 侧注意力衰减，故规则要少」 | **无**。这是草案唯一实质新增的论据 |

结论：草案 = §6.1 + §6.3 + §4 两行 + 模板 §1.1 的合并重述。**若照草案原文新设 §11，同一条纪律将在仓内出现第五种说法**，直接违反 §1.4「每条纪律只活在一处」（`:15`）与 §4.1「一个东西只有一个家」（`:53`）。

**合并方案**：不新设章节。§6.1 扩写为「载体选择 + 判定口径 + 切分规则」，§6.3 改为引用 §6.1，§4 表 AGENTS.md 行加交叉引用指向 §6.1。净新增内容只有两块：**判定轴换成可判定性**、**半可判定按粒度切分**。

### b) 与 §4（什么放哪）：**需要在 §4 表补一行新类别**

这是我建议的**唯一必要的 §4 改动**。理由与措辞见 §3.a 后的补充说明，一句话：

> §6.1 已经在指示「移进 lint 配置」，但 §4 没有给 lint/format 配置与 CI 门禁一个登记在册的家；§4.3 又把「册上查不到」判为未登记。草案一旦让迁移成为默认，这个缺口会被放大到影响日常执行。

拟增行（含「何时清」栏，满足 §4.1 生命周期要求）：

| 东西 | 家 | 何时清 |
|---|---|---|
| 工具门禁配置（lint / 格式化 / 类型 / 测试配置与 CI 门禁定义） | 项目层既有工具配置与 CI 流程 | 工具下线、配置删除或 hook 解绑时，该条纪律同时失去强制力；须回固定层复核并显式报告，不得静默失效 |

### c) 对 §1.3（只维护一份常驻规则文件）：**不冲突，但草案必须显式声明不改变它**

事实：§1.3 管的是**份数**（「只维护一份常驻规则文件」，不平行写 `.cursor/rules` 复述同一批纪律，`:14`）。草案管的是**内容**（常驻文件里放什么）。两者正交。

风险在于：草案只说「迁入对应工具配置」，不说这不算「第二份规则文件」。加上 §1.3 没有点名工具配置，条文读者可能得出「同一条纪律可以同时存在于 AGENTS.md 和工具配置」的结论。

**建议草案显式写一句**：本条只裁剪常驻规则文件的内容，不改变 §1.3 的单一常驻文件要求；工具配置不是给 Agent 读的常驻规则文件，不构成平行复述。

### d) 对 §2.3（编译器 /lazypack-setup）：**需要同步修改，且有一处硬冲突须裁决**

三个子项：

1. **生成更轻的 AGENTS.md —— 不需要做。** 事实：`skills/lazypack-setup/templates/resident-entry.md` 全文 13 行，托管块只有 4 条指针 + 4 个占位符；本仓 `AGENTS.md` 全文 9 行。两者都已远低于「一屏」。目标项目若 AGENTS.md 过长，问题在项目层既有内容，不在模板。setup 侧该做的表述是「不再新增散文」，而不是「生成更轻的 AGENTS.md」。

2. **增加工具配置生成逻辑 —— 与现有原则冲突，暂不建议。** 详见 §1.4(3) 与 §3.c。若维护者裁定条文确实要求 setup 写工具配置，则 `tool-or-user` 与零私有配置写入两条必须同步改写，不能只改条文。

3. **该新增的是只读探测，不是写盘动作。** setup 已有「诚实报告门禁」（`SKILL.md:23`）与 hook 出处读回机制（`SKILL.md:73-83`，能区分 `wired:preset:recommended` / `missing:preset:declined` / `install-failed:preset:install-error`）。草案真正缺的探测项是：**存在 lint/format 配置但未被任何 hook 引用**这一缺口。它只报告，不修。

## 3. 实施影响评估

### a) 哪些内容应迁移（可机检部分）

按「工具已存在」与「可机检但工具待建」分列，全部给出理由。

1. **§5.1 提交头 type 词表与形状** → 提交说明检查器。工具**本仓已存在**（`scripts/check_commit_msg.mjs`，运行时从固定层抽词表，不另写第二份清单），未接线。这是本仓最干净的一个「已工具化未生效」样本。
2. **§4 编码标准行中工具能查的条目**（格式、命名词法、复杂度） → lint 配置。这是 §4 该行已经写明、尚未落实的动作。
3. **§5.2 提交正文的可机检部分**（首行长度、须有正文段、脚注 `Closes #n` 的形态） → 提交说明检查器。**语义部分**（第一行是否真说清了「改了什么」、正文是否说清「为什么」）工具判不了，留在 `CODING_STANDARDS.md`。这是 §1(a) 切分规则的第一个样板。
4. **§6.5 质量双轨的可测部分**（「可测层行为改动须配套断言」可落为覆盖率/变异分数口径） → 本仓已有 `scripts/mutation-baseline.mjs` 与夜跑 workflow 模板。**语义部分**（某次改动是否属于「可测层」还是「迭代层」）留在提示词，由执行者与审查者判。
5. **§4 AGENTS.md 行中「每会话必踩」里可机检的部分**（指针目标是否存在、登记册相对链接是否可解析） → 已由 `check_doc_pairs.mjs` P4/P5 覆盖。指针**该指向什么**仍由 AGENTS.md 保留。

补充（对应 §2.b）：上述迁移全部落进「工具门禁配置」这个尚未在 §4 登记的家，所以 §2.b 那一行是这批迁移的前置条件，不是可选项。

### b) 哪些内容无法工具化，必须留在提示词

按「为什么工具判不了」分类，不按「重要程度」。

1. **报告诚实义务**（§6.4、§7.5、§7.6、setup 核心原则 5）。判定对象是「这份陈述是否成立」，不是「某个文件是否存在」。工具能验证 hook 文件在位，不能验证 Agent 没有把「已接线」说成「已生效」。**这一类的风险方向与其他所有纪律相反**：其他纪律漏掉会造成缺陷，这一类被工具化后反而会被工具的绿色结果掩盖。
2. **授权与确认边界**（§2.3 写盘前单次整体确认、§3.4 第④步请用户裁定、setup 第 3 步未答/超时记 `pending` 严禁静默假定默认）。判定对象是「用户是否已授权」，不在仓库里。工具能做粗粒度路径锁（CODEOWNERS 一类），但不能判断「这两份文档谁才是权威」「这次迁移是否已被整体确认」。
3. **角色语义边界**（§3.2「允许写」列的防撞车）。「这份改动属于文档行还是代码」需要理解 diff 意图，不是路径匹配。
4. **需要理解含义才能成立的判断**：§7.4 ADR 三条件（难逆转 / 没上下文会奇怪 / 真有取舍）、§6.5 改动属于可测层还是迭代层、§3.4 第①步「是否被声明为权威原件或持久来源」。
5. **工具化本身的成本判断**。VISION 要求「引入的维护成本是否值得」，这个判断的对象是「未来的维护成本」，任何工具都判不了。所以条文只能要求人做，不能提供闸门。

### c) /lazypack-setup 需要做什么

**新增提问（受 §2.3 与 setup「默认零提问」约束，仅在仓库内无法确定时问）**

1. 是否存在已存在但未被 hook 引用的 lint/format/类型/测试命令（缺口事实）。**声明为什么仓库内无法可靠确定**：配置存在不等于已接线，接线事实要看 hook 读回结果，探测只能给候选。
2. 工具配置的所有权：`tool-or-user` 保持不变（用户自管、setup 只检测与报告），还是本轮授权 setup 写入。**这一问不是 setup 能自决的**，它是 §1.4(3) 那处冲突的裁决入口，须由维护者回答。

理由：草案指向的「迁入工具配置」若由 setup 执行，就要生成 lint 配置与 CI 门禁定义；这既越过 setup 现有边界（零私有配置写入，`SKILL.md:124`），也超出 prompt-driven skill 的定位（`SKILL.md:11` 明说不装常驻 CLI 或 YAML 状态层）。若维护者裁定需要生成，应另开实施票并同步改写 `tool-or-user` 原则，不在本次条文修订里隐含通过。

**只读探测项可增**：检测「有工具配置但未被任何 hook 引用」，纳入现有 provenance 槽位如实报告，不新增状态词。

## 4. 最终条文措辞

**不同意草案原文。** 以下是替代文本，按「改写 §6.1 + §6.3 引用 + §4 两处交叉引用」落位，**不新设 §11**。

### 改写 `§6.1`

> **6.1 纪律的执行载体按「判定对象能否被机器复核」选择，不按「是否已产生强制后果」选择。**
>
> （a）判定对象可由确定性工具复核的，载体是该工具的配置（格式、lint、类型、测试、CI 门禁）。工具未接线、未运行或用户拒绝接入时，如实记为未生效；不得以条文已写、配置已存在或检查器已实现为由宣称门禁已生效。
>
> （b）判定对象需要理解含义、或取决于用户授权的，载体是常驻规则文件，只写不可由工具代劳的部分。
>
> （c）同一条纪律一部分可判定、一部分不可判定的，按粒度切分：工具只判机械部分，语义部分留给执行者与审查者。工具通过不等于语义合格；常驻文件也不得复述工具已判定的部分。
>
> （d）新增工具、文档或流程前，先判断它能否减少重复劳动与实际错误，以及引入的维护成本是否值得。判断本身不可工具化。
>
> （e）本条只裁剪常驻规则文件的内容，不改变 1.3 的单一常驻文件要求。工具配置不是给 Agent 读的常驻规则文件，不构成平行复述。

## 5. 章节归属建议

**建议：并入 §6（质量门禁），不新设 §11。** 草案题注的「拟议为新 §11 或并入既有章节」两个选项中，我选后者，且具体是**改写 §6.1**，不是追加一条平行条文。

理由，按重要性排序：

1. **§6.1 已经是这条原则。** 「能写成闸门的纪律先写闸门，再写散文」（`:89`）与草案首句同义。新设 §11 等于把同一句话在仓内写成第五种说法，直接违反 §1.4「每条纪律只活在一处」与 §4.1「一个东西只有一个家」。这是本意见最硬的一条反对理由。
2. **草案的 AGENTS.md 内容边界这一半，家在 §4 不在 §6。** §4 表 `AGENTS.md` 行（`:70`）已经写了内容上限与「每会话必踩」。正确做法是让 §6.1 讲判定口径、§4 行讲位置与份数并交叉引用，而不是在 §6 里重列一遍保留清单。
3. **归 §4 单独立章也不成立。** 草案给 §4 的增量只有「工具门禁配置」这一行类别，属于 §4 既有职责（§4.1 的「一个东西只有一个家」+ 生命周期栏），一行表格扩展不足以支撑一个章节。
4. **独立章节会切断与 §6.4/§6.5 的连接。** 草案最该强调的「未接线不得宣称生效」在语义上紧贴 §6.4（双角色都跑门禁）与 setup 的诚实报告原则，分到新章会让这层关系只能靠交叉引用维持。

**同时建议 §4 表补一行**（§2.b）。这是本轮唯一必要的固定层新增内容，且它不是新章节，是把 §6.1 已经在说的话给它一个登记在册的家。
