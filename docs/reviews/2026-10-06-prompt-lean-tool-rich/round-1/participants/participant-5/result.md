# 第一轮独立意见：Participant 5 — 「提示词瘦、工具肥」

> 依据提示词 `round-1/prompts/participant-5.md` 独立完成，未读取任何其他参与者的意见。
> 事实与观点分列：标注【事实】的条目给路径与条款号；其余为本人观点。推理过程与完整引文见同目录 `evidence.md`。

## 0. 总体立场

**方向同意，条文需三处修改后支持入固定层；建议并入 §4 新增 4.5，不设新 §11。**

草案的价值不在「工具优先」这句话本身——那在固定层已有近似表述（§6.1、§6.3、§4.1 表两行）——而在两点增量：

1. 把「哪类规则必须进工具」的**路由判据**（强制后果）第一次写成显式条文；
2. 给常驻入口（`AGENTS.md` / `CLAUDE.md`）的**内容边界**补了枚举。

但草案把规则的世界切成「工具层 / 提示词层」两半，漏掉了本体系早已存在的第三家（审查者执行的标准文档），也漏掉了本仓正在实践的第四态（确定性工具、手动运行、不接闸门）。按原文通过会在 §4.1 与 §6.3 上产生直接冲突。以下逐句说明。

## 1. 对草案逐句表态

### 句 1「AI Agent 的行为约束优先通过确定性工具（lint、格式化、类型检查、测试、CI 闸门）实现。」

**表态：同意（保留）。**

理由：

- 与既有条文同向。【事实】§6.1「能写成闸门的纪律先写闸门，再写散文」；§6.3「工具能查的不写进去」；§4.1 编码标准行「工具能查的条目移进 lint 配置后删」。草案是这三处的总纲化，不是新方向。
- 与产品愿景同向。【事实】`docs/VISION.md`：「已经声明、并且能用路径、哈希或正则判定的关系交给机器检查；需要理解含义的影响，由当轮执行和审查处理」——这正是 Smart Zone / Dumb Zone 划分，愿景文档里已经写了，只是没有上升到条文。
- 「优先」一词留了余地，正确：不是所有约束都能工具化（见 3b），强行工具化语义规则会产生误报，诱发 `--no-verify` 绕过文化，反而摧毁闸门公信力。

一处措辞保留意见：句中把「CI 闸门」与提交前工具并列，容易被读成固定层背书 CI。【事实】本仓现行口径是：固定层默认闸门是提交前 hook（§6.1、§2.3「能接到已有 format/lint/type/test 命令则写出提交前 hook」）；CI 属项目层（§2.2「验证命令」；`templates/.github/workflows/nightly-mutation-*.yml` 头注「复制到目标项目，本仓自身不运行该闭环」）。修订文本里我把 CI 标注为项目层可选增强。

### 句 2「判断标准：若违反规则必须产生强制后果（阻止提交、阻止合并、阻止发布），则该规则属工具层；」

**表态：修改。** 判据本体可用，但有三处要修。

**问题一：义务式与描述式的歧义（循环误读）。**「若违反必须产生强制后果，则属工具层」如果读成描述式——按现状分类——那么「现在只写在提示词里的规则」自动合法地留在提示词，判据失去改革力；正确读法是义务式——**凡是裁定为『违反须阻断』的规则，就必须落进工具，不得只留在提示词**。两种读法给出完全不同的合规判断。条文措辞必须钉死义务式（我的替代文本用「必须落进」）。

**问题二：二元漏了第三家。** 草案后半句（句 3）把「由人工审查判断」的规则划给提示词层——这与 §4.1 直接冲突。【事实】§4.1 给「编码标准」的家是 `CODING_STANDARDS.md`「由审查者执行」；§6.3「CODING_STANDARDS.md 由审查者在审查时执行」。需要语义判断的规则的家是**审查者执行的标准文档**，不是常驻提示词。按草案原文执行，命名达意、注释质量这类规则的归宿会是 `AGENTS.md`——恰是瘦身要防的膨胀。

**问题三：一条规则可以拆两半。** 判据隐含「一条规则整体归一层」的假设，但最常见的规则是混合体：文档同步 = 检测半（可拦）+ 修复半（语义）；命名 = 形状半（lint）+ 达意半（审查）。判据要加「机械可判部分」限定词，否则混合规则无处安放。

另有一个草案没写、但本仓已在实践的**第四态**：【事实】`docs/agents/commit-msg-check.md`（§5.1 提交头格式的确定性检查器）明确写着「未接 hook、CI 或定时器。格式通过不等于语义已验证……检查器在磁盘上存在、可手动运行，不等于门禁已生效」；`docs/agents/doc-pairs.md` 的 `check_doc_pairs.mjs` 同样未接闸门。机械可判、但维护者裁定暂不设强制后果的规则，可以落成**手动运行的检查工具**——工具的确定性收益照拿，强制的代价（误报阻断、绕过诱因）先不付。这是「工具肥」的一种合法形态，判据不应否认它。我的替代文本把它写成显式的第四种路由。

### 句 3「若违反规则仅作提示或由人工审查判断，则该规则属提示词层。」

**表态：修改（并入句 2 的处理）。**

- 「仅作提示」→ 提示词层：可以，但「提示词层」内部要再分常驻（`AGENTS.md`）与按需（`docs/agents/<主题>.md`）。【事实】§4.1「给 agent 的按需说明 | `docs/agents/<主题>.md` | 被闸门或工具替代后删」。不是所有提示都配常驻。
- 「由人工审查判断」→ 提示词层：错，应为审查标准文档层（见句 2 问题二）。

### 句 4「AGENTS.md 或 CLAUDE.md 只保留无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议）和每会话必踩的操作提示，」

**表态：修改。** 两处：

**枚举缺「指针」，而指针恰是当前常驻入口的主体。**【事实】§4.1「`AGENTS.md` | 只放指针 + 每会话必踩的几条 | 超过一屏往下挪」；编译产物 `skills/lazypack-setup/templates/resident-entry.md` 的受管块内容 = 两行必踩（纪律唯一事实源、双角色门禁要求）+ 四条指针（roles / ARTIFACTS / CODING_STANDARDS / RELEASE）。草案的枚举描述的是指针**指向**的核心约定，而不是常驻文件里实际放的东西。措辞上应把「指针」列为第一类保留内容。

**三类核心约定不完备，建议补第四类：诚实性与交接类行为约束。**【事实】§7.5「交接只写本会话亲自验证过的事实；未验证标『未验证』」、§7.6「工具调用未达预期时如实报告……不拼凑、不跳步」。这类约束完全无法工具化（工具检测不出「未验证却声称已验证」），也不是角色边界、文档归属或协作协议中的任何一类，但它们是这套纪律的信用底座，必须保留在提示词可达的范围。此外草案说「只保留……核心约定」的写法暗示约定**正文**住在 AGENTS.md 里；在编译架构下（【事实】DECISIONS.md 导语「项目层文件……由 `/lazypack-setup` 从本文件编译得出」），正文住 `DECISIONS.md` / `roles.md` / `ARTIFACTS.md`，常驻文件里通常是一行式明文或指针。修订文本兼容两种形态。

### 句 5「其余规则迁入对应工具配置或 CI 流程。」

**表态：修改。**

- 「迁入对应工具配置」：对，但迁移目的地按句 2 的修正应为三家（工具配置 / 审查标准文档 / 按需说明），不只是工具配置。
- 「或 CI 流程」作为默认目的地：不妥，理由同句 1——CI 可用性因平台而异（私有仓、无 CI 环境），固定层把它列为并列默认会在无 CI 项目里制造「条文无法执行」的常态。默认载体是提交前 hook（可移植、离线可用、§6.1 已有），CI 是项目层增强。
- 迁移动作要加前提：「以能实际接线为前提」。【事实】§2.3「能接到已有 format/lint/type/test 命令则写出提交前 hook；否则标明未接线或不适用及原因，不得宣称门禁已生效」。条文存在不等于门禁生效——这是本体系反复强调的诚实性边界，新条文不应例外。

### 背景与动机（Uncle Bob 实测 / Lost in the Middle / Smart-Dumb Zone）

**表态：认可方向；动机材料不进条文正文。**

- 【事实】论文与对谈的原始材料我未读到：issue #36 引的「访谈笔记（本轮对话整理稿）」不在公开仓（`docs/interviews/` 下未检索到相关内容；私有材料按 §10.2 在 vault，本轮无访问），arXiv:2307.03172 原文本轮未读。动机的真实性**无法判断**，只能按 issue 转述采信——需要进一步调研。
- 即使注意力论证完全不成立，本条依然成立：【事实】§1.4「每条纪律只活在一处。同一句话不得同时出现在 AGENTS.md、CONTEXT.md、演变史里」+ §1.3「只维护一份常驻规则文件」——瘦身的首要收益是消除双份真相与维护漂移，其次才是上下文注意力。把论证锚在 1.4 上比锚在论文上更稳，也更符合本仓风格（DECISIONS.md 全文无外部引用）。
- Lost in the Middle 对本条的适用度其实有限：编译产物 resident-entry 本来就短且位于文件头部（高注意力区），「中段退化」描述的是长文档病灶。真正中招的是把规则堆进常驻文件的目标项目——那恰是本条要治的病。

## 2. 特别问题回答

### a) 判断标准是否清晰？

**清晰到可操作，但有四个盲区**（详证据 §3）：义务式/描述式歧义、二元漏第三家、规则拆半、第四态未定义。修法都在我的替代文本里。

三个指定边界例：

| 边界例 | 判定 | 依据 |
|---|---|---|
| 文档同步检查 | 检测半进工具，修复半留审查/执行 | 【事实】§7.2「机器只拦能判断的几条（『改了 X 却没动 Y』），具体对子由项目层定义」；本仓已落地 `doc-pairs.md` 声明 + `check_doc_pairs.mjs` 检查器（未接闸门）——检测可工具化已被实证 |
| 命名规范 | 形状半（大小写、导出模式、文件名）进 lint；达意半留 `CODING_STANDARDS.md` 由审查者判 | 混合规则，须拆半处理；强行 lint 语义会产生误报 |
| 代码注释质量 | 基本不可工具化（「有没有注释」是弱代理），留审查标准文档 | 无法写出低误报的机械判定；Smart/Dumb Zone 边界案例 |

### b) AGENTS.md 瘦身边界如何界定？

保留清单（我的版本，四类）：**指针**；**无法工具化的核心约定**（角色边界、文档归属、多 AI 协作协议、诚实性与交接类行为约束）；**每会话必踩的操作提示**。

草案三类枚举**不完备**：缺指针（主体内容）、缺诚实性/交接类（§7.5/7.6）。不应删减。另注意：常驻文件里的约定通常是一行式明文或指针，不是约定正文（正文在 `DECISIONS.md` 等权威文件），边界措辞要兼容这一点。

### c) 「每会话必踩的操作提示」是否应留在 AGENTS.md？

**是，必须留。** 特征：作用于会话生命周期（开工/收尾/触碰某类文件时），没有 git 事件可挂钩子——会话开始时不存在可拦截的提交动作，工具无从发力。

典型例子（全部来自本仓现行文件）：

- 【事实】根 `AGENTS.md`：「开工先读 [文档归属与产物登记册]」「开工与收尾按 [文档防腐检查]……留下检查记录」「修改纪律或 skill 时，读 [固定层条文] 及对应 skill 正文」。
- 【事实】`templates/resident-entry.md` 受管块：「双角色门禁要求：执行者和审查者都必须运行适用的质量门禁……」——门禁本身是工具，但「审查者也必须跑」这个行为要求只能靠常驻明文（§6.4 正是这么规定的：「`AGENTS.md` 明写：执行者和审查者都必须跑门禁」）。

反面检验：若挪走——挪进 skill 则失去常驻性（skill 按需加载，开工时未必在场）；挪进登记册则常驻入口仍需一条指针指过去，绕一圈回到原点。数量上以 §4.1「超过一屏往下挪」为硬约束，不必另设条数上限。

### d) 固定层 vs 项目层？

**必须固定层，不能只做 §2.4 项目层默认值。** 理由：

1. 它约束的是固定层纪律**自身的编译落点**与常驻入口形态，是体系自描述规则——项目层没有权限定义「固定层条文住哪」。
2. 【事实】常驻入口由 `/lazypack-setup` 从固定层编译（DECISIONS.md 导语、§2.3），判据是编译器行为的依据，必须在编译器的上游即固定层。
3. 若落项目层默认值，每个接入项目可各自放弃，常驻入口会重新膨胀——与 VISION 的「懒」（「用户不应反复提醒 AI……」）直接相悖。
4. 它不越界：判据只定**载体路由**，不定工具选型；选型仍在项目层（§2.2、§6.2），两条边界清晰。

## 3. 与既有条文的关系

### a) 与 §6（质量门禁）

**强化 + 补充，不是重复。** §6.1 是操作顺序句（写纪律时先写闸门），草案是路由判据（哪类规则**必须**进闸门）+ 常驻入口内容边界（§4.1 的域）。三者语义可分。合并方式：判据进新 4.5，§6.1 原句保留不动——本仓条文体系本就接受「操作句与判据句并存」的镜像结构（【事实】§4.1 编码标准行与 §6.3 几乎互为复述而共存至今）。若第二轮有参与者判为重复，最小合并方案是把 §6.1 前半句改为「载体判据依 4.5」，我不坚持。

### b) 与 §4（什么放哪）

**需要在 §4.1 表补一行「家」**：工具化纪律（lint 规则、类型约束、测试断言、闸门脚本）→ 家为项目层工具配置与 hook/CI 脚本（由 setup 接线）→ 工具换代随之改。否则「迁入工具配置」的东西在「什么放哪」表里没有登记的家，违反 4.1 自身原则。

**登记册（`docs/ARTIFACTS.md`）不必新增内容类别**：工具配置是代码资产不是文档产物；工具的**操作手册**已有归宿——【事实】§4.1「给 agent 的按需说明 | `docs/agents/<主题>.md`」，本仓 `quality-gates/mutation-testing.md` 等即以此类别登记。

### c) 对 §1.3（只维护一份常驻规则文件）

**无冲突，正交互补。** 1.3 管「维护几份文件」，本条管「这份文件里放什么」。草案通过后 1.3 一字不改，反而获得内容判据支撑。

### d) 对 §2.3（编译器 `/lazypack-setup`）

**需要同步，但改动比想象小。** 【事实】现状盘点：`templates/resident-entry.md` 已是「两行必踩 + 四指针」的瘦形态（合规）；`templates/CODING_STANDARDS.md` 第 1 条已是「工具能查的，不写进散文」（合规）；SKILL.md 第 2 步已探测既有门禁命令、第 5 步已按真实状态渲染 hook（`wired/missing/n-a/install-failed` 四态 + 失败关闸）。即：**编译器已经在按草案精神工作**，条文通过主要是把既成事实升格为义务。真正的增量：

1. **常驻入口块外内容扫描**：探测块外（用户自写）规则中的机械可判项，输出「可工具化规则清单」迁移建议——只报告不自动迁移（块外字节不变的既有契约 + preserve-first 原则），迁移走既有受控迁移确认机制；
2. **可选 CI 装配问项**：探测到 `.github/` 等信号时问一句是否复制 CI 闸门模板（本仓 `nightly-mutation-*.yml` 已有先例形态）；
3. **连带同步成本**（这条最实）：【事实】`doc-pairs.md` P1（固定层与 setup 快照字节同源）、P2（5 个模板来源内容标识）、P3（版本字符串四处一致）——固定层任何升版都触发这三项机械检查，是既定成本不是新负担。

## 4. 实施影响评估

### a) 哪些内容应迁移？（若草案通过）

以「典型目标项目常驻入口里常见的可工具化规则」为准，举四条：

1. **提交信息格式**（Conventional Commits 标题形状与 type 集合）→ commit-msg hook。本仓已有确定性检查器 `scripts/check_commit_msg.mjs`（判定正文 `docs/agents/commit-msg-check.md`），现状手动运行、未接闸门——按修正判据属第四态；是否升格为强制闸门是维护者裁决项（见待裁决 1）。
2. **敏感信息防泄漏**（不得提交密钥/凭据）→ pre-commit + CI secret scanning。违反必须阻断，最典型的工具层规则，当前体系反而没有覆盖。
3. **文档同步对子**（「改了 X 没动 Y」）→ 检查器拦截。本仓 `check_doc_pairs.mjs` 已实现判定算法（P1–P8 声明），未接闸门；接入项目可把各自的对子接进 hook 或 CI。对应未定项「7.2 中『改了 X 没动 Y』的具体对子」。
4. **生成物勿手改**（§4.1 pipeline 行「勿手改，重跑生成」）→ CI 校验重新生成结果与提交内容一致。

### b) 哪些内容无法工具化，必须保留在提示词？

四类，每类给代表：

1. **会话行为类**：开工先读登记册、收尾留防腐检查记录、交接只写验证过的事实、工具失败如实报告（§7.5/7.6）。无法工具化的原因：作用对象是 agent 会话行为，会话启动时无 git 事件可拦，「未验证却声称已验证」不可机械检测。
2. **流程协议类**：§9 三轮投票、角色分配、主持人职责。社会性流程，无机械判定可言。
3. **语义判断类**：命名是否达意、注释质量、ADR 三条件取舍（§7.4）、文档归属冲突裁决。需要理解含义——【事实】VISION 明文把这类留给「当轮执行和审查处理」。
4. **角色边界的会话内部分**：规划者不写代码等防撞车边界（§3.2）。说明：CODEOWNERS + 分支保护可以在**人际协作**维度部分工具化角色边界（按路径指定审批人），但对「同一会话内多角色切换」无能为力——工具看得见路径，看不见谁在以什么角色说话。

### c) `/lazypack-setup` 需要做什么？

见 3d 的三点增量（块外规则扫描与迁移建议报告、CI 装配问项、P1–P3 连带同步）。新增**问题**只有一个方向：CI 装配与否；新增**文件**：无强制新文件（CI 模板为可选）。不重写更轻的 AGENTS.md 模板——已经是目标形态。

### d) 模板是否需要更新？

- `templates/RELEASE.md`：无关，不改。发版纪律是语义+流程规则，「阻止发布」的载体属项目层平台段（模板块外区已有「标签由谁打、与 CI 的先后由项目层写清」的槽位）。
- `templates/CODING_STANDARDS.md`：已合规，仅随固定层升版换来源标识与版本戳（P2/P3 机械动作）。
- `templates/resident-entry.md`：形态合规；可选微调是把「双角色门禁要求」行标注为「每会话必踩」类锚点，非必需。
- `skills/lazypack-setup/references/DECISIONS.md` 快照：强制同步（P1 字节同源）。
- 候选新模板（不阻塞本条通过）：CI 闸门工作流模板。建议列入未定项。
