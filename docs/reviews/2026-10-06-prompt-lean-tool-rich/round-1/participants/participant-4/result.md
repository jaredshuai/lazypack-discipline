## 1. 对草案逐句表态

草案可拆为四句，逐句表态：

**句 1：「AI Agent 的行为约束优先通过确定性工具（lint、格式化、类型检查、测试、CI 闸门）实现。」**
**同意。** 这是 §6.1「能写成闸门的纪律先写闸门，再写散文」的一般化，方向一致。工具枚举与 §2.2 项目层工具范围吻合。

**句 2：「判断标准：若违反规则必须产生强制后果（阻止提交、阻止合并、阻止发布），则该规则属工具层；若违反规则仅作提示或由人工审查判断，则该规则属提示词层。」**
**修改。** 判据本身是对的（先问后果要求，再问载体），但有两个缺陷：
- 缺第二轴「可判定性」。存在「须强制但机器不可可靠判定」的规则（见 1a），草案没有给它们去处，执行者会拿「工具化不了」当借口把整条强制规则留在提示词里躺平——这正是草案要治的病。
- 「提示词层」是含混桶。按 §4.1 与 §6.3 的既有分类，散文至少有两个不同的家：常驻文件（`AGENTS.md`/`CLAUDE.md`）与按需文档（`CODING_STANDARDS.md`、`docs/agents/<主题>.md`）。「由人工审查判断」的规则按 §6.3 应进 `CODING_STANDARDS.md` 由审查者执行，而不是堆进常驻提示词。

**句 3：「AGENTS.md 或 CLAUDE.md 只保留无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议）和每会话必踩的操作提示。」**
**修改。** 保留清单漏了常驻文件的首要内容：**指针**。§4.1 表格末行明文「`AGENTS.md`：只放指针 + 每会话必踩的几条，超过一屏往下挪」。三类「约定」列举可作为无法工具化的示例保留，但应补指针并注明列举非穷举。

**句 4：「其余规则迁入对应工具配置或 CI 流程。」**
**修改（轻）。** 迁入目的地除工具配置与 CI 外，还有审查者执行的按需散文（§6.3 通道）。建议改为「其余规则迁入工具配置、CI 流程或按需执行的文档，常驻文件不留副本」。

### 1a) 判断标准是否清晰？

**结论：主判据清晰可执行，但需补可判定性轴，否则边界情况无解。**

「违反必须产生强制后果 → 工具层」作为第一轴是好的：它把问题从「能不能自动化」（能力视角）扭转为「要不要强制」（需求视角），先定要求再找载体。但单轴不够，对三个点名的边界情况逐一判定：

- **文档同步检查（能检测但不好自动修复）**：工具化只看**检测**，不要求自动修复。检测可靠（低假阳性）即可进闸门——CI 红就是强制后果，修复仍由人做。本仓 `check_doc_pairs.mjs` 即此类（登记册明示「手动运行，未接 hook/CI」）。**真正的问题在假阳性率**：检测器假阳性高时不配做阻断闸门，应降级为「CI 警告 + 审查者必核」的中间态。草案未覆盖此中间态，建议第二轮讨论（见 evidence.md 待裁决 1）。
- **命名规范**：可分解。词法部分（大小写风格、前后缀）可判定 → lint；语义部分（名字是否表意）不可可靠判定 → §6.3 通道进 `CODING_STANDARDS.md` 由审查者执行。这正好演示两轴判据的用法。
- **代码注释质量**：不可可靠判定。若项目要求强制，执行载体是**人工审查**（§6.3 + §6.4 对抗性双跑），不是提示词自律。草案须明示这一落点，否则此类规则无合法强制通道。

### 1b) AGENTS.md 瘦身边界

「无法工具化的核心约定」应包括四类：
1. **指针**（各类内容的家与读取时机）——草案漏列，§4.1 末行明文在案；
2. 角色边界（草案已列）；
3. 文档归属原则（草案已列）；
4. 多 AI 协作协议（草案已列）。

草案三类列举方向正确但不完备，补「指针」后可接受；建议措辞上用「包括」而非穷举，避免把 §6.4 要求的「双角色门禁明文」这类固定层点名写入常驻文件的条目挤出去（§6.4：「`AGENTS.md` 明写：执行者和审查者都必须跑门禁」——这是一条无法工具化的自我承诺声明，属每会话必踩）。

补充说明「角色边界」为何无法工具化：路径 × 角色的写权限矩阵本身可机器检查，但**执行者自报角色不可机器核验**——hook 无法知道当前会话正以哪个角色行事。它属于「须强制 + 不可可靠判定」区，现由提示词 + 审查承担，归类正确但理由应写明（见 §4 条文 11.2 的覆盖）。

### 1c) 「每会话必踩的操作提示」应留在常驻文件

**应留。** 理由：
- 触发条件是语义事件（「开工」「讨论产品定位时」「交付其他 Agent 的结果时」），没有任何 hook 会在这些时刻点火，天然不可工具化；
- Lost in the Middle 的证据支持的是「短」，不是「无」——高注意力区放少量必踩项正是对该证据的正确运用。

典型例子（本仓现行 `AGENTS.md`，全文 9 行纯指针，是目标状态的样板）：「开工先读登记册」「开工与收尾按防腐检查执行」「交付或核验其他 Agent 结果时读交接核验指引」。

约束：必踩项自身也受本条管辖——某项一旦可被闸门覆盖（如防腐检查的机器部分接 CI），应迁出，常驻文件只留指针。

### 1d) 应纳入固定层，不是项目层默认值

**固定层。** 理由：
- 本条裁决的是「纪律的执行载体怎么分配」，这是固定层自身的主营业务（§1.4 一处一条、§2 两层结构、§4 什么放哪）；
- §2.4 项目层默认值的例子是技术栈选型、工具组合——本条不是选型，是跨项目不变的元规则；
- §6.1 第二句已经在固定层，本条是对它的加强与一般化，放项目层会造成「一般规则在项目层、特例在固定层」的倒挂。

## 2. 与既有条文的关系

### 2a) 与 §6（质量门禁）：一般化关系，非重复

- §6.1 第一句（提交前 hook 跑四闸门）是操作内容，保留；
- §6.1 第二句（「能写成闸门的纪律先写闸门，再写散文」）是本条在质量门禁域的特例；
- §6.3（「工具能查的不写进 `CODING_STANDARDS.md`」）是本条在编码标准域的特例。

处理建议：新条独立成 §11 并互指（见 §5）；§6.1 第二句可改为「执行载体分配见 §11」以守 §1.4 一处一条，也可保留现状靠 11.5 互指——两种都可行，提请维护者裁定，不阻塞本条通过。

### 2b) 与 §4（什么放哪）：不需新产物类别

「规则迁入工具配置」不产生新的文档类别——工具配置是项目层配置（§2.2），不是 §4 登记的文档产物。§4.1 已有两行是本条的既有先例：「编码标准……工具能查的条目移进 lint 配置后删」「给 agent 的按需说明……被闸门或工具替代后删」。新条只需引用这两行作为既有应用，§4 表格本身不必改。

### 2c) 对 §1.3（一份常驻规则文件）：无冲突，有加强

草案瘦身常驻文件，直接服务 §1.3 的目的（单一、高信噪比入口）。需澄清一点防误读：**工具配置不是 §1.3 禁止的「平行复述规则文件」**——lint 配置是规则的可执行正文，不是同一批纪律的散文副本，两者不构成「平行写」。迁入后散文侧删除（§1.4），一处一条不被破坏。

### 2d) 对 §2.3（`/lazypack-setup`）：方向被追认，改动极小

核对 `skills/lazypack-setup/SKILL.md` 与模板后的事实：生成的常驻入口模板（`templates/resident-entry.md`）只有指针 + 双角色门禁明文 + 固定层来源标注，已是瘦形态；`templates/CODING_STANDARDS.md` §1.1 已写「工具能查的，不写进散文」；pre-commit 模板四槽齐全且含 `missing`/`install-failed` 诚实状态。**本条基本是对 setup 现行方向的追认，不要求重做。**

需要同步的只有：
- 固定层升版后刷新 `skills/lazypack-setup/references/DECISIONS.md` 快照与模板头注的 `src=DECISIONS.md@x.y.z`（既有例行流程）；
- 可选后续票：setup 探测到仓库已有可接线检查脚本（如 `check_commit_msg.mjs`）时，增问「是否接为强制闸门」。建议单独立票，不随本条捆绑。

## 3. 实施影响评估

### 3a) 哪些内容应迁移

**本仓 `AGENTS.md` 无需迁移项**：现文 9 行、纯指针，已是本条目标状态的实例。本条对本仓的价值在约束未来膨胀；对下游项目的价值在 setup 生成物上（已合规，见 2d）。

若按本条加压审视本仓，迁移候选不在 AGENTS.md，而在**已存在但未接线的检查脚本**（登记册均明示「手动运行，未接 hook/CI」）：
1. `scripts/check_commit_msg.mjs`（§5.1 提交头格式——可判定）→ 可接 commit-msg hook 或 CI；
2. `scripts/check_doc_pairs.mjs`（§7.2 对子的机器部分——可判定）→ 可接 CI；
3. 上述两者的语义部分（提交正文是否说清「为什么」、文档语义是否同步）→ 不可判定，留审查者；
4. `docs/agents/freshness-check.md` 的五态记录流程 → 语义流程，不可工具化，留提示词 + 登记册当轮说明。

注意诚实边界：接不接线是各项目层决定（§2.2），本条只要求「须强制的规则不得只活在提示词」，不要求所有可工具化的检查一律强制接线。本仓是否示范接线，提请维护者裁定（evidence.md 待裁决 2）。

### 3b) 哪些内容无法工具化

必须留在散文层的现有规则（附不可工具化理由）：
- **§5.2 提交正文的语义**（「为什么」是否说清）——格式可 lint，语义需人读；
- **§7.4 ADR 准入三条**（难逆转、没上下文会奇怪、真有取舍）——纯判断；
- **§7.5/§7.6 诚实条款**（未验证标未验证、工具失败如实报）——工具无法核验 agent 是否真的验证过；
- **§9 多 AI 讨论章程**——程序性规则，由人主持执行；
- **§3 角色边界的身份归属**——路径矩阵可查，自报身份不可核验（见 1b）；
- **VISION.md 设计判断四问**——产品判断，非规则检查。

### 3c) `/lazypack-setup` 需要做什么

- 不必新增必答题；生成物已符合本条（2d）；
- 可选增强（建议后续实施票，不捆绑本条）：探测到既有检查脚本时增问「是否接为强制闸门」，并在完成报告中按两轴如实区分「已接线强制 / 可接线未接 / 不可工具化留散文」。

## 4. 最终条文措辞

不同意草案原文（三处缺陷见 §1），替代文本如下：

```text
## 11. 提示词瘦、工具肥

11.1 规则的执行载体按两轴定位：违反后果（必须强制阻断，还是仅提示或人工判断）
     × 可判定性（机器能否可靠判定违反）。须强制且可判定的规则，正文写进确定性
     工具（lint、格式化、类型检查、测试、提交前 hook、CI 闸门），不另留散文复述。

11.2 须强制但机器不可可靠判定的规则：先分解出可判定的子规则进工具；剩余语义
     部分进 CODING_STANDARDS.md 等按需文档由审查者执行，并按 §6.4 对抗性双跑
     压低漏检。不得仅以常驻提示词承担强制规则。

11.3 常驻规则文件（AGENTS.md 或 CLAUDE.md）只保留：指针（各类内容的家与读取
     时机）、无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议等）、
     每会话必踩的操作提示。其余迁入工具配置、CI 流程或按需文档；超过一屏往
     下挪（§4.1）。

11.4 工具配置是规则的执行载体，不算 §1.3 禁止的平行规则文件。规则迁入工具后，
     同义散文按 §1.4 删除，只活在一处。

11.5 本条是 §6.1「能写成闸门的纪律先写闸门，再写散文」的一般化；§4.1 表中
     「工具能查的条目移进 lint 配置后删」与「被闸门或工具替代后删」为其既有
     应用。
```

## 5. 章节归属建议

**新 §11（独立章节）。** 理由：

1. **域不同**：§6 管质量闸门（提交前跑什么），§4 管文档产物的家（什么文档放哪），本条管**规则的执行载体分配**——三者正交。并入 §6 会把本条收窄成门禁细则；并入 §4 会把「规则」与「文档产物」两类东西混进同一张表。
2. **不动既有编号**：固定层是扁平编号，新增 §11 不改任何既有条号，`templates/` 与 `skills/` 中对 §4/§5/§6 的引用零改动，升版成本最低。
3. **自我指涉的放置论据**：本条引用的 Lost in the Middle 证据（U 型注意力曲线）恰好支持把高频援引的原则放在文末——结尾是高注意力区。
