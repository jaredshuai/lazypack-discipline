# Participant 3 评审意见：固定层新增「提示词瘦、工具肥」原则

- **评审轮次**：第一轮（独立意见，互不可见）
- **评审席位**：Participant 3
- **议题来源**：Issue #36
- **核心态度**：**原则上赞同核心方向，但草案存在因果倒置与概念模糊硬伤，建议作实质性修改后纳入固定层**

---

## 1. 评审立场概览

「提示词瘦、工具肥」切中了当前大语言模型在软件工程协作中最核心的执行退化病灶（“Lost in the Middle”效应与“海盗法典”现象）。在固定层确立该原则方向完全正确且高度迫切。

然而，待评草案在定义和执行边界上存在关键缺陷：
1. **因果逻辑倒置**：草案以“是否产生强制后果”来界定是否属于工具层，混淆了**管理意图（是否应强制）**与**工程可行性（能否由确定性程序判定）**。大量高危规则因缺乏自动化判定手段而无法直接工具化，若按草案标准将陷入分类悖论。
2. **常驻入口定义不彻底**：草案提出 `AGENTS.md` 保留核心约定，但未明确保留的是**高层指针与索引**还是**规则正文**。若将长篇约定正文直接留存常驻入口，将迅速击穿固定层 §4.1 的“一屏原则”。
3. **遗漏门禁总触发令**：工具无法在自身未被调用的情况下自发提醒 Agent 调用自己，因此入口必须且只能保留“双跑门禁”的元指令（§6.4）。

Participant 3 主张：重构分层判定标准，明确定位常驻入口的“指针化”结构，并将该原则作为**固定层新独立章节（建议为新 §11）**发布。

---

## 2. 对草案逐句表态

### 待评草案原文
> [句 1] AI Agent 的行为约束优先通过确定性工具（lint、格式化、类型检查、测试、CI 闸门）实现。  
> [句 2] 判断标准：若违反规则必须产生强制后果（阻止提交、阻止合并、阻止发布），则该规则属工具层；若违反规则仅作提示或由人工审查判断，则该规则属提示词层。  
> [句 3] AGENTS.md 或 CLAUDE.md 只保留无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议）和每会话必踩的操作提示，其余规则迁入对应工具配置或 CI 流程。

---

### [句 1] 逐句评析：【修改】
- **态度**：修改（强化并补齐立论前提）。
- **理由**：
  - 方向正确，符合 Matt Pocock 的 Dumb Zone（确定性工具）与 Smart Zone（AI 推理）分层思想。
  - 但表述缺少核心指导语境：应明确“行为约束不依赖提示词对机械规则的自觉遵守”，并与既有固定层 §6.1（“能写成闸门的纪律先写闸门，再写散文”）形成上位概念的呼应，将范围从代码静态检查拓展至广义确定性约束（含关系检查脚本、断言测试与 CI）。

### [句 2] 逐句评析：【修改】
- **态度**：实质性修改（重构判定逻辑）。
- **理由**：
  - **因果倒置缺陷**：“产生强制后果”是治理手段与执行策略，不是规则能否归入工具层的本质属性。
  - **技术可行性才是分水岭**：能否进入工具层，首先取决于该规则是否具有**确定性判定逻辑（Deterministic Decidability）**（即能否用语法树、类型系统、正则、图算法、退出码或断言程序进行无歧义判定）。
  - 若规则要求“提交必须符合业务需求设计”（强制要求，违者不得合并），但该检查高度依赖语义理解与人工审阅，它在当前技术条件下无法工具化，只能由提示词指导审查者（Reviewer）执行。若按草案“必须产生强制后果则属工具层”，此类规则将无处安放，甚至造成“以为属于工具层而在提示词中漏管”的真空。
  - 因此，必须重构为：**具确定性判定者归工具层（并施加强制阻断）；需语义权衡者归提示词层**。

### [句 3] 逐句评析：【修改】
- **态度**：修改（明确“指针化”与补齐元指令）。
- **理由**：
  - 草案列出“角色边界、文档归属、多 AI 协作协议”，若将这些约定的详细正文直接写在 `AGENTS.md`，文件长度依然会严重超标，重蹈覆辙。
  - 必须明确：`AGENTS.md` 只保留这些约定的**指针与寻路索引**（正文各自归入 `docs/agents/roles.md`、`docs/ARTIFACTS.md` 等，见 §1.4、§4.1）。
  - 草案遗漏了最重要的元指令：**门禁总触发令（§6.4）**。工具是处于 Dumb Zone 的被动程序，必须由常驻入口明确下达“执行者与审查者均须运行门禁”的强制指令。

### 专项问题深入分析

#### a) 判断标准是否清晰？
- **结论**：原草案标准**不清晰且无法直接执行**。
- **边界模糊情况剖析**：
  1. **文档同步检查（如“改了 X 却没动 Y”，§7.2）**：
     - *工具层边界*：文件的物理关联、对子声明在场性、相对链接有效性。本仓 `scripts/check_doc_pairs.mjs` 能确定性检测，属于工具层。即便无法自动修复，也可通过非零退出码阻断提交或提示失败。
     - *提示词层边界*：文档正文的语义准确性、技术阐述是否契合现实、是否包含逻辑矛盾。此部分无法工具化，必须由执行者自律和审查者（Reviewer）按 `CODING_STANDARDS.md` 语义把关。
  2. **命名规范**：
     - *工具层边界*：词法与结构命名风格（PascalCase、camelCase、特定文件后缀等），可由 linter（Biome/Ruff/ESLint）精确拦截，属工具层。
     - *提示词层边界*：命名是否准确传达业务概念、是否符合 `CONTEXT.md` 领域词汇表、是否存在歧义，属 Smart Zone，必须由提示词指导模型或人工审查。
  3. **代码注释与设计质量**：
     - *工具层边界*：公共接口 docstring 的存在性与格式校验，可工具化。
     - *提示词层边界*：注释是否解释了“为什么而非怎么做”（Google CL 规范，§5.2）、架构解耦是否合理，无法工具化，必须留在提示词与审查标准中。

#### b) AGENTS.md 瘦身边界如何界定？
- **无法工具化的核心约定真实清单**：
  1. **意图与目标定位入口**：从何处读取项目顶层定位（`docs/VISION.md`）。
  2. **角色防撞车边界与权限模型**：各角色允许写什么、禁止碰什么（§3.1, §3.2）。
  3. **产物唯一事实源寻路**：各类工程材料的物理归属与登记总索引（`docs/ARTIFACTS.md`）。
  4. **跨会话防腐与交接协议**：开工检查、收尾核验与不可伪造证据要求（`docs/agents/freshness-check.md`, `handoff-verification.md`）。
  5. **门禁总触发令与诚实原则**：强制双跑门禁，严禁跳步与伪造事实（§6.4, §7.6）。
- **草案三类是否完备**：
  - 不完备。草案遗漏了“门禁总触发令”与“诚实报告原则”。且“多 AI 协作协议”在固定层中属于低频的 §9 章程，日常开发常驻入口需要的是“角色防撞车与交付交接指引”，措辞需校正。

#### c) 「每会话必踩的操作提示」是否应留在 AGENTS.md？
- **态度**：**应极其克制地保留，且仅限 1-3 条顶层操作指针**。
- **典型正例**：
  - “开工先读 `docs/ARTIFACTS.md` 并执行文档防腐核验”（环境准备与寻路动作，前置于任何工具运行）。
  - “执行改动后必须本地运行门禁命令，并如实记录结果”（触发 Dumb Zone 的启动指令）。
- **典型反例（必须剔除）**：
  - 缩进、引号、换行、行宽等编码格式（迁入 linter/formatter）。
  - 提交头 Conventional Commits 正则匹配（迁入 `commit-msg` hook 脚本）。
  - “可测层必须写单元测试”（迁入 coverage/CRAP 计算器与审查者执行标准）。
- **不合格提示的去向**：确定性校验入 Hook/CI；语义指导入 `CODING_STANDARDS.md`；流程动作由具体 Skill（如 `implement`, `to-spec`）按需加载。

#### d) 固定层 vs 项目层
- **结论**：**必须纳入固定层**。
- **理由**：
  - “Lost in the Middle”是基础大模型的通用认知瓶颈，跨模型、跨语言、跨项目普遍存在。
  - 固定层是 `/lazypack-setup` 编译器的上位规则（§2.1）。确立该原则，是指导编译器如何裁减生成项目层文件的法理依据；若降为项目层默认值（§2.4），无法形成跨项目不可违背的刚性约束力。

## 3. 与既有条文的关系

### a) 与 §6（质量门禁）的关系
- **关系定性**：**上位概括与原则强化**。
- **分析**：
  - 现行 §6.1 提出“能写成闸门的纪律先写闸门，再写散文”，这是“提示词瘦、工具肥”在提交前 hook 的局部体现。
  - 新原则不仅涵盖代码与测试，更涵盖项目整体行为控制（包括常驻入口瘦身、检查器脚本、CI 闸门）。
  - 若并入 §6，需将 §6 升格为“质量门禁与确定性工具约束”，将新原则置于首条总纲，现行 §6.1-§6.5 顺延为其具体分支。

### b) 与 §4（什么放哪）的关系
- **关系定性**：**完全协调，无需新增产物大类**。
- **分析**：
  - 现行 §4.1 表中已明确：“编码标准 -> CODING_STANDARDS.md，由审查者执行 -> 工具能查的条目移进 lint 配置后删”；“AGENTS.md -> 只放指针 + 每会话必踩的几条 -> 超过一屏往下挪”。
  - 工具配置（如 `biome.json`, `ruff.toml`, Git Hooks）属于 §2.2 定义的项目层配置与执行辅助，在 `docs/ARTIFACTS.md` 现有分类中完全可以被容纳，无需在固定层增设抽象概念。新原则强化了 §4.1 对 `AGENTS.md` 超过一屏必须下移的纪律约束。

### c) 对 §1.3（只维护一份常驻规则文件）的影响
- **关系定性**：**深度一致，且消除多规则文件蔓延的根因**。
- **分析**：
  - §1.3 严禁平行维护 `.cursor/rules` 等复述文件。
  - 开发者平行建立规则文件的核心诱因，往往是 `AGENTS.md` 过长导致 AI 遗忘，从而试图通过特定 IDE 规则补充提示。
  - 通过新原则将机械规则剥离至确定性工具，`AGENTS.md` 保持极简高注意力，消除了多处复述的需求，直接巩固了 §1.3 的落地。

### d) 对 §2.3（编译器 `/lazypack-setup`）的影响
- **关系定性**：**明确了编译器的输出边界与演进目标**。
- **分析**：
  - 现有 `skills/lazypack-setup/templates/resident-entry.md` 仅 13 行，天生具备“指针化”特征。新原则将锁定这一契约，严禁未来 setup 向常驻入口回灌具体规则。
  - 强化 setup 对确定性工具的配置能力：除现有 TS（Biome/tsc/Vitest）和 Python（uv/ruff/ty/pytest）外，推动将 `commit-msg` 检查与文档对子检查逐步纳入 setup 自动化接线能力。

## 4. 实施影响评估

### a) 哪些内容应迁移至工具层？（具体清单）
1. **代码格式与语法风格规范**：缩进、分号、单双引号、行宽、import 排序规则 $\to$ 迁入 `biome.json` / `ruff.toml`，由 pre-commit 强制执行。
2. **危险模式与类型约束**：禁止 `any`、禁止未处理的 Promise、禁止未导出的死代码 $\to$ 迁入 linter/tsc 严格模式配置。
3. **提交说明词法结构**：Conventional Commits 校验、Angular 8 种 type 检查 $\to$ 迁入 `commit-msg` hook 或 `check_commit_msg.mjs`。
4. **测试断言与覆盖底线**：可测层逻辑变更必须运行测试、覆盖率/CRAP 门槛 $\to$ 迁入 pre-commit hook 中的 test 门禁及 `calculate_crap.mjs`。
5. **敏感凭据与密钥防泄露**：禁止提交 `.env`、私钥、API Key $\to$ 迁入 gitleaks 或受控 Git 预检脚本。

### b) 哪些内容无法工具化？（必须保留在提示词及原因）
1. **角色防撞车边界（§3.1, §3.2）**：
   - *原因*：Git 无法感知同一开发机器上的 Agent 身份，无法在 OS 层对“规划者”和“执行者”动态赋予不同的文件写权限。这属于高阶流程约束，必须由 Agent 入口提示词明确认知。
2. **知识归属与事实源寻路（§1.4, §4.1）**：
   - *原因*：将意图映射到八大逻辑区域并定位权威文档（如 ADR、VISION、登记册），属于典型的语义理解（Smart Zone），工具无法自动替代人类/AI 进行知识结构导航。
3. **架构与业务取舍（§7.4）**：
   - *原因*：何种决策属于“难逆转、没上下文会奇怪、真有取舍”，不存在能计算布尔值的数学公式，只能由 Smart Zone 角色权衡判断。
4. **证据诚实性契约（§7.6, VISION.md）**：
   - *原因*：“如实报告、不拼凑、未验证标明未验证”，这是对抗 LLM 谄媚与幻觉的元准则，工具只能验证具体结果，无法杜绝缺乏该准则时 Agent 产生的越权或瞒报行为。

### c) `/lazypack-setup` 需要做什么？
- **提问清单**：遵循“少问多探 (V04=NEEDED)”，**不增加任何哲学性或原则性提问**；仅在探测到缺失具体工具时，继续提供 slot 级别的补缺提问。
- **文件生成**：
  - 确保生成的 `AGENTS.md` / `CLAUDE.md` 严格维持为纯指针与总触发令（与 `resident-entry.md` 对齐）；
  - 将生成的 `CODING_STANDARDS.md` 彻底净化，严禁残留任何工具能查的代码格式细节，仅保留双轨制与审查者职责。

### d) 现有模板是否需要更新？
- `skills/lazypack-setup/templates/resident-entry.md`：保持现有极简结构，无需大改；可微调注释，声明符合「提示词瘦、工具肥」原则。
- `skills/lazypack-setup/templates/CODING_STANDARDS.md`：强化 §1 原则，明确写明“审查者不审查 linter 已覆盖项，仅审查语义、可测层断言与架构约束”。
- `skills/lazypack-setup/templates/RELEASE.md`：保持稳定，强调提交格式由 hook/CI 校验。

## 5. 最终条文建议

Participant 3 认为待评草案逻辑存在缺陷，**反对直接采纳草案原文**，建议使用以下修改后的完整替代文本：

```markdown
## §11. 提示词瘦、工具肥

11.1 AI Agent 的行为约束优先通过确定性工具（格式化、lint、类型检查、自动化测试、关系检查脚本与 CI 闸门）实现，不依赖提示词对机械规则的自觉遵守。
11.2 分层判定标准：
  - **工具层（Dumb Zone）**：凡具有确定性判定逻辑的规则（能通过语法树、类型系统、状态、正则、算法或程序断言无歧义判定者），必须下沉至工具配置、Git Hook 或 CI 流程；凡违反必须阻断的致命约束，赋予阻止提交、阻止合并或阻止发布的强制后果。
  - **提示词层（Smart Zone）**：凡依赖上下文语义理解、设计权衡、架构演进或价值判断的规则，由提示词声明并由对应角色（规划者、执行者、审查者）执行。
11.3 常驻入口瘦身：`AGENTS.md`（或 `CLAUDE.md`）遵循一屏原则（§4.1），仅保留高注意力区不可替代的内容：
  - 核心约定的指针与寻路索引（角色边界、文档归属、防腐与交接协议）；
  - 门禁总触发令（执行者与审查者双跑门禁，§6.4）；
  - 每会话前置必踩的操作入口与诚实报告底线。
  具体的编码标准、格式细节与执行脚本一律移入对应工具配置、专用文档或 CI 流程，禁止在常驻入口中堆叠机械规则正文。
```

## 6. 章节归属建议

Participant 3 建议：**成为新 §11（独立章节）**。

### 理由对比：
1. **为何不建议并入 §4（什么放哪）**：
   - §4 的核心是代码库物理资产与知识形态的生命周期分类（词汇表、ADR、工单、代码等）。
   - 「提示词瘦、工具肥」不仅决定内容放哪，更决定了 **Agent 行为控制权的分配机制**（LLM 提示词 vs 确定性进程），超出了文档分类的范畴。
2. **为何不建议并入 §6（质量门禁）**：
   - §6 侧重于代码开发中的静态检查、测试与审查者职责。
   - 但新原则不仅约束“代码门禁”，更直接约束了“提示词文件的撰写与裁剪标准（AGENTS.md / roles.md / 编译器逻辑）”。若缩限在 §6，极易被窄化理解为单纯的“CI/Hook 配置指南”，削弱了其作为提示词瘦身法理依据的地位。
3. **独立为新 §11 的体系价值**：
   - 固定层现有结构中，§1-§3 确立基础与角色，§4-§7 确立工程实践，§8-§10 确立自演进与治理。
   - 新设 §11 作为“系统治理元原则”，统领人机协作中的注意力与执行力分配，与 §1（地基与边界）呼应，地位清晰，检索明确，为后续各 Skill 的瘦身提供全局上位法依据。
