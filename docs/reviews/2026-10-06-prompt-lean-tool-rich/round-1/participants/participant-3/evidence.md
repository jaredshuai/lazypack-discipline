### 1.4 外部文献与工程实证
- **Lost in the Middle 现象**：Liu et al. (2024), *Lost in the Middle: How Language Models Use Long Contexts*, Transactions of the Association for Computational Linguistics (TACL). 证实无论模型总上下文窗口多大，对长上下文处于中间位置（20%~80% 深度）的信息检索准确率和注意力权重呈现显著 U 型退化。
- **Uncle Bob × Matt Pocock 实践访谈**：在提示词中堆积详尽准则时，LLM 会将规则降级为“海盗法典（guidelines，仅供参考）”而非强制法则；只有通过编译器、测试套件与静态分析器的硬性失败才能维持系统边界。
- **Smart Zone vs. Dumb Zone 架构模型**：Matt Pocock 引用 Dex Horthy 的概念：
  - Dumb Zone（确定性工具层）：执行成本极低、零随机性、无幻觉、可重复、直接阻断。
  - Smart Zone（认知决策层）：高推理成本、存在概率漂移、擅长权衡与合成，但极不擅长机械守纪。

## 2. 关键论证步骤（Argumentation Steps）

### 论证步骤 1：从认知退化（U 型曲线）推导“提示词瘦”的必然性
1. **注意力有限性**：大语言模型在单次推理中，Prompt 开头（System instructions 顶部）与末尾（最新用户输入）享有最高注意力权重。
2. **规则中段吞没**：当 `AGENTS.md` 堆砌了 50~100 条机械规则（如格式规范、单引号/双引号、路径别名等）时，这些规则必定落入 U 型曲线的中段盲区。
3. **推论**：任何企图靠在常驻规则文件中“详尽列举全部纪律”来约束 Agent 的做法，在信息论和注意力机制上都是不可持续的。常驻入口必须做到极致的“瘦”，只保留最高优先级的元指令与索引指针。

### 论证步骤 2：剖析“强制后果”作为划分标准的因果倒置缺陷
1. **原草案逻辑**：
   $$\text{若违反规则必须产生强制后果} \implies \text{该规则属于工具层}$$
2. **反例归谬**：
   - 规则 A：“严禁在未经授权的情况下删除核心生产数据库脚本”。
   - 属性分析：该规则在工程管理上绝对必须产生强制后果（阻止合并、阻止部署）。但如果当前仓库没有针对特定 SQL 破坏性语法的 AST 扫描工具，该规则只能由人工审查员在 PR 中判断。
   - 矛盾产生：若按原草案，规则 A 被判定为“工具层”，但由于工具层缺席，而提示词层又因草案认为“该规则不属提示词层”而将其移出，导致该绝对致命规则处于无人监管状态。
3. **纠正后的判定逻辑**：
   $$\text{规则是否具确定性可判定性（Decidability）} \implies \begin{cases} \text{是} & \to \text{下沉工具层（致命者接强制阻断）} \\ \text{否} & \to \text{保留提示词层（由 Smart Zone 角色把关）} \end{cases}$$
   区分“判定机制”（工具可行性）与“处置策略”（强制后果），逻辑方能自洽。

### 论证步骤 3：论证常驻入口必须“指针化”，而非内嵌正文
1. **现状对比**：
   - 若将“角色边界（§3 表格）”、“文档归属（§4.1 表格）”、“协作协议（§9 章程）”直接塞入 `AGENTS.md`，文本量立即突破 200 行，瞬间摧毁 §4.1 的“超过一屏往下挪”底线。
2. **本仓与模板实证**：
   - 本仓 `AGENTS.md`（10 行）与模板 `resident-entry.md`（13 行）均证明：**最有效的常驻入口形态是“事实源指针清单 + 双跑门禁元指令”**。
   - Agent 开工时通过指针去读取 `docs/ARTIFACTS.md` 与 `docs/agents/roles.md`，实现按需加载（On-demand retrieval），既保护了核心上下文窗口，又确保了长规则只活在单一权威位置（§1.4）。

### 论证步骤 4：论证“门禁总触发令”不可被工具替代的元循环悖论
1. **工具的被动性**：linter、pytest、biome 是静态 CLI 或服务，不具备主动唤醒 Agent 的意识。
2. **Agent 的行为特征**：在长会话中，Agent 最常见的违规模式不是“运行了门禁但忽略报错”，而是“根本不运行门禁，直接宣布完成”。
3. **结论**：必须在最高注意力区的 `AGENTS.md` 中明文保留 §6.4 的元指令：“执行者和审查者都必须跑门禁”。这是一条无法工具化、但能激活工具层的提示词。

### 论证步骤 5：评估新 §11 独立成章的系统收益
1. **独立成章（新 §11）**：
   - 将“提示词瘦、工具肥”立为上位原则，同时辐射 §1（常驻入口规范）、§2.3（编译器生成规范）、§4（文档裁剪规范）与 §6（质量门禁实现）。
   - 避免将该原则仅仅理解为“写 pre-commit hook”，而是升华为整个 lazypack 生态处理 LLM 认知边界的根本哲学。

## 3. 待裁决的边界情况（Border Cases for Triage）

以下是在第二轮和第三轮讨论中需要各参与者与维护者重点裁决的边界议题：

### 边界 1：半自动化/半工具化脚本的层级归属（如 `check_doc_pairs.mjs`）
- **现象**：本仓的 `node scripts/check_doc_pairs.mjs` 和 `check_commit_msg.mjs` 具备确定性算法和退出码（0/非零），但目前在仓内**未接入 Git Hook，亦未接入 CI**（每次由 Agent 手动执行）。
- **裁决点**：这类“有判定能力但未强制挂载闸门”的脚本，究竟属于工具层还是提示词辅助工具？
- **Participant 3 倾向**：属于工具层能力。其判定逻辑已从散文固化为代码；未接 hook 仅是当前工程门禁的接线状态差异（§2.3），其本质已属 Dumb Zone，应优先推动其接入 hook 或 CI 阻断。

### 边界 2：小众语言或初创项目的“工具匮乏期”降级策略
- **现象**：在某些小众开发环境或多语言混编项目中，缺失健全的类型检查器或 linter，导致某些本可确定性检测的规则（如命名规范、import 格式）无法工具化。
- **裁决点**：在工具链缺失时，这些机械规则是否应临时回流至 `AGENTS.md`？
- **Participant 3 倾向**：**坚决不回流至 `AGENTS.md`**！应回流至 `CODING_STANDARDS.md`（由审查者执行），并在产物登记册中注明工具缺失。常驻入口 `AGENTS.md` 必须对机械规则保持永久免疫，否则一旦开口子就会不可逆膨胀。

### 边界 3：软性警告（Warnings / Advisories）的归属
- **现象**：linter 中大量规则被配置为 `warn` 级别（例如性能建议、弃用提醒、复杂度假阳性），它们不会导致构建失败（不阻断 exit 0）。
- **裁决点**：若按原草案“必须产生强制后果才属工具层”，这些 warning 是否被开除出工具层？
- **Participant 3 倾向**：这再次证明了原草案“以强制后果划分工具层”的谬误。Warning 产生于确定性工具，属于工具层的建议输出，可作为审查者在 Smart Zone 进行综合判断时的输入材料。

### 边界 4：审查者（Reviewer）角色的职责动态边界
- **现象**：固定层 §6.3 规定“`CODING_STANDARDS.md` 由审查者在审查时执行；工具能查的不写进去”。
- **裁决点**：随着工具链不断完善（例如新引入了更强的 linter 插件），审查者的审查清单如何动态同步？
- **Participant 3 倾向**：严格落实 §4.1“工具能查的条目移进 lint 配置后删”。新规则一旦工具化并具备门禁能力，审查者文档中对应的散文条目必须物理删除，实现 Dumb Zone 对 Smart Zone 的单向替代，持续释放审查者的认知带宽。
