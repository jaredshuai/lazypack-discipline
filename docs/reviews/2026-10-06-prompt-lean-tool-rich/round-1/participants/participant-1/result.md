## 0. 总体立场

**方向同意，草案判据不同意。建议改写后并入 §6，不立为新 §11。**

三句话概括：

1. 草案选错了分类轴。「违反必须产生强制后果」判的是**门禁是否接线**，不是**规则该住在哪一层**。本仓已有一条更精确、且已在执行的轴：**可判定性**（路径、哈希、正则、存在性、退出码）。判据应换成后者，把「强制后果」降级为独立的第二步问题。
2. 草案的实质内容**已在既有条文与编译产物中存在**（§6.1、§6.3、§7.2、§4 表三行，以及 `CODING_STANDARDS.md` 模板 §1.1）。新增独立 §11 会直接撞上 §1.4「每条纪律只活在一处」。
3. 草案有一个会导致**双事实源**的可执行性缺陷：「其余规则迁入对应工具配置」若照字面执行，与本仓 §5.1 的现行设计相反——`check_commit_msg.mjs` 在运行时从 `docs/DECISIONS.md` §5.1 抽取 type 词表，条文正文就是规则源。必须把「规则声明层」与「规则执行层」分开写清，否则通过该条会让维护者被迫在 lint 配置里另抄一份口径，违反 §4.1。

## 1. 对草案逐句表态

草案拆为四句（S1–S4）。

### S1「AI Agent 的行为约束优先通过确定性工具（lint、格式化、类型检查、测试、CI 闸门）实现。」

**修改。**

- 同意「优先」的取向。
- 但措辞把工具限定在四种代码门禁（lint/format/type/test/CI），而本仓已投产的确定性工具是**文档与流程类**：`scripts/check_doc_pairs.mjs`（P1–P8）、`scripts/check_commit_msg.mjs`、`scripts/handoff_manifest.js`、`skills/lazypack-harvest/scripts/sanitize_helper.js`。括号里的枚举会把这些排除在外，而这恰是本仓实际收益最大的一类。
- 改为「确定性工具」为类名、不闭集枚举四种代码门禁；并明确工具需要判定口径时**读取条文/声明正文**，不在配置里另抄。

### S2「判断标准：若违反规则必须产生强制后果（阻止提交、阻止合并、阻止发布），则该规则属工具层；若违反规则仅作提示或由人工审查判断，则该规则属提示词层。」

**删除并重写。这是草案最弱的一句。**

四个缺陷：

1. **轴错位。** 该判据把「该不该由工具执行」和「有没有接成闸门」压成一件事。一条规则完全可以：可被机器判定、检查器也写好了，但尚未接闸门。本仓正是这种状态——`docs/agents/doc-pairs.md:14` 与 `docs/agents/commit-msg-check.md:7` 都明写「未接 hook、CI 或定时器」，`git config core.hooksPath` 未设置，仓库无 `.githooks/`、无 `.github/workflows`（仅有供复制的 `templates/.github/workflows/`，模板注释自陈「本仓自身不运行该闭环」）。
2. **产生第三态。** 「必须产生强制后果」可读成规范（应当有闸门）或描述（已有闸门）。按描述读法，S2 的前件对本仓两条规则都不成立，于是 §5.1 提交头格式、§7.2 文档对子既不属工具层（无强制后果）也不属提示词层（并非仅作提示）——判据不封闭。
3. **反向暴露出治理冲突。** `docs/agents/freshness-check.md:68` 明写「要把确定性检查接入门禁，须另有实施票写明范围和授权。本文件不授权接入 hook、CI、定时任务」。草案若把「必须产生强制后果」当成归属判据，等于让条文自己主张接闸门，与现行的**授权边界**冲突。接线须继续留作独立一步。
4. **与 §6.4 直接打架。** §6.4 要求「`AGENTS.md` 明写：执行者和审查者都必须跑门禁」，`skills/lazypack-setup/templates/resident-entry.md:7` 也确实把这句明文写进常驻入口托管区。这条规则**当然可工具化**（门禁本身即工具），按 S2 应迁入工具层；但 §6.4 明确要求它留在提示词里，靠对抗性双跑压概率。S2 会把这条迁走。草案列举的三类保留项也不含它，覆盖不到。

**建议的替代判据（三段，见 §4 条文全文）：① 规则声明只有一个家；② 可判定性决定执行载体；③ 门禁接线是独立一步，需另票授权。** 其中②沿用本仓已有口径：`docs/VISION.md:31`「已经声明、并且能用路径、哈希或正则判定的关系交给机器检查；需要理解含义的影响，由当轮执行和审查处理」；`docs/agents/doc-pairs.md:24`「机器判定只使用路径、哈希、正则与存在性，不做语义理解」。

也就是说：**新条文最有力的判据在仓库里已经写好了，草案应当引用它，而不是另造一个较弱的。**

### S3「AGENTS.md 或 CLAUDE.md 只保留无法工具化的核心约定（角色边界、文档归属、多 AI 协作协议）和每会话必踩的操作提示，其余规则迁入对应工具配置或 CI 流程。」

**修改。** 保留意图，改两处。

- 「只保留无法工具化的核心约定」措辞不自洽：若以「无法工具化」为筛选条件，那么可工具化的约定就一律不得出现在常驻文件——这与 S3 自己要求的「每会话必踩的操作提示」并存时相互抵消；也与 §6.4 冲突（见上）。筛选条件应是**「每会话都要在场、且缺席会造成越界或谎报」**，不是「无法工具化」。
- 「迁入对应工具配置」须限定为「迁入执行器」，不含把判定口径移出条文（S1 理由 3 的双源风险）。

草案列举的三类**不完备**，且其中一类归属可议：

| 草案列 | 表态 | 理由 |
|---|---|---|
| 角色边界 | 保留 | §3.1–3.2「允许写」列是防撞车边界，靠当轮在场生效；工具只能事后判定路径越界 |
| 文档归属 | **降级为指针** | §4 表 + `docs/ARTIFACTS.md` §1 已是权威正文，且 P4/P5 已机器检查其链接可解析。常驻文件里只该有入口，不该有归属规则本体 |

草案**漏掉四项**，按我的筛选条件都该常驻：

1. **指针与读取顺序**（本仓 `AGENTS.md:5-9` 全是这一类；这是常驻文件的实际主体，草案反而没列）；
2. **必须明文可见的门禁要求**（§6.4）；
3. **停止并交回用户的条件 + 如实报告要求**（§7.5、§7.6、§2.3「不得宣称门禁已生效」、`skills/lazypack-setup/SKILL.md:23` 核心原则 5）——这类规则的失效后果是**谎报交付**，是最高危的，必须每会话在场；
4. **脱敏与公开/私有边界**（§8.3、§10.2、§10.3）。`sanitize_helper.js` 头部注释正是这个分工的现成范式：「`noKnownViolations = true` does NOT equal authorization to dispatch without host agent review」——工具给补充检测信号，语义审查仍在人/Agent 侧，两者叠加而非二选一。

### S4（背景与动机第 4 条）「当前痛点：`AGENTS.md` 越写越长（已超一屏）」

**删除——对本仓不成立，且诊断错了问题。**

- 实测：`AGENTS.md` 共 9 行 / 799 字节（`wc` 结果）。§4 表的更新触发是「超过一屏往下挪」，本仓远未触发。草案把一个不适用于本仓的痛点写成动机，评审时会削弱条文可信度。
- 更关键：**真正的注意力成本不在常驻文件的长度，而在指针扇出后的读取义务。** `AGENTS.md:5` 第一条就是「开工先读 [文档归属与产物登记册](docs/ARTIFACTS.md)」，而 `docs/ARTIFACTS.md` 实测 **549 行 / 238,232 字节**；其 §3 表格单个单元格（VISION.md 登记行）就塞进了十条以上带日期的裁定叙述。这恰好是 Lost in the Middle 的形态：规则被塞进超长正文的中段。
- 所以条文应当管的是**「常驻入口指向的正文，其体量与整读义务」**，而不只是「规则条数」。按草案现文，把 5 条规则迁进 lint 后，仍可以让 AGENTS.md 用一条指针要求整读 238 KB——草案判据对此完全无感。
- 另一处体量：`skills/lazypack-setup/SKILL.md` 51,583 字节 / 337 行，本身就是提示词层制品；它受 §1.4 约束，但草案的「AGENTS.md 瘦身」框架也覆盖不到 skill 正文。

## 2. 特别问题的回答

### a) 判断标准是否清晰？

不清晰（见 S2 的四点）。边界情况的处置，按我建议的可判定性轴：

| 边界情况 | 判定 | 说明 |
|---|---|---|
| 文档同步检查 | **可判定部分属工具，语义部分属审查** | 本仓已这样切：P1(哈希)、P2(git blob)、P3(版本串)、P4/P5(链接存在) 交工具；「目标有没有被写成已交付」「历史有没有被改写」在 `freshness-check.md` §1 明确留给人工阅读栏 |
| 命名规范 | 拆两条：路径/前缀正则 → 工具；语义命名 → 审查者 | 混合规则不得整条判给一层，必须**按判定的那一句**分流 |
| 代码注释质量 | 属审查者 | 「无法用路径、哈希、正则、存在性或退出码判定」即落入语义区。注意工具可查「注释在场/长度」，但那不是质量 |
| 提交头格式（§5.1） | 工具，**且条文仍是规则源** | 现行实现即如此：脚本运行时抽取词表，`--rules` 只切换哪份文件供词表。这是本条最该引用的先例 |
| 未接闸门的工具检查 | **归属明确是工具层，接线状态另行如实报告** | 这正是把 S2 拆成两轴的收益：`check_commit_msg.mjs` 存在但未接 hook，不改变它属工具层这一归属 |

### b) AGENTS.md 瘦身边界

见 S3。筛选条件改为「每会话必踩、缺席即越界或谎报」；保留清单补四项、降级「文档归属」为指针、把 §9 从 AGENTS.md 清单中移出。

### c) 「每会话必踩的操作提示」是否应留在 AGENTS.md？

**应留。** 典型例子（均可指到既有条文）：

- 「开工先读登记册 / 按防腐检查留检查记录」（本仓 `AGENTS.md:5-6`）——顺序性知识，工具无法决定你何时该读；
- 「执行者和审查者都必须跑门禁」（§6.4）；
- 「未接线、不适用、运行失败按事实报告，不宣称门禁已生效」（§2.3、setup 核心原则 5）；
- 「未验证的标未验证；工具卡住如实报告，不拼凑不跳步」（§7.5、§7.6）；
- 「两角色不得写同一类文件」（§3.2）；
- 「争议或未分类文件原地保留、列清单交裁决」（§3.4 第④步）。

不该留的：判定口径的细节正文、状态词表、路径表——这些有唯一权威正文，常驻文件只给指针。

### d) 固定层 vs 项目层

**该进固定层，但只进「三轴分离」这一条，不进任何具体载体清单。**

理由：可判定性优先是跨项目的执行载体选择原则，属 §9.1「改固定层条文」范畴；而「哪些槽位接成阻止提交/阻止合并/阻止发布」依赖项目工具链与授权，属 §2.2 项目层，且已由 `freshness-check.md:68` 的授权边界管着。草案若写入 CI 闸门的具体形态（构建红、PR 挂），就越过了 §2.4 的层级。

## 3. 与既有条文的关系

### a) 与 §6（质量门禁）：补充 + 局部重复，应合并而非并列

重复面：

- §6.1「能写成闸门的纪律先写闸门，再写散文」——已是工具优先，且**已含顺序**；
- §6.3「工具能查的不写进去」——已是同一判据的散文版本；
- §6.2 已定默认工具；§6.4/6.5 已管双跑与双轨。

补充面（草案真正新增的只有这一件）：把 §6.3 的范围从 `CODING_STANDARDS.md` **扩到常驻规则文件**。这是有价值的推广，但只需扩写既有句子，不需要一章新条文。

合并方式建议：新增 §6.6 承载「三轴分离 + 常驻必踩清单」，并把 §6.3 末句改为指向 §6.6，避免两处各说一半。

### b) 与 §4（什么放哪）：需要新增一行，草案没提

**§4 表现在没有「工具配置与门禁接线」这一类。** 而本仓确实存在未登记归属的一类制品：`scripts/*.mjs`、`skills/lazypack-setup/templates/pre-commit.sh`、`templates/.github/workflows/*.yml`、`templates/config/*.timer|service`、`templates/scripts/nightly-mutation-runner.sh`。

于是「其余规则迁入对应工具配置」在现行 §4 下**没有登记的目的地**——迁入即成为 §4.3 所说的「册上查不到」项。草案通过后 §4 必须补一行，否则新条文与 §4.1「一个东西只有一个家」直接冲突。这是实施前必须先裁的一项。

同步改 §4 的 `AGENTS.md` 行：现为「只放指针 + 每会话必踩的几条 / 超过一屏往下挪」——「一屏」是纯长度判据，与新条文的载体判据是两个轴，并存会让维护者不知以哪个为准。改为指向 §6.6 的必踩清单，长度触发词保留为兜底。

### c) 对 §1.3 的影响：不冲突，但要防止新条被用来正当化平行复述

§1.3 只管「一份常驻文件」，草案同样只约束常驻文件，方向一致，不改变执行。

风险在 §1.4：一旦「工具肥」被理解成「规则在工具配置里再写一份」，就会生出 `AGENTS.md` + lint 配置的双事实源，正是 §1.4 与 §4.1 禁止的。条文中必须写「工具读取条文/声明正文作为口径，配置不另抄」——现成的正面样本是 `commit-msg-check.md` §词表抽取 与 `doc-pairs.md`「判定算法仍在脚本中，脚本不复述字段正文」。

### d) 对 §2.3（`/lazypack-setup`）的影响：需要，但不是「生成更轻的 AGENTS.md」

`resident-entry.md` 模板已是 4 个条件指针 + 1 条明文门禁，无进一步瘦身空间（模板 L8–L11 是 `__*_POINTER__` 条件渲染，F05/P7 逻辑已防止死链）。

需要动的两处：

1. **§2.3 要写明「接线须有授权」**，把 `freshness-check.md:68` 的边界升为固定层一句，否则 §6.6 主张工具优先时，setup 会被读成可以擅自接 hook/CI。现有 setup 已有对应保护（全拒绝分支「绝对不创建 `.githooks/pre-commit`、不配置 `core.hooksPath`」，`SKILL.md:131-134`），条文应与之一致，不必新造。

## 4. 实施影响评估

### a) 若草案通过，哪些内容应迁移

对本仓而言，**`AGENTS.md` 没有可迁移的散文**（9 行全是指针与一句门禁明文，属必踩项）。真正的迁移红利在「已判定但未接线」，即接线而非搬家。给出具体条目：
