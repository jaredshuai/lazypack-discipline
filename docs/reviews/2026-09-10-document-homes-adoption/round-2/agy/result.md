## 1. 互评总览与核心认同/异议声明

三席在 R1 独立意见中展现了高度共识：八区逻辑导航不强加物理目录、现行六状态词保持闭环、单入口规则、前置双检强约束（`issue-tracker.md` 非 setup 首创）、关票不等于删除授权、清道夫受控于四步关卡、保留/迁移双模式平级并存、CHANGELOG 非完整验收台账。

### 1.1 本席位之核心认同声明（认同主对手 Cursor/Grok）
- **具体认同 1（恢复“事件驱动，不用定时器”）**：高度认同 Cursor/Grok 在 §3.4 恢复 0.2.0 原文“事件驱动，不用定时器”（CG R1 §3.4）。F1 候选草案脱落此句纯属排版编辑疏漏，绝非有意放宽为允许定时器或后台轮询。恢复此句坚守了纪律极简与事件驱动的核心原则。
- **具体认同 2（ARTIFACTS 保护与 Section 3 隔离）**：高度认同 Cursor/Grok 在 §2.3/§4.4 中关于“登记册处于 PAUSE/BROKEN 时严禁写穿”及“八区映射写入 Section 3 且不改动 Section 2 四槽”的保护约束。这确立了跨项目的机器修改安全底线，防止自动化工具破坏人工资产或破坏受管块指纹。

### 1.2 本席位之核心异议声明（异议 Qoder CLI 与 Cursor/Grok 各一处）
- **有据异议 Qoder CLI（§1.1 措辞收窄）**：坚决反对 Qoder 将“更新”收窄为“状态更新”（Qoder R1 §1.1）。在实际地基流程中，工单消费者除变更 `Status:` 词汇外，更执行验收条件动态追加、评论日志追加及父子工单层级地图维护（如 wayfinder）。收窄为“状态更新”将导致工单内容与拓扑关系的消费者逃逸前置依从性核查。
- **有据异议 Cursor/Grok（§4.1 回退假定）**：反对 CG 在 §4.1 耐久行中引入“未声明时沿用地基本地默认 `.scratch/<feature>/`”（CG R1 §4.1）。在 `lazypack-setup` 体系下，第 1 步前置双检强校验 `issue-tracker.md` 必须存在且非空，未声明配置根本无法通过门禁；且对使用 GitHub/Linear 等外部 tracker 的项目，“未声明沿用 .scratch”会产生将远程工单误降级为本地草稿的严重逻辑误导。

## 2. 核心分歧议题 A–E 逐项深入审阅与收敛

### 议题 A：§4.1 耐久家（需求、工单与规格落点、缺口处理与后果比较）
- **各方方案比较**：
  - Cursor/Grok：以 tracker 声明为准；未声明沿用 `.scratch/`；`docs/work/` 是需按 1.1 核查后才采用的推荐落点，未核查不得当作已生效的家。
  - Qoder CLI：保留候选“标准默认：`docs/work/<feature>/`（需适配）；保留模式见 `issue-tracker.md`”。
  - AGY：以 `issue-tracker.md` 实际声明为准，定性为“标准推荐（需核查消费者适配）”，保留模式平级并存。
- **具体后果比较与本席裁决**：
  - *后果 1（若按 Qoder 保留“标准默认”）*：在 `to-tickets:62` 物理写死 `.scratch/` 的事实下，项目层若误将 `docs/work/` 当作已生效的默认，新开工单仍会被上游写回 `.scratch/`，造成双重权威与幽灵工单混乱。
  - *后果 2（若按 CG 写入“未声明沿用”）*：违背 setup 前置双检硬约束，且外部 tracker（如 GitHub Issues）无需也不应回退至 `.scratch/`。
  - *适配未通过时的流程连续性*：当 1.1 消费者核查未通过（存在写死）时，**工作流在保留模式下无缝继续**：工单仍在既有声明路径（`.scratch/<feature>/`）下创建与更新，审查与实现正常执行，清道夫 Gate 1/2 将其作为权威原件予以阻断保护，不发生误清。
- **收敛后精确表文**：
  > `| 需求、工单与规格 | 以 docs/agents/issue-tracker.md 声明的实际位置为准（标准推荐 docs/work/<feature>/ 须按 1.1 核查消费者；未核过或保留模式维持既有声明路径） | 按保留目的与有效引用判断；关票不自动构成删除授权 |`
- **与 0.2.0 义务变化**：新增工单落点由 tracker 声明管辖、推荐落点须前置核查、关票不构成删除授权之义务。

### 议题 B：§2.3 / §4.4 保护文字与 Section 3 承载边界（固定原则 vs 模板细节）
- **各方方案比较**：
  - Cursor/Grok：在 §2.3/§4.4 明确写入 Section 3、不改四槽、无原件不虚构、PAUSE/BROKEN 不写穿、工单迁移受 1.1 约束。
  - Qoder CLI：保留原候选，主张 Section 3 与 PAUSE 属于模板与实施细节。
- **固定原则 vs 模板细节界定**：
  - *跨项目固定原则*：①“PAUSE/损坏状态绝不写穿”是保护用户人工成果与异常中断的铁律；②“八区映射承载于非受管协作区（Section 3），严禁改动 Section 2 受管插槽”是保证受管块指纹（`header.fp`）不被破坏的生命线；③“无原件不虚构登记”杜绝了 AI 预建空文档。这些必须升格为固定层条文。
  - *模板实现细节*：具体字段正则、表格列宽、占位符命名等留模板与实施规格。
- **收敛后精确表文**：
  - **§2.3**：`...写出 docs/ARTIFACTS.md 时须读取并登记 docs/agents/issue-tracker.md，并在其非受管协作区（Section 3）登记已存在的各逻辑区域实际原件，不改动 Section 2 受管槽；无原件不虚构登记；登记册处于 PAUSE 或损坏时只报告待裁、严禁写穿。默认保留既有合理位置（保留模式），并提供迁至标准推荐路径的治理选项（迁移模式）...`
  - **§4.4**：`4.4 存量项目的非标路径在初始化时默认保留并在登记册 Section 3 登记；登记册处于 PAUSE、损坏或未托管时只报告待裁、不写穿。治理迁移选项触发时，AI 须整体输出源路径至目标路径的映射清单、链接与附件影响评估，经用户整体审阅确认后执行，不逐文件打扰。工单类迁移另受 1.1 消费者核查约束；未通过前保持保留模式。`
- **与 0.2.0 义务变化**：setup 编译器与迁移流程被施加了 PAUSE 阻断保护、真实原件核实、Section 3 隔离写入之安全义务。

### 议题 C：§3.4 恢复“事件驱动，不用定时器”
- **对方方案摘要**：CG 建议恢复 0.2.0 原文；Qoder 未明确表态。
- **本席判定与理由**：**完全接受 CG 提议**。条文删除该句属于编辑无意脱落。lazypack-discipline 自诞生起便立足于事件驱动响应，彻底摒弃任何常驻后台的轮询扫描器或 cron 定时任务。恢复该句既符合历史意志，又彻底封堵了未来借“清道夫按需扫描”之名偷偷引入定时器守护进程的漏洞。
- **收敛后精确表文**：
  > `3.4 书记员在每张票关闭后扫一遍；清道夫在发版前或按需扫一遍。事件驱动，不用定时器。清道夫执行清理时必须严格遵守四步清理关卡：①排查是否在登记册、工单配置或 .out-of-scope/ 中声明为权威原件或持久来源；命中登记或权威原件者不得当作可丢弃缓存自动清除，是否归档或删除仍依保留目的、有效引用与特定授权判断；②核验内容是否处于活跃状态（读取项目 issue-tracker.md 与 triage-labels.md 实际声明的状态词，不写死状态字符串；状态无法确定时报告未知并暂停自动清理，不改写原状态，不擅自视为活跃）；③按保留目的与复现条件鉴别是否为可丢弃缓存（严禁仅凭文件名或目录名推定，严禁将 specs、issues、out-of-scope 记录视为临时缓存）；④存在争议或未分类文件原地保留并列清单请用户裁定，裁决前不移动、不归档。严禁仅凭目录名或关票事件一键物理清空。`
- **与 0.2.0 义务变化**：维持原有“事件驱动，不用定时器”纪律；新增清道夫清理时的四步关卡拦截义务。

### 议题 D：§1.1 消费者核查之“更新”措辞范围
- **对方方案摘要**：Qoder 建议将“更新”改为“状态更新”；CG 维持“更新”。
- **本席判定与理由**：**坚决反对 Qoder，维持“更新”全称**。在真实开发中，执行者（implement）与规划者（to-spec/wayfinder）对工单的写入远不止修改 `Status:`：包括更新 Acceptance Criteria 验收清单、记录阻断原因、调整优先级、挂载子任务 ID。若将前置核查限制在“状态更新”，则只要某个技能不改状态仅改内容，就会被视为不受核查约束，一旦其硬编码 `.scratch/`，便会导致工单正文与内容撕裂。
- **收敛后精确表文**：
  > `1.1 地基是 Matt Pocock 的 skills。本包只补它没管的部分，不替代、不并行复述。项目层用 docs/agents/issue-tracker.md 声明实际工单位置；使用非上游默认位置前，须核查开票、取票与更新消费者是否遵从该指引；存在写死路径时记为受限，不能只因指针已改就宣称适配完成；不侵入修改全局安装副本。`
- **与 0.2.0 义务变化**：新增使用非默认路径前的前置依从性核查义务（标“是”）。

### 议题 E：日常映射维护权责划分
- **三方共识梳理**：
  - 清道夫权限封死：“只清不登、只删移动、不新增”，绝对不具备向 `docs/ARTIFACTS.md` 写入新登记行的权限；
  - setup 编译器：仅在初始化或受管块重跑时，将已存在的物理原件登记入 Section 3；
  - 书记员：在关票后或文档集中巡视时，依据既有 `docs/` 规范维护 Section 3 登记行；
  - 执行者：仅写入与当前工单提交 diff 直接相关的文档行。
- **本席裁定**：现行 §3.1 角色权限防撞车矩阵（规划者/执行者/审查者/书记员/清道夫）完全闭环，无需引入“文档管理员”等冗余角色，条文明确清道夫权限即已足够。
