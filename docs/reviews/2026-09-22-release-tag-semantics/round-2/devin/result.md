## 一、驳 qoder（分配对手）

### 1.1 命名之争：方向让步，理由驳回

**qoder 主张**：本轮把「平台段」统一改名「项目段」，同步 `DECISIONS.md:66`/`:84`/`:133` 与快照。
**我第一轮主张**：回退「平台段」与 §4.1 一致，diff 最小。

**我的裁定：向 qoder 的方向让步，但驳回其公开理由，替换为更硬的论据。**

驳回的部分——「平台二字本身在暗示按平台/地点分，正是裁定要拆掉的读法」**是误读**：

- 「平台段」的「平台」指**目标平台**。§4.1 的清理条件原文是「换平台改平台段」（N5），现行 §5.7 的例举「微信开发者工具 / DevEco / npm publish」全是分发目标，不是执行位置。
- 裁定要拆的是**执行地点**（本机/云端）推定，不是目标平台概念。把「平台=地点」写进留档会为将来坏改动提供词源学借口，必须纠正。

让步的部分——「项目段」方向仍是对的，但论据不是词源学，是**死词汇 + 不覆盖不对称**：

- 「平台段」只活在固定层（N2：产物侧零命中）。编译产物实际使用的词族是「项目打包与发布（项目层）」（`templates/RELEASE.md:27`）与「块外项目层区域」（`SKILL.md:175`/`:253`/`:255`）。
- 关键不对称：块外字节按不覆盖原则逐字节保留（`managed-blocks.md` §5.3）。若固定层坚持「平台段」，我们**永远无法**把该词推进既有编译仓——反向对齐路径不存在。发散是永久的，收敛只能在固定层一侧完成。
- 加上 N3 的批次经济学：改 §5.7 本来就触发 5 个模板的标识行重算与全域 `[UPGRADE]`，本轮顺带改名的边际成本近零，分轮做则每次各推一波。我第一轮的「diff 最小」论点低估了传播面的真实代价。

**保留条件**：改名必须同批做全——`DECISIONS.md:66`（「换平台改平台段」→「换平台改项目段」）、`:84`、`:133`（未定项「平台段模板」→「项目段模板」）、快照 `references/DECISIONS.md` 同行；漏任何一处就是把现在的五词并存变成六词并存。

### 1.2 正面意图句：认——我的落点句不够

qoder 指认草案最大缺口是缺正面意图句，并给出论证链：草案 S1–S5 无任何意图/地点词，块外 `:40`「本地脚本打出安装包或构建产物只是试打」是**唯一在场的地点相关句**，新条文生效后读者会拿它解释 S2，得出「本机产物 ⇒ 非发版」——草案反而固化它要拆的误读。

**我被说服。** 我第一轮补的「发布动作与成功判据由项目层在本区写明」回答的是「定义槽位归谁填」，不回答「边界判据是什么」；它对 `:40` 的解释路径没有拦截力。固定层需要正面意图句。

但保留一点精确性：我的落点句**不是作废，是被吸收**——qoder 主案末句的「发版完成的认定方式由项目层规定」正是该槽位。意图句管认定标准，落点句管谁来写完成判据，两者解决不同问题，都应进条文。

### 1.3 P5 标签不可移动性：驳 qoder 的项目层落点

qoder 把「移动已推送标签须显式授权」放到项目层指引，理由是「超出发版语义」。**用 qoder 自己的判据反驳**：其 §3.1 提出「只能同真的是定义，属固定层」——若某项目可声明「本仓版本标签可移动」，则「标签标识产生该发布物的提交」跨项目不再恒真，下游无法信任标签语义。可移动性不是取值，是定义的组成部分。

且只有固定层一句短禁令才能从条文层掐掉 qoder 自己点名的诱因：一旦「每次发版须打标签」生效而重复发版无出口，执行者的自然反应就是 force-move。把禁令放种子，等于允许项目层授权它——与 S3 的标识语义自相矛盾。

**主张**：固定层加「已推送的版本标签不得移动或复用」（「已推送」限定使无远端项目该句自然空置，不构成负担）。若第三轮被否，退回种子提醒是底线——但我请投票者先回答：一个可被项目层宣告可移动的「标识」，还剩多少跨项目语义？

## 四、grok 的 §5.4 关系句：采纳，术语微调后入条文

grok 提议在 §5.7 写明「§5.4 仍决定发版时版本号如何升、哪些提交类型不触发版本发版；它不表示单次提交或单次构建已经发布成功」。**采纳**，理由：

- 真实歧义存在：§5.4「其余不触发发版」可被反读为「`feat`/`fix` 提交即已发版」，与意图认定句直接冲突；不钉死这个边界，新条文生效后歧义原样残留。
- 不是 §1.4 违例：该句做的是**适用范围划界**（§5.4 管版本算术，不管发布完成），不复述 §5.4 内容。
- 微调：「发布成功」→「发版已完成」，与 P2 术语决定一致。

## 五、我修订后的最终条文（第三轮候选）

> **5.7** 打包上传的具体方案属项目层（§2.2），写在 `RELEASE.md` 项目段。是否构成发版按发布意图认定，不按执行地点或构建产物的存在推定：本机执行的正式发布是发版，云端产出的测试包可以不是发版。生成构建产物不自动构成发版。§5.4 决定发版时的版本升位与哪些提交类型不触发发版，不代表单次提交或单次构建的发版已完成。每次发版须以 Git 版本标签标识产生该发布物的提交；已推送的版本标签不得移动或复用；标签存在不证明该次发版已完成。标签创建者、是否推送远端、标签与打包、上传和 CI 的先后关系、同一提交重复发版或分渠道发布的标注方式、发版完成的认定方式，由项目层规定。

与各方文本的差异：

| 差异点 | 相对草案 | 相对 qoder 主案 | 相对 grok 文本 |
|---|---|---|---|
| 意图句 + 双锚点 | 新增 | 同 | 加锚点 |
| §5.4 关系句 | 新增 | 新增 | 同（术语改「发版已完成」） |
| 「标识产生该发布物的提交」 | 「对应提交」收紧 | 同 | 「被发布的提交」→ 同义收紧 |
| 已推送标签不得移动或复用 | 新增 | **新增（P5 分歧点）** | 新增 |
| 「发版已完成」 | 「发布成功」换术语 | 同 | 「上传或交付成功」→ 统一 |

附带说明：意图句「不按产物存在推定」与 S2 有语义交叠，**保留是刻意的**——S2 是可直接模式匹配的钝否定句（针对 #4 现场的错误模式），意图句是判据，两句话读法不同。

**若被否的退让底线**：P5 不可移动句退回种子；§5.4 关系句可删（歧义仍在，但可接受度高于没有意图句）。意图句与「发版已完成」术语我视为不可让。
