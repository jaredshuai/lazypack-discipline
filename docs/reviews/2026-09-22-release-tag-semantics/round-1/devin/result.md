## 二、对草案逐句表态

草案原文（裁定记录所附）：

> 打包上传属项目层，写在 `RELEASE.md` 项目段。生成构建产物不自动构成发版。每次发版须以 Git 版本标签标识对应提交；标签存在不代表发布成功。标签创建者及其与构建、上传和 CI 的先后关系由项目层规定。

**S1「打包上传属项目层，写在 `RELEASE.md` 项目段。」— 同意，建议修改一处用名。**

- 实质内容与现行首句一致，分层不变，正确。
- 但「项目段」与 §4.1 表的「固定段 + 平台段」用词不一致（F5）。同一文件内的同一区域，固定层两处应统一称谓。建议保留「平台段」，或若改用「项目段」则须同轮修订 §4.1——前者 diff 更小。
- 删去「（微信开发者工具 / DevEco / npm publish 等）」例举：中立偏赞成。固定层宜抽象，例举会过时；模板 §2 才是放平台细节的地方。

**S2「生成构建产物不自动构成发版。」— 同意，且认为必须入固定层，项目层默认值不够。**

理由：

1. 这是对「发版」一词的语义界定，与 §5.3（SemVer）、§5.5（CHANGELOG 语义）同类——§5 整节都在钉死跨项目的术语语义，不是流程偏好。
2. §2.4 的项目层默认值是可扩展、可改写的；种子文案位于受管块之外（F7、F11），项目可整段重写。若该语义只活在种子层，等于允许各项目自定义「发版」边界，跨项目约束名存实亡。
3. 实证：§5.4 已逻辑蕴含该结论（F2），但因无明文，用户在 #4 现场仍产生「打出安装包即应有 tag」的预期错位。蕴含不够，须明文；而明文若要约束所有编译产物，只能进受管块的事实源。

**S3「每次发版须以 Git 版本标签标识对应提交。」— 同意，不过强。**

- 相对现行「打 git 标签」，本句是精化而非加码：明确了标签的对象（对应提交）与用途（标识）。这是可追溯性的最低要求，与 F12 的愿景句直接对应。
- 关于「是否存在不应强制标签的正当发版形态」：我未能举出。候选反例逐一检查后均不成立——热修直传、持续部署、应用商店自增 build 号，发版动作背后都存在一个对应提交，而打标签成本近零。真正无对应提交的「发版」（如直接交付未入库的构建结果）恰恰是该纪律应当禁止的形态，因为它无法被接续者从 Git 历史读懂。
- 保留一点注意义务：本句与 §5.4 叠加意味着每次 `feat`/`fix` 触发的发版都应留标签。对高频持续部署项目这可能偏重，但那是 §5.4 既有张力，非本草案新引入，不在本议题范围。

**S4「标签存在不代表发布成功。」— 同意，入固定层，理由同 S2。**

- 它钉死的是「标签 = 发版意图/对应提交的标识」而非「发布结果」。在「标签触发 CI」模式下标签先于结果存在，此句防止「见 tag 即推定已发布」的误推——这正是 #4 现场用户预期的另一面镜像。
- 与 S3 合读语义自洽：发版必有标签（标识动作对象），有标签未必已发布成功（结果在项目层判据下成立与否）。

**S5「标签创建者及其与构建、上传和 CI 的先后关系由项目层规定。」— 同意。**

- 完整落实裁定第 3 条（F10），把流程编排留在项目层，固定层只管语义边界。分层切口正确。

**总评：草案五句方向全部同意；建议两处修改——S1 的「项目段」回退为「平台段」，以及补一条「发版动作与成功判据由项目层写明」（见下节遗漏分析）。**

## 三、专项问题回答

### 3.1 两个语义句应入固定层还是项目层默认值就够？

**入固定层。** 理由见 S2/S4 表态。补一条结构性论证：本纪律的约束力传递链是「固定层 → setup 快照 → 受管块」。块外种子（F7）不受指纹保护、可被项目改写（F11），它适合放「建议默认」，不适合放「跨项目强制语义」。这两句若只进种子，等于把定义权下放给各项目，与 §9.1「只有改固定层条文才开会」所保护的稳定性目标相悖。

### 3.2 「每次发版须以 Git 版本标签标识对应提交」是否过强？

**不过强。** 见 S2 表态的反例排查。补一句正向论证：本句要求的不是「发版必须走 tag 触发流水线」这类流程绑定（裁定已明确不强制，F10），而只是「发版这个事件在 Git 历史中留下可定位的锚点」。任何正当发版形态都能满足；满足不了的形态缺少交付与源码的对应关系，本身就不该被认定为发版。

### 3.3 草案是否完整覆盖「按发布意图区分，不按执行地点区分」？遗漏的歧义？

**方向覆盖成立，但有缺口。**

覆盖面：草案五句不含任何执行地点词。「本机执行正式发版」落入「发版 → 须打标签、标签 ≠ 成功」；「云端只出测试包」落入「生成产物 ≠ 发版 → 不强制标签」。按意图区分的目标达成。

遗漏歧义（按严重性排序）：

1. **「发版」只有否定式定义，没有判定责任的落点。** 草案说了什么不算发版（产物、标签），但「哪一步算本项目的发布动作、以什么判据算成功」无人认领。现行首句「打包上传属项目层」隐含却不显式——项目层可以只写打包命令而从不声明发布动作，#4 的歧义会以新形式残留。这是我认为必须补的一句。
2. **非发版场景打版本标签未约束。** 草案只规定 发版 → 必有标签，未规定 非发版 → 不打版本标签。若 CI 给测试包打 `v1.3.0-rc.1` 式 SemVer 标签，会制造假发版信号。注意：现种子「不发版就不打版本标签」（F7）恰好补足了反向约束；若该种子句按意图口径保留（预发布版真实交付给测试者也算一次发版），则固定层可保持单向约束不写反向句。我倾向固定层不写，在意见中显式记录此不对称是刻意的。
3. **标签的可见性未规定。** 仅存在于本机的标签对「接续者读 Git 历史」（F12）不可见。可在 S3 加「推送至协作远端」之类限定；但考虑单机项目可能无远端，此点我标为**可选收紧项**，交第二轮与维护者裁，不强推。
4. **用名漂移**（S1 已述）：「项目段」vs §4.1「平台段」。

## 四、我提出的最终条文措辞

在草案基础上最小修改（标注差异）：

> **5.7** 打包上传属项目层，写在 `RELEASE.md` 平台段。生成构建产物不自动构成发版；发布动作与成功判据由项目层在本区写明。每次发版须以 Git 版本标签标识对应提交；标签存在不代表发布成功。标签创建者及其与构建、上传和 CI 的先后关系由项目层规定。

与草案的差异：

- 「项目段」→「平台段」：与 §4.1「固定段 + 平台段」一致（F5）。
- 增补「发布动作与成功判据由项目层在本区写明」：补上缺口 1，使「什么算发版」在项目层有显式落点，同时不把任何具体发布形态升格为跨项目纪律（守住裁定「最小补充」边界）。
- 可选收紧（不强推，请第二轮表态）：「标识对应提交」→「标识对应提交并推送至协作远端」。

## 五、对 `templates/RELEASE.md` §2 措辞的影响预判

若第四节条文生效，受管块内第 23 行（F8）与新条文兼容（release → tag 方向一致），无需校准；快照 `references/DECISIONS.md` §5.7（第 84 行）与受管块固定段是否吸收新句属同步任务，不在块外种子校准范围。

块外种子「### 本机试打、发版与版本标签」（第 38–44 行，F7）需要校准的句子：

| 现行句 | 处理 | 理由 |
|---|---|---|
| 小节标题「本机试打、发版与版本标签」 | 改为「试打、发版与版本标签」或「构建产物、发版与版本标签」 | 标题把「本机」焊进试打概念，与意图区分方向冲突（F10-②） |
| 「本机试打不等于发版：本地脚本打出安装包或构建产物只是试打，不构成发版」 | 改写为去地点化措辞，如：「生成构建产物不自动构成发版：为验证打出的包（本机或云端）只是试打产物；本机也可以执行正式发版。是否发版看是否执行了本区写明的发布动作」 | 原句暗示「本机 ⇒ 试打」，正是裁定要求不原样升格的部分（F10-②）；且新条文要求种子把读者引向「发布动作在本区写明」 |
| 「不发版就不打版本标签：版本标签只在发版时打」 | 保留，可微调与条文互指 | 与条文单向约束互补（见缺口 2），种子层保留反向约束是刻意的；真实交付的预发布版属发版，不冲突 |
| 「标签由谁打……」与「与 CI 的先后……」 | 保留 | 与条文末句一致 |
| （建议新增一句）「标签存在不代表发布成功，发布成功判据在本区写明」 | 新增 | 镜像新固定层语义，防「见 tag 推定已发布」 |
| 「本机打包与云端打包分别在开发哪个阶段接线……」 | 保留 | 接线时机留项目层，与条文及裁定一致 |

连带校准点：`skills/lazypack-setup/SKILL.md` 第 254 行播种条目（F9）的「本机试打不等于发版」同样需去地点化，与新种子措辞同步。以上均只影响未来播种，既有仓块外内容按不覆盖原则保留（F11）。
