### S1：两处问题

1. **术语**：「项目段」是全仓第五种叫法（F10）。若本轮不处理术语统一，条文会立即产生一个新的检索不可命中词，后续 §7.2 的「改了 X 没动 Y」配对无法机器化。我主张本轮定词为「**项目段**」并把「平台段」在三处旧位置一并改掉（`DECISIONS.md:66`、`:84`、`:133` 及快照同行），理由：模板 :27 已把该节命名为「项目打包与发布（项目层）」（F10），且「平台」二字本身在暗示「按平台/地点分」，正是裁定 2.2 要拆掉的读法。
2. **§1.4 重复**：「打包上传属项目层」的实质主张已经住在 §2.2（F3）。§5.7 需要的是**指针**（写在哪一段），不是重申分层归属。建议改为「打包上传的具体方案属项目层（§2.2），写在 `RELEASE.md` 项目段」——保留指回，避免同句两处独立成立。

### S2：入固定层，理由见 §3.1；措辞建议保留

现句为单向否定（产物 ⇏ 发版），逻辑安全，不需要改写。但**它不足以单独承载裁定 2.2**，必须和新增的意图句同条出现，否则读者会拿 F8 的地点式旧句去解释它。

### S3：不是新强度，真实增量在「对应提交」三字

F6 显示块内固定段**早已**强制「每次发版必须在 Git 打对应版本标签」。因此问「S3 是否过强」在本仓语境下不成立为「新增义务」，它是把既有事实从编译产物升格回条文。真正的增量只有「标识对应提交」，而这恰是原摩擦的正解：F16 的现场是「产物来自未提交的工作树，标签不存在」——即"谁对应谁"无人规定。所以 S3 应收紧为**标签必须指向产生该发布物的提交**，直接封掉「先随手 build 再补个 tag」这条路。

**不应强制标签的正当发版形态**，我核查两类，结论不同：

- *不成立*的两类：主干持续部署无离散版本号（已被 §5.3/§5.4 的离散版本前提排除，F2，不是 S3 新增限制）；非 Git 仓库（§5.1 与 F6 整体预设 Git，属全层前提，不由本条承担）。
- *成立*的两类：**同一提交重复发版**（上传失败重试、渠道驳回后重发）与**分渠道/分批发布**（同 commit 先发微信、次日发鸿蒙）。此时标签已存在：移动即改写已推送引用（破坏性），不移动则两次发版共享一个标签——S3 字面在此两难，而草案没给许可，项目层也没有明文授权点。**修法不是放开 S3，而是把「重复发版/分渠道如何标注」明文交项目层**（我案已含）。同时警告：任何写成「每次发版须有唯一新标签」的措辞都会把执行者推向 force-move tag，这一类风险要在条文层就掐掉。

### S4：同意，但「发布成功」这个术语我不接受

S4 是纯否定句。它的价值是防止「tag 推上去了 → 汇报已发布」这个特定错误模式（issue 现场同族）。但只留否定句会重演本票的病因：读者仍然没有认定口，只能猜。所以正面那半必须有归属——**认定方式留项目层**（与我案末句一致）。

术语上，F11 证明「发布成功」是新引入词，而该区域已有一套「未选定 / 已选定未验证」（F9），且那个「验证」的对象是**方案实跑过没有**，不是**某次发布成功没有**。两套词族同区出现会被混用（「发布未验证」在两个读法下真值不同）。建议改用条区内已有词汇：**「标签存在不证明该次发版已完成」**。若会议坚持要「发布成功」这个术语，则同一轮必须在 §5 或 CONTEXT 里给它一句定义，否则视为未收口。

### S5：同意，不动

内容等价于 F7 的 :42/:43/:44，且与裁定 2.3 一致。仅一处提醒：草案用了「构建 / 上传 / CI」三个词，现行条文与模板用「打包 / 上传」（F1、F7）。同一概念两套词，建议本轮统一为条文的「构建／上传／CI」并在模板校准轮同步 :42/:43/:44 的用词，或反过来。我倾向后者（改动面小、模板是对外产物）。

## 3. 三个特别问题的回答

### 3.1 「S2/S4 入固定层还是 §2.4 项目层默认值就够」——入固定层

我给一条可复用判据，而非逐案表态：**能在不同项目取不同真值而不破坏其他条文可解释性的，才是项目层默认值（§2.4）；只能同真的，是定义，属固定层。**

- S2 只能同真。任一项目若可声明「我这儿的构建产物就构成发版」，§5.4 的提交→版本映射与 §5.5 的 CHANGELOG 生成对象立刻失去一致解释（产物触发的那次「发版」没有对应提交，F2）。
- S4 只能同真。任一项目若可声明「标签存在即发布成功」，§5.5 的对外变更记录就会记载未发生的发布。
- 反证 F17 triage 的理由：「条文已蕴含 → 所以落项目层」这一步是反的。**蕴含关系恰恰说明它属固定层内容**；把它落到项目层，等于允许每个项目自行决定是否承认一条固定层定理。而 §2.4 明写项目层默认值「不必开 §9 会议」即可由头脑风暴改动（F3）——一条需要跨项目恒真的边界，放在一个可随手改的层面上，保护不了任何东西。
- 另有一条来自本层自身结构：文件开头声明项目层「由本文件编译得出，出现分歧以本文件为准」。若「试打≠发版」只活在块外种子（F7），而块外字节按 §5.3 契约逐字节不覆盖（`SKILL.md:255`），那它就永久退化成项目层可自主丢弃的一行——与它的真值地位不符。

结论：S2、S4 入固定层；S5、S3 的重复发版策略、发布完成的认定方式留项目层。这与裁定「固定层定边界、项目层定流程」是同一刀，只是我把刀落在「定义 vs 取值」上，落点更稳，便于日后判定新条款归属。

### 3.2 S3 是否过强

不过强，但**现措辞在两个真实形态下会卡死**（重复发版、分渠道发布，见 §2 的 S3 段）。修法：收紧对应关系（标签指向产生该发布物的提交），同时明文把重复/分批的标注策略交给项目层，并避免任何「一次发版一个唯一标签」的读法。另：不要在本条暗示「必须先有 tag 才有构建」——裁定 2.3 已排除，我同意，理由是那会把顺序这一项目层取值升成跨项目强制。

### 3.3 草案是否覆盖「按发布意图区分，不按执行地点区分」——没有，这是本轮最大缺口

裁定 2.2 给了两个正面命题：本机可以执行正式发布、云端可以只出测试包。逐句核对草案：**S1–S5 无一句涉及意图或地点**（F1 草案原文）。草案只有一条单向否定（S2），而"按什么认定发版"这个肯定面完全空缺。

后果是可预见的：块外 :40 仍写着「本地脚本打出安装包或构建产物**只是试打**」（F8），这是明确的地点式定性。草案生效后，读者会用这条**唯一在场的地点相关句子**去解释新增的 S2，得出「本机产物 ⇒ 不是发版」——这正是裁定 2.2 点名要拆掉的读法。也就是说，**草案会被用来固化它想纠正的误读**。这不是措辞偏好，是条文与种子同盘时的实际解释路径。

所以我的主案在 S2 之前加一句正面认定口（意图，不是地点，不是产物存在），并把两个具体形态写进条文当反例锚点。

**其余遗漏歧义清单**（含提问点名的两个）：

1. **本机执行正式发版**：草案未表态。必须正面写「本机执行的正式发布是发版」。
2. **云端只出测试包**：草案未表态。必须正面写「云端产物可以不是发版」。
3. **谁认定发布意图**：草案无主语。裁定第三节把「默认由人确认发布意图」明列为**项目层推荐**，所以固定层不该写「须由人确认」；至少要排除「由产物存在推定」，正面主体留项目层（F7 的「标签由谁打」槽位）。我案按这个分寸处理。
4. **试打能否占用或推进版本号**：草案与 §5.4 都未答。我倾向**不入固定层**，落在项目段一行即可；但请会议明确表态，不要留给执行者推断。
5. **无构建产物的发版**（纯文档站发布、只改配置的发布）：S2 只说「产物 ⇏ 发版」，字面安全；但存在反向误读风险「无产物 ⇒ 无发版」。我倾向不写（本仓自身就属此类，见第 6 点），请第二轮验证是否真有人如此误读。
6. **本仓自我一致性**：F12 实测本仓 0 标签，而 §5.7（现行 F1）与块内 :23（F6）都已要求每次发版打标签。若把「固定层版本 0.3.0 → 0.4.0」算发版，本仓当下即违规；若不算，那"不算"的理由就是**发布意图**——本仓以文档与 skill 分发、不以标签发布。这是一个极好的、来自本仓自身的意图优先论据，也请主持人在收口时明确本仓是否受本条约束，否则这条不一致会被后续 harvest 当新 issue 再提一次。
7. **术语「发布成功」**：见 §2 的 S4 段（F11、F9）。
8. **词族「打包 / 构建」**：见 §2 的 S5 段。

## 4. 我提出的最终条文

### 4.1 主案（§5.7，五句）

> **5.7** 打包上传的具体方案属项目层（§2.2），写在 `RELEASE.md` 项目段。
> 发版按**发布意图**认定，不按执行地点或构建产物的存在推定：本机执行的正式发布是发版，云端产出的测试包可以不是发版。
> 生成构建产物不自动构成发版。
> 每次发版须以 Git 版本标签标识，标签指向产生该发布物的提交；标签存在不证明该次发版已完成。
> 标签创建者、标签与打包／上传／CI 的先后关系、同一提交重复发版或分渠道发布时的标注方式，以及发版完成的认定方式，由项目层规定。

设计说明：第 2 句补裁定 2.2（草案缺的那一维）；第 3 句 = S2 原样；第 4 句 = S3＋S4，其中「指向产生该发布物的提交」是对 F16 现场的正解，「不证明该次发版已完成」避开 F11 的新术语；第 5 句 = S5 ＋重复发版出口。相对草案净增一句、换一处术语、补两处归属。

### 4.2 极简案（若会议坚持最小改动）

草案原文只动两处：在「生成构建产物不自动构成发版」前插入「发版按发布意图认定，不按执行地点推定。」；把「项目段」改回「平台段」或反之完成三处同步。**我认为极简案不足以拆掉 F8 的地点式旧句**，但可作第二轮的退让底线。

## 7. 一句话总结

草案方向正确但**不完整**：它把「产物 ⇏ 发版」「标签 ⇏ 成功」两条否定写进了固定层，却漏掉了裁定自己的正面命题「按发布意图认定」，从而留下被块外地点式旧句解释的通道；同时「发布成功」是未经定义的新术语，「项目段」是第五种叫法。我的主案补一句正面认定口、收紧「标签指向产生该发布物的提交」、把重复发版与完成认定交给项目层，并要求同轮完成术语与快照同步。
