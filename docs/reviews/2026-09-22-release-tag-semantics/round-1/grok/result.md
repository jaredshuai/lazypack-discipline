## 2. 逐句表态

### 句 1：「打包上传属项目层，写在 `RELEASE.md` 项目段。」

**修改。**

打包上传属于项目层，这句应保留，依据是现行 §2.2 与 §5.7。删去微信开发者工具 / DevEco / npm publish 举例，同意：举例不是工具白名单，固定层不必点名厂商。

不同意把「平台段」改成「项目段」，且只改 §5.7。现行 §4 表仍把这一家叫做平台段，未定项仍写「平台段模板」。现行模板 §2 的标题是「项目打包与发布（项目层）」，文件里没有「平台段」三字，但也没有「项目段」这个标题。只改 §5.7 的用词，会让同一段同时叫两个名字。

平台段应理解为 `RELEASE.md` 固定段之外、由项目书写的打包与上传部分。这与 #3 之后平台内容位于受管块之外的布局一致，不是要求把打包说明写回受管块。

### 句 2：「生成构建产物不自动构成发版。」

**修改：句子保留，并补上意图与地点。应写入固定层，不只做 §2.4 默认值。**

应入固定层的理由：

- 这是跨项目的词义边界。Issue #4 的 triage 已把「打出安装包是否就该有 tag」记为预期错位；当时选择只改种子，并明确升格须走 §9。现在讨论的就是这一步。
- 项目层种子在受管块外。`docs/ARTIFACTS.md` 2026-09-21（#4）写明：已编译仓的块外旧种子不会自动补上这段指引。只放 §2.4 默认值，现有项目可以继续没有这句，新项目也可以在选定方案时删掉种子。词义边界若可被项目层删掉，就不是跨项目强制。
- 「不自动」是对的强度。它不禁止「确认发布意图之后，用同一次构建去发版」。它禁止的是把产物生成本身当成发版。

只保留这句还不够，见第 3 节。它没有写出裁定里的正面标准：按发布意图区分，不按执行地点区分。

### 句 3：「每次发版须以 Git 版本标签标识对应提交」

**修改：义务保留，不视为过强；「版本标签」和「对应提交」要写清。**

现行 §5.7 已经要求「每次发版打 git 标签」。草案增加的是「版本标签」和「标识对应提交」。这两点应当保留。

这条没有过强到需要删除，因为不该强制打版本标签的情形，在本纪律里本来就不是发版：

- 未确认发布意图的本机试打、云端测试包、CI 冒烟产物：由句 2 排除，不是发版，也就不落入「每次发版」。
- §5.4 写明不触发版本发版的提交类型：不是发版。
- 同一次版本的再次上传、分阶段放量：标识的仍是已经发布的那次提交，不需要为此再打一个新版本标签。草案没有要求「每次上传都打新标签」。

本纪律之内，我没有看到一种仍应叫做发版、却不应有 Git 版本标签的形态。SemVer 预发布（如 rc）在有发布意图时仍是发版，标签所标版本号沿用 §5.3，不另开豁免。

需要收窄的地方：

- 「git 标签」若不加「版本」，浮动标签或测试标记也能充数。应限定为版本标签，且所标版本号遵循 §5.3。`v` 前缀只出现在现行模板示例 `v1.2.0` 里，本条不新增强制前缀。
- 「对应提交」应写成「被发布的那次提交」，避免标签打在事后的空提交上仍算满足。
- 不规定恰好一个标签。一次提交发布多个包时，标签个数由项目层定。
- 不规定附注标签或轻量标签。那是操作细节。

### 句 4：「标签存在不代表发布成功。」

**修改：应写入固定层；「发布成功」不要在固定层另下定义。**

应入固定层的理由与句 2 相同。只把标签放进受管固定段、却不写「标签不等于上传或交付成功」，已编译项目仍会把打标签当成发布已经完成。现行模板受管块 §1.3 只有「必须打对应版本标签」，没有这句否定。

「发布成功」四字本身没有定义。商店审核、npm publish、内网交付不是同一种成功。固定层若自己定义成功，就会把项目层的上传标准吸进来，与「打包上传属项目层」冲突。

改为：版本标签的存在，不代表项目层已经定义的上传或交付成功。成功标准仍由项目层写在平台段。

### 句 5：「标签创建者及其与构建、上传和 CI 的先后关系由项目层规定。」

**修改：归属同意，补上「是否推送」。**

创建者与先后关系留在项目层，与裁定第三节一致，也与 §2.4 的分工一致。这里用项目层规定就够，不必写成固定层流程。

原句没写标签是否推送到远端。本地标签可以「标识」提交，远端和 CI 却看不见。是否推送属于操作细节，仍由项目层规定。固定层既不把「本地已有标签」写成发布完成，也不强制「必须先推送」或「必须由 CI 创建」。

## 3. 三个集中问题

### 3.1 两句定义放哪一层

「生成构建产物不自动构成发版」和「标签存在不代表发布成功」写入固定层。§2.4 的项目层默认值不够，理由见句 2、句 4。

标签由谁创建、是否推送、与构建上传 CI 的先后、发布意图如何确认（人工确认或另行写明的自动发布策略），留在项目层。裁定评论第三节的推荐流程不写入 §5.7。草案没有收录它们，这是覆盖正确，不是遗漏。

### 3.2 强制版本标签是否过强

在「发版才打版本标签」这个范围内，不过强。不应打版本标签的，是未构成发版的构建，不是发版的例外清单。

过强只会发生在把「发版」读成每一次部署、每一次 CI 成功或每一次构建。句 2 加上「按发布意图」之后，这条义务不会落到测试包上。

无法判断的部分见第 6 节：不用 Git 的交付是否还叫本纪律下的发版，必读材料没有定义。

### 3.3 草案是否覆盖「按发布意图区分，不按执行地点区分」

没有覆盖完整。

草案没有出现「发布意图」或「执行地点」。它只是不提本机和云端，再用「不自动」否定「有产物即发版」。沉默挡不住现行模板第 40 行：该行把本地脚本的产物写成「只是试打」。本机执行的正式发版会被这句挡在发版之外；云端只出测试包则被「不自动」盖住一半。若有人把 CI 变绿当成发布意图，草案没有句子可以反驳。

应补的固定层边界只有这一句：是否构成发版，按发布意图区分，不按执行地点区分。意图如何被确认，不写入固定层。

另一处歧义在 §5.4 的「不触发发版」。该条可能被读成：`feat` 一提交就已经是发版。草案没有处理这句和「不自动构成发版」的关系。建议在 §5.7 写明：§5.4 仍决定发版时版本号如何升，以及哪些提交类型不触发版本发版；它不表示单次提交或单次构建已经发布成功。不改 §5.4 的映射表。

## 4. 建议的完整条文

用以替换现行 §5.7。与草案不同，这是完整替代文本：

> 打包上传属项目层，写在 `RELEASE.md` 固定段之外的平台段。是否构成发版，按发布意图区分，不按执行地点区分；生成构建产物不自动构成发版。§5.4 仍决定发版时版本号如何升，以及哪些提交类型不触发版本发版；它不表示单次提交或单次构建已经发布成功。每次发版须用 Git 版本标签标识被发布的提交，标签所标版本号遵循 §5.3。版本标签的存在不代表项目层定义的上传或交付已经成功。标签由谁创建、是否推送，以及它与构建、上传和 CI 的先后关系，由项目层规定。

不在本条改 §4 表的「平台段」用词。若另有决定要把这一家改名为「项目段」，须同时改 §4 表与 §5.7，不能只改其中一处。
