# 本仓提交说明格式检查

本文件是 `scripts/check_commit_msg.mjs` 的唯一判定正文。标题形状与 type 集合的规则来源仍是 [DECISIONS.md §5.1](../DECISIONS.md)。本检查器按固定层 §2.4 落在本仓，不改 §5.1，也不升格成所有接入仓的门禁。

检查器：`node scripts/check_commit_msg.mjs <message-file> [--rules <path>]`（Node 标准库，只读）。它检查一份候选提交消息文件，不创建提交。不传 `--rules` 时，命令仍是 `node scripts/check_commit_msg.mjs <message-file>`。

未接 hook、CI 或定时器。格式通过不等于语义已验证，不等于代码正确或需求完成。检查器在磁盘上存在、可手动运行，不等于门禁已生效。

脚本头部只放指向本文件的指针，以及每次运行都要带的那句声明；不复述抽取、标题判定和四态定义。

## 何时运行

1. 准备提交说明时，对手头的消息文件手动运行上述命令。需要改读另一份含 §5.1 行的文件时，才加上 `--rules <path>`。
2. 改了规则文件里的 §5.1 标题句或本文件的抽取口径后，用同一命令确认抽取仍然成功。
3. 改判定口径时先改本文件，再改脚本。

## 词表抽取

只读一份规则文件，在运行时抽出 type。不读取 setup 快照，不在脚本内保存 type 名称。

- 不传 `--rules`：规则文件是 `docs/DECISIONS.md`，相对本脚本所在仓库根。当前工作目录改变时，这个缺省路径不变。
- 传入 `--rules <path>`：规则文件是该路径。Node 的 `fs` 按当前工作目录解析相对路径，不改写到脚本所在仓。失败原因写「规则文件」，不把传入路径展开成本机绝对路径。
- 消息文件是唯一的位置参数。`--rules <path>` 可以写在它前面或后面。
- `--rules` 出现多次，或后面没有路径：消息文件已经可读时是 `exec-failed`，原因分别是 `--rules 出现了多次`、`--rules 缺少路径`。这时不读词表。
- 未给出消息文件，或该路径不存在、不是普通文件：仍是 `not-run`。这时不读规则文件，即使命令里写了 `--rules`。

抽出步骤对选中的那一份文件相同：

1. 以 `5.1 ` 开头的正文行必须恰好一行。零行或多行都是抽取失败。
2. 该行必须恰好有一处「`N 个（\`词表\`）`」。括号为全角。反引号内的标记按空白拆开，每个标记必须匹配 `^[a-z][a-z0-9]*$`，且个数必须等于 N。
3. 该行其余反引号片段：
   - 整个片段匹配 `^[a-z][a-z0-9]*$` 的，按出现顺序追加为 type；
   - 含有大写、`#`、`(`、`)`、`!` 或非 ASCII 的，视为形状示例或脚注示例，不进入词表；
   - 其他片段（空片段、第二份空白分隔词表、仅含连字符的标记）使抽取失败。
4. 抽出的 type 不得重复，不得为空。

当前 §5.1 行能走出上述步骤。条文改写后若走不通，结果是 `exec-failed`，检查器不改用内置清单。

## 标题判定

消息文件按 UTF-8 读取（允许文件开头的 BOM，判定前只在内存中去掉）。第一行是标题，去掉行尾的 CR。后续行不参与格式成败。

标题整行必须匹配 `^([a-z][a-z0-9]*)(\([^)]+\))?(!)?: (\S.*)$`。

含义：type、可选的非空 scope、可选的 `!`、冒号、一个空格、然后至少一个非空白字符。scope 与 `!` 按 Conventional Commits 1.0.0 视为可选。这是测量口径，不改写 §5.1 的括号写法。

| 顺序 | 条件 | 状态 | 规则文案 |
|---|---|---|---|
| 1 | 标题不匹配上述形状 | `format-fail` | 标题缺 `type: 描述` 形状 |
| 2 | 形状匹配，但 type 不在抽出的集合中 | `format-fail` | type 不在 §5.1 允许集合 |
| 3 | 形状匹配且 type 在集合中 | `format-pass` | 无 |

命中第一条就停止，不把两条叠成一次失败。

## 信息行

下列内容只输出，不改变状态，也不计入失败：

- 标题之后是否还有非空行（`body-nonempty`）。脚注行算非空正文。
- 整行匹配 `Closes #n`、`Fixes #n` 或 `Refs #n` 的脚注。没有则报告 `none`。

§5.2 的「为什么 / 未完成」不做判断。脚注词没有被 §5.1 收成封闭词表，检查器不因出现或缺少这些词而失败。

## 四态

状态字面量与退出码两两不同。

| 状态 | 退出码 | 何时 |
|---|---|---|
| `format-pass` | 0 | 标题形状与 type 都通过 |
| `format-fail` | 1 | 标题形状不符，或 type 不在抽出的集合 |
| `not-run` | 2 | 未给出消息文件，或该路径不存在、不是普通文件。此时不读词表 |
| `exec-failed` | 3 | 消息文件可读，但所选规则文件缺失、不可读、不是合法 UTF-8，或词表抽取失败；或消息文件不是合法 UTF-8；或 `--rules` 重复、缺少路径。不传 `--rules` 时，规则文件仍是 `docs/DECISIONS.md`，缺失原因仍是 `无法读取 docs/DECISIONS.md: <code>` |

每次输出都包含同一句声明：未接 hook/CI；不是门禁；格式通过不等于语义已验证，不等于代码正确或需求完成。

人类可读摘要的第一行是 `check_commit_msg: <状态>`。随后是声明、`rule` 或 `reason`、信息行。最后另起一段 JSON，字段与摘要一致：`status`、`exit_code`、`rule`、`reason`、`info`、`types`。`types` 只在抽取成功时出现。摘要不把传入路径解析成本机绝对路径。

## 边界

- 不接 `commit-msg` 或 `pre-commit`，不修改 `templates/pre-commit.sh`。
- `--rules` 只切换哪一份文件提供 §5.1 词表。它不是通用规则引擎，不接受另一种规则语言，也不在其他仓库装配检查器。
- 不判断说明是否与 diff 相符。`format-pass` 只说明标题形状和 type。
- 不写入、不删除、不改名任何文件。
- 检查器自己运行失败（`not-run` / `exec-failed`）不是格式通过。传入 `--rules` 后得到 `format-pass`，仍然不等于语义已验证。
