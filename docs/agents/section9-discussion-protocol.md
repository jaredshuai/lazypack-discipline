# §9 多 AI 讨论执行规程

**最后更新**：2026-01-08  
**修订**：Issue #29 实战后加入 3 个流程改进（提示词路径格式、工作区检查、平台错误处理）

## 文档说明

本文件规范 §9 多 AI 讨论的具体执行流程，是 `DECISIONS.md` 第 9 节原则的操作细则。

- **§9 原则层**：为什么要多 AI 讨论、何时触发、基本理念
- **本文件操作层**：怎么做、谁做什么、路径规范、边界清晰化

本规程基于 issue #36 的实践经验固化，用于减少未来讨论的流程摩擦。

---

## 角色定义

### 主持人（Droid）

**职责**
- 生成讨论目录结构和提示词
- 汇总各轮次参与者的输出
- 识别收敛度和分歧点
- 提出流程建议（是否需要下一轮）

**权限边界**
- 可以：结构化整理意见、识别共识与分歧、建议流程
- 不可以：投票、提出自己的方案、裁决价值观分歧

**角色切换**
- 在裁决阶段后，从"中立主持"切换为"执行维护者决策"
- 此时可以提出具体方案和实施计划

### 参与者（5 位 AI）

**职责**
- 独立思考并输出意见（第一轮）
- 阅读他人意见并互评收敛（第二轮）
- 如有必要，参与修订后投票（第三轮）

**交付物要求**
- **第一轮强制**：`result.md` + `evidence.md`
- **第二轮强制**：`result.md` + `evidence.md`
- **第二轮可选**：`clauses.md`（如果有具体条文建议）

**缺席处理**
- 主持人补发提示词（提供绝对路径）
- 维护者重新执行该席位
- 汇总时标注"补发状态"（如适用）

### 维护者（用户）

**何时介入**
- 裁决技术论证各自自洽的价值观分歧
- 解决流程僵局（如第二轮仍无法收敛）
- 确认是否需要第三轮
- 批准最终方案和实施范围

**裁决范围**
- 价值观分歧：章节归属、优先级权衡、风格取舍
- 实施边界：哪些是强制项、哪些另开票
- 历史遗留：路径不一致等问题的最终决定

**最终权威**
- 维护者的裁决即为最终决策
- 主持人角色切换后执行维护者决策

## 阶段化流程

### 准备阶段

**主持人职责**

1. **创建标准目录结构**（一次性定好，避免后续改动）
   ```
   docs/reviews/YYYY-MM-DD-<议题>/
   ├── README.md（状态追踪）
   ├── EXECUTION-PLAN.md（可选，复杂议题用）
   ├── round-1/
   │   ├── prompts/
   │   │   ├── participant-1/prompt.md
   │   │   ├── participant-2/prompt.md
   │   │   ├── participant-3/prompt.md
   │   │   ├── participant-4/prompt.md
   │   │   └── participant-5/prompt.md
   │   └── participants/（预留，各参与者稍后创建子目录）
   ├── round-2/
   │   ├── prompts/
   │   │   ├── participant-1/prompt.md
   │   │   ├── participant-2/prompt.md
   │   │   ├── participant-3/prompt.md
   │   │   ├── participant-4/prompt.md
   │   │   └── participant-5/prompt.md
   │   └── participants/
   └── round-3/（可选，视第二轮结果决定）
       ├── prompts/
       │   ├── participant-1/prompt.md
       │   ├── participant-2/prompt.md
       │   ├── participant-3/prompt.md
       │   ├── participant-4/prompt.md
       │   └── participant-5/prompt.md
       └── participants/
   ```

   **临时工作目录**（参与者输出位置）：
   ```
   %TEMP%/lazypack-discussion/<session-id>/
   ├── participant-1/
   ├── participant-2/
   ├── participant-3/
   ├── participant-4/
   └── participant-5/
   ```
   - Windows: `%TEMP%` 或 `C:\Users\<user>\AppData\Local\Temp\`
   - Unix: `/tmp/`
   - session-id 格式：`YYYY-MM-DD-<议题>`，如 `2026-10-06-prompt-lean-tool-rich`

2. **生成第一轮提示词**
   - 路径：`round-1/prompts/participant-{1-5}/prompt.md`（每个参与者独立子目录）
   
   **自包含约束（强制）**：
   
   每轮提示词文件必须**完全自包含**：所有背景材料、草案文本、参考内容直接内联，不得使用文件系统路径引用（相对路径或绝对路径）。外部 AI 执行器无法访问本地文件系统。
   
   - ❌ 错误示例：`参见 [通用背景材料](../common.md)`
   - ❌ 错误示例：`参见 E:\project\docs\background.md`
   - ✅ 正确示例：直接在提示词中内联完整背景材料
   
   **提示词生成 Checklist**：
   
   每个 participant-X/prompt.md 必须包含：
   - [ ] 完整背景材料（内联，不引用）
   - [ ] 完整草案文本（第二轮起，内联）
   - [ ] 完整 P0 裁定结果（如有，内联）
   - [ ] 第一轮其他参与者意见摘要（第二轮起，内联或说明可忽略）
   - [ ] 该参与者的角色与视角说明
   - [ ] 输出路径（绝对路径，Windows/Linux 兼容）
   - [ ] 讨论独立性约束（见下文"提示词必须包含的约束项"）
   - [ ] 无相对路径引用（生成后扫描确认）
   - [ ] 无绝对路径引用（生成后扫描确认）
   
   **主持人自查清单**（生成后执行）：
   1. 随机抽查一个提示词文件
   2. 假设"这个文件会被复制给没有任何上下文的外部 AI"
   3. 检查是否能独立理解和执行
   4. 用正则扫描：`grep -E '\]\(\.\.\/|\]\([A-Z]:\\' participant-*/prompt.md`
   
   - 明确输出路径（临时目录的绝对路径）：
     - Windows 示例：`C:\Users\<user>\AppData\Local\Temp\lazypack-discussion\2026-10-06-<议题>\participant-N\`
     - Unix 示例：`/tmp/lazypack-discussion/2026-10-06-<议题>/participant-N/`

   **提示词路径交付格式**：
   - 向维护者提供提示词路径时，使用**5 个独立的代码块**，每个路径一个代码块
   - 不使用树状结构、不使用列表、不增加额外说明
   - 示例（正确）：
     ```
     E:\codespace\lazypack-discipline\docs\reviews\YYYY-MM-DD-<topic>\round-N\prompts\participant-1\prompt.md
     ```
     ```
     E:\codespace\lazypack-discipline\docs\reviews\YYYY-MM-DD-<topic>\round-N\prompts\participant-2\prompt.md
     ```
     ```
     E:\codespace\lazypack-discipline\docs\reviews\YYYY-MM-DD-<topic>\round-N\prompts\participant-3\prompt.md
     ```
     ```
     E:\codespace\lazypack-discipline\docs\reviews\YYYY-MM-DD-<topic>\round-N\prompts\participant-4\prompt.md
     ```
     ```
     E:\codespace\lazypack-discipline\docs\reviews\YYYY-MM-DD-<topic>\round-N\prompts\participant-5\prompt.md
     ```
   - 便于维护者逐个点击复制按钮，在 5 个不同 IDE 中打开并直接发送给外部 AI

3. **提交准备阶段成果**
   - 让维护者检查目录结构和提示词
   - 等待维护者确认开始执行

**维护者职责**
- 检查议题描述是否清晰
- 确认目录结构符合标准
- 开始执行（分别用 5 个提示词调用 AI）

### 提示词必须包含的约束项

所有轮次的提示词都必须包含以下约束，确保讨论独立性和流程隔离：

**讨论独立性约束**

"你是独立评审者，不是项目维护者。讨论期间你只能：
1. 阅读提示词提供的材料
2. 进行独立思考和论证
3. 输出到指定临时目录（提示词中提供的绝对路径）
4. 第二轮起阅读其他参与者意见

禁止调用任何项目工具、流程、检查器或读取项目当前状态。你的任务是基于提供的材料进行独立评审，而非对项目进行维护操作。"

**路径隔离说明**

提示词必须明确告知参与者：
- 输出到系统临时目录（提供绝对路径）
- 不在项目 git 目录下工作
- 主持人负责最终搬运存档

---

### 第一轮：独立意见

**路径规范**
- 提示词：`round-1/prompts/participant-{1-5}/prompt.md`（独立子目录）
- 输出目录（临时）：`%TEMP%/lazypack-discussion/<session-id>/participant-{1-5}/`
- 交付物：
  - `result.md`（核心意见，强制）
  - `evidence.md`（支撑论据，强制）

**执行流程**
1. 维护者用 5 个提示词分别调用 AI
2. 各参与者在临时目录（提示词提供的绝对路径）下输出交付物
3. 维护者说"好了" / "完成了"表示全部提交完成
4. **主持人职责**：从临时目录读取各参与者输出并汇总

**讨论独立性约束**（提示词必须包含）
- 参与者是独立评审者，不是项目维护者
- 只能阅读提示词提供的材料
- 只能输出到指定临时目录
- 禁止调用项目工具、流程、检查器或读取项目当前状态

**汇总触发**
- **用户信号**：维护者说"好了" / "完成了" / "可以汇总了"
- **主持人行为**：从临时目录读取输出并汇总，不逐个验证文件是否存在
- **信任机制**：信任维护者的确认信号
- **汇总输出**：`round-1/ROUND-1-SUMMARY.md`（项目目录）

**缺席处理**
- 如某参与者未输出，维护者告知主持人
- 主持人补发该席位的提示词（提供绝对路径）
- 维护者重新执行该席位
- 汇总时可标注"参与者 N 补发"（如适用）

---

### 第二轮：互评与收敛

**前置条件**
- 第一轮汇总完成（`ROUND-1-SUMMARY.md` 已生成）
- 维护者决定进入第二轮

**提示词定制化**
- 路径：`round-2/prompts/participant-{1-5}/prompt.md`（独立子目录）
- 内容针对每位参与者的第一轮立场定制
- 包含：第一轮汇总、其他参与者意见、互评要求
- **必须包含讨论独立性约束**（见上文"提示词必须包含的约束项"）

**交付物要求**
- 输出目录（临时）：`%TEMP%/lazypack-discussion/<session-id>/participant-{1-5}/`
- **强制交付物**：
  - `result.md`（互评后的立场）
  - `evidence.md`（支撑论据）
- **可选交付物**：
  - `clauses.md`（具体条文建议，如适用）

**讨论独立性约束**（提示词必须包含）
- 第二轮可以阅读其他参与者的第一轮意见
- 仍然只能输出到指定临时目录
- 仍然禁止调用项目工具或读取项目当前状态

**汇总触发**
- 同第一轮，维护者说"好了"即触发汇总
- **主持人行为**：从临时目录读取输出并汇总
- 汇总输出：`round-2/ROUND-2-SUMMARY.md`（项目目录）
- 汇总内容增加：收敛度评估、是否需要第三轮的建议

---

### 第三轮：修订后投票（可选）

**触发条件**
- 第二轮汇总显示仍有重大分歧（如 3:2 或更分散）
- 维护者认为需要更多信息辅助裁决

**投票机制**
- 提示词：`round-3/prompts/participant-{1-5}/prompt.md`（独立子目录）
- 提供修订后的方案（基于第二轮收敛结果）
- 要求投票 + 简要理由
- **必须包含讨论独立性约束**（见上文"提示词必须包含的约束项"）
- 输出目录（临时）：`%TEMP%/lazypack-discussion/<session-id>/participant-{1-5}/`
- 交付物：`result.md`（投票 + 理由）

**汇总输出**
- **主持人行为**：从临时目录读取输出并汇总
- `round-3/ROUND-3-SUMMARY.md`（项目目录）
- 包含最终投票分布和关键理由

---

### 每轮结束后的工作区检查（强制）

主持人在汇总完成、提交到 git 之后，**必须**执行以下检查：

1. **运行 `git status`**
   - 检查是否有 untracked files（可能是遗留产物、临时文件、上一个任务的残留）
   - 检查是否有未推送的 commits

2. **清理遗留产物**
   - 如果发现不应该存在的文件（如 Mission 验证报告、临时调试文件等），判断是否应该删除
   - 删除确认为遗留产物的文件
   - 单独提交清理操作：`git commit -m "chore: clean up stray artifacts after round-N"`

3. **推送所有 commits**
   - 确保所有本地 commits 都推送到远程
   - 运行 `git push origin main`

4. **最终验证**
   - 再次运行 `git status`
   - 确认显示：`nothing to commit, working tree clean`

**为什么这个环节重要**：
- 讨论过程可能产生临时文件或遗留产物
- 未推送的 commits 会在下次操作时造成混乱
- 保持工作区干净是流程卫生的基础

**示例**：
Issue #29 讨论中发现的遗留产物：`mutation-testing-validation-report.md`（来自上一个 Mission 的验证报告）

### 维护者裁决阶段

**何时触发**
- 第二轮收敛后（多数情况）
- 或第三轮投票后仍有僵局

**裁决内容**
- 技术论证各自自洽的价值观分歧（如章节归属、优先级）
- 实施边界（哪些是强制项、哪些另开票）
- 路径不一致等历史遗留问题

**主持人角色切换**
- **裁决前**：中立主持，不投票不提方案
- **裁决后**：执行维护者决策，可提出具体实施方案

**主持人搬运职责**
- 维护者裁决后，主持人负责从临时目录搬运所有参与者输出到项目存档目录
- 搬运路径：
  - 源：`%TEMP%/lazypack-discussion/<session-id>/participant-N/`
  - 目标：`docs/reviews/YYYY-MM-DD-<议题>/round-N/participants/participant-N/`
- 搬运完成后确认：所有 `result.md`、`evidence.md`、`clauses.md`（如有）已复制
- **用户不做任何复制粘贴工作**

**维护者信号**
- 说"作为维护者裁决" / "我裁决为" / "最终决定"
- 主持人识别后切换角色并执行搬运

## 实施边界清晰化

### 强制实施项（条文通过后必须完成）

以下项目必须在本轮讨论议题关闭前完成：

1. **更新 DECISIONS.md**
   - 版本号递增（如 v2.0 → v2.1）
   - 更新修订记录
   - 新增或修订条文内容

2. **连带改动**
   - 更新引用该条文的其他文档
   - 更新相关表格（如 ARTIFACTS.md）
   - 同步受影响的 skill 文件

3. **派生一致性同步**（§6.6① 要求）
   - 如条文修订影响已派生到目标项目的 skill，需更新派生版本
   - 标记派生版本的变更状态

4. **验证脚本全绿**
   - 运行 `scripts/verify-consistency.py`（如有）
   - 确保交叉引用完整性
   - 确保路径和链接有效

### 可选实施项（另开实施票）

以下项目可以在本轮讨论后另开 issue 处理：

1. **功能增强**
   - 新增工具或自动化脚本
   - 增强现有 skill 的能力

2. **工具接线**（第四态可以保持）
   - 将纸面规范自动化
   - CI 集成
   - 自动化验证增强

3. **其他改进**
   - 文档重构
   - 示例补充
   - 教程更新

**判断标准**
- 强制项：条文变更直接要求的最小一致性修改
- 可选项：条文变更触发的扩展性改进

│   │   └── participant-5/prompt.md
│   ├── participants/
│   │   └── participant-{1-5}/        # 注意有 s，最终存档位置

### 命名规范

**统一规则**
- 提示词目录：`prompts/participant-N/prompt.md`（独立子目录，防止参与者 AI 用 ls 时看到其他提示词）
- 临时输出目录：`%TEMP%/lazypack-discussion/<session-id>/participant-N/`（无 s）
- 最终存档目录：`participants/participant-N/`（有 s，小写）
- 汇总文件：`ROUND-N-SUMMARY.md`（全大写）
- 状态追踪：`README.md`（在议题根目录）

**避免的错误**
- ❌ `prompts/participant-1.md`（缺少子目录隔离）
- ❌ `participant/`（缺 s）
- ❌ `Participant-1/`（首字母大写）
- ❌ `round-1-summary.md`（全小写）
- ❌ `PARTICIPANTS/`（全大写）

## 用户交互协议

### 明确的信号约定

| 用户说什么 | 主持人理解为 | 主持人行为 |
|-----------|------------|----------|
| "好了" / "完成了" / "可以汇总了" | 所有参与者已提交 | 从临时目录读取输出并汇总，不逐个验证 |
| "进入第二轮" / "开始第二轮" | 第一轮完成，启动第二轮 | 生成第二轮提示词 |
| "进入第三轮" / "需要投票" | 第二轮后仍有分歧 | 生成第三轮提示词 |
| "作为维护者裁决" / "我裁决为" | 维护者最终决策 | 角色切换，执行搬运，然后执行维护者决策 |

### 主持人不做的事

1. **不逐个验证文件存在性**
   - 信任维护者的"好了"信号
   - 如文件缺失，维护者会主动告知

2. **不自行决定价值判断**
   - 不决定章节归属
   - 不决定优先级权衡
   - 不决定风格取舍

3. **不在裁决前提出方案**
   - 维护者裁决前保持中立
   - 仅整理意见和识别分歧

4. **不在裁决阶段调用 mission-planning**
   - 维护者裁决后，角色已切换为"执行者"
   - 此时可直接提出实施方案，不需要再规划

### 用户不做的事

1. **不做任何复制粘贴工作**
   - 所有文件搬运由主持人负责
   - 用户只需调用 AI 并确认"好了"

2. **不手动整理目录结构**
   - 主持人负责从临时目录搬运到存档目录
   - 用户不介入文件操作

3. **不需要记住复杂路径**
   - 提示词中已包含完整绝对路径
   - 参与者 AI 直接使用提示词提供的路径

## 常见问题处理

### Q1: 参与者缺席怎么办？

**问题场景**
- 某参与者未在指定目录输出交付物
- 或输出不完整（缺少 evidence.md）

**处理流程**
1. 维护者告知主持人："参与者 3 缺席"
2. 主持人补发该席位的提示词，提供绝对路径
3. 维护者重新执行该席位
4. 汇总时可标注"参与者 3 补发"（可选）

---

### Q2: 第二轮收敛度很高，还需要第三轮吗？

**判断标准**
- **高收敛**（如 4:1 或 5:0）：通常不需要第三轮
- **中等收敛**（如 3:2）：由维护者决定
- **低收敛**（如 2:2:1）：建议第三轮或直接维护者裁决

**决策流程**
1. 主持人在第二轮汇总中给出收敛度评估和建议
2. 维护者决定：
   - 直接裁决（如收敛度足够）
   - 进入第三轮（如需要更多信息）

---

### Q3: 条文通过后的实施边界在哪？

**强制项**（见"实施边界清晰化"章节）
- DECISIONS.md 更新
- 连带改动
- 派生一致性同步
- 验证脚本全绿

**可选项**（另开票）
- 功能增强
- 工具接线
- 其他改进

**判断原则**
- 如果不做会导致文档不一致 → 强制项
- 如果不做不影响一致性，但有改进价值 → 可选项

---

### Q4: 如何处理路径不一致的历史遗留？

**问题场景**
- 旧讨论用 `participant/`（无 s）
- 新讨论用 `participants/`（有 s）

**处理流程**
1. 维护者作为最终权威裁决
2. 后续统一使用本规程的标准路径
3. 历史目录可选择：
   - 保持原样（不破坏历史记录）
   - 重命名统一（增强一致性）
   - 由维护者决定

---

### Q5: 如何判断是技术分歧还是价值观分歧？

**技术分歧**
- 可通过证据、逻辑、测试验证
- 有明确的对错标准
- 例：语法错误、性能数据、兼容性测试

**价值观分歧**
- 双方论证各自自洽
- 无明确的对错标准，取决于优先级
- 例：章节归属、风格偏好、抽象层次

**处理方式**
- 技术分歧：继续论证，直到收敛
- 价值观分歧：维护者裁决

## 附录：issue #36 经验教训

本规程的设计基于以下具体教训：

1. **路径命名不一致**
   - 问题：第一轮用 `participant/`，第二轮用 `participants/`
   - 解决：统一为 `participants/`，在准备阶段一次性定好

2. **用户交互不清晰**
   - 问题：主持人逐个验证文件，维护者不知道何时算"完成"
   - 解决：约定"好了"信号，主持人信任维护者

3. **主持人角色混淆**
   - 问题：裁决阶段后还调用 mission-planning，角色不清
   - 解决：明确角色切换时机，裁决后可直接提方案

4. **实施范围不明确**
   - 问题：条文通过后不知道哪些是强制项
   - 解决：明确"强制实施项"和"可选实施项"

5. **参与者缺席处理不规范**
   - 问题：补发提示词时路径不一致
   - 解决：补发时提供绝对路径，标记补发状态

6. **讨论输出污染项目 git diff**
   - 问题：参与者直接输出到项目目录，污染 git diff，与其他 AI 编程会话产生干扰
   - 解决：参与者输出到系统临时目录（`%TEMP%/lazypack-discussion/<session-id>/`），主持人裁决后统一搬运到存档目录
   - 附加收益：提示词隔离（独立子目录），参与者 AI 用 ls 不会看到其他提示词

7. **平台错误（如 GitHub push 失败）的处理**
   - 问题：讨论过程中遇到 GitHub 500 Internal Server Error，导致 push 失败
   - 解决：
     * 第一次失败：等待 1-2 分钟后重试
     * 连续 3 次失败：告知维护者，暂时跳过 push，继续流程
     * 所有本地 commits 保持完整，可稍后手动推送
     * 不因平台临时性故障中断讨论流程
   - 经验：平台错误是外部因素，不应阻塞讨论进度；本地 commits 完整即可，推送可异步完成
