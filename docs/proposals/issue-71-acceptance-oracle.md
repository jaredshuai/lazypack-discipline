# Issue #71: 验收基准冻结（Acceptance Oracle）

**提案类型**: 固定层讨论议题  
**关联 Issue**: #71  
**提案日期**: 2026-10-09  
**状态**: 待讨论

---

## 1. 现状分析

### 1.1 问题陈述（Test Oracle Problem）

外部讨论提出的失败模式：

> AI 误解需求 → 按错误理解写实现 → 再按同一错误理解写测试断言 → 测试全部通过。

代码与测试共享同一个错误假设时，「测试全绿」只证明实现符合断言，不证明断言符合需求。代码覆盖率 100% 同样无法解决这个问题。示例：

- 需求：系统 A 的管理员只能管理系统 A 的权限，不能改系统 B 的权限；
- AI 误解为：只要是管理员就能改任何系统的权限；
- 产出：越权实现 + 与错误理解一致的断言 + 全绿测试。

### 1.2 固定层条文的当前覆盖

**§6.5 质量双轨**（DECISIONS.md:118）：
```
可测层（领域逻辑、数据推导）行为改动必须配套断言；
迭代层（页面、组件）以语法/类型检查为底线，推导逻辑下沉到可测层。
```

**§6.5 单迭代上限补充**（0.7.0）：
```
一张票构成合格范围，当且仅当其关闭前能指出：
- 哪些行为断言由本票 diff 覆盖（可测层），或
- 哪些类型断言由本票 diff 覆盖（迭代层）
```

**§6.4 对抗性双跑**：执行者和审查者都必须跑门禁。

**§7.3**：需求变更经 `grill-with-docs` → ADR → 登记册状态互指。

### 1.3 项目层模板与工具的当前覆盖

**CODING_STANDARDS.md:15-16**：
```
核心领域逻辑、状态推导、数据清洗与算法等行为改动，必须配套自动化测试断言。
严禁提交无断言或断言被注销的可测层逻辑。
```

**roles.md §4.1 逐项验收表**：按票据验收条目逐项对应，状态四态（已验证通过/已验证失败/未验证/不适用）；§4.2 区分自动化/假对象测试与真实环境/人工实测。

**report-layers 校验器（#32/#33）**：控制逻辑与用户体验双轴分述，`unverified` 状态下拦截「已对齐」声称。

**夜跑变异测试闭环（#35 落地）**：基线棘轮只涨不跌（`mutation-baseline.mjs` update 拒绝下调），等价变异体豁免走三元组 + reason 论证的显式流程。

### 1.4 结构性缺口

现行条文要求的都是「**有**断言」「断言**通过**」「测试**敏感**」，没有任何条文要求「断言的**依据**独立于实现、先于实现存在」：

| 防线 | 防的是什么 | 防不住什么 |
|---|---|---|
| §6.5 双轨 | 无断言的行为改动 | 断言本身写错 |
| CODING_STANDARDS 禁注销断言 | 断言被删除/注释 | 断言被**改写**以适配错误实现 |
| 变异测试 + 棘轮 | 测试不敏感（抓不到注入的错误） | 预期结果本身就错（变异测试自证其局限：原始断言错仍可拿高分） |
| report-layers 双轴 | 未验证宣称已对齐 | 验证所依据的预期错误 |

即：文中「AI 写代码 → AI 写测试 → AI 宣布自己正确」的自证循环，在现行条文下没有断点。

## 2. 拟议方案

### 方案 A：§6.5 增补「验收基准冻结」补充条款（推荐）

在 §6.5 内追加补充条款，沿用 0.7.0「可判定内核 + 行为层拆分」的先例（单迭代上限补充条款的形态）：

**可判定内核**（机器或审查者可判定）：
- 票据声明冻结断言清单（路径 + 断言标识）的，执行者 diff 触碰清单内断言时，提交正文必须含三选一裁决留痕：实现错（修正实现）/ 断言错（修正断言并写明理由）/ 需求变（附 ADR 或处置票号）；
- 无裁决留痕的触碰按退回处理（审查者判定，未来可工具化为 commit-msg 检查）。

**行为层**（指引，不可机器判定）：
- 关键行为预期（验收样例：输入 → 预期输出，含权限边界与异常路径）由规划者在开工前落入票据，经用户确认后冻结；
- 验收测试依据冻结的验收契约编写，不参照实现内部结构；
- 范围限定：仅可测层关键行为（权限、资金、状态机、数据删除等）适用；迭代层 UI 不强求。

**理由**：
1. ✅ **断自证循环**：验收预期的正确性来源从「AI 自述」变为「开工前经用户确认的冻结契约」，这是文中 Acceptance Oracle 建议的直译；
2. ✅ **与既有条文同构**：冻结清单 + 裁决留痕的形态与 §7.7② 存在性对子（文档同步/处置票/登记更新三有一）同一思路，学习成本低；
3. ✅ **零新增角色**：冻结动作落在规划者既有职责（写规格、票）内，执行者/审查者边界不变（§3.2 不破）；
4. ✅ **可判定部分可工具化**：符合 §6.6①② 口径/执行分离与「能写成闸门的先写闸门」；
5. ⚠️ **成本**：每张涉关键行为的票多一步「冻结清单」动作；小票过度冻结的风险需边界条款兜住。

### 方案 B：新设独立条文（如 §6.8 验收基准）

内容同方案 A，但作为独立条款而非 §6.5 补充。

**理由**：
1. ✅ 概念独立性强，便于引用（「验收基准」一词有独立的家）；
2. ⚠️ 与 §6.5 双轨、单迭代上限形成三处相邻但分散的断言纪律，违反「同一主题只活在一处」（§1.4）的风险更高；
3. ⚠️ 条文编号成本：插入 §6 需重排或追加，都不如挂 §6.5 补充自然。

### 方案 C：不进固定层，仅项目层指引（不推荐为最终态）

写成 `docs/agents/acceptance-oracle.md` 按需说明，不改 DECISIONS.md。

**理由**：
1. ✅ 成本最低，立即可用；
2. ❌ 无约束力：自证循环正是「提示词里的义务句管不住」的典型场景，按 §6.6③「须阻断者不得只活在常驻提示词」，该规则的可判定内核（触碰冻结断言须留痕）应落工具/审查闸门；
3. ✅ 可作为过渡形态：若 §9 裁定暂不入固定层，先以指引层交付，iteration-scope.md 即此前例（§6.5 可判定内核 + 指引层行为倡导）。

## 3. 条文修改建议（方案 A 草案）

### 3.1 DECISIONS.md §6.5 追加补充条款

```
**补充：验收基准冻结（Acceptance Oracle）**

一张票涉及可测层关键行为（权限、资金、状态机、数据删除等）时：

- 规划者在开工前将关键行为预期（验收样例：输入 → 预期输出，含边界与
  异常路径）落入票据，经用户确认后冻结为验收基准；验收测试依据该基准
  编写，不参照实现内部结构。
- 执行者 diff 触碰已冻结断言的，提交正文须含三选一裁决留痕：
  实现错（修正实现）/ 断言错（修正断言并写明理由）/ 需求变
  （附 ADR 或处置票号）。无留痕的触碰由审查者退回。
- 范围溢出保护：迭代层与票据未声明冻结清单的行为不适用本条；
  冻结清单本身是票据内容，其变更按 §7.3 走需求变更流程。
```

### 3.2 模板联动（若裁定通过）

- `templates/CODING_STANDARDS.md` 可测层一节补一句：「冻结验收断言的修改按 §6.5 验收基准冻结条款执行，严禁为转绿静默放宽」；
- `templates/roles.md` §4.1 逐项验收表增加一列或一行标注「冻结基准」（可选，讨论定）；
- setup 快照随下次固定层同步更新（先例：0.7.0 同步票）。

### 3.3 明确不进本提案的配套项

| 配套项 | 去向 | 理由 |
|---|---|---|
| 属性测试（Property-based） | 项目层工具选型（§2.4） | 不同功能不同验证强度，不做一刀切门禁；可参照夜跑闭环模式先做运营指引 |
| 差分测试（Differential） | 项目层工具选型（§2.4） | 需要独立参考实现，适用面窄 |
| Verification / Validation / 测试有效性三分 | `docs/agents/` 按需说明或 report-layers 判定口径 | 概念澄清层，无阻断需求 |

## 4. 边界与例外

### 4.1 小票与探索性改动

- 票据未声明冻结清单的，本条不激活——避免给 typo 级小票加流程负担；
- 「关键行为」的判定下沉项目层/规划者，固定层不枚举业务类型清单（权限、资金等为示例非闭合枚举）。

### 4.2 冻结断言写错了怎么办

- 这正是「断言错」裁决分支存在的理由：允许改，但必须留痕理由，且审查者可见；
- 冻结的目的不是断言永真，而是让「预期变更」从静默变为显式事件。

### 4.3 与变异测试的分工

- 变异测试回答「测试有没有能力发现实现偏离断言」（测试有效性轴）；
- 本条回答「断言的预期结果从哪来、谁能改」（Oracle 来源轴）；
- 两者互补不替代：断言本身错时变异测试仍可高分，冻结条款不降低变异测试价值，反之亦然。

### 4.4 存量票据

- 不追溯：已关闭票据不补冻结清单；在途票据由规划者决定是否补，不强制。
