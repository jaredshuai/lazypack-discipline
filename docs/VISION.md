# 产品愿景

状态：`current`（产品方向）。来源：维护者于 2026-09-09 在本项目讨论中明确的核心思想。本文描述产品目标，不代表所述自动化已经全部实现；实际交付以产品文件与对应验收证据为准。

## 用户专注于产品，lazypack 处理开发中的家务

lazypack 像自动收拾房间的机器人：让用户专注于创造和使用产品，把开发过程中的整理、检查和接续交给系统。用户不应反复提醒 AI 更新文档、寻找决策、遵守协作边界，或决定每一份材料该放在哪里。

“懒”意味着降低用户的决策与维护负担。自动化要保护已有工作、如实报告失败，在需要用户判断的地方保留明确选择。

## 从需求出发，再匹配技术方案

setup 先理解用户要做什么、谁使用、运行在哪里、如何交付，以及已有项目与资源约束。先利用仓库和当前会话中已有的事实，只补问影响方案而无法可靠推导的问题。

技术栈与模板是内部可匹配的能力。用户表达目标后，系统推荐复杂度适当的组合，说明关键取舍；不要求用户先学习工具菜单，也不替用户猜测尚未明确的需求。

简单小工具应有轻量路径。跨平台桌面应用、企业管理后台前端、后端服务需要分别判断运行、交互与维护要求，不能仅凭类别名称绑定某个框架。具体框架、版本与配置由配方及其适用条件管理，本文不维护工具选型表。

## 先完善纪律自动化，再扩展模板组合

产品优先完善文档同步与归档、AI 协作与交接、质量检查和决策追踪。纪律明确之后，再积累经过验证的模板组合，减少项目从启动到日常开发的常见错误。

文档归属应是 lazypack-setup 的基础交付：根据目标项目已有资料，明确各类内容的位置、更新触发、维护职责和替代归档方式，并让 AI 从项目入口读取和执行。它面向所有接入项目，不依附于某个技术套餐；应复用已有权威文档，按需要补齐，不批量生成空文档。只修好 lazypack 本仓的文档入口不算这项产品能力已经交付；目前首期 preserve-existing 已有当前宿主代表性实证，但完整跨环境适配与物理迁移仍未交付。

模板应按需求装配，并复用项目已有的有效能力。增加工具、文档或流程之前，先判断它能否减少重复劳动和实际错误，以及引入的维护成本是否值得。

## 设计判断

评估一项能力时，回答：

- 它减少了用户哪项反复决策、提醒或整理工作？
- 需求更简单时，是否仍有更轻的方案？
- 系统能自动完成哪些步骤，哪些取舍确实需要用户判断？
- 如何验证它的效果，失败时如何保护已有工作并恢复？
