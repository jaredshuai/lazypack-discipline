# 产品愿景

状态：`current`（产品方向，唯一现行产品宗旨）。来源：维护者于 2026-09-09 在本项目讨论中明确的核心思想；2026-09-22 确认，任务交给 AI 之后，用户不必再替它整理提交；[2026-10-18 #94 最终裁决](https://github.com/jaredshuai/lazypack-discipline/issues/94#issuecomment-6247753464)经维护者采纳，维护者同时授权本轮实装。本文记录已采纳的产品方向，AI 裁决或文档写入本身不构成产品验收；实际交付以产品文件与对应验收证据为准。

## 模板优先，标准装配先行

lazypack 优先建设经过验证、可反复使用的工程模板，并保证声明支持的标准装配可靠工作。官方模板是正式维护、可版本化的纪律产物、Hook、配套脚本、配置和配方，不限于未来的技术栈模板。标准装配按声明的条件与步骤新增内容，或处理已有内容；在声明条件内，原位保留、安全登记和受控迁移都属于标准装配路径。新仓或旧仓、仓库大小不单独决定一项请求是标准还是扩展。

这套顺序取代“先完善纪律自动化，再扩展模板组合”和“纪律明确之后再积累模板”。先让官方模板成为可装配、可验证的产品交付，再依据实际使用补强；不需要等全部纪律自动化成熟后才积累模板。可靠性和验证投入集中在可重复的官方模板生产与标准装配：AI 选择适用模板，填写项目配置，按最小必要范围接线，并验证产物；优先复用 Matt skills 和项目已有能力，项目执行不临场重写模板内已经可靠的实现。它不把技术栈选择提升为更高优先级，也不否定已有纪律、Hook、脚本、配置和试点，或轻量场景的按需路线。

质量责任以已经声明的产物、适用条件和现有契约为边界。“经过验证”只表示在明确的环境、参数与装配路径中通过可追溯的检查和必要的真实宿主验收，不保证未知情况零缺陷。模板优先改变装配来源与推进顺序，不自动扩大环境、参数、结构或接入方式的支持范围；具体判断按下文顺序执行。

## 用户专注于产品，lazypack 处理开发中的家务

lazypack 像自动收拾房间的机器人：让用户专注于创造和使用产品，把开发过程中的整理、检查和接续交给系统。用户不应反复提醒 AI 更新文档、寻找决策、遵守协作边界，或决定每一份材料该放在哪里。

“懒”意味着降低用户的决策与维护负担。自动化要保护已有工作、如实报告失败，在需要用户判断的地方保留明确选择。

用户交代目标之后，AI 在已经确认的目标、验收范围和权限内，选用适用的已有技能，把上下文传下去，一直推进到完成或真实阻塞。用户不管理技能调用，但看得懂进展，也看得懂哪些事项要自己决定。这是 2026-09-22 #10 裁定确认的方向。首个验证（#19，宿主 Cursor 3.21.18 / Windows）已于 2026-09-23 验收，只证明该宿主、该技能基线与该任务范围，不外推。本段不表示无感全自动已经交付，也不表示任意宿主或任意任务都能自动执行。

新增页面和操作沿用项目已经确认的视觉约定，用户不必反复提醒 AI 保持一致。这不承诺完整设计系统，也不承诺所有项目统一审美。这是 2026-09-22 #7 裁定确认的方向。试点尚未开展。本段不表示图标检查或视觉约定维护已经交付。

用户把开发任务交给 AI 之后，不必反复提醒安全检查，也不必自己拼接多份报告。交付时能看清检查了什么、哪些问题有依据、如何处理，以及哪些范围仍未检查。这是 2026-09-22 #6 裁定确认的方向。首个试点（yifangbao，施工票 #27）已于 2026-09-23 验收：真实安全问题被盲审查出、修复并复核，单次样本不计检出率或误报率。本段不指定工具，也不表示安全审查能力已经交付或可外推。

## 从需求出发，再匹配技术方案

setup 先理解用户要做什么、谁使用、运行在哪里、如何交付，以及已有项目与资源约束。先利用仓库和当前会话中已有的事实，只补问影响方案而无法可靠推导的问题。

技术栈特定模板是官方模板中的一类内部可匹配能力。用户表达目标后，系统推荐复杂度适当的组合，说明关键取舍；不要求用户先学习工具菜单，也不替用户猜测尚未明确的需求。

简单小工具应有轻量路径。跨平台桌面应用、企业管理后台前端、后端服务需要分别判断运行、交互与维护要求，不能仅凭类别名称绑定某个框架。具体框架、版本与配置由配方及其适用条件管理，本文不维护工具选型表。

模板应按需求装配，并复用项目已有的有效能力。增加工具、文档或流程之前，先判断它能否减少重复劳动和实际错误，以及引入的维护成本是否值得。

## 接续开发后的可维护性

任务交给 AI 之后，用户不必再替它整理提交。接续者应能从 Git 历史读懂改了什么、为什么改、影响哪里，以及哪些事项尚未完成。

让用户在 AI 持续开发后，仍能看懂项目结构、关键流程和变化依据；让下一位 Agent 能依靠同一份项目知识接续工作。图是表达方式，不是交付数量指标。这是 2026-09-22 #5 裁定确认的方向，试点验证尚未开展。本段只记这项用户收益和边界，不表示总览、流程说明或图已经交付。来源讨论里的 “Architecture as AI” 只是探索背景，不是当前能力承诺。

开发过程中应自动检查受影响的文档。能确定、并且这一次任务已经授权的内容直接同步；有疑问的内容指出来；只有出现新的决策时才交回用户。接续者应能看出说明依据的是哪一版实现、哪些内容已经核对、哪些仍待确认。未声明或尚未核对的范围留在检查记录里，保持可见。已经声明、并且能用路径、哈希或正则判定的关系交给机器检查；需要理解含义的影响，由当轮执行和审查处理。实现与有效需求、ADR 或规则冲突时，保留双方依据并交回裁决。历史验收和来源材料保持当时的记录。重新生成全部文档、安装外部文档站、定时任务、自动批准或自动合并，都不在这个目标里。

上一段是产品目标与取舍。某个仓库有没有把这件事接进日常开工和收尾，以该仓库的流程、检查记录和验收为准。

文档归属应是官方模板与标准装配的基础交付：根据目标项目已有资料，明确各类内容的位置、更新触发、维护职责和替代归档方式，并让 AI 从项目入口读取和执行。它面向按声明条件支持的接入项目，不依附于某个技术套餐；应复用已有权威文档，按需要补齐，不批量生成空文档。首期 preserve-existing 已有当前宿主沙箱的代表性验证，本地受控迁移引擎已进入本仓 skill。对任意目标仓和环境的无限通用改造不是当前承诺；在已声明条件内，跨宿主行为、外部目标仓生产迁移和大型旧仓接入仍缺少实测，状态为 UNPROVEN。仓库大小不单独决定支持，具体环境、参数和结构按下文判断。只修好本仓文档入口，不等于已向目标项目交付这项能力。

## 判定顺序与支持边界

评估 setup 或模板修改、自动审查建议、Issue 实施和接入方式时，按以下顺序判断：

1. **先守安全底线。** 保护现有数据、权限、对外发送与资料留存；失败后按既有契约恢复或清理本次改动，不覆盖外部变更，并如实报告无法恢复的部分。这些是 [固定层条文](DECISIONS.md) §2.3、§3.2、§3.4、§4.4、§7.5–§7.6、§8.3、§10.3 已有的持续约束，不因场景非标准或不受支持而豁免。修复应阻止进一步损害，但不自动承担让非标准结构成功的义务。本文不新增“所有故障绝无半写”或系统级抗崩溃原子性的承诺。
2. **再核对既有有效承诺。** 以现行 skill、references、presets 等权威正文中的行为和适用条件为准，并服从固定层与维护者明确裁定。违反已承诺行为属于应修缺陷；承担已承诺的保护责任，不以预先枚举每一种异常为前提。
3. **扩大范围须另行裁定。** 超出已声明能力的运行环境、参数、结构或接入方式属于扩展请求，先说明收益、新增复杂度和安全退出方案，再由维护者裁定。改变支持矩阵、增加条件分支、Bot 等级、单仓特例或既有成功试点，都不自行授权扩展。
4. **承诺不清时保留依据待裁。** 权威正文的承诺缺失、过宽或互相冲突时，列明来源、适用范围、证据和风险，不自动判为缺陷或判为不支持。未验证不等于不支持；历史验收只说明当时范围，也不自动扩大支持。登记册用于定位权威正文和记录证据，不能把其中整列“依据与边界”直接当作支持矩阵。

对未列入标准装配的结构采用有限支持：能在既有承诺内确定且安全处理时复用现有路径；不能确定时保护原状，说明具体冲突、未覆盖项和可行的适配路径。

## 设计判断

评估一项能力时，回答：

- 它减少了用户哪项反复决策、提醒或整理工作？
- 需求更简单时，是否仍有更轻的方案？
- 系统能自动完成哪些步骤，哪些取舍确实需要用户判断？
- 如何验证它的效果，失败时如何保护已有工作并恢复？
