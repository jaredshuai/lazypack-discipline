# 顺序发送与生命周期控制契约（references/dispatch_lifecycle.md）

本文档定义 `/lazypack-harvest` 的 7 阶段生命周期控制、顺序发送事务边界与 R1/R2 恢复机制，依据冻结规格 `SPEC.md` §2。

---

## 1. 七阶段生命周期总览

1. **阶段 1：可见会话上下文获取（Context Acquisition）**
   - 仅读取当前对话可见历史；**严禁扫描历史会话数据库或宿主外部文件**。
   - 来源业务项目完全只读（零暂存、零修改、零删除）；严格保留 dirty 状态（Preserve Existing State）。
2. **阶段 2：事实、建议与勘误分流（Disambiguation & Correction）**
   - 识别真实工程纪律摩擦 vs 正常业务调试。
   - 剔除会话后半段澄清勘误的作废错误（Scenario 6 / T17）。
   - 保留未撤回的固定层异议，忠实提炼转分诊（Scenario 5 / T16）。
   - 剔除仅有敏感片段而无纪律议题的输入（Scenario 7 / T18）。
3. **阶段 3：候选识别、独立拆分与证据聚合（Splitting & Merging）**
   - 拆分基准：**按可独立处理的问题拆分**（不同修复单元/不同分诊走向）。
   - 围绕同一核心摩擦点的多次报错、推演和讨论，**一律聚合到同一条候选证据中**，杜绝碎片化发帖。
4. **阶段 4：正文构造与深度脱敏（Construction & Sanitization）**
   - 按五要素模板构造正文，全面脱敏；生成候选指纹 `CANDIDATE_FP`。
5. **阶段 5：前置依赖与标签核验（Prerequisite & Label Check）**
   - 核验目标仓 `jaredshuai/lazypack-discipline` 及写通道。
   - 动态查询 `harvest` 标签是否存在；缺失/离线/无法核验则安全阻断，保存草稿（`DEPENDENCY_BLOCKED`）。
6. **阶段 6：逐条顺序发送与事务安全控制（Sequential Dispatching）**
   - 同步顺序逐条处理候选：`候选 1` → `候选 2` → `...`。
7. **阶段 7：状态呈现与下游交接**
   - 输出恰好一个批次主状态，分项展示逐候选真实状态、URL 或草稿路径。

## 2. 逐条顺序发送与分支处置策略

在阶段 6 发送中，每个候选按以下分支严格处置：

### 分支 1：单条创建成功
- 收到远端 201 成功响应，获取真实 Issue URL。
- 执行本地记账落盘（写入系统临时目录）：
  - 若本地落盘成功：标记为 `CANDIDATE_PUBLISHED`，推进下一条候选；
  - **若本地落盘失败**：远端已创建为客观事实，**严禁改为 UNKNOWN**！标记为 `CANDIDATE_PUBLISHED` 且 `local_persist_failed: true`；**立即中止本轮后续候选发送**，主状态收口为 `PERSIST_FAILED`。
  - **账本异常保护**：若本地账本文件损坏或读取失败，必须先保留现有文件原始字节不覆盖，如实报告读取/持久化受阻；已有远端成功事实和真实 URL 绝不抹改为未知。发送前若遇账本异常，不得依据坏账本的空结果直接盲目创建；能做的只读核对优先，无确证则保留未决；未发起创建请求的候选不标远端 `RESULT_UNKNOWN`；批次按冻结阶梯定义及实际事件汇总，不添加自动重发路径。

### 分支 2：单条超时未知（504 / 网络断开）
- 当前候选先标记为 `CANDIDATE_UNKNOWN`，落本地草稿。
- **其后所有未尝试候选一律标记为 `CANDIDATE_SKIPPED`，严禁标记为未知**。
- **立即中止本轮 R1 后续发送（停发事件不可撤回，后续已跳过项留待下次手动触发 R2 处理）**。
- 立即发起一次已脱敏只读核验：
  - 若核查仍无法证实：当前候选保持 `CANDIDATE_UNKNOWN`，禁止盲目重试；因存在未知项，按 §5.2 阶梯判定主状态为 **`RESULT_UNKNOWN`**；
  - 若核验证实远端已创建：当前候选**更新为 `CANDIDATE_PUBLISHED` 并记录真实 Issue URL**；但**本轮停发后续事实不可逆**（后续跳过项保持 `CANDIDATE_SKIPPED`）；最终根据更新后的全候选状态数组，按 §5.2 阶梯重新计算批次汇总码（如存在已发布与跳过项且已无未知，唯一收口为 **`PARTIAL_SUCCESS`**）。

### 分支 3：单条明确被拒（401/403/422）
- 当前候选标记为 `CANDIDATE_REJECTED`，落本地草稿；
- 其后所有未尝试候选标记为 `CANDIDATE_SKIPPED`；
- 立即中止本轮后续发送。

### 分支 4：命中查重
- **证实重复（CONFIRMED）**：已核实属于同一问题且持有真实 Issue URL。标记为 `CANDIDATE_DUPLICATE_CONFIRMED`，跳过本条发送，推进下一条候选。
- **疑似重复（SUSPECTED）**：命中检索线索但 URL 未能证实。标记为 `CANDIDATE_DUPLICATE_SUSPECTED`，本轮跳过发送，输出警示，严禁虚构 URL。
- **未发送草稿放行**：此前因离线等未发送的 `CANDIDATE_DRAFT` 或被拒的 `CANDIDATE_REJECTED`，在依赖满足时**属于正常待发项，严禁因草稿存在而当成重复阻断**。

## 3. R1 与 R2 生命周期解耦与恢复机制

- **本次运行 R1 内部中止**：
  - 在一次运行 R1 中，发生超时、明确被拒或持久化失败，锁定 R1 本轮停止，绝不继续发送后续。
- **下一次手动运行 R2 启动（用户重新触发同一会话）**：
  - R2 启动时，**首先对历史关联未知项执行已授权只读核验**（“关联”指同一可独立处理问题/同一指纹，绝非同一次运行下的所有问题）。
  - **分支 R2-A（核验证实已创建）**：
    - 历史未知项更新为 `CANDIDATE_PUBLISHED` 并获得真实 URL；
    - 证实属于历史核查成功，**不是 R2 新发生超时**；
    - **R2 放行并推进独立的候选 3（在 R1 中被跳过的问题）**；
    - 候选 3 发送成功，批次收口为 `PUBLISHED_SUCCESS`。
  - **分支 R2-B（核验仍未查到）**：
    - 历史未知项在 R2 中保持 `CANDIDATE_UNKNOWN`，**阻断该相同问题重发**；
    - **但不得因候选 2 未决而无理阻断不相关的独立候选 3 发送**。
