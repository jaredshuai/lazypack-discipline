# 发版与提交纪律 (RELEASE)

> 派生自 lazypack-discipline 固定层 DECISIONS.md@0.3.0（依据 lazypack-setup 内置快照编译，来源内容标识: 1c78a216d27b82666c9724701f858f2bafe2b10d；离线事实源查阅 lazypack-setup/references/DECISIONS.md）§5。

## 1. 提交与版本规则（固定段）

### 1.1 提交头 (Conventional Commits 1.0.0)
- 格式：`type(scope)!: 描述`
- 允许的 8 个 Angular type：`build`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`, `test`，加上 `chore`, `revert`。
- 破坏性改动使用 `!` 或正文注明 `BREAKING CHANGE`。
- 脚注使用 `Closes #n` 或 `Fixes #n` 关联票据。

### 1.2 提交正文 (Google CL 规范)
- 第一行独立说清「改了什么」。
- 正文说清「为什么做此改动」、有哪些未做完或折衷之处、关联的 Issue / Bug 号。

### 1.3 版本号映射 (SemVer 2.0.0)
- `!` 或 `BREAKING CHANGE` -> Major 升级 (`vX.0.0`)
- `feat` -> Minor 升级 (`v0.X.0`)
- `fix` / `perf` -> Patch 升级 (`v0.0.X`)
- 其他 type 不触发版本发版。
- 每次发版必须在 Git 打对应版本标签（如 `v1.2.0`）。
- 变更记录遵循 Keep a Changelog 1.1.0 格式，由提交历史自动编译生成，禁止手写篡改。

## 2. 项目打包与发布（项目层）

> 本区位于受管托管块外部，记录**这个项目怎么打包、怎么上传**。setup 仅在文件首次编译（`[NEW]`）且块外尚无正文时播种本草稿；一旦本区已有内容，重跑不得覆盖、不得重排、不得再播种。现行打包说明以本区为准，不得把受管固定段或本草稿陈述为已选定方案。

当前状态：**打包方案未选定**。

### 打包方案状态（两态）

- **未选定**（本草稿默认）：项目尚未确定打包与上传方案。执行者不得把本段当成已选定的现行打包事实。
- **已选定未验证**：方案已写入本区，但对应打包或上传步骤尚未在本项目实跑验证。选定不等于已验证上传。实跑通过后去掉未验证标注。

### 本机试打、发版与版本标签

- **本机试打不等于发版**：本地脚本打出安装包或构建产物只是试打，不构成发版。
- **不发版就不打版本标签**：版本标签只在发版时打；何种提交触发发版见块内固定段。
- **标签由谁打**：选定方案后在本区写明——由人打标签，还是由 CI 在发版流程中打。未选定前不要假定已有自动打标签。
- **与 CI 的先后**：若采用「先打标签、标签触发云端打包或发布」，在本区写清触发关系与入口。暂未接线 CI 则如实写「未接线」，不在本区展开完整流水线步骤。
- 本机打包与云端打包分别在开发哪个阶段接线，由项目层在本区写明；未决定前保持「未选定」。

### 未选定时如何改写本区

选定方案后，由执行者按文档跟着改直接改写本节：写明产物形态、命令或操作入口，以及仍为未验证的步骤。不要改受管标记行或块内固定段。
