# 多 Agent 流水线参考模型 (Agent Pipeline Models)

本文记录 Uncle Bob（Robert C. Martin）提出并实测的五段式多 agent 流水线分工模型，经 issue #39 整理，供接入 lazypack-discipline 的项目与 AI agent 参考。

**定位与边界**：本文是参考模板（reference），不是固定层条文，也不是强制要求。项目可以完整采用、按需裁剪，或完全不采用（见 §4、§5）。采用与否不影响 `/lazypack-setup` 生成的其他产物。

---

## 1. 五段式流水线概述

流水线由五个 agent 角色串联组成，前一段的产物是后一段的唯一输入：

```
specifier → coder → cleaner → hardener → QA
```

| 阶段 | 角色 | 一句话职责 |
|------|------|------------|
| 1 | specifier | 人写需求 → Gherkin 验收测试 + QA 流程 |
| 2 | coder | 写实现 + 单元测试，跑通 Gherkin |
| 3 | cleaner | CRAP 分析，收拾烂摊子 |
| 4 | hardener | 变异测试，100% 覆盖，毫不留情 |
| 5 | QA | QA 文档 → 可执行脚本，操作界面输出确定性结果 |

两个要点：

1. **阶段之间只传产物，不传对话。** 上游 agent 把结果写成文件（Gherkin 文本、代码、测试报告、QA 脚本），下游 agent 从文件读起，不继承上游的会话上下文。
2. **每一段都有机器可验证的完成标准。** Gherkin 跑没跑通、CRAP 分数降没降、变异体杀没杀光、QA 脚本过没过，都不靠自我评价。

## 2. 角色定义

### 2.1 specifier（规格者）

- **职责**：人写需求 → Gherkin 验收测试 + QA 流程。
- **输入**：人类写下的需求描述。需求由人负责，这是流水线的人机边界：人定「要什么」，agent 定「怎么验」。
- **输出**：
  1. Gherkin 验收测试（Given / When / Then），逐条覆盖需求要点；
  2. QA 流程文档，写明后续 QA agent 要在界面上验证哪些操作、期望看到什么结果。
- **工作方式**：把模糊的人话需求翻译成可执行判定的规格。写作时只关心「验收标准是否无歧义」，不关心怎么实现。
- **不做什么**：不写实现代码，不写单元测试。

### 2.2 coder（编码者）

- **职责**：写实现 + 单元测试，跑通 Gherkin。
- **输入**：specifier 产出的 Gherkin 验收测试。
- **输出**：实现代码与配套单元测试，Gherkin 验收测试全部通过。
- **工作方式**：以「让 Gherkin 变绿」为唯一完成标准。允许先写出粗糙但正确的实现——质量收拾交给下游，不在这一段追求一步到位。
- **不做什么**：不做超出验收范围的重构，不处理验收测试未覆盖的加固项。

### 2.3 cleaner（清洁者）

- **职责**：CRAP 分析，收拾烂摊子。
- **输入**：coder 产出的代码与测试。
- **输出**：重构后的代码，行为不变（测试保持绿），CRAP 分数下降。
- **工作方式**：对代码跑 CRAP（Change Risk Anti-Patterns，由圈复杂度与覆盖率推导出的风险分数）分析，按分数从高到低收拾：拆长函数、降复杂度、给薄弱路径补测试。重构前后测试必须始终是绿的，证明行为没被改坏。
- **不做什么**：不加新功能，不改外部行为。

### 2.4 hardener（加固者）

- **职责**：变异测试，100% 覆盖，毫不留情。
- **输入**：cleaner 重构后的代码与测试。
- **输出**：变异分数达标的测试套件（原始模型要求 100% 杀伤）。
- **工作方式**：跑变异测试（mutation testing，工具如 Stryker 或 mutmut）：往代码里注入微小变异，凡有变异体存活，就补断言把它杀死。「毫不留情」指不放过任何一个存活变异体——存活一个就是未完成。工具接入方法见本仓 `docs/quality-gates/mutation-testing.md`。
- **不做什么**：不改产品代码逻辑；发现测不动的坏设计时，退回上一段处理，不自己顺手改。

### 2.5 QA（质检者）

- **职责**：QA 文档 → 可执行脚本，操作界面输出确定性结果。
- **输入**：specifier 产出的 QA 流程文档，以及前四段的全部产物。
- **输出**：可执行的 QA 验收脚本（如 Playwright / Selenium），运行后输出确定性的通过 / 失败结论。
- **工作方式**：把 specifier 写的、给人读的 QA 流程，翻译成机器执行的界面操作脚本：脚本驱动真实界面逐步操作，最后给出一眼可判定的结果，不给「看起来差不多」的主观结论。
- **不做什么**：不修改代码与测试；验收不过时产出失败报告，交回对应阶段处理。

## 3. 配套原则

流水线成立靠三条配套原则。缺任何一条，分工的好处都会打折。

### 3.1 每个 agent 只做一件事

把任务切窄，上下文随之变短，减轻 lost in the middle。

机制：语言模型处理长上下文时，对中部内容的注意力弱于头尾（lost in the middle）。让一个 agent 同时背需求、写实现、做重构、跑变异，提示词与会话记录必然又长又杂，关键约束容易被淹没在中部。任务切窄之后：

- 每段的提示词只需描述一件事，约束少而明确；
- 会话里积累的无关内容少，模型更容易抓住重点；
- 完成标准单一，agent 不用在多个目标之间反复权衡。

### 3.2 用完即毁

每个 agent 完成本段任务即销毁，下一段带干净上下文进来，打破上下文轨迹。

机制：不搞一个从头干到尾的全能 agent，也不把上一段的会话记录喂给下一段，阶段之间只交接产物文件。好处：

- 下一段不被上一段的试错轨迹污染——coder 中途放弃的方案、specifier 划掉的措辞，都不该影响 cleaner 的判断；
- 每段从零开始，上下文预算全部花在当前任务上；
- 出问题时定位简单：哪段产物不合格，就重跑哪段。

### 3.3 代价账

| 方案 | 耗时 | 说明 |
|------|------|------|
| 五段式流水线 | 约 1 小时 | agent 串联执行的机器时间 |
| 人工完成同等交付 | 约半天 | 同一开发者手写实现、重构、加固、验收 |

按 issue #39 的实测记录：流水线约 1 小时完成的工作，人工大约需要半天，效率约 4-5 倍，且质量更高——因为每一段都留下机器可验证的产物，重构有没有做、测试杀伤率够不够、验收过没过，都不依赖自觉。

代价是真金白银的 token 费用与编排成本。对一次性小改动，五段式未必划算，取舍见 §4。

## 4. 适用场景与裁剪

五段式不是唯一形态。项目可以按质量要求裁剪阶段组合：

| 组合 | 阶段 | 适用场景 |
|------|------|----------|
| 五段式（完整） | specifier → coder → cleaner → hardener → QA | 高质量要求：核心业务逻辑、对外交付物、出错代价高的代码 |
| 三段式 | coder → cleaner → hardener | 中等质量要求：需求已由人定清，省去 specifier 与 QA，重点保代码质量 |
| 二段式 | coder → cleaner | 快速迭代：原型、内部工具、探索性功能，先保证不烂尾 |

裁剪建议：

1. **保住底线：每段产物可机器验证。** 裁掉角色可以，裁掉「完成标准可判定」不行。
2. **coder + cleaner 是最稳的最小组合。** 单留 coder 一段没有质量收拾环节，容易烂尾，不建议。
3. **hardener 是性价比分段。** 变异测试直接衡量测试质量，对防御回归的收益最直接。
4. **specifier 与 QA 涉及人机边界。** 裁掉 specifier，意味着需求要由人直接写成可执行的验收标准；裁掉 QA，意味着界面验收由人手工执行。先想清楚这两件事改由谁做，再裁。
5. 阶段组合与各段工具（CRAP、变异测试）的选型属项目层默认值，由项目按自身情况决定，不回写固定层。

## 5. 与固定层的关系

固定层指本 skill 附带的 [DECISIONS.md](DECISIONS.md) 快照所记录的现行纪律条文。本文与它的关系：

1. **本文是参考模板，不是强制条文。** 固定层不要求任何项目使用五段式流水线；不采用也不影响项目通过 `/lazypack-setup` 获得的其他产物。
2. **不强制映射到固定层角色。** 固定层 §3 定义了规划者、调查者、执行者、审查者、书记员、清道夫六个角色。五段式的 specifier、coder、cleaner、hardener、QA 是另一套分工粒度，与这六个角色没有一一对应关系。项目若想把两套角色关联起来，属项目层自己的决定，本文不替它做映射。
3. **采纳方式属项目层。** 项目决定采用（全量或裁剪）时，按固定层 §2.4（项目层默认值）把选择记录在本项目自己的文档里，不修改固定层，也不要求修改本 skill。
4. **与既有条文不冲突。** 流水线的机器可验证产物、验收测试前置等做法，与固定层 §6 质量门禁、§6.5 质量双轨的方向一致；但本文不新增门禁要求——是否把流水线各段接进提交前 hook 或 CI，由项目层决定。
