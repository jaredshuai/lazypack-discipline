# 文档路由与逻辑归属参考规范 (Document Routing Reference)

本文档是 `/lazypack-setup` 在执行文档归属与整理（包括原位保留模式 `preserve-existing` 与受控迁移模式）时，用于指导 Agent 进行指针先行探测、八大逻辑区域归属识别、同一主题权威判定、细粒度章节锚点提取、受控物理迁移规划以及安全登记至 `docs/ARTIFACTS.md` Section 3 的**底层技术参考规范**。

---

## 1. 核心定位与原则

1. **保留既有原位 (`preserve-existing`) 为首要默认路径**:
   - 落实 [DECISIONS.md §1.4、§2.3、§4.2–§4.4](DECISIONS.md) 现行条文；
   - 存量文档优先进行只读识别与就地安全登记；
   - **整理文档 $\neq$ 必须物理迁移**：绝不把文件搬迁或目录重构作为文档归属整理的前提；八大逻辑区域是统一导航的认知边界，**绝不强制目标项目预先建立八个独立目录**；已有 README 章节、存量文档、配置文件与真实外部链接均可复用。
2. **块外解耦契约**:
   - 本规范指导的所有存量原件与迁移登记，**严格追加在 `docs/ARTIFACTS.md` 的 Section 3（非受管协作区，位于 `<!-- lazypack:end block=artifacts-register -->` 之后）**；
   - 本规范正文不属于 Section 2 受管块模板，不计入受管块 `header.input`，避免参考规范变动引发受管区伪 UPGRADE 或伪 DRIFT。
3. **内容与授权决定权威**:
   - 权威基准来源于文档实质内容与用户显式确认，文件名与创建日期仅作为候选线索；
   - 未登记产物视为未决，先向维护者核实，严禁机械猜测。
4. **受控物理迁移准入（Phase 2 演进）**:
   - 仅当存量文档位置严重违背工程规范（如历史工单与规格散落且无法索引），或用户显式要求重组特定目录结构时，方可启动物理迁移规划；
   - 物理迁移必须生成完整的变更计划（包含出站重写、全仓入站引用重写及登记册更新），并经用户单次整体确认绑定计划指纹后，通过**应用层顺序批次执行与补偿回滚**完成，不宣称系统级抗崩溃原子性。

## 2. 指针先行与有界探测安全边界

### 2.1 指针追踪优先级 (Pointer-First Discovery)
探测启动时，Agent 必须按以下顺序优先追踪既有权威指针，不得盲目全盘扫描：
1. **既有登记册**: 读取目标项目现存的 `docs/ARTIFACTS.md`，提取已在 Section 2 或 Section 3 登记的相对路径与锚点，作为基准已登记集合；
2. **任务跟踪声明**: 读取 `docs/agents/issue-tracker.md`，提取项目声明的实际工单位置；
   - **`.scratch/` 持久材料追踪**: 若 `issue-tracker.md` 明确声明实际工单路径位于 `.scratch/`（例如 `.scratch/tickets/` 或 `.scratch/<feature>/tickets/`），该路径内的工单与规格材料**严格作为持久权威来源**纳入候选探测范围，绝不因路径包含 `.scratch` 误判为临时缓存（遵从 DECISIONS.md §1.1 与 §3.4）；
   - **未声明文件边界**: `.scratch/` 目录下未在 `issue-tracker.md` 中声明的临时文件（如 `tmp.log`、运行时快照），其性质仅表示“不在本次已授权登记范围”，绝不能单凭其处于 `.scratch/` 目录或未声明身份就武断判定为“可丢弃缓存”；
3. **常驻入口指针**: 读取 `AGENTS.md` 或 `CLAUDE.md` 中的规范性链接与章节定位；
4. **根目录与存量文档扫描**:
   - 根目录 Markdown 文件：`README.md`, `CONTRIBUTING.md`, `SPEC.md`, `ARCHITECTURE.md` 等；
   - 常见文档目录：`docs/**`, `doc/**`, `specs/**`, `design/**`, `architecture/**`；
   - 配置文件与外部链接：`package.json` 中的 `bugs` / `repository` URL，或项目配置声明的外部跟踪器。

### 2.2 严格排除区、优先顺位与敏感边界 (Bounded Scanning)
1. **通用排除区与声明优先顺位 (Precedence & Fail-safe Exclusions)**:
   - **声明在先优先于通用剪枝**: 项目已明确声明的合法仓内原件（例如 `docs/agents/issue-tracker.md` 明确声明的实际工单路径位于 `.scratch/tickets/`、或常驻入口指针明确指向的规格路径）**优先于通用目录剪枝规则**；对于已被权威指针声明的仓内路径，Agent 必须正常追踪纳入候选范围，绝不因目录名包含 `.scratch` 等被粗暴过滤；
   - **未声明的通用排除区**:
     * 依赖目录：`node_modules/`, `vendor/`；
     * 版本控制元数据：`.git/`；
     * 构建产物与缓存：`dist/`, `build/`, `target/`, `out/`, `.cache/`, `.pytest_cache/`, `__pycache__/`；
     * 虚拟环境：`.venv/`, `venv/`；
     * IDE 临时配置：`.idea/`, `.vscode/`, `.DS_Store`；
     * 备份目录：`.lazypack-backup/`。
2. **安全硬边界不可逾越 (Security Boundaries)**:
   - 包含敏感密钥标识的文件路径（`.env*`, `credentials.json`, `client_secret.json`, `*.pem`, `*.key`, `id_rsa`, `id_ed25519`, `.ssh/`）**一律静默排除，绝对禁止读取其文件内容**，无论是否有指针指向；普通设计文档（如 `docs/credentials-architecture.md`）正常解析；
   - 扫描报告中概括声明“部分敏感配置与系统目录已按安全边界排除，本次探测属于有界扫描”，严禁静默跳过后声称“全仓无界 100% 完整覆盖”。
3. **符号链接与 Junction 越界防御**:
   - 遇到符号链接（Symlink）或 Junction 时，必须检查其解析后的真实绝对路径（`fs.realpathSync`）；
   - 若符号链接指向代码仓工作区根目录之外，**立即停止深入并安全阻断**，严禁未经授权读取外部宿主文件系统。
4. **四类登记对象的存在性与核验契约**:
   - **本地文件与章节 (Local Files & Sections)**: 物理文件在磁盘真实存在且非空，有效章节锚点必须在文件内存在对应标题；
   - **目录索引入口 (Directory Index Entries)**: 项目声明或实际存在的权威目录（如 `docs/interviews/`, `docs/adr/`），磁盘上该目录真实存在；
   - **声明的外部 URL (Declared External URLs)**: 仅依据配置文件（如 `package.json` 中的 `bugs` / `repository` URL）中显式声明的合法 HTTP/HTTPS URL 登记元数据；**绝不发起外部网络请求抓取，亦不宣称远端存在已验证**；
   - **留存协作种子与私有存储绑定 (Retention Seeds & Vault Bindings)**: 维持现有非空与 `session-authorized` 契约（ideas 种子必须非空；raw_qa 必须经当前会话显式绑定且不向公开产物暴露绝对私有路径，未绑定严格保持 `unbound` 零写入零预登记）。

## 4. 权威范围判定与状态流转契约

### 4.1 `current` 同一主题权威范围判定
- **同主题唯一性原则 (DECISIONS.md §4.2)**:
  `current` 表示“当前唯一的现行有效基准”。其唯一性边界是**同一业务主题或具体用途的权威范围 (Same-Topic/Purpose Scope)**，**绝非**整个逻辑区域单选！
- **多主题合法共存范式**:
  * *需求与验收区*：`specs/cart.md`（购物车）与 `specs/search.md`（搜索）分属不同功能，**各自合法为 `current`**；
  * *设计与决策区*：`docs/adr/001-db.md`（数据库引擎）与 `docs/adr/002-auth.md`（认证方案）分属正交技术决策，**各自合法为 `current`**；
  * *现状与说明区*：根目录 `README.md` 与独立子模块 `docs/api.md` 互为补充，各自合法为 `current`。
- **集合目录不自动批准**:
  登记目录索引（如 `docs/adr/`）仅作为检索入口，**绝不自动将目录下所有历史文档均批准为 `current`**。历史旧 ADR 必须按其演变状态单独登记。

### 4.2 同主题冲突聚合、替代确认与未选中保护
- **同主题冲突判定**: 当且仅当两份或多份材料针对**完全相同的业务主题或技术选型**竞争现行基准时，触发同主题冲突判定。
- **合并提问交互**: Agent 必须在整体提案中将冲突项聚合呈现，明确请用户裁定现行基准与替代关系：
  * **选定现行基准**: 用户选定项标注为 `current`；
  * **明确确认取代关系才登记 `superseded`**: 只有当用户**明确确认存在替代/废弃关系**时，被替代项才登记为 `superseded`，并在说明栏准确标注“被 [新产物相对路径] 取代”，形成双向引用；
  * **未确认替代关系保持待裁 (未选中不等于被取代)**: 若用户仅裁决某份材料为 `current`，但未确认其他候选材料的状态或替代关系未知时，其他候选材料**严格保持未决（`待裁 / unconfirmed`）或原有状态**；Agent **严禁擅自将其自动降级为 `superseded` 或 `reference`**！
  * **禁止自动归档与物理删除**: 状态变化本身绝不构成移动或删除文件的授权；被取代旧原件物理位置**保持原样不变，首期绝对不自动执行 `git mv` 移动至归档目录**；已有登记行依首期保护不予覆盖。

### 4.3 严格锁死固定 6 状态词与在途流程状态
- **登记册 6 种合法状态词**: `current`, `reference`, `exploration`, `superseded`, `pipeline`, `wip`。严禁自造任何扩展状态词！
- **三种在途流程状态与零写入契约**:
  1. `pending`: 用户未答复、按 Ctrl+C 中止或会话超时；
  2. `declined`: 用户在审查提案后明确输入拒绝（如 `n`）；
  3. `migration-unsupported-declined`: 用户强烈要求物理迁移但未获正当性确立，或拒绝原位保留登记。
  **契约保证**: 上述三种在途流程状态**严禁作为产物状态词写入登记册**，且 Agent 承诺对目标文件保持**严格的零相关写入**；零写入门禁必须在执行写盘前判定拦截，严禁事后宣布零写入。

## 5. 登记结构、细粒度定位与 Markdown 安全转义契约

### 5.0 Section 3 丰富可用表头结构与信息提供契约
1. **推荐标准表头格式**:
   `| 产物相对路径 / 锚点 | 逻辑区域 | 状态 | 维护者 / 更新触发 | 来源 / 替代关系 / 依据说明 |`
2. **Agent 提案必填信息**:
   相对路径或锚点（`path#anchor`）、归属的八大逻辑区域、裁决后的状态词、明确的维护职责与更新触发条件、来源凭据与替代关系说明。
3. **存量旧表头绝对兼容**:
   若目标项目已有 Section 3 采用 4 列旧表头或其他排版，严格遵循前缀保护，保留原有表头与历史登记行，不强制重排。

### 5.1 细粒度定位格式 (`path#anchor`)
- 当一个物理文件承载多个逻辑功能时，允许使用 `path#anchor` 形式细粒度登记；
- **真实 URL 契约**: 外部工单或规范采用标准 HTTP/HTTPS URL；服务元数据记录于 `issue-tracker.md`，**严禁生造非标伪协议**。

### 5.2 锚点解析与 Slug 算法
1. **有效锚点解析算法**: 提取 Markdown 标题行内容、纯小写、移除特殊字符、空格转单个 `-`；
2. **保守锚点原则**: 无法可靠解析锚点或重名标题时，退回使用相对路径并在说明列文字定位。

### 5.3 Markdown 表格字符安全转义
管道符 `|` 转义为 `\|`；反引号成对闭合；换行使用 HTML `<br>` 或压缩为单行。

## 6. 重跑重新评估与追加幂等性契约

1. **每次重跑重新评估**: 只读执行项目探测；
2. **细粒度去重键与幂等追加**: POSIX 规范相对路径或锚点路径；完全匹配触发幂等跳过；
3. **存量同键冲突保护**: 保持原手工行不覆写并向用户报告待裁。

## 7. 受控物理迁移与链接重写规约 (Controlled Physical Migration & Link Rewriting)

当存量文档经判定必须进行物理迁移时，必须严格遵循以下受控规格，杜绝盲目搬迁或不可逆破坏：

### 7.1 边界明确的 Markdown 链接支持范围与死链界定
1. **支持的格式**:
   - 标准内联链接：`[text](url)` 与 `![alt](url)`；
   - 附带标题链接：`[text](url "title")`；
   - 包含锚点与参数链接：`[text](url#anchor)`、`[text](url?query#anchor)`；
   - 相对路径寻址：如 `./foo.md`、`../bar.md`、`sub/doc.md`。
2. **不支持与严格阻断 (Fail-Closed)**:
   - 包含自定义模板宏（如 `{{...}}`、`<%...%>`）的 Markdown 文件；
   - 包含复杂动态 HTML 标签（如 `<a href="{{path}}">`）；
   - **规则**：若检测到不支持语法，**必须立即停止计划生成并向用户报告，严禁猜测重写**。
3. **死链校验范围界定**:
   - “零死链”断言严格且仅限于**有界扫描范围内 Markdown 文件的标准相对链接**；
   - 不保证非 Markdown 文件（代码、配置文件、CI 脚本）中未声明引用的有效性。

### 7.2 整体确认与指纹刚性绑定 (Fingerprint Binding)
1. **双指纹机制**:
   - **`input_fp`**：所有涉及的源文件、原位保留文件、引用文件及 `docs/ARTIFACTS.md` 执行前的 SHA256 聚合哈希；
   - **`plan_fp`**：规范化后的变更计划（包含所有动作、重写前后哈希、路径映射及完整保留项元数据）的 JSON 聚合哈希。
2. **批准刚性绑定**:
   - 用户的单次整体确认必须绑定该次提案的具体 `plan_fp`；
   - 执行前 Helper 复核 `approved_plan_fp === current_plan_fp` 且磁盘无漂移；
   - 若执行前外部修改了任何相关文件，**立即阻断执行 (`APPROVAL_DRIFT_BLOCKED`)，重新计算并展示实际差异**。

### 7.3 备份隔离与路径边界防御 (B1 & B2 规约)
1. **备份物理隔离 (B1)**:
   - 备份根目录默认置于操作系统临时目录（`os.tmpdir()`），每个项目与事务使用独立路径，**严禁在代码仓工作区内部创建备份目录**；
   - 自定义备份目录必须通过真实物理路径（`fs.realpathSync`）校验位于目标工作区之外。
2. **严格路径边界 (B2)**:
   - 计划与执行入口必须对所有路径统一进行防逃逸校验；
   - 严禁父目录逃逸 (`..`)、绝对路径跨根、Windows 跨盘符以及符号链接/Junction 越界。

### 7.4 三类冲突与回滚防覆写 (B3 规约)
1. **`pre_write_target_collision` (写入前目标占用)**:
   - 计划写入的目标物理路径在执行前已存在，或父目录被普通文件占用；安全中止，零写盘。
2. **`mid_execution_mutation` (执行中变动)**:
   - 批次执行过程中探测到源文件、引用文件或登记册被外部并发修改；立即中断，触发基于 WAL 的逆序应用层补偿回滚。
3. **`pre_rollback_collision` (回滚前冲突与防覆写)**:
   - 回滚还原引用文件、登记册或已删源文件前，复核当前磁盘实时状态；
   - 若磁盘文件与最后一次成功写入的状态不符（被外部并发修改、删除或重建），**刚性禁止覆盖外部修改 (`PROHIBIT_ROLLBACK_OVERWRITE`)**；
   - 系统主动暂停并挂起（`SUSPENDED_ON_CONFLICT`），保留现场与外部数据，不虚构系统级原子恢复。

### 7.5 物证验收哈希准则
- 出站链接重写的目标文件，其物理哈希**必须与计划中的预期输出哈希 (`expectedTargetSha256`) 一致**，不要求与源文件原始哈希相同。
