# 文档路由与逻辑归属参考规范 (Document Routing Reference)

本文档是 `/lazypack-setup` 在执行文档归属与整理（包括原位保留模式 `preserve-existing` 与受控迁移模式）时，用于指导 Agent 进行指针先行探测与逐区覆盖记录、八大逻辑区域归属识别、同一主题权威判定、细粒度章节锚点提取、本地 CI/脚本路径失效信号的只读核对、受控物理迁移规划以及安全登记至 `docs/ARTIFACTS.md` Section 3 的**底层技术参考规范**。

---

## 1. 核心定位与原则

1. **保留既有原位 (`preserve-existing`) 为首要默认路径**:
   - 落实 [DECISIONS.md §1.4、§2.3、§4.2–§4.4](DECISIONS.md) 现行条文；
   - 存量文档优先进行只读识别与就地安全登记；
   - **整理文档 $\neq$ 必须物理迁移**：绝不把文件搬迁或目录重构作为文档归属整理的前提；八大逻辑区域是统一导航的认知边界，**绝不强制目标项目预先建立八个独立目录**；已有 README 章节、存量文档、配置文件与真实外部链接均可复用。
2. **块外解耦契约**:
   - 本规范指导的所有存量原件与迁移登记，**严格追加在 `docs/ARTIFACTS.md` 的 Section 3（非受管协作区，位于 `<!-- lazypack:end block=artifacts-register -->` 之后）**；
   - 本规范正文不属于 Section 2 受管块模板，不计入受管块 `header.input`，避免参考规范变动引发受管区伪 UPGRADE 或伪 DRIFT。
3. **内容与授权决定权威**:
   - 权威基准来源于文档实质内容与用户显式确认，文件名与创建日期仅作为候选线索；
   - 未登记产物视为未决，先向维护者核实，严禁机械猜测。
4. **受控物理迁移准入（Phase 2 演进）**:
   - 仅当存量文档位置严重违背工程规范（如历史工单与规格散落且无法索引），或用户显式要求重组特定目录结构时，方可启动物理迁移规划；
   - 物理迁移必须生成完整的变更计划（包含出站重写、全仓入站引用重写及登记册更新），并经用户单次整体确认绑定计划指纹后，通过**应用层顺序批次执行与补偿回滚**完成，不宣称系统级抗崩溃原子性。
5. **发现覆盖可追溯、失效信号只待裁**:
   - 探测范围先冻结再扫描，八大逻辑区域逐区留痕（见 §2.3）；每个已发现项都必须在记录中给出**去向**（已登记 / 拟登记 / 待裁 / 保护跳过 + 理由），不得凭模型判断静默收窄覆盖；
   - 存量文档中的仓内相对路径引用只做只读存在性核对（见 §2.4）；「不存在」仅作待裁线索，绝不据此自动把任何文档标为 `superseded`，未知/动态/外部引用一律不伪判 missing，不执行所发现的任何命令，不出仓读取敏感文件。

## 2. 指针先行与有界探测安全边界

### 2.1 指针追踪优先级 (Pointer-First Discovery)
探测启动时，Agent 必须按以下顺序优先追踪既有权威指针，不得盲目全盘扫描：
1. **既有登记册**: 读取目标项目现存的 `docs/ARTIFACTS.md`，提取已在 Section 2 或 Section 3 登记的相对路径与锚点，作为基准已登记集合；
2. **任务跟踪声明**: 读取 `docs/agents/issue-tracker.md`，提取项目声明的实际工单位置；
   - **`.scratch/` 持久材料追踪**: 若 `issue-tracker.md` 明确声明实际工单路径位于 `.scratch/`（例如 `.scratch/tickets/` 或 `.scratch/<feature>/tickets/`），该路径内的工单与规格材料**严格作为持久权威来源**纳入候选探测范围，绝不因路径包含 `.scratch` 误判为临时缓存（遵从 DECISIONS.md §1.1 与 §3.4）；
   - **未声明文件边界**: `.scratch/` 目录下未在 `issue-tracker.md` 中声明的临时文件（如 `tmp.log`、运行时快照），其性质仅表示“不在本次已授权登记范围”，绝不能单凭其处于 `.scratch/` 目录或未声明身份就武断判定为“可丢弃缓存”；
3. **常驻入口指针**: 读取 `AGENTS.md` 或 `CLAUDE.md` 中的规范性链接与章节定位；
4. **根目录与存量文档扫描**:
   - 根目录 Markdown 文件：`README.md`, `CONTRIBUTING.md`, `SPEC.md`, `ARCHITECTURE.md` 等；
   - 常见文档目录：`docs/**`, `doc/**`, `specs/**`, `design/**`, `architecture/**`；
   - 配置文件与外部链接：`package.json` 中的 `bugs` / `repository` URL，或项目配置声明的外部跟踪器。
5. **子项目根发现 (Sub-project Root Discovery)**:
   - **从仓内安全目录与项目清单枚举子项目根**，不以根目录名称、常见容器名白名单或模型假设代替：
     * **仓根直接子目录**: 先枚举仓库根的**直接子目录**（不按容器名筛选），对每个直接子目录只读检查其是否构成候选子项目根——自身含有**工程标记**（项目清单，如 `package.json`、`Cargo.toml`、`go.mod`、`pyproject.toml`、`*.sln`、`build.gradle` 等）或存在文档标记（`README`、`RELEASE`、`CHANGELOG` 匹配无扩展名或常见文档扩展名 `.md` / `.rst` / `.txt` 等；`docs/**`、`specs/**` 均仅以安全目录存在作为候选标记，后续内容读取受 §2.2、§2.3 有界扫描约束，不隐含无界递归）。命中任一即纳入候选；`packages/`、`apps/`、`services/`、`modules/`、`crates/` 只是常见示例，**绝不作为白名单**；
     * **项目清单声明的成员**: 读取工作区声明（如 `package.json` 的 `workspaces`、`pnpm-workspace.yaml`、`Cargo.toml` 的 `[workspace] members`、`go.work`、`pyproject.toml` 工作区声明）中识别成员所需的字段，不复制清单正文，不扫描其他本地配置，把声明的成员一并纳入候选；
     * 枚举只做只读目录/清单检查，遇到嵌套 `.git` 仓库或 submodule 只作边界识别，不穿透其内部；
   - **把每个子项目根的存量文档纳入候选范围**：其 `README`、`RELEASE`、`CHANGELOG`、`docs/**`、`specs/**` 都按 §2.3 逐区记录，不因位于子目录而遗漏；
   - **子项目根只读且受同一排除/敏感边界约束**：枚举只读取清单与安全目录结构，不进入 §2.2 排除集合与敏感路径，不读取仓外路径；符号链接/Junction 越界按 §2.2 阻断；
   - **覆盖与未覆盖都要留痕**：仓根某直接子目录不含任何工程/文档标记、某类清单不可枚举（未知工作区工具），或某安全目录不存在时，都在 §2.3 记录中写明该子项目发现手段的检查结果与未覆盖原因。

### 2.2 严格排除区、优先顺位与敏感边界 (Bounded Scanning)
1. **通用排除区与声明优先顺位 (Precedence & Fail-safe Exclusions)**:
   - **声明在先优先于通用剪枝**: 项目已明确声明的合法仓内原件（例如 `docs/agents/issue-tracker.md` 明确声明的实际工单路径位于 `.scratch/tickets/`、或常驻入口指针明确指向的规格路径）**优先于通用目录剪枝规则**；对于已被权威指针声明的仓内路径，Agent 必须正常追踪纳入候选范围，绝不因目录名包含 `.scratch` 等被粗暴过滤；
   - **未声明的通用排除区**（路径段精确匹配，比较前路径已小写化，与 `doc_scanner.mjs` 的 `excludedDirs` 同一集合）:
     * `node_modules`, `.git`, `vendor`, `dist`, `build`, `target`, `out`, `.cache`, `.pytest_cache`, `__pycache__`, `.venv`, `venv`, `.idea`, `.vscode`, `.lazypack-backup`, `.DS_Store`, `raw-qa`（规范 raw_qa 目录名，防扫描读取敏感原始问答）。已配置的 `retention.paths.raw_qa` 仓内路径可能非规范路径，须调用 `doc_helper.mjs scan`/`plan` 时以可重复的 `--exclude <相对路径>` 显式传入，同样静默排除。
     * **嵌套 Git 边界预检**: 调用 `doc_helper.mjs scan`/`plan` 前，用受同一排除集合与符号链接/Junction 边界约束的只读安全目录枚举，预检嵌套 Git 根：包含 `.git` 目录或 `.git` 文件的目录，以及 `.gitmodules` 已声明的 submodule 路径；不穿透这些边界。每个找到的根都必须逐项以可重复的 `--exclude <相对路径>` 传入 helper。预检不可完成时，只处理已界定范围并报告未覆盖，绝不直接运行全仓 helper；不新增扫描器，也不假设 `doc_scanner.mjs` 会自动排除整个嵌套仓库。
2. **安全硬边界不可逾越 (Security Boundaries)**:
   - 敏感文件按下列显式集合精确匹配，**一律静默排除，绝对禁止读取其文件内容**，无论是否有指针指向。匹配的是完整文件名或明确的前后缀，用来避免误杀普通设计文档（如 `docs/credentials-architecture.md` 仍正常解析）：
     * `.env`（文件名恰好等于 `.env`）；
     * `.env.*`（文件名以 `.env.` 开头）；
     * `credentials.json`；
     * `client_secret.json`；
     * `*.pem`（文件名以 `.pem` 结尾）；
     * `*.key`（文件名以 `.key` 结尾）；
     * `id_rsa`；
     * `id_ed25519`；
     * `.ssh/`（路径以 `.ssh/` 开头，或路径中含有 `/.ssh/`）。
   - 扫描报告中概括声明“部分敏感配置与系统目录已按安全边界排除，本次探测属于有界扫描”，严禁静默跳过后声称“全仓无界 100% 完整覆盖”。
3. **符号链接与 Junction 越界防御**:
   - 遇到符号链接（Symlink）或 Junction 时，必须检查其解析后的真实绝对路径（`fs.realpathSync`）；
   - 若符号链接指向代码仓工作区根目录之外，**立即停止深入并安全阻断**，严禁未经授权读取外部宿主文件系统。
4. **四类登记对象的存在性与核验契约**:
   - **本地文件与章节 (Local Files & Sections)**: 物理文件在磁盘真实存在且非空，有效章节锚点必须在文件内存在对应标题；
   - **目录索引入口 (Directory Index Entries)**: 项目声明或实际存在的权威目录（如 `docs/interviews/`, `docs/adr/`），磁盘上该目录真实存在；
   - **声明的外部 URL (Declared External URLs)**: 仅依据配置文件（如 `package.json` 中的 `bugs` / `repository` URL）中显式声明的合法 HTTP/HTTPS URL 登记元数据；**绝不发起外部网络请求抓取，亦不宣称远端存在已验证**；
   - **留存协作种子与私有存储绑定 (Retention Seeds & Vault Bindings)**: 维持现有非空与 `session-authorized` 契约（ideas 种子必须非空；raw_qa 仓外别名必须经当前会话显式绑定且不向公开产物暴露绝对私有路径，未绑定严格保持 `unbound` 零写入零预登记；仓内路径限 `docs/raw-qa/` 或用户明确指定的相对路径（Agent 不自创），以仓库本身为私有为前提、无需会话绑定，写前重新核实，无法核实为私有不写盘，**绝不为普通文档放宽私有存储安全防线**；仓内核验细则（全部推送目标为 `PRIVATE` 且查询绑定解析出的主机、路径含 `..`/符号链接/Junction/真实路径越界、Git 顶层为本仓根、忽略规则与发布站点源的检查、git 历史告知）见 [retention-sections.md §1.4](retention-sections.md)）。

### 2.3 逐区探测覆盖记录 (Per-Zone Coverage Record)

本小节约束的是「本轮实际查了什么、查到了什么」，用于防止登记覆盖随模型判断静默收窄。它不新增产物，记录去向见本节末条。

1. **范围先冻结再扫描**: 探测开始前，先按 §2.1 的指针优先列表与 §2.2 的排除集合、敏感边界冻结本次搜索范围，明确列出纳入的指针、目录、文件与显式排除项；范围一经冻结，不得在扫描过程中凭模型判断事后收窄。确需调整时，在原记录中并列写出调整前的范围、调整后的范围与调整原因。记录显式排除项时遵守 §2.2 的静默契约：只写排除类别与范围，**不复述敏感文件的路径或文件名**。
2. **八大逻辑区域逐区留痕**: 对 [§3](#3-八大通用逻辑区域匹配规则) 的八个逻辑区域（方向、需求与验收、设计与决策、规则与术语、工作与进度、现状与使用说明、验证与观察、来源材料）逐区给出至少一条记录，每条含三个字段：
   - **实际搜索范围**: 实际枚举到的指针（如 `docs/ARTIFACTS.md`、`docs/agents/issue-tracker.md`、常驻入口）与目录/文件（含 §2.1 第 5 项枚举到的子项目根及其 README/RELEASE 等）；未纳入的目录或文件只写理由类别（命中排除集合、敏感边界、超出授权、留存策略未决等），不输出敏感路径；
   - **发现情况**: 发现的存量原件（`path#anchor`）清单；确无发现时显式写「未发现」，同时保留实际搜索范围，不得留空、不得跳过该区；
   - **未覆盖原因**: 该区未被完整覆盖时写明原因（声明缺失、目录被排除、敏感边界、留存策略未决、符号链接/Junction 越界等）。仅在**声明的有界搜索范围**内已逐项检查且无遗漏时，才可写「已完整覆盖（限声明的有界范围）」；不得把「已完整覆盖」扩大为全仓无界全覆盖。
3. **每个发现项必须有去向**: 逐区发现记录中的每个原件都要给出一种去向：**已登记**（已存在于 Section 3 或受管区）、**拟登记**（本轮拟追加 Section 3）、**待裁**（交用户裁决：同主题冲突、未确认替代关系等）、**保护跳过**（既有受保护/人工登记/暂停/未授权项，写明理由）。既有登记、待裁与受保护项合理不必追加；本规范不设「登记行数不得少于发现数」这类计数下界，但不得省略去向或凭模型判断静默收窄覆盖。
4. **记录去向**: 逐区覆盖记录随 SKILL 第 4 步预览与第 6 步完成报告一并呈现。它本身不是受管产物，也不写入 `docs/ARTIFACTS.md` 受管块。

### 2.4 本地 CI/脚本路径失效信号检查 (Local Path Reference Signal Check)

本小节约束如何把「既有文档引用了本地 CI 工作流/脚本路径，但该路径在磁盘上不存在」这类信号查出来并如实留痕，同时不越权改写。它只读，不新增产物。

1. **只做只读存在性核对**: 对本轮已按 §2.1（含第 5 项子项目根发现）与 §2.3 读取的存量文档中出现的**仓内相对路径引用**，逐条记录以下信息：
   - **引用原文/目标相对路径**: 引用原文，以及按解析基准得到的仓内目标相对路径；无法可靠解析目标路径时写明原因。仅对非敏感条目记录；命中 §2.2 敏感集合、指向仓外或符号链接/Junction 越界时，按 §2.4 第 6 项仅记类别，不暴露路径或原文。
   - **出处**: 引用所在文件与位置（`path#anchor`，或行号/小节）；
   - **解析基准**: 该引用相对哪个基准解析（仓库根、引用文档所在目录，或其他声明基准），写明判定依据；
   - **实际检查结果**: 磁盘上目标: 存在 / 不存在 / 不适用。
   - **读取边界**: 对 CI、脚本或其他非文档目标引用，仅核对路径存在性，不读取目标内容；仅当目标是 Markdown 文档且落在 §2.2、§2.3 的既有有界扫描范围内时，才读取其内容。
2. **只判「可判定」的仓内静态引用**: 仅当引用同时满足 ①仓内相对路径、②静态字面量、③解析基准确定 三个条件时，才允许记为「不存在」。任一条件不满足一律不得判 missing，须如实标为下列类别之一：
   - **未知**: 待定引用（占位符、`TODO`、未落定路径）；
   - **动态**: 模板变量、运行时拼接、glob、环境变量展开等；
   - **外部**: `http(s):` / `file:` 等协议 URL、远端仓库、包名、发布源、应用市场条目等。
3. **历史/示例上下文不推断现行故障**: 引用位于历史记录、示例块、迁移对照、历史日志等语境（如「旧版路径」「示例」围栏）时，只作**上下文事实**记录，并在出处标注其历史/示例语境；不得据此推断现行流程失效，不标 missing，也不作为现行失效的待裁线索。
4. **失效信号只作待裁线索**: 「不存在」结果仅作为**待裁线索**上报，绝不据此自动把任何文档标为 `superseded`、自动改写引用、自动移动或删除文件，也不改变任何状态词。是否更正引用或调整状态交由用户裁决；报告如实记录本轮是否获得用户授权处理以及实际处理结果，未获授权时保持原样并如实标注。
5. **不执行所发现命令**: 本检查只做路径存在性与静态文本核对，绝不执行文档中出现的任何 CI、构建、脚本或发布命令；不得把「路径存在」陈述为「该流程/命令已验证可运行」。
6. **不出仓、不读敏感**: 引用指向仓外、符号链接/Junction 越界路径，或命中 §2.2 敏感集合的文件时，只记录「超出授权范围 / 按安全边界排除」，绝不读取其内容，也不发起外部网络请求。
7. **记录去向**: 失效信号清单随 SKILL 第 4 步预览与第 6 步完成报告一并呈现；同样不是受管产物。

## 3. 八大通用逻辑区域匹配规则

## 4. 权威范围判定与状态流转契约

### 4.1 `current` 同一主题权威范围判定
- **同主题唯一性原则 (DECISIONS.md §4.2)**:
  `current` 表示“当前唯一的现行有效基准”。其唯一性边界是**同一业务主题或具体用途的权威范围 (Same-Topic/Purpose Scope)**，**绝非**整个逻辑区域单选！
- **多主题合法共存范式**:
  * *需求与验收区*：`specs/cart.md`（购物车）与 `specs/search.md`（搜索）分属不同功能，**各自合法为 `current`**；
  * *设计与决策区*：`docs/adr/001-db.md`（数据库引擎）与 `docs/adr/002-auth.md`（认证方案）分属正交技术决策，**各自合法为 `current`**；
  * *现状与说明区*：根目录 `README.md` 与独立子模块 `docs/api.md` 互为补充，各自合法为 `current`。
- **集合目录不自动批准**:
  登记目录索引（如 `docs/adr/`）仅作为检索入口，**绝不自动将目录下所有历史文档均批准为 `current`**。历史旧 ADR 必须按其演变状态单独登记。

### 4.2 同主题冲突聚合、替代确认与未选中保护
- **同主题冲突判定**: 当且仅当两份或多份材料针对**完全相同的业务主题或技术选型**竞争现行基准时，触发同主题冲突判定。
- **合并提问交互**: Agent 必须在整体提案中将冲突项聚合呈现，明确请用户裁定现行基准与替代关系：
  * **选定现行基准**: 用户选定项标注为 `current`；
  * **明确确认取代关系才登记 `superseded`**: 只有当用户**明确确认存在替代/废弃关系**时，被替代项才登记为 `superseded`，并在说明栏准确标注“被 [新产物相对路径] 取代”，形成双向引用；
  * **未确认替代关系保持待裁 (未选中不等于被取代)**: 若用户仅裁决某份材料为 `current`，但未确认其他候选材料的状态或替代关系未知时，其他候选材料**严格保持未决（`待裁 / unconfirmed`）或原有状态**；Agent **严禁擅自将其自动降级为 `superseded` 或 `reference`**！
  * **禁止自动归档与物理删除**: 状态变化本身绝不构成移动或删除文件的授权；被取代旧原件物理位置**保持原样不变，首期绝对不自动执行 `git mv` 移动至归档目录**；已有登记行依首期保护不予覆盖。

### 4.3 严格锁死固定 6 状态词与在途流程状态
- **登记册 6 种合法状态词**: `current`, `reference`, `exploration`, `superseded`, `pipeline`, `wip`。严禁自造任何扩展状态词！
- **三种在途流程状态与零写入契约**:
  1. `pending`: 用户未答复、按 Ctrl+C 中止或会话超时；
  2. `declined`: 用户在审查提案后明确输入拒绝（如 `n`）；
  3. `migration-unsupported-declined`: 用户强烈要求物理迁移但未获正当性确立，或拒绝原位保留登记。
  **契约保证**: 上述三种在途流程状态**严禁作为产物状态词写入登记册**，且 Agent 承诺对目标文件保持**严格的零相关写入**；零写入门禁必须在执行写盘前判定拦截，严禁事后宣布零写入。

## 5. 登记结构、细粒度定位与 Markdown 安全转义契约

### 5.0 Section 3 丰富可用表头结构与信息提供契约
1. **推荐标准表头格式**:
   `| 产物相对路径 / 锚点 | 逻辑区域 | 状态 | 维护者 / 更新触发 | 来源 / 替代关系 / 依据说明 |`
2. **Agent 提案必填信息**:
   相对路径或锚点（`path#anchor`）、归属的八大逻辑区域、裁决后的状态词、明确的维护职责与更新触发条件、来源凭据与替代关系说明。
3. **存量旧表头绝对兼容**:
   若目标项目已有 Section 3 采用 4 列旧表头或其他排版，严格遵循前缀保护，保留原有表头与历史登记行，不强制重排。

### 5.1 细粒度定位格式 (`path#anchor`)
- 当一个物理文件承载多个逻辑功能时，允许使用 `path#anchor` 形式细粒度登记；
- **真实 URL 契约**: 外部工单或规范采用标准 HTTP/HTTPS URL；服务元数据记录于 `issue-tracker.md`，**严禁生造非标伪协议**。

### 5.2 锚点解析与 Slug 算法
1. **有效锚点解析算法**: 提取 Markdown 标题行内容、纯小写、移除特殊字符、空格转单个 `-`；
2. **保守锚点原则**: 无法可靠解析锚点或重名标题时，退回使用相对路径并在说明列文字定位。

### 5.3 Markdown 表格字符安全转义
管道符 `|` 转义为 `\|`；反引号成对闭合；换行使用 HTML `<br>` 或压缩为单行。

## 7. 受控物理迁移与链接重写规约 (Controlled Physical Migration & Link Rewriting)

当存量文档经判定必须进行物理迁移时，必须严格遵循以下受控规格，杜绝盲目搬迁或不可逆破坏：

### 7.1 边界明确的 Markdown 链接支持范围与死链界定
1. **支持的格式**:
   - 标准内联链接：`[text](url)` 与 `![alt](url)`；
   - 附带标题链接：`[text](url "title")`；
   - 包含锚点与参数链接：`[text](url#anchor)`、`[text](url?query#anchor)`；
   - 相对路径寻址：如 `./foo.md`、`../bar.md`、`sub/doc.md`。
2. **不支持与严格阻断 (Fail-Closed)**:
   - 包含自定义模板宏（如 `{{...}}`、`<%...%>`）的 Markdown 文件；
   - 包含复杂动态 HTML 标签（如 `<a href="{{path}}">`）；
   - **规则**：若检测到不支持语法，**必须立即停止计划生成并向用户报告，严禁猜测重写**。
3. **死链校验范围界定**:
   - “零死链”断言严格且仅限于**有界扫描范围内 Markdown 文件的标准相对链接**；
   - 不保证非 Markdown 文件（代码、配置文件、CI 脚本）中未声明引用的有效性。

### 7.2 整体确认与指纹刚性绑定 (Fingerprint Binding)
1. **双指纹机制**:
   - **`input_fp`**：所有涉及的源文件、原位保留文件、引用文件及 `docs/ARTIFACTS.md` 执行前的 SHA256 聚合哈希；
   - **`plan_fp`**：规范化后的变更计划（包含所有动作、重写前后哈希、路径映射及完整保留项元数据）的 JSON 聚合哈希。
2. **批准刚性绑定**:
   - 用户的单次整体确认必须绑定该次提案的具体 `plan_fp`；
   - 执行前 Helper 复核 `approved_plan_fp === current_plan_fp` 且磁盘无漂移；
   - 若执行前外部修改了任何相关文件，**立即阻断执行 (`APPROVAL_DRIFT_BLOCKED`)，重新计算并展示实际差异**。
3. **留存策略载体复核（默认启用，无跳过旗标）**：
   - `plan` 在读取迁移输入前对所有受支持的策略载体（`docs/agents/roles.md`、根 `AGENTS.md`、根 `CLAUDE.md`）记录原始字节 SHA-256，写入 `planSummary.retentionPolicy`（`version: 2`，`files` 字典键固定为这三个路径）；每个文件不存在时以对应值 `null` 明确绑定缺失状态。三个载体一律同时绑定，不能因为角色文件存在就忽略旧入口或入口优先级切换。该快照随 `plan_fp` 审批，计划不保存角色文件正文或仓外私有别名。
   - `execute` 在迁移内容读取、备份、WAL 和写盘之前重读同一组路径。修改、删除或新增文件均返回 `APPROVAL_DRIFT_BLOCKED` / `RETENTION_POLICY_DRIFT`；不可读、非普通文件或父目录/文件为符号链接或 Junction 时返回 `RETENTION_POLICY_UNREADABLE`。规划阶段遇到这些不可安全读取的情况则拒绝生成计划。
   - 旧计划缺少快照或仅含单载体 v1 快照等不受支持结构时返回 `RETENTION_POLICY_BASELINE_MISSING`，重新生成并确认计划，不能沿用旧审批。文件从规划到执行一直缺失时兼容放行；已有文件即使没有留存字段也绑定整个文件，正文未变可继续，字段被删除或正文损坏会改变摘要并阻断。
   - 当前 `retention` input 字典并未统一以机器 JSON 持久化到角色正文，因此不从自然语言猜测 `paths.raw_qa`。整个文件的字节变化（包括无关说明或换行）也需要重新审批；本检查不能证明原有策略有效，§2.2 的显式 `--exclude` 传递要求仍须满足。出现漂移后先重新读取留存策略并更新排除参数，再生成与批准新计划。
   - 本检查是执行入口的一次快照复核，不提供跨进程锁；复核后并发修改策略的竞态仍不在原子性保证范围内。
   - CLI `scan` 与 `plan` 均在扫描前先读取策略快照、扫描后再次核对，漂移时不输出结果；`plan` 在返回计划前额外核对；`buildMigrationPlan` 自身也在构建前后核对。未显式传入的自定义敏感路径不会自动从正文推导，因此扫描仍须使用 §2.2 要求的排除参数。
   - 固定策略载体保留在原位：计划器拒绝将上述任一载体及其真实路径、硬链接别名用作迁移源、目标或入站引用重写对象，执行器同样拒绝这类动作（`POLICY_FILE_RESERVED`）。任一策略载体若引用待迁移文档，则停止该迁移计划，保留原位或先在独立获批的 setup 更新中处理引用，再重规划；不默默跳过引用，也不将策略载体正文复制进计划动作。扫描器仍可在内存中读取这些元数据文件以抽取链接；写保护不表示从不读取策略正文。
   - setup 按 SKILL 第 5 步第 0 项先执行已批准的迁移，成功后才写角色文件及其他 setup 产物；规划时同时传入当前与拟写策略的 raw_qa 仓内排除路径并集。只把已批准迁移的预期输出作为后续相关文件的基线，不把外部变更当作自己的输出吸收。
   - 符号链接/Junction 防御覆盖静态检查时的根目录、策略文件及其中间目录；Windows 缺少 `O_NOFOLLOW` 时不能原子防御检查到打开之间的替换，其他平台的父目录替换也存在竞态。本工具不提供对抗并发替换的文件系统沙箱。

### 7.3 备份隔离与路径边界防御 (B1 & B2 规约)
1. **备份物理隔离 (B1)**:
   - 备份根目录默认置于操作系统临时目录（`os.tmpdir()`），每个项目与事务使用独立路径，**严禁在代码仓工作区内部创建备份目录**；
   - 自定义备份目录必须通过真实物理路径（`fs.realpathSync`）校验位于目标工作区之外。
2. **严格路径边界 (B2)**:
   - 计划与执行入口必须对所有路径统一进行防逃逸校验；
   - 严禁父目录逃逸 (`..`)、绝对路径跨根、Windows 跨盘符以及符号链接/Junction 越界。

### 7.4 三类冲突与回滚防覆写 (B3 规约)
1. **`pre_write_target_collision` (写入前目标占用)**:
   - 计划写入的目标物理路径在执行前已存在，或父目录被普通文件占用；安全中止，零写盘。
2. **`mid_execution_mutation` (执行中变动)**:
   - 批次执行过程中探测到源文件、引用文件或登记册被外部并发修改；立即中断，触发基于 WAL 的逆序应用层补偿回滚。
3. **`pre_rollback_collision` (回滚前冲突与防覆写)**:
   - 回滚还原引用文件、登记册或已删源文件前，复核当前磁盘实时状态；
   - 若磁盘文件与最后一次成功写入的状态不符（被外部并发修改、删除或重建），**刚性禁止覆盖外部修改 (`PROHIBIT_ROLLBACK_OVERWRITE`)**；
   - 系统主动暂停并挂起（`SUSPENDED_ON_CONFLICT`），保留现场与外部数据，不虚构系统级原子恢复。

### 7.5 物证验收哈希准则
- 出站链接重写的目标文件，其物理哈希**必须与计划中的预期输出哈希 (`expectedTargetSha256`) 一致**，不要求与源文件原始哈希相同。

#### 输出及排除的策略载体保护

`scan`/`plan` 的 `--out` 不得指向策略载体或其真实路径/硬链接别名，包括当前缺失的载体路径；在扫描前及写输出前检查。输出文件及其任一父目录为符号链接或 Junction 时返回 `POLICY_OUTPUT_UNSAFE`，以避免悬空或间接链接创建载体。该保护不提供并发替换的原子保证。

排除集合不得覆盖现存策略载体或其祖先目录；CLI 在扫描前、计划器在使用扫描图前、执行器在输入内容读取前均拒绝这类排除（`POLICY_CARRIER_EXCLUDED`）。这避免显式排除隐藏策略载体的入站引用。若敏感路径与策略载体冲突，应暂停迁移，通过单独获批的配置调整解决；不能绕过保护。
